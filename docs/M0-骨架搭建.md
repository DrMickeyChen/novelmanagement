# M0 · 骨架搭建

> 第二期第一站。**这一期一行业务代码都没拆、没改** —— 只做四件事：
> 父 POM 改多模块、抽出 `novel-common`、gateway 起来并配好路由、所有服务注册进 Nacos。
>
> 本文档 = 设计论证 + 实施记录 + 踩坑。和 `docs/P1`~`docs/P6` 并列。

## 三、★★ 最大的一个红利：12 个锁定文件一个字节都没动，而且它们**依然是对的**

铁律 2 说三端各有 4 个文件 md5 锁定（`request.js` / `auth.js` / `stores/user.js` / `styles/index.css`）。
M0 把后端从「一个 8080」变成「网关 8080 + 单体 8090」，本来以为至少要动 `request.js` 里的地址 —— **结果一个字节都不用改**：

| 为什么不用改 | 依据 |
|---|---|
| 三个 `request.js` 走的是 **`baseURL: '/api'`（相对路径）** | 谁在 8080 上接，它根本不关心 |
| `request.js` 里那句错误提示文案「请确认 backend 已在 **8080** 端口启动」 | M0 之后 **8080 上确实是用户要确认的那个入口（网关）**，文案仍然准确 |
| `dev-proxy/vite.config.js` 的 `/api` `/uploads` → `localhost:8080` | 网关接过来了，转发目标没变 |

★ 这就是**把网关放在 8080、让单体退到 8090**（而不是「网关另开一个端口」）的全部理由。
★ 反过来说：**如果当初把网关放在 8081，这 12 个文件里至少有 4 个非改不可** —— 而那正是铁律 2 要防的事。

## 四、★★ 三个「现在不做，将来会死得很难看」的设计

### 4.1 `novel-common` 的 Spring starter 全部 `<optional>true</optional>`

**Spring Cloud Gateway 是 WebFlux 的。它的 classpath 上只要出现 `spring-boot-starter-web`
（带来 `spring-webmvc` + `tomcat-embed-core`），启动就直接失败：**

```
Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway.
```

M0 的网关**不依赖 `novel-common`**，所以这一条在 M0 不会炸。
但 **M1 的网关一定要用 `JwtUtil`** —— 那一刻如果 `novel-common` 的依赖是普通 scope，
WebMVC 会**顺着 `novel-common` 悄悄爬进网关**，然后报一个和 `novel-common` 看起来毫无关系的错。

`optional` 让传递性**在结构上**断掉：`novel-common` 自己编译得到这些类，但**一个字节都不传给下游**。
下游各服务自己声明自己需要的 starter —— 这也正是「服务边界单向」在 POM 层面的样子。

★ **代价是「编译不过」，而编译不过是当场就能发现的**（`novel-common` 引不到某个类就报错）；
传过去则是**启动时才炸**。这个交换永远划算。

★ 但 `jjwt-api` **不加 optional**，`jjwt-impl` / `jjwt-jackson` 是 `runtime` scope ——
JWT 是真正需要传到运行时的那个，而且下游（M1 的网关）拿到 `jjwt-api` 就能编译，
运行时自动带上实现，不用再声明一次。

### 4.2 父 POM 的 `artifactId` 改叫 `novel-parent`

父 POM 原来自己叫 `novel-backend`，而**子模块也必须叫 `novel-backend`**
（`spring.application.name`、`lb://novel-backend`、jar 名、文档全指着它）。
同名父子在 Maven 里是合法的，但会让人永远读不清「novel-backend 是父还是子」。

### 4.3 `spring-boot-maven-plugin` 只放 `pluginManagement`，不放 `plugins`

父 POM 里如果直接写 `<build><plugins>`，`novel-common` 也会被打成 fat jar ——
**库打成可执行 jar 会让下游拿不到类**。
放 `pluginManagement` 则只提供版本和配置，`novel-backend` / `novel-gateway` 各自声明一次来激活。
`novel-common/target/novel-common-1.0.0.jar` 实测 **61,532 字节**，是普通库 jar。

## 五、踩坑记录

### 坑 1 ★★ Windows 多网卡 → 注册上去的是虚拟网卡 IP

Nacos 客户端默认取**第一块非 loopback 网卡**的地址。Windows 上装了 VMware / VirtualBox /
Hyper-V / WSL 之后，那个「第一块」很可能是 `192.168.56.1` 之类的虚拟网卡地址。

**注册上去的 IP 就是网关接下来要连的 IP** —— 这是这条坑的全部机理。

★ **症状要说准，否则排错方向会跑偏**（这是实测 ③ 顺带澄清的）：

```
实例在 Nacos 里「有」，但连不上   →  网关先拿到实例、再去连 → 连不上
                                    500 + Connection refused / timed out
实例在 Nacos 里「没有」           →  网关根本没得连
                                    503 + No servers available for service
```

**多网卡属于第一种（500），不是 503。** 原计划里把它写成 503，是被「看起来像路由配错」
这个印象带偏了 —— 而 503 的语义是「一个实例都没有」，两者排错方向完全不同：
500 + Connection refused 要去看**注册上去的地址对不对**，503 要去看**服务有没有注册上**。

★★ 还有一个更隐蔽的地方：**如果网关和后端在同一台机器上，虚拟网卡 IP 往往是能连通的**
（Tomcat 绑 `0.0.0.0:8090`，本机到 `192.168.56.1:8090` 照样通）—— 于是这个坑
在「单机跑全部服务」的开发期**可能根本不发作**，等到 M2/M3 服务分散到不同机器才炸，
那时候没人会想起来是 M0 埋的。**所以 `ip: 127.0.0.1` 是买确定性，不是修一个已发生的故障。**

**对策**：`spring.cloud.nacos.discovery.ip: 127.0.0.1`，**两个服务都要写**。
（单网卡的生产机器可以省掉，见 `docs/部署.md`。）

### 坑 2 ★★ `spring-cloud-starter-alibaba-nacos-discovery` 的名字有个 `starter`

正确的 artifactId 是 `spring-cloud-**starter**-alibaba-nacos-discovery`。
写成 `spring-cloud-alibaba-nacos-discovery`（少一个 `starter`）时，报错是：

```
'dependencies.dependency.version' for com.alibaba.cloud:spring-cloud-alibaba-nacos-discovery:jar is missing
```

★ **这个报错完全指不到「artifact 不存在」** —— Maven 把它当成一个「用户自己声明的、没写版本的依赖」，
于是去 `dependencyManagement` 里找版本、找不到，报的是版本缺失。
真正的原因要靠翻 SCA BOM 的 pom 才能确认。

### 坑 3 ★★ `/actuator/gateway/routes` 返回 404 —— 两件事，缺一个的症状一模一样

```yaml
management:
  endpoint:
    gateway:
      enabled: true          # ← 端点本身要不要【被创建】
  endpoints:
    web:
      exposure:
        include: gateway     # ← 创建出来之后要不要【从 HTTP 暴露出去】
```

★ **Spring Cloud Gateway 的 actuator 端点默认是 `enabled: false`**
（和 health / info 那些不一样，它们是默认开的）。
只写了 `exposure.include` 时，`/actuator` 列表里只有 `health / info / self` ——
**gateway 端点压根没被创建**，所以 404 的原因在上面那一行，不在 expose 上。

### 坑 4 ★★ `dependencyManagement` 的 BOM import 是**先到先得**

```xml
<!-- ★ 顺序不能反 -->
<dependency>spring-cloud-dependencies:2023.0.3</dependency>     <!-- 必须在前面 -->
<dependency>spring-cloud-alibaba-dependencies:2023.0.3.2</dependency>
```

Spring Cloud BOM 必须在前面，才能让 `spring-cloud-*` 系列锁在 2023.0.3；
SCA BOM 放后面只补它独有的（`nacos-*` 等）。**反了的话两边都要抢着定版本，谁赢取决于顺序，且不报错。**

### 坑 5 ★★ 日志路径跟着**进程的工作目录**走 → 启动目录不能跟着 jar 一起搬

`logging.file.name: logs/novel-backend.log` 是**相对路径**，落点 = 进程的工作目录。

拆模块后 jar 变成 `backend/novel-backend/target/novel-backend.jar`，
**如果顺手把 `-WorkingDirectory` 也改成 `backend/novel-backend`，日志会静默搬到
`backend/novel-backend/logs/`** —— `CLAUDE.md`、`README.md`、`docs/环境配置.md` 里所有说
「日志在 `backend/logs/`」的地方**全部变成假话，而且没有任何报错**。

**对策**：`-WorkingDirectory` **保持 `backend/` 不动**，只改 jar 路径。
`logs/` 于是仍然解析到 `backend/logs/`，文档里关于日志的话一个字都不用改。

★ M0 顺手给**网关**也加了同一份文件日志（`logs/novel-gateway.log`）——
理由一样：网关是用 `Start-Process` 隐藏窗口起的，而排障时最需要翻的恰恰是它的历史输出
（`No servers available for service: novel-backend` 这种只在日志里有）。
两个日志并排在 `backend/logs/`。

### 坑 6 ★★ 打包必须打**整个 reactor**，不要进子目录

```bash
mvn -Dmaven.repo.local=<repo> -f backend/pom.xml package     # ★ 对：聚合 POM，一次编三个模块
cd backend/novel-backend && mvn package                       # ✗ 错
```

进子目录敲的话 reactor 里只有一个模块，`novel-common` 会用**仓库里的旧版本**
（第一次甚至是「找不到」）—— 症状是**「明明改了 `Result.java`，运行结果没变」，而且不报错**。

单模块构建要用 `-pl novel-backend -am`（`-am` = also make，带上它依赖的 `novel-common`）。

★ 老规矩仍然有效：**必须在后端停掉的时候打包** —— jar 正在运行时 `repackage` 会失败
并留下一个**瘦 jar**（`java -jar` 起来报 `NoClassDefFoundError`）。

### 坑 7 ★ `UploadProperties` 的 `package` 声明没跟着目录改 → `duplicate class`

`git mv` 只搬文件、**不改文件内容**。`UploadProperties.java` 被搬到
`com/novel/common/upload/` 之后，里面的 `package com.novel.config;` 还在 ——
于是编译报 **`duplicate class com.novel.config.UploadProperties`**，并连带一堆
「cannot find symbol」（因为同包引用全部失效）。

★ 这是 M0 **唯一一个真正改了包名的文件**。搬完要跑一遍
「每个文件的 `package` 声明 vs 它的目录路径」的全仓比对。

### 坑 8 ★ XML 注释里**不能画 `-----` 分隔线**

```xml
<!-- ---------------------------------------- -->     <!-- ✗ 解析失败 -->
```

报错是 `in comment after two dashes (--) next character must be > not -`。
用 `====` 画分隔线即可。（`<!--` 和 `-->` 本身只含两个连字符，不受影响。）

### 坑 9 ★★ 上传 / SSE 过网关**必须真测**，不能靠「看起来正常」

网关是基于 WebFlux 的，理论上流式转发、不缓冲 body。但这两条都有「不报错但坏掉」的失败模式，
而且**会一路潜伏到 M1 才炸**，那时会以为是 M1 改坏的：

| 风险 | 为什么容易漏 |
|---|---|
| **大文件上传被截断 / 413** | 只 `GET /uploads/...` 看图片能出来，等于什么都没验 |
| **SSE 被网关攒批** | `text/event-stream` 攒完再吐**也是 200、内容也完整**，只是「打字机效果」没了 |

M0 的实测结果见 §六。

### 坑 10 ★ 评论频控**占坑在校验之前** —— 被拒的请求照样计入 10 秒

这是 P6 的既有行为，M0 写回归脚本时实测撞到的：

`CommentServiceImpl.reply()` 里 `requireNotTooFast(userId)` 排在 `requireVisibleComment()` **之前**
（代码注释里叫「第 1 步：占坑」）。所以：

- 「回复一条**待审**的评论」→ 返回 `4001`（四种情况统一码）
- **紧接着**再回复一条**已过审**的评论 → 返回 **`4004`（频控）**，而不是 200

★ 不是 bug（占坑先于校验是防刷的正确做法），但**写验收脚本时必须把两次调用隔开 10 秒**，
否则会得到一个看起来像「功能坏了」的 4004。

### 坑 11 ★ 不要顺手「清理」历史文档

`docs/P2:497`、`docs/P3:450`、`docs/P4:510` 里写的是 `java -jar target/novel-backend.jar`
（那时在 `backend/` 下）。**那是当时的事实，不要改。**

M0 之后正确的路径是 `backend/novel-backend/target/novel-backend.jar` ——
**由本文档负责说明这件事，而不是回头篡改那三份记录。**

## 六、验收证据（实测）

### ① 网关路由到单体 —— 响应**逐字节一致**

```
:8080/api/novels?page=1&size=3   → 200 / 900 字节
:8090/api/novels?page=1&size=3   → 200 / 900 字节
cmp -s 两个响应文件                → 完全一致
```

★ 这条比「都返回 200」强得多：**证明网关只是转发，没有改写响应体的任何一个字节。**

### ② Nacos 服务列表

```
count = 2
novel-backend   127.0.0.1:8090
novel-gateway   127.0.0.1:8080
```

### ③ 硬证据：它真的在走 `lb://`，不是静态转发

把单体**停掉**，再请求 `:8080/api/novels`。

★★ **实测结果和「预想」不一样，以实测为准**：

| 停掉后经过 | 响应 | 网关日志 |
|---|---|---|
| **立刻**（Nacos 心跳还没超时） | **500** | `Connection refused: getsockopt: /127.0.0.1:8090` |
| 等到心跳超时、实例被摘掉之后 | 503 | `No servers available for service: novel-backend` |

**两种都是 5xx，都证明它依赖后端实例**，但**第一种的证据更强** —— 报错里直接印出了
`/127.0.0.1:8090`，也就是「网关把服务名 `novel-backend` 解析成了这个地址」。
这比 503（只说明「一个实例都没有」）更能排除「其实写死了 `http://localhost:8090`」。

★ 为什么会先 500 后 503：网关的负载均衡器有一份**本地实例缓存**，Nacos 的摘除是
**心跳超时**驱动的（不是立刻的）。所以刚 `Stop-Process` 的那几秒，缓存里那个实例还在，
网关照样往上连 —— 连不上就是 `Connection refused` → **500**。

★ **这条对排查的意义**：以后看到 `:8080` 报 500 且日志是 `Connection refused`，
第一反应应该是「后端进程没了 / 端口不对」，**不是**「网关路由配错了」。
反过来 503 才是「Nacos 里没有可用实例」—— 只可能是**服务压根没注册上**。

★ 恢复：单体重新起来后，网关**不会立刻**恢复 —— 要等 Nacos 把重新注册推过来。
实测是**几秒内**（重启单体 → 第一次探测就 200），但**中间会有一小段 503**，这是正常的。

### ④ 网关专项（防止坑 2 / 坑 3）

| # | 检查 | 结果 |
|---|---|---|
| 1 | `dependency:tree` grep `spring-boot-starter-web:jar\|spring-webmvc\|tomcat-embed-core` | **零命中** ✓（★ 见下面的正则陷阱） |
| 2 | 网关启动日志 | `Netty started on port 8080`，**没有** `Tomcat started` ✓ |
| 3 | `/actuator/gateway/routes` | 两条，uri 都是 `lb://novel-backend` ✓ |
| 4 | 单体启动日志 | `Tomcat started on port 8090` + `nacos registry, novel-backend 127.0.0.1:8090 register finished` ✓ |
| 5 | 日志落点 | 仍在 `backend/logs/`（**不是** `backend/novel-backend/logs/`）✓ |

> `tomcat-embed-el` **在**网关的依赖树里，但那是 `spring-cloud-starter-gateway` 自己带的
> （`Path=` / `Method=` 谓词要 SpEL），**不是** WebMVC 漏进来了。
> 用 `-Dincludes=org.apache.tomcat.embed` 追过来源。
> `spring-web` 也在（`spring-webflux` 依赖它）—— 它是两套栈的公共底座，
> **要害是 `spring-webmvc`（servlet 那一套）**，不是 `spring-web`。

> ★★ **正则陷阱（实测踩到）**：`spring-boot-starter-web` 是
> **`spring-boot-starter-webflux` 的前缀** —— 用宽松写法 `grep "spring-boot-starter-web"`
> 会在**完全正常**的网关依赖树上命中一行，看起来像「MVC 漏进来了」，
> 排查方向直接跑偏。**必须锚定**：`spring-boot-starter-web:jar`。
>
> ```bash
> mvn -f backend/novel-gateway/pom.xml dependency:tree \
>   | grep -cE "spring-boot-starter-web:jar|spring-webmvc|tomcat-embed-core"   # 必须 0
> ```

### ⑤ 过网关的专项回归（`.tmp-m0/m0_gateway_probe.py`，**21/21 通过**）

| 项 | 结果 |
|---|---|
| 封面：过网关 POST → 过网关 GET → **逐字节比对** | md5 一致 ✓ |
| **300KB** 文件过网关 | 取回 307,270 字节，md5 一致，**没有被截断** ✓ |

### ⑥ 写路径全链路（`.tmp-m0/m0_write_path.py`，**56/56 通过**，全部经 `:8080`）

```
注册读者A/B → 提交作者申请 → 管理员审通过 → 重新登录拿到 AUTHOR

- 新书是**草稿**（`status=0`，后端写死，请求体里传不进去）

- 新评论是**待审** → 读者列表里**看不到**
- **待审的父评论下回复 → `4001`**（四种情况统一码）
- 书评**带 `score`**、章评没有
- `replyCount` 是**真实总数**（不受 `replies` 截断影响）
- `mine` / `liked` **匿名时整个键消失**（不是 `false`）
- **取消点赞不删评论**（`/like` 后缀少写就是删评论）
- 结尾断言**种子基线完好**：`READER` 0 / `AUTHOR` 2 / `ADMIN` 15 条菜单，

## 七、★ 为什么 `/doc.html` **没有**走网关（这是有意的）

接口文档直连 **`http://localhost:8090/doc.html`**，不透传。
**这是开发期唯一一个不走 `:3000`、也不走网关的入口。**

`/doc.html` 不是一个独立的页面：它加载后会再去拉 `/webjars/**`（前端资源）
和 `/v3/api-docs/**`（接口清单）。要透传就得给这一整套加路由，
还要处理 `X-Forwarded-*` 头和 springdoc 的 server 地址推断 ——
是一件独立的、会把 M0 拖长的活，**而且和 M0 的验收标准（路由通 + Nacos 可见）无关**。

★ 上线时这一项本来就关掉了（`springdoc.api-docs.enabled=false`，见 `docs/部署.md` 第五节）。
