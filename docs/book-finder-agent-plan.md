# 阅读端找书 Agent 实施计划

状态：里程碑 A 基础版已实现（2026-10-13），使用与验证说明见 `book-finder-agent.md`；里程碑 B 尚未实施。下文保留原计划，实际目录、执行方式和已验证范围以交付说明为准。

## 1. 目标与范围

在 reader-web 增加登录后使用的找书助手，使用现有 DeepSeek Flash 接口，让读者用自然语言筛选站内小说、追问和换一批。每次推荐 3～5 本实际存在且可见的作品，展示封面、简介、推荐依据和条件符合情况。

示例：先说“找已完结的悬疑小说，至少一百万字”，再说“换一批，类似第二本的”。后端保留硬条件，将“第二本”解析为上一轮展示的作品 ID，并排除已经推荐的作品。

里程碑 A：工具调用、执行循环、结构化结果、多轮会话、SSE、权限和运行控制。

里程碑 B：书籍资料知识库、证据检索、RAG、索引更新、评测与面试演示材料。向量检索以确认 Embedding 接口和现有 ES 版本能力为前提。

MCP 对外工具服务、独立 Rerank 模型、跨会话长期偏好记忆和移动端接入留作后续扩展，不作为第一版完成条件。

## 2. 已核实的现状

- novel-ai 已独立，端口 8085；已有模型配置、Key 加密、配额、用量记录和 SSE 能力。
- AiModelClient 当前发送 system/user 消息，没有工具定义、tool_calls 解析和工具结果回传协议，需要扩展模型接入层。
- novel-search 的 GET /api/search 目前仅有 keyword/page/size 参数，空关键词返回空列表。不能直接满足“所有已完结悬疑小说”的结构化筛选。
- search 已采用 ES 检索 + content 批量装配，且有数据库关键词降级；新筛选条件在正常与降级路径都必须一致。
- AiSecurityConfig 当前 /api/ai/** 仅允许作者和管理员。读者入口必须单独授权，不能放宽整个作者 AI 路径。
- reader-web 已有独立搜索页、分类页和作品详情页，可复用作品展示与跳转方式。

## 3. 架构与职责

调用链：reader-web → gateway → novel-ai → novel-search / novel-content；novel-ai 调用模型。内容变更通过现有 MQ 链路更新检索资料，保持 content 不同步调用 search 的约定。

Java 负责工具白名单、参数校验、权限、硬条件筛选、执行上限和最终作品可见性复核。模型负责理解需求、选择工具、整理资料和生成有依据的推荐理由。

工具：

| 工具 | 用途 | 实施阶段 |
| --- | --- | --- |
| searchBooks | 分类、标签、完结状态、字数范围、关键词与排除 ID 筛选 | A |
| getBookDetails | 批量读取读者可见的简介、标签、封面和真实状态 | A |
| searchBookEvidence | 检索候选书资料并返回资料 ID、出处与文本 | B |

最终推荐中的作品 ID 必须来自工具结果。输出前重新校验可见性和硬条件；不满足的作品剔除或有界补查。没有候选时说明原因，放宽硬条件须由读者明确同意。简介没有证明的风格特点不能写成确定事实。

## 4. 实施顺序和工作量

以下是单人开发的粗估工作量，按工作日计算，不是交付日期承诺；模型接口兼容性和真实环境联调会影响工期。

| 阶段 | 工作 | 产出 | 粗估 |
| --- | --- | --- | --- |
| 0：接缝确认 | 核实实际模型 ID、工具协议、现有字段/索引映射、网关与服务健康；确定响应契约 | 接口契约、Mock 模型脚本、评测题集 | 0.5～1 天 |
| 1：搜索工具 | 扩展筛选和空关键词查询；补批量可见详情；正常/降级路径遵守相同条件 | 两个 Java 工具、内部接口、筛选测试 | 1～2 天 |
| 2：Agent 后端 | 工具调用协议、执行循环、结构化结果、Redis 会话、读者配额、运行日志和限制 | 可通过接口完成多轮找书 | 1.5～2.5 天 |
| 3：阅读端与联调 | 聊天入口、阶段进度、推荐卡片、换一批、停止请求、异常重试和移动宽度适配 | 里程碑 A 可演示 | 1～2 天 |
| 4：知识库与 RAG | 建立资料和出处；证据工具；变更更新/重建；根据接口条件增加 Embedding 与混合检索 | 里程碑 B 可演示 | 3～5 天 |
| 5：评测和交付 | 跑固定题集、修复问题、记录指标、架构图、启动说明和演示脚本 | 面试展示材料 | 1～2 天 |

基础版约 4～8 个工作日；包含 RAG 和评测的展示版约 8～15 个工作日。每阶段通过验收后再推进下一阶段。

## 5. 会话、输出与运行控制

- 会话以登录用户为所有者，Redis 保存近期对话、当前条件、上轮有序推荐 ID 和已推荐 ID；初始 TTL 24 小时。设置历史大小上限，明确会话过期提示。
- 同一会话同一时间只执行一个请求，避免“第二本”指向并发结果。使用请求 ID 防止重试重复执行和重复记账。
- 计划使用 POST /api/ai/book-finder/chat 返回 SSE；独立的会话读取/清除接口按契约实现。网关和 AI 服务同时检查登录与权限。
- SSE 事件区分阶段进度、文本、最终结构化结果、错误和结束；不展示模型隐藏推理。工具执行期间可以展示“正在搜索作品”“正在核对资料”。
- 最终结果包含 conversationId、回答、当前条件、推荐卡片和是否需要追问；书籍 ID 使用字符串，避免 Java Long 在 JavaScript 中丢失精度。
- 推荐依据区分简介/标签/检索证据，附可追溯资料 ID。软偏好支持“符合 / 不符合 / 资料不足”，不伪造置信度。
- 起步上限：每次请求最多 4 轮模型调用、8 次工具执行、单次工具最多返回 20 本候选；整体超时初始 60 秒。最终根据联调数据调整。
- 限制输入长度、输出 Token、用户并发和每日请求数；累计每一轮模型用量，异常与中止也记录已发生的消耗。
- 客户端断开后取消本地任务，尽力中止上游调用；不能承诺已发生的模型费用可以撤销。
- 书籍文本属于不可信资料，不能覆盖系统规则或触发白名单之外的工具；API Key 不进入客户端、提示词或运行日志。

## 6. RAG 与 Skill

知识库首先收录书名、作者、分类、标签和简介，补充具有出处的主题/风格资料。不自动把模型生成的推测当作事实。整部小说不能一次性塞进提示词。

先实现关键词证据检索和基于证据的回答，再接独立 Embedding 模型做向量检索。混合检索先应用硬条件，再融合关键词与向量候选并去重；独立重排序模型按实测收益决定是否增加。

资料记录书籍 ID、来源类型、来源章节/字段、文本、资料版本和更新时间。推荐默认只引用简介和无剧透资料；章节证据只有具备明确可用范围时才开放。

导入、修改、上下架后更新或删除对应资料；重建任务可查询进度、重试失败，避免旧任务覆盖较新的资料。最终输出仍以 content 的可见性为准。

应用级 Skill 使用版本化资源文件封装任务说明、适用条件、允许工具和输出要求，先设计“按条件找书”“相似书推荐”“换一批”三个策略。由 Java 注册允许的策略，不把任意 Markdown 当作可执行代码，也不依赖 Codex 的技能加载机制。

## 8. 验收标准

基础版：

1. “完结 + 分类 + 字数范围”正常与降级查询都满足硬条件，空关键词可筛选。
2. “换一批”排除已推荐作品；“第二本这种风格”正确读取上轮第二本；无第二本时追问。
3. 下架、草稿和待审核作品不能出现在最终推荐中，其他用户不能读取或清除会话。
4. 模型伪造 ID、未知工具、非法参数、空结果、服务失败和超时有明确处理；不会无限循环。
5. 推荐卡片可进入真实作品详情，封面可显示；SSE 正常结束，重试不产生重复卡片。
6. Mock 验证工具调用闭环，受控真实接口验证 tools/tool_calls/tool 消息和用量字段；真实验收记录实际请求次数和消耗。

RAG 展示版：

1. 固定题集至少 30 个，覆盖硬筛选、多轮、软偏好、无结果、无依据和异常场景。
2. 安全与硬条件用例要求全部通过；统计推荐依据准确率、重复推荐率、耗时和 Token 消耗，不预先宣称指标达成。
3. 每条引用能追溯资料；缺乏证据时明确资料不足；默认输出不泄露章节剧情。
4. 修改、下架与重建测试验证资料更新，记录检索结果与真实可见性出现延迟时的处理。
5. 对比关键词检索与混合检索效果，再决定是否启用 Rerank。

## 9. 开工前需要确认的配置

确认模型是官方接口还是第三方接口，记录实际 base URL、模型 ID 和工具调用能力；Key 沿用管理后台的安全配置入口，不写入计划或源码。

确认可用的 Embedding 接口、ES 版本与部署资源。尚未具备时先交付里程碑 A 和关键词 RAG，不把向量检索描述成已完成。

开发验证先使用 Mock，真实模型验收限定请求数量并记录消耗，不改动原有测试种子与用户数据。
