## 四、★★★ 判断（都是被代码「逼」出来的，不是审美）

### ★★★ 判断 1：错误必须按「能不能在建 emitter 之前判定」分流 —— 走错一条就会输出一句指向错误方向的假话

`AiController` 今天写着 `ERROR_MESSAGE = "生成失败，请稍后重试"`。
★★★ **这在 P4 是对的**（唯一的失败源是 mock 的模拟故障，「稍后重试」是准确的建议）。**在 E1 它同时错两次。**

**第一次错：四个故障共用一句话，其中三个「重试」永远不会成功。**

| 真实故障 | 错误码 | 「请稍后重试」对不对 |
|---|---|---|
| AI 功能未启用（`enabled=0`） | `AI_DISABLED(5001)` | ✗ 要**管理员**去开 |
| 没配 API Key | `AI_API_KEY_MISSING(5002)` | ✗ 要**管理员**去填 |
| 今日额度用完 | `AI_QUOTA_EXCEEDED(5004)` | ✗ **今天**重试都不可能成功 |
| 上游超时 / 5xx | `AI_CALL_FAILED(5003)` | ✓ 这句是对的 |

**★★★ 第二次错（更隐蔽）：前三个故障全都发生在流开始之前，而它们会渲染成一句指向「代理配错」的话。**
`author-web/src/utils/sse.js` 有**两条互不相同的错误出口**：

```js
// :215-221  ← 非 2xx：把响应体里的 message 原样显示
// :233-241  ← 2xx 但 Content-Type 不是 text/event-stream：
//             返回 `响应不是事件流（Content-Type: xxx），请检查代理配置`
```

→ 「配额用完」如果按 `ResultCode` 的老规矩返 `200 + {"code":5004}`，
用户看到的是「**请检查代理配置**」——
★ 这比第一次错更严重：**它不是在说一句含糊的话，是在把人指向一个完全无关的系统。**

**判据（钉在结构上，不钉在文案上）：**

> **凡是「在创建 `SseEmitter` 之前就能判定」的失败，必须走真实 HTTP 状态码；
> 只有「流已经开始之后」的失败才走 `event: error` 帧。**
>
> 理由是硬的：**SSE 一旦开始响应头就发出去了，状态码改不了** ——
> 「能不能在开始前判定」直接决定错误走哪条路。

| 时机 | 故障 | 出口 | 用户看到 |
|---|---|---|---|
| 建 emitter 前 | 额度用完 | **HTTP 429** + `5004` | 「今日 AI 额度已用完」 |
| 建 emitter 前 | 未启用 / 未配 Key | **HTTP 503** + `5001/5002` | 「AI 功能未启用」/「尚未配置 API Key」 |
| 建 emitter 前 | 必填素材缺失（润色没选中） | **HTTP 400** | 「润色需要先在正文里选中一段」 |
| 建 emitter 前 | 模板缺失 | **HTTP 503/500** + `5005` | 「该场景尚未配置提示词模板」 |
| **流已开始后** | 上游超时 / 5xx / 解析失败 | `event: error` 帧 | 「生成失败，请稍后重试」 |

★ **body 里的 `code` 不变**（`Result.error(ResultCode)` 照旧），**只把 HTTP 状态码换成真实的** ——
`ResultCode` 的 5001~5005 分段原样保留，`ResultHttpStatus` **一个字都不用改**。
★ **HTTP 状态决定用户看到什么，body 的 code 决定程序怎么判断** —— 这句写进了 `AiController` 的注释。

**★★★ 阳性对照（这条护栏必须能证明自己会失败）**：
把 `AiPreflight.httpStatusOf` 的 `case 5004 -> 429` 改成 `-> 200`，重新打包实测 ——
拿到 `HTTP/1.1 200 OK` + `Content-Type: application/json` + `{"code":5004,...}`，
而 `sse.js:233` 对这两个字节的判据是 `!contentType.includes('text/event-stream')` →
返回「响应不是事件流（Content-Type: application/json;charset=UTF-8），**请检查代理配置**」。
★ **不需要真机就能证明「200 那条路会输出一句指向代理配错的假话」** ——判据是字节级的。

#### 2.2 ★★★ 失败语义四档 —— 判据是「缺失会不会让模型产出【看起来正常但错】的东西」

| 情形 | 处置 | 判据 |
|---|---|---|
| **未知占位符 `{{foo}}`** | ★★ **保存模板时就拒绝**（400，指出是哪个词） | ★★★ **半径差三个数量级**：写时拒绝 = 「1 个管理员的下一次点击」；读时拒绝 = 「**全体作者 × 该场景**」，且故障出现在作者点按钮那一刻 —— 错误指向产品功能，而不是模板 |
| **必填占位符无值** | **HTTP 400 + 明确说缺什么；不建 emitter、不扣配额、不调模型** | 它是**参与生成的输入**，与铁律 10「参与筛选的输入一律不降级」同构。★ 给空串的后果：模型收到「需要润色的文字：」后面什么都没有 → **它自己编一段** → 前端显示成「润色结果」让作者采纳，**而额度已经花了** |
| **可选占位符无值** | ★★ **该行整行移除**（含其上紧邻的纯标签行）+ 一条 INFO；**绝不填 `""`、绝不填占位符原文** | 铁律 10：**降级 = 让字段【消失】，不是让它变空**。模型收到的是一份**语义完整**的提示词 |
| 该 scene 无模板 / `enabled=0` | **`AI_PROMPT_NOT_FOUND(5005)`** | ★ **不用内置兜底提示词**：那会悄悄改变模型行为，而管理员以为自己删掉了模板 —— 两端都不知道对方存在 |
| 模板被绕过管理端改坏 | 渲染时撞上未知占位符 → **抛 `IllegalStateException` 走 500** | ★ 故意不给好看的业务码：5001~5005 返 HTTP 200 会**在监控上隐身** |

★★ **「空行向上级联」是实测补的一条**：可选占位符整行移除后，紧邻的**纯标签行**（如 `前情摘要：`）
也要一起走 —— 否则模型收到的是一行孤零零的标签。★ 那是一个「看起来正常但错」的提示词。

**两条配套要求**
- ★ **配额必须在渲染成功之后才扣**（否则用户被模板问题白扣一次额度）。
- ★ **渲染结果要有总长度护栏**（`@Size` 只管输入，管不住拼装结果）。超限 → 明确失败，**不静默截断**：
  截断正文中段会让模型接着一段「没头没尾」的文字续写，**产出看起来正常但接不上**。

#### 2.3 模板缓存？**不缓存** —— 判据是「加载代价落不落在请求路径上」

- **模板**：读发生在「用户点按钮」时，按 `uk_scene_name` 查一张几十行的表 = 单行主键级查询。
  缓存的收益小于它引入的失效问题：本项目**刻意不接 Nacos Config**，多实例失效只能靠 TTL 轮询，
  症状是「管理员改了模板，某些请求还用旧的」—— **静默、随机、不可复现**。
  ★ **不缓存 ⇒「改了立刻生效」是免费得到的**（管理端与 AI 调用在同一个 JVM）。
- **词库**（判断 3.5）：DFA/Trie 的构建代价**落在消费路径上**，必须缓存 → 进程内不可变快照 + 显式 reload + 定时兜底。

### ★★★ 判断 3：两层违禁审核 —— 词库 fail-closed，AI 层走 MQ，而「人工处置」的信号就是 `audit_log`

#### 3.0 ★★ 承重事实（它让后面四个问题都变简单）

> **这条链上 AI 不是「门」，是「给人工审核员的提示」。**
> 评论落库即 `status=0`（读者不可见），章节 `submit()` 后是 `status=1待审核` ——
> **两者都必须经人工才可见**（P5 的审核中心 / 评论管理就是那道门）。
> 所以 AI 层挂掉、延迟、漏审的后果是「**人工少了一条提示**」，
> **不是「违规内容被放出去」**。

★ 这条同时是整条链 **fail-closed** 的依据。

#### 3.1 ★★★ 分工：全部投 MQ，消费端先跑关键词再决定要不要调 AI

```
章节 submit() / 评论 insertComment()
        │  只多一件事：AfterCommit 投一条 AI_AUDIT（载荷只有 id）
        ▼
   novel-topic: AI_AUDIT  →  group-content-ai-audit（content 消费）
        ▼
   ① 取待审正文（章节本地读；评论走既有 content→interaction 内部读；评论已删 → ACK）
   ② 关键词层（内存 DFA，免费，毫秒）
        ├─ 无命中 → 写 risk_level=0 + status=2(机器排除) + audit_user_id=NULL，**不调 AI**
        └─ 命中/存疑 → 调 AI 语义复核 → risk_level=1..3 + hit_words + ai_comment，status=0 进人工队列
```

★★ **为什么不是「提交时同步跑关键词、命中才投 MQ」**：那会让**筛选逻辑住在两个进程里**
（`投不投` 在请求路径 + `调不调 AI` 在消费端，中间隔着 MQ，**没有任何一条日志能同时看到这两个判断**），
且「无命中」这个结论**不落库** → **提交了 N 条、审了 M 条，N−M 是多少、少的是哪些，查不出来**。
★ 这正是铁律 8 说的「一条不会失败的护栏」。全投之后，每一档都能被看见：
`status=0/1` 的源行 + 无 `ai_audit_result` 行 + 有 `ai_usage_log` 失败行 → **左连接即可定位**。
★ 且词库升级后，队列**可重放**（消费端重跑）；同步预筛的存量内容压根没进过队。

#### 3.2 ★★★ AI 审核【不碰任何业务状态机】—— 而「人工处置了」的信号就是那条 `audit_log`

★★★★★ **做法上做了一次【反转】**：

> **不是「确认 AI 结果」去写 `audit_log`，而是「`audit_log` 被写」这件事本身就是确认。**

`ChapterServiceImpl` 把 `transitStatus` 注释成「章节状态的**唯一**改动入口」，它顺带写 `audit_log` 与趋势统计。
一个「确认违规」按钮顺手 `UPDATE chapter SET status=4` 就会**绕开这个唯一入口** →
`audit_log` 缺一条、趋势图少一个点，**而且不报错**。

**反转的做法**：在 `AuditLogServiceImpl.record(...)` 的**同一个事务里**加一句联动：

```sql
UPDATE ai_audit_result SET status=?, audit_user_id=?, audit_time=?
 WHERE target_type=? AND target_id=? AND status=0
```

`APPROVE → 2(已排除)`、`REJECT → 1(已确认违规)`，其余 action（SUBMIT/REVERT）不联动。

★ `AuditLogServiceImpl.record` 是**所有人工处置的汇聚点**（章节在 content 内直接调；
评论 / 作者申请经 `AUDIT_RECORD` 消费者调带 `operatorId` 的重载）——
所以这一处挂载**覆盖全部入口**，且：**天然幂等**（`status=0` 是乐观条件）、
**天然顺序无关**、**零新 Tag、零新边、零跨服务写**。
★ `AUTHOR_APPLY(4)` 天然不命中（`ai_audit_result.target_type` 没有 4）✓。

★★ **这同时堵住了「队列页跳转处置后，队列行永远停在待确认」这个洞** ——
那是决定 6「只标确认/排除 + 跳转既有处置页」如果不做联动就**必然**留下的问题：
**一个不会消失的待办**。

**连带结论**
- ★ **`audit_log.target_type` 沿用 2/3，不新增第五种**：① 它回答的是「**审的是什么东西**」，不是「哪一次审的」；
  ② 新增 5 之后那条 switch 分支的标题该写什么？「AI 审核 #17」—— 管理员点进去看到的**不是内容，是一次审核**；
  ③ `ai_audit_result.target_type` 注释定死 `1小说 2章节 3评论`（无 4），两张表会给出**两套冲突的词汇表**。
- ★ **「排除」（AI 误杀）不写 `audit_log`**：它不改任何内容状态，**没有状态流转可记**
  —— 与「发表评论不记流水」同一条论证。它只更新 `ai_audit_result`（status=2 + audit_user_id + audit_time），单库单事务。
- ★ **「判的是不是当前这一版」用两个【已有的】列回答**：队列页并排显示「AI 判定时间(`create_time`)」
  与「内容最后更新时间」。**不加 `content_hash` 列** —— 本仓库没有 ALTER 惯例（见 §十一）。

#### 3.3 ★★★ 这条消息【不是】「幂等免费」的 —— 并由此订正铁律 7 的一处表述

`MqConstant.java:225-260` 对 `NOVEL_INDEX` 写着：

> 幂等天然、顺序无关、不需要 SETNX、不需要时间戳 —— 唯一的理由是**载荷里没有数据**。

★★★ **`AI_AUDIT` 的载荷形状与 `NOVEL_INDEX` 完全一样（只有一个 id），但它【不幂等】：
调一次 AI 是【非纯函数】的** —— 温度 > 0，同一个 `{targetType:3, targetId:94}` 消费两次
会得到**两份不同的判定**。

→ **判据的精确化（E1 的产出之一）**：

> `NOVEL_INDEX` 幂等免费，**不是因为「载荷只有一个 id」，而是因为「读真值之后做的那件事是纯函数」**。
> **「读真值」只有在【读完之后那件事也是确定的】时，才是幂等的充分条件。**

**处置：`AI_AUDIT` 比 `NOVEL_INDEX` 强一档 —— 幂等键是【内容指纹】，不是消息键。**
- 载荷 `{targetType:Integer, targetId:Long, at:Long}`；**指纹由消费端算**（它读的就是文本本身）：`hash(读到的正文)`。
- ★★ **为什么不用消息键**：那是「同一次发送重投」级别的幂等，**挡不住「内容没变却又被审了一遍」**；
  反过来它还会**误伤**「改了内容重新提交」—— 那**应该**重审。
- ★★ **所以粒度是「内容版本」而不是「判定结果」**：内容没变 → 永远只审一次（**这就是省钱的那道闸门**）；
  内容变了 → **应该**重审（新指纹，新键）。
- 写在既有的 `novel:mq:idempotent:{messageKey}` 命名空间下，`SET ... NX EX 86400` **一条命令**。
  24 小时 TTL 的副作用是自愈的。
- ★ **不写时间戳、不用 ORDERLY**：乱序不会让结论变错。
- ★★ **载荷里不许放枚举**：`rocketmq-spring` 的类型转换失败发生在方法体被调用**之前**，
  我们的 `try/catch` 没机会执行，载荷里的枚举**改名/删值会让在途消息全部静默进 DLQ**。
  `targetType` 用 `Integer`（与 `ai_audit_result.target_type` 的裸 `TINYINT` 对齐）。
  ★ 顺带一条能写进注释的安全结论：**给 `AiScene` 加 `AUDIT(5)` 不会影响任何在途消息** ——
  `AiScene` 住在 `novel-content`，载荷类住在 `novel-common/mq`，而 **`novel-common` 不依赖 content**，
  **结构上不可能**被载荷引用（判据不靠 grep 某个词）。

#### 3.4 ★★★ 一个 Tag 一个消费组一个载荷类 —— ★ 命名必须远离 `AUDIT_RECORD`

- **Tag `AI_AUDIT`，组 `group-content-ai-audit`，消费方 = content，两个生产者**（content 发章节、interaction 发评论）
  —— 与 `AUDIT_RECORD`（auth + interaction 两个生产者）**完全同形**，是本项目已有的成熟形状。
- ★★ **一个 Tag 只能有一个 listener、一个载荷类**（同组两个 listener = 后注册覆盖前一个且不报错）
  → 载荷必须**一个类覆盖两种目标**，这正是「载荷只带 id、文本由消费端取」的**另一个**理由。
- ★★★ **命名要远离 `AUDIT_RECORD`**：`group-content-audit` 与 `group-content-ai-audit` **形近**。
  `MqConstant` 里新增的常量与 `TAG_AUDIT_RECORD`/`GROUP_CONTENT_AUDIT` **隔开排列并互相引用说明**。
  **症状对照：某个 Tag 收不到消息且不报错 → 先查有没有两个 Tag 共用一个消费组。**

#### 3.5 ★★★ 词库：新表 + 内存快照，而「词库是空的」和「读不到词库」必须走不同分支

**为什么是【新表】而不是配置文件 / 只有 Redis**：它是**业务数据** —— 要能追溯来源、
能被运营增删改、要有 `enabled` 做灰度。这三件事只有表能给。

★★★ **决定性的一条：加【新表】是本仓库唯一「对已有库也幂等生效」的 DDL 形状**（`CREATE TABLE IF NOT EXISTS`）。
改列不行（`schema.sql` 的 CREATE 改了，已有库不会变），而本仓库**没有任何 ALTER / 迁移惯例**
—— 不要在一期里顺手发明一个。

**★★★ 铁律 10 的直接应用：词库是「参与筛选的输入」→ 一律不降级。**

| 情况 | 判据 | 处置 |
|---|---|---|
| `enabled=1` 的词条数为 **0** | 配置状态（还没录词） | **fail-closed：拒审**（返错）+ WARN |
| 加载**失败** / 快照没建起来 | 故障 | **fail-closed：拒审**（返错）+ ERROR |
| Redis / DB 连不上 | 故障 | 同「加载失败」—— **绝不能「当成空词库继续」** |

★★ **理由**：「当成空的放过去」= 违禁内容进库，**而且日志上没有任何异常** ——
这是铁律 8「一条不会失败的护栏」的教科书形态，**而且是最坏的一种：它连「我没在工作」都不说**。

**★★ 三个强制阳性对照（S7 实测 18/18 通过）**
- **①（拒审 ≠ 全放行）**：把 1/2/3 号种子词 + 探针全部 `enabled=0` 再 reload →
  断言扫描返 **5007**（不是 200 + 命中 0）；★ 并**追加一条**：连「干净的一句话」也拒
  （证明拒的是**词库不可用**，不是这段文字有问题）。同时断言 `loaded=true 但 ready=false、wordCount=0`。
- **②（关掉即不命中）**：关探针 → reload → 断言不再命中；**再打开 → reload → 断言又命中**
  （后半条是白捡的对照：证明第一次的「不命中」是开关造成的，不是别的原因）。
- **③（改了立刻生效 + 快照真被换过）**：新建探针（`enabled=1`）**不 reload** 直接扫 → 断言命中 0
  且 `version` 不变；reload → 断言命中，且 `version` **+1**，
  且 `status` 上 `enabledRows=4 > wordCount=3`（★ 「陈旧」是一个**能看见的数字**）。

★ **诚实的多实例说明（写进注释，不假装解决）**：多实例时两个快照可能不同。
补偿是**把陈旧变成一个能被看见的数字** —— 管理端显示「快照时间 / 词条数 / 上次 reload」。

#### 3.6 ★ 误杀怎么收场：关键词命中 **≠** 违规

大纲自己写了「关键词词库匹配 —— 快、免费、**误杀多**」。
→ **命中不做任何状态流转**，只做两件事：写一行 `status=0` 的待办 + 决定要不要调 AI。

三条理由（都写进了注释）：
1. **自动驳回会把「看起来正常的假话」变成一个终态**：章节 `REJECTED` 是作者能看到的驳回结果，
   而驳回理由得有人写 —— 机器替人驳回 = 作者收到一句 AI 生成的、**没人负责的理由**。
2. **这条链上已经有门了**：AI 与关键词都只是提示，自动处置等于**把提示变成裁决**。
3. **口径一致性**：`audit_log` 只记人的动作（表注释的分工），机器自动驳回会往这张表掺进「不是人做的」流水。

`status` 取值落位：无命中 → `risk_level=0` + **`status=2`(已排除)** + `audit_user_id=NULL`
（★ 判别式「`audit_user_id IS NULL` = 机器排除的」→ 页面显示「**机器排除**」而不是「已排除」）；
命中/存疑 → `status=0` 进队列。

★★ **`risk_level` 是 `NOT NULL` 且没有「未知」取值** —— 这一列**在结构上容不下「审核没跑成」**。
→ **「没审成」必须表达为「没有这一行」**（与「降级 = 让字段消失」同构）。
→ ★ **解析失败必须 ACK 且不写行**（重试会重复烧钱、结果一样）。
→ ★★ 如果哪天有人给审核失败补一个 `risk_level=0`，那就是**把「审核失败」渲染成了「审核通过」**。这句写进了注释。

★ **同一 (target_type, target_id) 只保留一条待办**：新判定到达且旧行仍是 `status=0` 时就地覆盖，命中 0 行则 INSERT。
理由：队列是**待办**不是历史（历史由 `audit_log` 承担）；两条待办会让人做第二次处置 → **一条「没发生过的」人工流水**。

### ★★ 判断 4：配额 —— 「检查」和「记账」分开，且被拒绝的请求不许吃额度

`AiController` 今天的 `remaining` 与 `total` **是同一个常量**，恒等、永不递减。
E1 换成 Redis 计数器 `RedisKeyConstant.AI_QUOTA + userId + ":" + yyyyMMdd`（键定义早已存在，零引用）。

```
① 预检（GET，为了给出漂亮的 429）           ← ★ 与 ② 不能同时原子
② SET ... 0 EX 90000 NX  →  INCR           ← ★ TTL 的建立必须是原子的（同 COMMENT_LIMIT 的论证）
③ if (n > limit) { DECR; 429 }             ← ★ 先占位再判断，满了就还回去
④ 生成 → finally 写 ai_usage_log
```

★ **为什么不是「先 GET 判断再 INCR」**：那在并发下会双双通过（`COMMENT_LIMIT` 的注释论证过同一个形状）
—— 所以 **① 只用来给好看的 429，② 才是权威闸门**。
★★ **「预检（漂亮的）状态码」与「扣减（精确）」不能同时原子 —— 这是一个明确的取舍**：
选**精确扣减**，代价是竞态下退化成错误帧（用户看到「生成失败」而不是「额度用完」，但**额度没有超发**）。
★ **为什么不是「INCR 后直接 429、不 DECR」**：那会让**被拒绝的请求也吃额度** ——
用户点 10 次白丢 10 次配额，而界面上看不出来（`remaining` 掉得比实际快）。
★ **这是一个「看起来正常的假数据」**，与铁律 10 反对的是同一种东西。
★ 日期在 key 里 → **即使 EXPIRE 丢了也只是内存泄漏、不是正确性问题**。

**`ai_usage_log`** 每次调用都写（成功与失败都写）；**`error_msg` 只能来自白名单常量**
（`upstream_401` / `timeout` / `parse_failed` / …），**绝不含上游 message**（防泄漏 + 防 Key 片段落库）。

#### ★★★ 「静默为 0」的坑，必须有阳性对照

DeepSeek 的流式响应**只在最后一块**带 `usage`，且**最后那一块的 `choices` 可能是空数组**。
- 无脑取 `choices[0].delta.content` → 最后一块 `ArrayIndexOutOfBoundsException`；
- ★ 为了躲它而**跳过 `choices` 为空的块** → **usage 一起被跳过** →
  **`ai_usage_log` 的 token 全是 0，且不报错**。

**★★ R1 实测把这句话订正了一半（见 §8.4 的 `R1-E4`）：**

| 这半句 | 实测 |
|---|---|
| 「`usage` 只在最后一块」 | **对**。303 帧里恰好 1 帧带 `usage`，就是最后一帧 |
| 「最后那一块的 `choices` 可能是空数组」 | **对 DeepSeek 不成立**。实测那一帧是 `[{"delta":{"content":""},"finish_reason":"length"}]` —— **一个元素、content 是空串**，不是 `[]` |

★★★ **但护栏照写，一个字都不能省。** 空 `choices` 是 **OpenAI 官方协议**里 `stream_options.include_usage` 的形状
（DeepSeek 在这点上**偏离了**它自称兼容的那份协议）。
**只按 DeepSeek 的形状写，就是让代码在换一个 OpenAI 兼容端点时静默失效** ——
而失效的表现恰好是「token 全 0 且不报错」，也就是这段注释本来要防的那件事。
★ **判据要从「DeepSeek 会怎样」写成「协议允许什么」** —— 这和铁律 8 的三种形状同源：
**把判据钉在某一次观测上，它就只在那个观测成立时有效。**
★ 实测另外两条也一并记下：`delta` 的键只有两种形状（首帧 `{role,content}`、其余 `{content}`），
**`content` 从不缺席、也从不 `null`** —— 所以「取 `choices[0].delta.content`」在本样本里**不会** NPE。
★ 这一段的可复现证据是 `docs/tools/recorded/r1-stream.sse`（真实字节，见该目录 README）。

> **判据：`ai_usage_log` 里 token 全 0，和「模型没返回 usage」长得一模一样。**
> → **只有一次真实调用能证明它。** 这是**唯一无法用假端点覆盖**的一条：
> 假端点返回的是**我们以为的**形状，用它验等于**用假设验假设**。

**处置**：取「**最后一个非空 `usage`**」+ 对 `choices` 判空，两条写进了同一段注释。
★ 项目另外用一个字段把它标出来：`AiUsageVO.tokenUntracked` = `success=1 AND total_tokens=0`，
**列表与汇总用的是逐字相同的判据** —— 所以「今天有 N 次未统计」在明细里找得到。

### ★★ 判断 6：两个 provider 的真相来源必须都显示出来，否则「填了 Key 不生效」是静默的

- YAML `novel.ai.provider`（`mock`/`deepseek`）→ **决定哪个 Bean 存在**（结构性、启动期）
- DB `ai_config`（`api_key`/`base_url`/`model`/`enabled`）→ 运行期参数

★★ **如果 YAML 还是 `mock`，管理员填完 Key 什么也不会发生，而且看不到原因** ——
他会以为填错了，然后反复重填。
→ **`GET /api/admin/ai/config` 必须同时返回「生效中的 provider（只读）」**，
页面据此显示横幅：「当前后端配置为 **mock**，此处填写的 Key 不会生效」。

**零改动自动消失** —— 这正是 P4 把 `provider` 做成后端字段的全部意义
（其类注释：「靠人去记得摘掉的标识，一定会忘记摘」）。S11 实测 `provider=deepseek` 时标签确实消失了。

### ★★★ 判断 7（S11 实测新增）：`requireOk` **永不读取**上游响应体 —— 比方案说的更严

方案里写着「上游返回的 body 一律不进错误出口，**只进服务端日志**」。
**实测：日志里也没有。** 全文件 grep `invalid_request_error` / `Authentication Fails` = **0 命中**。
翻 `AiModelClient.requireOk`：`body.close()` 直接关连接，**从不 read**。

★ **这个选择是对的，而且理由是结构性的**：后者需要一个「必须永远正确」的脱敏器，
而脱敏器失灵的后果就是**泄漏 Key** —— 又是一条不会失败的护栏。
「不读」**在结构上不可能泄漏**。与铁律 8 同族：把判据钉在「**有没有这条路径**」上，
而不是「过滤器写对没写对」。

★★ **代价必须记下来（诚实记账）**：非 401/403 的上游 4xx/5xx 因此**丢掉唯一能解释它的文本**。
管理员看到的是 `upstream_4xx (HTTP 400)` + 用量页那句「上游拒绝了本次请求（4xx）」，
而真实原因（`max_tokens` 超了 / 模型名写错 / 模板不合法）**一个字都没有**。
★ 考虑过「按状态码开白名单：401/403 不读、其余读并截断」，**没有采用** ——
它的正确性依赖「厂商只在这两个状态里回显 Key」这个**对第三方行为的假设**，
而那正是本项目一路在拒绝的东西。

### ★★★ 判断 8（S11 实测新增）：`Accept` 头是判断 1 整套设计的**承重件**

实测事故：第一次跑 429 用例，拿到的是 **HTTP 500 + 空 body**。日志：

```
GlobalExceptionHandler - 业务异常 | code=5004
Failure in @ExceptionHandler ... HttpMediaTypeNotAcceptableException: No acceptable representation
```

**原因在测试客户端**：它写了 `Accept: text/event-stream`。
建 emitter 之前的失败走 `@ExceptionHandler` 写 **JSON**，而内容协商只看 `Accept` ——
客户端只接受事件流时它**写不出任何表示**。
改成 `Accept: text/event-stream, application/json;q=0.9` 之后**同一个请求立刻变成 429 + 完整 JSON**。

★★★ **`sse.js:146` 早就写死了这个头**，注释里还记着实测数据（`400 + Accept: text/event-stream` → `Content-Length: 0`）。
**所以前端一直是对的，是验收脚本踩了它记过的坑。**

★★ **由此得到一条写进本文档的判据：**

> **「建 emitter 之前的失败」这套设计成立的前提，是客户端的 `Accept` 同时接受 JSON。**
> 谁把它「整理」成 `Accept: text/event-stream`，**判断 1 的四个状态码会全部退化成 500 + 空 body**，
> 而前端只会看到「请求失败（HTTP 500）」（`sse.js` 的 `catch{}` 兜住了空 body，
> 所以**不报错、不白屏**，只是所有可操作的文案一起消失）。

★ 这是一条典型的「不会失败的护栏」：**验收脚本只要用对了头就永远发现不了它**。
★ 而这次事故白捡了一个**零成本的阳性对照**：同一个请求、只换 `Accept` 头，一个 429、一个 500。

### S4 —— 真客户端 + 假端点 + 配额（免费）

★★★ **中断机制的实测订正（推翻 P4 的一句注释）**：
P4 在 `AiController` 写着「不能只靠 ③，① 这个标志位才是必须的」。
**S4 实测：真正让生成停下来的是 ③（`SseEmitter.send()` 失败），而 ① 从头到尾没被触发。**
证据 = 探针打出 `send() 失败的那一刻 aborted=false`；同一份实测里「上游停止推送」是真的
（假端点第 11 帧看到连接断开、没跑到终点）—— **所以钱确实没白烧，被推翻的只是「这该记在 ① 头上」。**

★★★ **阳性对照失败了，而且失败得很有价值**：把 `if (aborted.get())` 改成 `if (false && …)`，
结果**和对照组一模一样**。★ 这说明「阳性对照本身也要能失败」——
我原本以为的判据（假端点会一直吐到结束）**根本区分不出这两种实现**，
因为它测的是「连接断开」而不是「标志位有没有起作用」。
最后是靠**第三个探针 build**（直接打日志）才拿到结论 —— **不是靠调阈值**。

其它：
- ★ **`AiFailure` 枚举是结构性护栏**：`error_msg` 只能取白名单常量，**上游返回的原文永远进不来**。
  理由不是洁癖 —— 真实 DeepSeek 的 401 响应体**会回显 Key 片段**。
- ★ **假端点用模型名当选故障开关**（`fake-slow` / `fake-429` …），因为 `ai_config.model`
  是现成的、可写、零代码的旋钮 —— 与 `base_url` 同一个手法。
- ★ **`HttpClient.Redirect.NEVER`**：**默认的 NORMAL 会把 `Authorization` 头重发到跳转后的主机**。
  一个配错的 `base_url` 能把 Key 送到第三方。★ 这条是安全设置，注释里写死了。
- ★ **已知欠债（诚实记账）**：JDK `HttpClient` **没有「读响应体」超时**。
  `RESPONSE_TIMEOUT` 只覆盖到「响应头返回」。上游把响应头发出来之后挂住不吐数据，
  这个 `ai-stream-N` 线程会被一直占着（池子最大 4）。★ 不假装解决，写在 `AiModelClient` 的类注释里。
- ★ **`novel.ai.daily-quota`（YAML）已删** —— P4 时 YAML 与 `ai_config.daily_limit` 两个数并存，
  **改 YAML 那个不会有任何效果、也不会有任何提示**。
  「一个转了却什么都没发生的旋钮」和「一条不会失败的护栏」是同一种坏东西。
  ★ 连带：`GET /api/ai/quota` 在 AI **停用**时也必须能答（种子就是 `enabled=0`）——
  所以 `dailyLimit()` **刻意不抛异常**，只在值不可用时 WARN + 回落常量。

### S5 —— 管理端两页

- ★★★ **MyBatis-Plus 的 wrapper `condition` 参数【只决定用不用，不决定算不算】。**
  `.ge(startDate != null, AiUsageLog::getCreateTime, atStartOfDay(startDate))` 旁边注释着
  「只在非空时被调用（condition 参数保证）」。**Java 先求值实参再调方法** → `atStartOfDay(null)` 无条件执行 → NPE。
  症状：`GET /api/admin/ai/usage` **不带任何筛选** → 500。★ 这是主路径不是边角：页面刚打开就是这个请求。
  ★ 教训：那条注释是一个**从未被验证的断言**，而且写在那行代码旁边、读起来像已经验过了。
  修法不是给 helper 补判空（那个形状本身是陷阱），而是**先把可能为 null 的转换落到局部变量**。
- ★★ **`@JsonIgnore` 护栏的失效方式也是【静默】的**：body 里塞 `renderedSystemPrompt` →
  **既不报错也不生效**（`FAIL_ON_UNKNOWN_PROPERTIES=false` 静默丢弃），日志里 0 处 `INJECTED`。
  ★ 判据就是「日志里没有那个词」——**去掉 `@JsonIgnore` 它就会亮**，所以这是一条**能失败的**判据。
  ★ 要记住的一句话：这条护栏**两个方向都不报错**。

### S6 —— 渲染接入 + 前置闸门（仍免费）

★★ **错误出口分流全部实测**（这一条推翻了「必须靠浏览器看」的预设）：
实测表格 `400`(必填缺失) / `403`(2002 别人的作品) / `404`(2001 不存在) / `429`(5004) / `503`(5001/5002)

① `AiPreflight.httpStatusOf` 的 `case 5004 -> 429` 改成 `-> 200`；② `AiQuotaServiceImpl.decrement(key)` 注释掉。
实测：HTTP **200** + `application/json` + `{"code":5004,...}` ✓；计数器 **50 → 51** ✓（被拒的请求吃了额度）。

★★ **403 这条要一次性夹具，种子验不了它**：种子里 12 本书**全部** `author_id=4` →
「动了别人的作品」在种子上**不可能构造**。做法：插一个 `author_id=1` 的一次性作品 →
用 author01 请求 → **403 + `{"code":2002,"message":"这不是你的作品"}`**
+ `NovelAccessGuard` 的 `[越权尝试]` 日志。

★★ **验收 AI 生成必须用 author 账号，admin 会得 403**（`/api/ai/**` 不在 `/api/admin/**` 的规则下）。
★ 我第一版验 DECR 时误用 admin token，于是「配额没被消耗」这个结论**看起来成立、其实什么都没验**。

★★ **配额那条不能只看 `remaining`，要看 Redis 的原始计数器**：
`remaining = max(0, limit - used)` → used=50 与 used=53 都显示 0，**判据在闸值上不可分**。
实测（本机无 redis-cli，用 Python 裸 RESP 读）：把 limit 还原成 50 → 连打 4 次全部 429 →
再读计数器**仍是 53**。★ 若 DECR 被摘掉，读数会是 57 —— **差分成立**；阳性对照构建里**真的看到 51**。

**两套编号，同一个数字含义不同**，别跨表套用。

★★ **给评论写夹具要三步，漏一步的症状极具误导性**：① 建作品+章节并提交章节；
② ★ **作品本身也要提交**；③ 管理员审核通过。漏了第 2 步的症状是读者侧发评论拿 **`2001 作品不存在`**
—— 排查方向会指向「书建失败了」或「id 传错了」，而真相是「书还在草稿箱」。

### S10 —— 前情摘要

★★★ **抓到一个真 bug（不是判据写错）**：`AiSummaryVO.chapterCount` 原本算成
`end - start + 1 - skipped.size()`。区间 [5,6] 且跳过第 4 章时得 **1**，而真正参与压缩的是 **2** 章 ——
因为 `start` 已经被推到了 5，**第 4 章根本不在区间里**，减它是重复扣。
★ 修法：章数在循环里【数出来】（`coveredCount++`），不要从区间长度反推。
★ 这个形状值得记：**两个都对的东西相减，得到一个错的**。
「区间长度」和「跳过数」各自都是对的，只有它们的差在「跳过项落在区间外」时无意义。
★ 边界夹具（ch4 在区间左端）只差 1；**中段空章**（1有 2空 3有）才把真值 2 与错值 3 分开 ——
所以 `mid-gap` 那条不是重复劳动。

其它判据与手法：
- **③/⑤ 解耦的差分**：同一条 `POST /api/ai/write` 请求，摘要存在前后各打一次日志。
  之前 `移除=[outline, summary]` 且 user message 里没有「前情摘要」那一行；
  之后 `移除=[outline]` 且**摘要原文逐字出现**（198 字全串比对，不是截断子串）。
  ★ 断言必须钉在「summary 在不在移除列表里」，**不能钉在整串 `移除=[summary]`**。
- **★ 一条把日志/响应/库串起来的判据**：mock 的摘要自报「本次压缩覆盖正文约 N 字」，
  那个 N 就是 `AiSummaryVO.sourceChars` —— 断言两者相等。它同时证明
  「发出去的正文」=「VO 报的正文」=「实际读到的章节正文」。
- **不能重压**：`endChapterNo = 上一条的 end` → **HTTP 400 + code 400**，文案指名第 3 章；**不扣额度**。
- **跳过要报出来**：区间 [4,6] 里第 4 章空的 → `skippedChapterNos=[4]`，
  且**落库的区间是 5~6**（存的是实际覆盖，不是请求区间）。
- **预算护栏**：13592 字 → 400，文案含「8000」「第 8~40 章」「endChapterNo」；**不扣额度**。
  ★★ **阳性对照做足了**：把 `MAX_SOURCE_CHARS` 改成 80000 重新打包重启，
  **同一个请求 13592 字 → 200，覆盖 8~40**，扣 1 次额度。之后还原成 8000 再打包一次。
  这条同时证明「护栏拦住了」和「拦住它的确实是这个常量」。
- **失败不落库**：正文含 `__MOCK_FAIL__` → `code 5003`，`ai_summary` **没有新行**。额度扣了 1（诚实记账）。

★★ **新端点上的失败状态码有【两个来源】，不是一套**：
- 本服务里那几道（区间/预算/归属/参数）走**项目通用约定** `200 + 业务码`
  （只有 400 段因为 `ResultHttpStatus` 的映射才变成真 400）。实测 `我是作者但作品不存在` → **200 + 2001**。
- 闸门里那几道（停用/额度/模板/组装）被 `AiPreflight` 换成了**真实状态码**。
- **生成中途失败** → **HTTP 200 + code 5003**（`5003` 不在 `ResultHttpStatus` 里，
  也不经过闸门的翻译 —— 它发生在闸门**之后**）。
★ 两者对前端都诚实（`request.js` 两条分支都渲染 `message`），所以**不改**；
但「同一条链路上错有两种形态」这件事必须写下来，否则下一个人会以为漏改了。
★ SSE 那条链上同一个失败是 `event: error` 帧 —— **同一个 5003，两个出口**。

★★ **mock 模式下的「额度账」与「用量账」对不上**：`MockAiAuditEvaluator` 会写 `ai_usage_log`
（实测 4 行，`model='mock'`、token 全 0、`user_id=0`），而 `MockAiStreamSource` **一个字都不写**。
★ 不改（账本记的是「花掉的钱」，mock 没花钱），但看用量页时
「今天调了几次」与「额度少了多少」在 mock 下**必然不等**。

### 收尾补丁 ① —— `ai-stream-N` 的 traceId（`e1完成` 提交之后补的）

**为什么补**：它在「已知技术债」里的原话是「修它要重打包重启，而收益只在下一次排查时兑现」——

| 改**之前**（同一份日志文件里，重启前的 48 行） | `[] [ai-stream-1]` ×32、`[] [ai-stream-2]` ×16 |

| 同一个 id 在 **gateway** | 1 行，`[reactor-http-nio-10]`（**生成它的那个线程**） |
| 同一个 id 在 **content** | 7 行 `[http-nio-8082-exec-4]`（请求线程）＋ **2 行 `[ai-stream-1]`**（池线程） |

★ **对照组是白捡的**（同 M5 那条）：改前/改后、请求线程/池线程，四种行**在同一份输出里**，

**★★ 验了两遍，而第二遍是刻意的。** 第一遍验完之后我改了一处**注释** ——
行为一个字没变，但**源码和「被验过的那个构件」就不再是同一份了**。
于是重新打包、重启、**重跑一次同样的实验**（又一条 traceId，`c02f96c8…`），
让最终躺在 `target/` 里的那个 jar 就是**被验过的那个**。
★ 代价是 0 元 + 一个额度单位；收益是「验过了」这句话没有隐含前提。
★ **反过来说：如果验完之后还要改代码，那之前那次验收的证据仍然是有效的（行为未变），
但它指向的构件已经不是最终交付物了 —— 这句话不写清楚，下一个人会以为两者是同一个东西。**

**★★★ 顺带记一个自己踩的判据坑（同铁律 8 的第一种形状）**：
就绪判据我写成了 `curl -s -o /dev/null <url>` —— 它**对 503 也返回 0**。

**★★ 顺手订正一处 CLAUDE.md 的错误原因（结论不变，机制说反了）**：
原文写「前端看不到 traceId —— `request.js` 是锁定文件、响应拦截器 `return res.data`，**响应头在前端被丢掉**」。
实测 `curl -D -` 打网关，**响应头里根本没有 `X-Trace-Id`** —— `TraceIdFilter` 只读不写、

按新说法，正确的做法是**从网关日志按时刻反查**（本次验收就是这么取到 id 的）。
★★ **同一条错误机理在 `docs/M5-治理.md` 里还有两处，本次一并订正**（§6.2 的正文 + 十三节债表那行）——

### 坑 2 ★★★ `Vue` 模板里不能写 `{{ '{{名字}}' }}` —— `/ai` 页面曾经**从未编译通过**

**症状**：`GET :5175/admin/src/views/ai/index.vue` → **HTTP 500**，
`Error parsing JavaScript expression: Unterminated string constant`。

**根因**：模板里写了 `<code>{{ '{{名字}}' }}</code>`。**Vue 的模板编译器找插值结束符时不认识字符串字面量** ——
它扫到字符串里那个 `}}` 就当插值结束，表达式变成 `'{{名字`（没闭合的字符串常量）→ 编译失败。
★★ 已用 `@vue/compiler-sfc` 实测四种写法：

```
FAIL  {{ '{{名字}}' }}                         ← 最初写的
OK    <code v-pre>{{名字}}</code>               ← 采用
OK    {{ '{' + '{' + row.name + '}' + '}' }}   ← 能过，但可读性差，没用
```

★★★ **教训：「接口通了」不等于「页面在」。**
S6 的验收全部走 HTTP（预览端点、配置读写），页面本体一次都没在浏览器里渲染过 ——
而 vite 的失败**不在任何日志里**，只在 `curl` 那个 500 上。
判据要钉在**编译产物**上：`curl -o /dev/null -w '%{http_code} %{content_type}'` 模块 URL，
要看到 `200 text/javascript`（**不是** 200 就当过，SPA 回落 HTML 也是 200 —— 铁律 4）。
★ 现已对 **admin-web 全部 21 个 `.vue`** 跑过 `compiler-sfc` 解析，全部通过。

### 坑 3 ★★ 打包前停进程【必须】，而且中途失败会留下半新半旧的 target

### 坑 4 ★★ 自己的验收脚本里「数个数」的断言，两次误报

### 坑 9 ★ 环境细节

### 坑 10 ★★★ 录制代理的文件名由**启动参数**决定，而跑批脚本以为它由**请求**决定 —— 差点为它再花一次钱

`rec.py` 的命名是 `"%s-%02d-%s" % (PREFIX, _seq[0], "stream"|"json")`，
而 `PREFIX` 来自**启动时的环境变量** `REC_PREFIX`（那次是 `proxycheck`）。
跑批脚本却写的是 `newest("r1-")` / `newest("r2-")` —— **这两个名字永远不会存在。**

结果：R1 的 `R1-E1` 与 R2 的 `R2-H1` **都报「没有录制文件」**，
而**它们想找的那两个文件，一个 87669 字节、一个 670 字节，都好端端躺在 `recorded/` 里**（叫 `proxycheck-02-*` / `proxycheck-03-*`）。

★★★ **真正的危险不是这两条假失败，而是它引导你去做的那个动作**：
「录制没成功 → 那就再跑一次真调用」—— **再花一次钱去重新生成一份本来就在手上的字节。**
（正确动作：`ls recorded/` 按时间戳认领。这次就是这么做才没重复计费。）

**根因（铁律 8 家族的又一例）**：判据本身没问题，**是测具里多出了一条没人声明、也从未被阳性对照过的隐含假设**
——「文件名由请求决定」。而**阳性对照本来是免费的、且早就摆在眼前**：
`proxycheck` 那一步已经产出过 `proxycheck-01-stream.sse`，
只要当时用它跑一次 `newest("r1-")` 并断言「能找到」，$0 就能发现这个 bug。
★ **「测具能找到自己产出的东西吗」本身要有一条断言**，否则所有「录制对不上」的失败
都会伪装成「被测对象没产出」。

|---|---|
| **只是不想花钱** | `PUT /api/admin/ai/config` 把 `enabled` 置 `0`（种子基线本来就是 `0`）—— **一行配置，不用重新打包** |
| 退回 mock | 重启 content 时去掉 `--novel.ai.provider=deepseek`（或显式给 `mock`）。★ **YAML 默认值就是 `mock`**，所以「什么都不给」= mock |
| 换掉一把配错的 Key | 管理端点「清除 Key」（`clearApiKey: true`），或直接 `UPDATE ai_config SET api_key=NULL` |
| **整期回退** | `git revert <e1完成>` + 重新打包。★ **DDL 是幂等的**：`ai_sensitive_word` 是 `CREATE TABLE IF NOT EXISTS`，**留着不影响任何东西**（新表，无人引用）；4 条种子词、5 条模板的改动同理，删除表/行都不影响其余 21 张表 |
| 词库出问题 | 把 `enabled` 全置 0 → **系统 fail-closed 拒审**（这是设计要的，见判断 3.5）；要「继续放行」得改代码，**没有那个开关** |

★★ **唯一不可逆的是花钱** —— 所以「回滚」的第一道闸门不是 git，是 `enabled=0`。
★ 交付时 `ai_config.enabled = 0` 且 `api_key` 为空，**克隆下来跑不出一次计费调用**。

### ★ 已知技术债（诚实记账，不在本期修）

| 债 | 症状 | 为什么留 |
|---|---|---|
| **全链路的 traceId 仍然串不起来**（`ai-stream-N` 那半截**已修**，见收尾补丁 ①） | RocketMQ 的生产回调 / 消费行仍是 `[]`（日志里 `NettyClientPublicExecutor_N`） | ★ 那些线程归 **RocketMQ 客户端自己**管，不是我们的池 —— 任何 `TaskDecorator` 都够不着。**要让它们带上 traceId 得把 id 塞进消息头、在消费端重新入 MDC**，那是另一件事。★ 别把它当成「补一个装饰器就好了」 |
| **JDK `HttpClient` 没有「读响应体」超时** | 上游发完响应头再挂住 → 占住一个 `ai-stream-N` 线程（池子最大 4） | 判断 7 同类；已在 `AiModelClient` 类注释里写死 |
| **`POST /api/ai/summary` 没有前端入口** | 只能 curl 触发 | ★★ **不是「缺一个按钮」** —— 端点是同步的，而 `request.js` 的超时是 **15 秒**（锁定文件，不能改）。长区间的一次真实压缩会在**前端侧超时**：后端跑完、钱花了、摘要落库了，作者看到失败提示。★★ 更坏的是**重试陷阱**：`endChapterNo` 必须严格大于上一条，所以作者重试拿到的是 **400**，而摘要其实**已经在库里了**。★ `AiSummaryService` 的类注释早就写了这一条（「真要给作者用之前，这条必须先处理」）—— 真要加 UI，先做「异步化 + 任务表 + 轮询」或「按请求放宽超时 + 把 400 渲染成『已生成过』」 |
| **`ai_config` 无唯一键** | 理论上能插出第二条 | 见上「不动」 |
| **作者分不出「等一会儿会好」和「要找人」** | 错误帧永远是「生成失败，请稍后重试」 | **刻意的**：作者改不了 Key，告诉他「Key 无效」只会让他去做一件他做不到的事。★ 代价是真实的，写在判断 1 里 |
