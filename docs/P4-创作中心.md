# P4 · 创作中心 —— 实施方案与实施记录

> 对应项目大纲 §1285。**验收原话**：
>
> > **P4 创作中心**（5~6 天）｜在 `author-web` 里做：作品管理、章节管理、**工作台（大纲树 + 右侧工作区 + AI 面板）**、提交审核｜**作者能在界面上完成一本书的从建到发布；切换节点时大纲树纹丝不动**

## Context

P0（脚手架）、P1（认证权限）、P2（内容主干）、P3（读者端）已验收。P4 的起点是：**`author-web` 基本是空的** —— 只有一条 P0 的连通性验收路由、一个占位左侧栏、两个 api 文件。读者端在 P3 长出的那套范式（`usePagedList` / `format.js` / `App.vue` 的中文语言包）它一样都没有。

后端作者侧的**作品 / 章节 CRUD 在 P2 就完备了**，P4 要补的是三块全新的：**大纲树**（`novel_outline` 表在 `docs/sql/schema.sql` 里已经建好，但 Java 侧一行代码都没有）、**封面上传**（端到端不存在）、**AI 面板**（大纲 §6.3 / §8 属于第三期 E1，`ai_config.enabled` 种子值是 `0`）。

## 设计要点与坑

### D-1 ★★ 三层嵌套路由 —— 两个方向相反的坑

```
/novel/:novelId/work/:nodeId
  AppLayout          顶部导航 + 左侧作品栏
    └ WorkLayout      :novelId 不变 → 不重挂载 → ★ 大纲树纹丝不动（挂这一层）
        └ NodeWorkspace :nodeId 变 → 需要重新加载 → <router-view :key="nodeId"> 强制重建
```

1. **大纲树写进页面组件** → 切节点时跟着重挂载 → 闪烁、滚动位置跳回顶部、折叠状态复位。**要提到 `WorkLayout` 这一层。**
2. **右侧工作区不加 `:key`** → Vue Router 默认复用同组件实例 → 切节点时内容不刷新（还显示着上一章）。**要加 `<router-view :key="route.params.nodeId" />`。**

★ 也**没有**挂到全局 `AppLayout` —— 那样「我的作品」「章节管理」页也会冒出大纲树。★ 顺带补了 `author-web` 缺失的 `scrollBehavior`。

### D-2 ★★ 树组装：`groupingBy` 的 null key 是个 100% 复现的坑

**裁决：接口返回嵌套结构，不是扁平列表。** 大纲 §7.3⑦ 说「一次查全量，前端组树」是**传输策略**（不要懒加载），§6.3 说「整棵大纲树」是**响应形状**，两者不矛盾。

**让后端组树的理由**：树节点上的状态图标长在**另一张表**（`chapter`）上，让前端组树就等于让前端做一次跨表 join，还要自己维护 `nodeId → chapter` 的第二份映射。后端一次 `selectByIds` 就顺手拼上了，无 N+1。

```java
// ★★ 绝对不能用 Collectors.groupingBy —— 它在 key 为 null 时抛 NullPointerException。
//    而「根节点的 parentId 是 null」正是最正常的情况：
//    也就是说，只要这本书有一个根节点，GET /outline 就 500。
Map<Long, List<OutlineNode>> byParent = new LinkedHashMap<>();
for (OutlineNode node : all) {
    byParent.computeIfAbsent(node.getParentId(), k -> new ArrayList<>()).add(node);
}
```

另外四条：

- **排序只写一份**：`ORDER BY sort ASC, id ASC` 放在 SQL 里，分桶后每个 List 天然有序。`sort` 有大量并列（历史数据默认全 0），**没有 `id` 兜底列时同一请求两次可能给出不同顺序**。
- **叶子节点的 `children` 必须是空 `List`，绝不能是 `null`** —— `spring.jackson.default-property-inclusion: non_null` 会把 null 字段**整个从 JSON 里抹掉**，前端 `node.children.length` 拿到 `undefined` → `TypeError` → **整棵树白屏**。而这个 bug **只在恰好没有子节点的节点上出现**，最容易漏。**已实测**：叶子节点的 `children` 真的是 `[]`。
- **`roots` 用数组不用单个对象**：`parent_id IS NULL` 的行数据库拦不住多行（MySQL 没有「条件唯一索引」，唯一索引里 NULL 互不相等），只能 Service 层保证。万一出现两个根，返回单个对象会反序列化失败 → **整个创作中心打不开**；返回数组最坏只是渲染出两棵树。另外「这本书还没有大纲」返回 `[]`。
- **环保护**：DFS 传的是当前**路径**上的 id 集合，回溯时 `remove`（不 remove 的话集合语义变成「访问过的全部」，兄弟重复会被误判成环）。**理由**：`StackOverflowError` 是 `Error` 不是 `Exception`，**掉不进 `GlobalExceptionHandler` 的兜底** —— 一个坏节点能让**整个创作中心**打不开。

★ 实施后发现这条环保护**在正常路径上触发不到**，真实症状和补救见**实施记录 ③**。

### D-3 ★★ 两个 `status` 字段的裁决：`novel_outline.status` 是死列

**一句话**：树上的图标一律显示 `chapter.status`，外加「未创建正文」这一个派生状态；`novel_outline.status` **P4 不写不读**。

前端只需一行判断，不需要第二份映射（后端同时给 `chapterStatusDesc`）：

```js
const icon = (n) => !n.chapterId ? '○未创建正文' : n.chapterStatusDesc
```

**三条理由：**

1. **它是冗余的**。`0未开始` ≡ `chapter_id == null`；`1写作中` ≡ `chapter_id != null AND status ∈ {0,1,4}`；`2已完成` ≡ `chapterStatus == 2`。所有取值都能从另外两个字段推出来。
2. **维护它会造出双向依赖**。章节状态流转在 `ChapterServiceImpl.transitStatus`，要让大纲 status 跟着变，章节模块就得**反向写 `novel_outline`**。而大纲模块本身又在读章节 —— 两个包互相依赖，**将来拆微服务时拆不开**。不写它就必然静默腐烂：审核通过了一章，大纲图标还是「写作中」，没有测得到。
3. **UI 上放不下**。大纲 §7.3 只给了一组图标，就是 `chapter.status` 那四个 +「当前编辑中」（前端临时态）。

**这一列保留不删**（删列要改 P2 已落地的 DDL，而它零成本），但在 `OutlineNode` 实体上写清楚了**它是死的**。

### D-4 ★★ `move` 的形状与防环

**形状裁决：`{targetParentId, beforeNodeId}`，不是「有序 id 数组」，也不是 `position` 索引。**

| 方案 | 否决理由 |
|---|---|
| 有序数组 | 前端每次拖拽都要算出完整新顺序，而 `el-tree` 的 drop 事件给的是「拖到哪个节点上、什么位置」，**不是**新数组 |
| `position: 2` | `position` 是**相对量**，两人同时拖拽时同一个「2」对应两份不同的兄弟列表。★ 更致命：**没有任何 `position` 值能表达「追加到末尾」** |
| **`beforeNodeId`（采纳）** | `beforeNodeId = null` **唯一且稳定地**表示「追加到末尾」，而这是最高频的操作 |

```
dropType = 'inner'  → { targetParentId: 目标id,   beforeNodeId: null }
dropType = 'after'  → { targetParentId: 父id,     beforeNodeId: 下一个兄弟id或 null }
dropType = 'before' → { targetParentId: 父id,     beforeNodeId: 该节点id }
```

★ **前端拿 `targetParentId` 的坑**：`el-tree` 根层级的 `data.parent.data` 是**包裹用的虚拟根**，它的 id 是 `undefined`。必须转成 `null` 再发。

**防环（`requireNoCycle`）**：判据方向是「判 `targetParentId` 是不是 `nodeId` 自己或它的子孙」，**从 `targetParentId` 往上走**（目标父节点通常在浅层，走的路更短）。

```java
// ★★ visited 集合不是防御性编程，是【必须】的：库里可能【本来就有】环。
//    有环的话 while 循环永远走不到 null —— 一个 HTTP 请求把 Tomcat 工作线程占死。
//    所以用 visited.add() 的【返回值】判断。
// ★ 两种情况给【不同的】码：用户做错了 → OUTLINE_PARENT_ILLEGAL(3009)；
//    数据本来就坏了 → OUTLINE_TREE_BROKEN(3010)。
```

**跨父移动必须同时重排原父节点的子序列**：

```java
// ★★ 漏掉这一步的症状很典型：把第 2 个节点拖走后，原来的第 3、4 个节点
//    sort 还是 2、3 —— 表面看顺序没变，但从此这个列表缺了 0。
//    真正暴露是在【几次拖拽之后】，而此时已经没人记得是哪一次操作造成的。
if (!Objects.equals(node.getParentId(), targetParentId)) {
    renumber(orderedChildIds(all, node.getParentId(), nodeId));
}
```

★ **`Stream.toList()` 返回不可变 List**（`Collectors.toList()` 可变，两个方法名几乎一样，**编译器不会有任何提示**）—— `orderedChildIds` 的结果必须 `new ArrayList<>(...)` 拷一份再 `add`。

★ **`sort` 可以直接写、不用先挪临时值**，因为 `novel_outline` 上**没有唯一键**（这点和 `chapter.chapter_no` 完全不同）。**别给 `sort` 加唯一键**，加了 `renumber` 立刻开始撞。

### D-5 ★★ `POST /nodes/{nodeId}/chapter`

**事务**：整个方法一个 `@Transactional`，内含三次写（chapter insert / chapter_content / outline update）。**不拆** —— 回填失败会留下「大纲节点看不见、章节列表里躺着一章」的孤儿章节。

★ **加 `SELECT ... FOR UPDATE`，这是「连点两下只建一章」的唯一保证。** 不加锁时两个并发请求都读到 `chapterId == null`，都去调 `chapterService.create()`，第二次撞 `uk_novel_chapter_no` → 用户看到 **3004「该章节序号已存在」**，一句和「我要建正文」毫无关系的话，然后他多半再点一次。★ **锁必须在事务里才有效**，没有事务的话 MySQL 在语句结束就释放锁，**锁形同虚设且不会有任何报错**。

**幂等**：已有 `chapter_id` 时返回 `{created: false, chapter}`，**不报错**。用户点第二下时意图和第一下完全相同。**实测**：连点两下返回 `created: false`，全书只有一章。

**悬空自愈**：`node.chapter_id` 指向的章节可能已被删除（作者在**章节列表**里删的，那条路径不经过大纲树）。这里 `log.warn` + 清空 `chapter_id` + 重新建，**不报错**。理由：这是唯一能把作者彻底卡死的情形 —— 页面显示「已有正文」，点进去 3001，而**界面上没有任何按钮能修**。**实测**：日志里有 `[悬空章节链接]` 的 WARN，自愈建出了新章。

| 字段 | 来源 | 理由 |
|---|---|---|
| `title` | 节点标题，**只在这一刻拷一次** | `chapter.title` 的写入口只有 `saveContent`，它带着「`PENDING` 期间不能改」的守卫。做「改节点标题同步章节标题」等于多开一条绕过守卫的写路径，**且没有任何症状** |
| `chapter_no` | `ChapterService.create` 内部的 `MAX+1` | ★★ **绝不能按树的位置算**。按位置算意味着把节点从第 3 位拖到第 5 位就要重排两章正文的序号 —— 而那两章可能**已经发布**，读者正在看的目录会突然变化。**拖大纲不该改动已发布作品的目录。** |

★ **正文故意不拷**：`node.content` 是「这一段要写什么」的剧情笔记，不是正文。塞进去有两个后果：① 作者打开新章节看到一堆自己的笔记；② 更隐蔽 —— 它让「空正文」永远不成立，`submit` 里那道 `CHAPTER_CONTENT_EMPTY` 从此形同虚设。

★ **不调 `syncNovelStat`**：新建的必是草稿，而 `chapter_count` 的口径是「**已发布**章节数」。顺手调一下「反正没坏处」是错的 —— 它会重算 4 个冗余列并 `UPDATE novel`，凭空给这本书加一次行锁。

★ **加锁顺序**（先锁 `novel_outline` 行、后写 `chapter`）写进了注释：将来若有方法反过来，就是经典的 AB-BA 死锁，而第二个方法出现时没人会想起来。

### D-6 级联删除用**内存 BFS**，不用递归 CTE

| | `WITH RECURSIVE` | Java 内存 BFS（采纳） |
|---|---|---|
| **数据有环时** | **死循环到 `cte_max_recursion_depth`（默认 1000）才报错** | `visited` 直接跳过 |
| 深度上限 | MySQL 有限制 | 无 |
| 复用 | 只此一处 | `collectSubtreeIds` 同时被 `delete` 和前端弹窗的计数用到 |

★ MP 的 `deleteByIds` **是 `@TableLogic` 感知的**（走 `UPDATE ... SET deleted = 1`），**不需要手写 `deleted = 0`**。这和 `ChapterMapper#logicDeleteAndFreeChapterNo` 完全不同。`OutlineNodeMapper` 保持**空接口**，类注释里写清楚了为什么它可以空着。

★ **删除接口返回计数** `{deletedNodes, linkedChapterCount}`。`linkedChapterCount > 0` 时前端提示「其中 N 个节点已有正文，**正文未被删除**，可在章节列表中找到」—— 用户的直觉一定是「删了大纲我的正文没了」。**实测**：删 C 子树（6 节点）→ `deletedNodes: 6`、`linkedChapterCount: 1`、**正文章节一个都没少**。

★ **没有单独的 count 接口**：整棵树已经在浏览器里了，前端递归求和就行。再加一个接口是多一次往返、多一处可能不一致。

### D-7 ★★ 归属校验：**请求体里也有 id，这才是真正的洞**

`novel_outline` 上没有 `author_id`，归属只能经 `novel` 判定。**这一跳放进了 `NovelAccessGuard`**（不在 `OutlineServiceImpl` 里写 private 方法 —— 那份校验里有 `[越权尝试]` WARN，而那个类的注释已经确立「越权必须留痕只有一处实现」）。

新增 4 个方法，`requireOwnedOutlineNode` **完全照 `requireOwnedChapter` 的形状写**（含「孤儿」分支那条措辞不同的 WARN）。

| 接口 | 校验 |
|---|---|
| `GET .../outline` | `requireOwned(novelId)` |
| `POST .../outline/nodes` | `requireOwned(novelId)`；★ **`dto.parentId` 非空时再 `requireNodeInNovel(novelId, parentId)`** |
| `PUT /outline/nodes/{nodeId}` | `requireOwnedOutlineNode(nodeId)` |
| `DELETE /outline/nodes/{nodeId}` | `requireOwnedOutlineNode(nodeId)` |
| `PUT /outline/nodes/{nodeId}/move` | `requireOwnedOutlineNode(nodeId)`；★ **`dto.targetParentId` 非空时再 `requireNodeInNovel(node.getNovelId(), targetParentId)`** |
| `POST /outline/nodes/{nodeId}/chapter` | `requireOwnedOutlineNodeForUpdate(nodeId)` |

★ **加粗那两行是这套校验里唯一的洞，而且它不体现在「URL 上有几个 id」这个维度上 —— 它在请求体里。** 不校验的症状极其隐蔽：把自己的节点挂到别人的节点下 → `GET /outline` 走的是 `requireOwned(自己的novelId)` 查全量，**别人的节点查不出来** → 自己那个节点变成孤儿，**在树上完全不显示，且没有任何错误**。作者会以为「保存失败」，再拖一次，循环。**实测**：跨作品 `targetParentId` 返回 3007。

### D-8 ★★ SSE：用 `fetch` + `ReadableStream`，**不用 `EventSource`**

大纲 §8.3 原文：「前端用 `EventSource`，注意它**不支持自定义请求头**，所以 token 得走 query 参数或 Cookie」。

**这一条必须偏离，理由是本项目自己定的铁律**：§7.5 明确拒绝了「把 token 放 URL」（token 会留在浏览器历史、服务器 access log、Referer 头里）。而 §8.3 的建议正是把 token 塞进 query —— **大纲里这两条直接打架**。

**解法**：`fetch()` 可以自定义头、可以读 `ReadableStream`，把 `response.body` 用 `TextDecoder` 逐块解出 SSE 帧。**token 走 `Authorization` 头，与其它接口完全一致**，后端仍是 `SseEmitter`。

`utils/sse.js` 里必须处理的四件事：**中断**（`AbortController`；★ 组件 `onBeforeUnmount` 必须 abort）、**上游报错**（约定 `event: error` 帧）、**401 不整页跳登录页**（作者正在写东西，跳走等于丢稿；只在面板里显示「登录已过期，请刷新页面」）、**`[DONE]` 哨兵**（E1 换真实实现时前端不用改）。

`SSE_TIMEOUT_MS = 3 分钟`。**实测**：中断后日志里有 `AI 流被中断` 且**不是 error 堆栈**（用户点停止不该污染错误日志）。

### D-9 自动保存：30 秒 debounce + **异步 `onBeforeRouteLeave` flush**

大纲 §7.3 ⑤：「切换节点前自动保存。不然用户写完一千字点下一个节点，稿子没了。」

**`NodeWorkspace` 是带 `:key` 的，切节点会销毁它** —— 所以正确的位置是 Vue Router 的**异步**离开守卫：

```js
// ★ 守卫可以返回 Promise，router 会等它 resolve 再导航 —— 这才是"切节点前
//   强制 flush"的正确实现。用 onBeforeUnmount 里发请求是【错的】：
//   请求发得出去，但组件已经没了，失败了没人能提示，用户以为存上了。
onBeforeRouteLeave(async () => {
  if (!dirty.value) return true
  try { await save(); return true }
  catch { /* 提示保存失败 + 提供"留在本页"选项 */ return false }
})
```

★ 编辑器内容**不进 Pinia**：它按节点分片、只被当前工作区读写，放进全局 store 等于每次敲键盘都触发全站响应式更新（与 `stores/reader.js` 里「进度不进 Pinia」同一条理由）。**展开/折叠状态才进 store + localStorage**。

### D-10 上传链路的三个安全点

`/uploads/**` 那条白名单**在 P0 就加了**，但**没有资源映射** → 在那之前是**空放行**：放行了，但访问会 404。P4 补齐了 `WebMvcConfig`。

**三个安全点（一个都不能省）**：

1. **文件名绝不采信客户端**。只取扩展名、且用白名单（`jpg/jpeg/png/webp`），文件名自己生成（`UUID`），按日期分目录。**实测**：路径穿越的文件名（`../../pwn-s14.png`）不报错，落盘仍在 `uploads/cover/` 下、没有在 `uploads` 之外生成任何文件 —— 因为后端根本没用这个名字。
2. **校验真实内容，不只看扩展名**。扩展名是客户端给的。至少校验 `Content-Type` + **文件头魔数**（jpg `FF D8 FF`、png `89 50 4E 47`、webp `RIFF....WEBP`）。★ 这一条是要能在面试里讲出来的：**只校验扩展名等于没校验**。**实测**：`.png` 扩展名 + PHP 内容被拒（报文原话「只支持 jpg / jpeg / png / webp 格式的图片（文件头不是 jpg / png / webp 中的任何一种）」）、`.jsp` 被拒、`shell.jsp.png` 被拒、**被拒的三次没有留下任何文件**。
3. **大小上限**。超限抛的是 `MaxUploadSizeExceededException` —— `GlobalExceptionHandler` 接了它 → **HTTP 400**（不是 500），报文「文件太大了，最大允许 10MB，请压缩后重试」。**实测**：11MB → 400。

★ 上传目录是**外部绝对路径**（`C:/Users/Asus/novel-uploads`），**不在 `backend/src/main/resources/static/` 下** —— 放那里会被打进 jar，运行时写入无效。

## 实施记录（对方案的修正）

S0~S13 全部执行。以下是**实施中发现方案本身有问题**、或者方案没预料到的地方。**其中 ①②是负向用例抓出来的两个真 bug。**

### ① ★★★ `move` 可以造出第二个根 —— `create` 的 3008 不变式被拖拽绕过（**真 bug**）

**症状**：`roots` 从 1 变成 2，树上凭空多出一棵顶层树，而「全书大纲」不再包含全部内容 —— 这恰恰是 `OutlineTreeVO` 注释里说的「roots 长度大于 1 表示数据有异常」。

**这是负向用例 17 发现的，不是看出来的。**

**根因**：`OutlineServiceImpl.move()` 在 `targetParentId == null` 时直接把 `parent_id` 写成 NULL。

```java
// create 里有守卫：
if (dto.getParentId() == null && 已有根) throw new BusinessException(OUTLINE_ROOT_EXISTS);  // 3008
// move 里【没有】。而这条规则【数据库拦不住】：
// parent_id IS NULL 的行，MySQL 没有「条件唯一索引」这种东西
// （唯一索引里 NULL 互不相等，UNIQUE(novel_id, parent_id) 对多行 NULL 完全无效）。
// 所以它只能靠代码守 —— 而这里少守了一处。
```

**触发路径是真实的、用户点得到的**：在 `el-tree` 里把节点拖到根节点的**上边/下边**（`dropType = prev` / `next`），`dropNode.parent` 是**包裹用的虚拟根**（`level === 0`），`toIdOrNull(undefined)` 得出 `null`。顺带也盖住了「拖到空白处」（el-tree 在树容器上触发 dragover 时传的 `dropNode` 就是虚拟根）。

**修复**（两层，和深度上限一样是「UI 挡 + 后端兜底」）：

- **后端**加守卫，只拦「本来不是根、却要变成根」这一种：节点本来就是根（根之间排序）放行；数据本来就有两个根不在这里报错（那是 `requireNoCycle` 该撞上 3010 的地盘）。
- **前端** `allowDrop` 返回 false（禁止光标）：落点会是顶层就拒绝。

**实测**：修复后 `code=3008 这本作品已经有根节点了`、`roots` 仍然是 1、被拖的节点还在原来的父节点下。

### ② ★★ 删除作品不清理 `novel_outline` —— 留下永远不会被清理的孤儿节点（**真 bug**）

**症状**：删完一本书，库里还有 **11 行** `novel_id` 指向那本已删作品的大纲节点。

**这是回归脚本跑完清理临时作品时发现的** —— 不在任何一条负向用例的清单里。

**根因**：`novel_outline` 是 P4 加的表，而 `NovelServiceImpl.delete()` 是 P2 写的，**不知道有这张表**。

**为什么这不会「看不见就算了」**：孤儿节点本身确实查不出来（取大纲要过 `requireOwned(novelId)`），但它是**只增不减**的 —— 每删一本书留一批，谁也发现不了。**数据洁癖在这里不是洁癖：它是一条不可能被观测到的泄漏，而修复成本是一行。**

**修复**：在 `NovelServiceImpl.delete()` 里、`novelMapper.deleteById(id)` **之前**加：

```java
outlineNodeMapper.delete(new LambdaQueryWrapper<OutlineNode>().eq(OutlineNode::getNovelId, id));
```

用 MP 的 `delete(wrapper)` 而不是手写 SQL：`@TableLogic` 会自动翻译成 `UPDATE ... SET deleted = 1`，和别处一致。**顺序**：先删大纲、后删作品 —— 反过来的话中途失败会留下「作品没了、大纲还在」的脏数据；而先删大纲再删作品，最坏是「大纲标了删除、作品还在」，那个状态用户看得见，能重试。（整个方法在同一个事务里，两种顺序其实都会一起回滚；但保持一致的习惯比依赖回滚更可靠。）

**实测**：删完作品后 `novel_outline` 里那 11 行**全是 `deleted = 1`** 的逻辑删除，没有活的孤儿。

### ③ ★★★ 一个环**永远不可能被 `buildNode` 走到** —— 环的真实症状是**静默消失**

方案 D-2 写的环保护是「DFS 时检测到环就 `log.error` + 剪断该分支」。**实施后发现这段代码在正常路径上触发不到**，我前后两版负向用例其实都没测到它。**这个发现改变了这一条验收标准的写法。**

**为什么触发不到**：每个节点只有**一个** `parent_id`。环上的每个节点都以环上的另一个节点为父，所以**整个环没有任何一个节点以环外的节点为父** —— 它是一个**没有入口的连通分量**（像 ρ 那种「带尾巴的环」需要某个节点有两个父，这里做不到）。从根出发根本进不去。

**两次踩进同一个坑**（值得记下来，因为两次的症状都**看起来像成功**）：

| 版本 | 造环方式 | 渲染出的节点数 | 我的误判 |
|---|---|---|---|
| 第一版 | `A1.parent_id = A1a` | 少了（看着像剪断成功） | 其实**把 A1 整支从 A 下面摘走了**，`byParent` 里再没有节点的父是 `A`，压根没遍历到 |
| 第二版 | 自环 `A1a.parent_id = A1a` | 4 个（本来 5 个） | 其实 A1a 的父变成了它自己，**它也不再是 A1 的孩子了**，照样走不进去 |

**马脚**：日志里没有那条「检测到环」。**「渲染出的节点少了」和「分支被剪断」在输出上长得一模一样。**

**那环的真实症状是什么？那些节点在树上完全不出现，而且没有任何迹象。** 作者看到「我建的节点没了」，日志一片安静 —— 拿这个去查是查不出来的。这和本项目其它地方的约定不一致（越权要留痕、3010 要 `log.error`）—— **一次静默的数据丢失，比一条错误日志难查得多。**

**修复**：在 `tree()` 里加 `warnUnreachable(novelId, all, roots)` —— 组完树后比对「库里的全部节点」和「树里实际渲染出来的节点」，有差就记一条：

```
[大纲数据异常] N 个节点不可达（父链成环，或父节点已不存在），它们在树上不会出现 | novelId=... nodeIds=[...]
```

**只记日志、不改变返回结果**：作者仍然能打开创作中心、看到其余部分、把坏掉的节点删掉。抛异常的话就变成「整本书打不开了」。

`buildNode` 里那段环检测**保留不删** —— 它是一道便宜的兜底（也顺带守着深度）。但**验收标准改成了它真正能观测到的样子**：

> 用例 3 的期望不是「看到剪断日志」，而是：**① 不 500、不 StackOverflow；② 其余节点照常渲染；③ 日志里有一条 `[大纲数据异常] ... 个节点不可达`。**

**实测**：HTTP 200、无重复节点、渲染出 4 个（本来 5 个，脱开的正好是那一个，其余一个不少）、日志里有那条 error、`totalNodes` 在还原后恢复正常。

★ **真正拦住环的那道闸在 `move` 的 `requireNoCycle`**（用例 4 验证：返回 **3010**「大纲结构异常，请刷新后重试」，不是 3009「你操作错了」）—— 它从 `targetParentId` 沿父链往上走，用 `visited.add()` 的返回值判断，所以环里走不出去也不会死循环。

### ④ ★★ Spring 内容协商会让 SSE 请求的错误响应 **body 变空**

| 请求头 | 400 响应的 body |
|---|---|
| `Accept: text/event-stream` | **`Content-Length: 0`，完全空的** |
| `Accept: text/event-stream, application/json;q=0.9` | `{"code":400,"message":"请告诉 AI 你想写什么"}` |

AI 接口的成功路径只有 SSE 能产出，所以 `Accept` 里必须带 SSE；但**只写 `text/event-stream` 会让错误响应没内容** —— 前端拿到 400 却不知道原因，只能显示「生成失败」。

**`q=0.9` 是关键不是装饰**：它让成功路径仍然选流（实测两种 Accept 下吐出的字节**完全相同**），同时错误路径有 JSON 可用。**不能写等权重。**

**实测**：`Accept: text/event-stream, application/json;q=0.9` 下，token 失效返回 401 且 **body 不是空的**（`{"code":401,"message":"未登录或登录已过期"}`）；空 prompt 返回 400 且 body 里有后端那句话。

### ⑤ ★★ 封面上传把每一张图都写坏了（**真 bug**，症状只有浏览器裂图）

**落盘文件 = 【前 12 字节】+【整个文件】**。70 字节的 PNG 存成 82 字节，PNG 签名在文件里出现两次。

**为什么难发现**：接口返回 200、`Content-Type: image/png`、文件长度非零 —— **每一条能想到的检查都通过**，只有浏览器显示裂图。

**只能靠按字节比对发现**：上传前的 `Buffer` 和取回来的 `Buffer` 做 `equals`。

### ⑥ ★ `GlobalExceptionHandler` 的分层：内部原因**只在日志里**

`Exception.class` 兜底走 `log.error("系统异常 | {} {}", method, uri, e)` 并返回**通用**的 `SYSTEM_ERROR(500)`「服务器开小差了」。也就是说**内部的详细原因不在响应体里** —— 这是**对的**（不漏内部细节），但**断言必须去日志里找**。

**我因此写错了一条断言**：用例 7（传一个不存在的 `beforeNodeId`）我原本在**响应体**里找 `beforeNodeId`，实际拿到的是通用的「服务器开小差了，请稍后再试」。真因是兜底**故意不漏内部细节**。改成：断言响应体里**没有**漏细节 + 断言**日志里**有 `拖拽入参不一致：beforeNodeId=... 不是 targetParentId=... 的子节点`。

★ 用例 7 期望 **HTTP 500** 是**对的**：`beforeNodeId` 不是 `targetParentId` 的子节点，说明前后端约定被打破 = 故障，不是业务分支。

### ⑦ 我自己在测试里写错的四处（**「测试写错」和「代码真的错了」在输出上长得一模一样**）

1. **造环的方式**（见 ③，连错两版）。
2. **断言写死了节点数**：「还原后树恢复正常（8 个节点）」—— 但 C 子树在这一步之前已经被删掉了，实际是 5。改成和**注入环之前抓的 `nodesBefore` 比较**。
3. **目录接口的路径猜错了**：按 REST 直觉写了 `GET /novels/{id}/chapters`，拿到 `undefined`。实际目录是 `NovelDetailVO.chapters`，**跟着详情一起回来的**（P3 的决定：种子书只有几章，为一屏目录多发一个请求不划算）。
4. **`progress` 的单位理解错了**：它是 **0~100 的整数百分比**，不是 0~1 的比例。我传 `0.66`，Jackson 往 `Integer` 字段反序列化浮点会**直接截断成 0** —— 接口返回 200、字段也在，**只有值是错的**。顺便补验了 DTO 里那条刻意的设计：**传 150 被夹到 100、传 -5 被夹到 0，不是 400**（越界不该把整条进度丢掉）。

## 环境与工具踩坑（P4 期间新踩到的）

### 1. ★★ Windows 上强杀 vite 之后，端口会「静默顺延」—— 拓扑悄悄就错了

**现象**：`Stop-Process -Force` 杀掉 vite 之后，`Get-NetTCPConnection -State Listen` 显示端口**空闲**，`curl` 也确认**没有响应**；但重新 `npm run dev`，vite 报 `Port 3000 is in use, trying another one...`，**不报错、直接顺延到 3001**。于是 proxy 跑到 3001、admin 跑到 5176、reader 跑到 5177，**四个端口的映射全错**。

**为什么特别阴**：`:3000` 上**还残留着一个旧的 proxy 进程在正常应答**，所以 `curl localhost:3000/author/` 是 200，**看起来一切正常**。而 `dev.log` 是**输的那一套**写的，日志里说的端口和实际不符。**唯一的发现方式是把「进程 → 端口 → 哪个应用」三者对上。**

**根因**：Node 默认用 `SO_EXCLUSIVEADDRUSE`，被强杀的进程留下的 socket 会在一小段时间内拒绝重新绑定；而 `vite.config.js` 里没有 `strictPort: true`，所以它**默默换端口**而不是失败退出。

**处置**：① 杀进程后**等 6~8 秒**再起；② 起来后**必读 `dev.log` 里的 `Local:` 行**确认四个端口都对；③ 用 `grep -c "in use" dev.log` 应该得到 **0**。

★ 如果给 `vite.config.js` 加 `strictPort: true`，这个类问题会变成**启动即失败**，比静默错位好得多。**记在遗留里。**

### 2. ★★ 流式和上传接口必须**按字节**验收

P4 期间有两个 bug 是「每条常规检查都通过、只有按字节比对才暴露」：

- **SSE**：`data:` 后**没有分隔空格**；含换行的 `data` 被拆成多行 `data:`，**多个 `data:` 行必须 `join('\n')`**；**绝不能把 `\r\n` 归一化成 `\n`**；**绝不能 `.trim()`**。这三条是同一个理由：SSE 的载荷是**逐字节**的，任何「顺手规整一下」都会改变内容。
- **上传**：见实施记录 ⑤（落盘 = 前 12 字节 + 整个文件）。

**结论**：这两类接口的验收标准是 `Buffer.equals`，不是「状态码 200 + 长度非零」。

## 遗留（不影响验收，但面试可能被问）

1. **编辑已发布的章节后，树节点的 `chapterStatusDesc` 不刷新**，直到下次整树加载（已通过 `handleChapterSaved` 部分缓解）。
2. **`GET /outline` 是全量返回**（含 `content`）。★ 观察点：**若实测响应体超过 500KB**，正确的做法不是裁 `content`，而是让前端只在展开时按需拉 `content`（树结构字段留在列表接口里）。
3. **`renumber` 在「一卷三百章」时会发 300 条 UPDATE**。优化方向：只在 `sort` 真的不连续时才重排，或者用一条 `CASE WHEN` 批量更新。
4. **批量操作在前端循环**（决定 10）。部分失败的语义在前端汇总，服务端没有批量接口。
5. **AI 是 mock**。E1 接真实模型时只加 `DeepSeekAiStreamSource`，前端一行不改。
6. **`vite.config.js` 没有 `strictPort: true`**（见环境踩坑 1）。
