## 已拍板的决定（不要重新讨论）

| # | 决定 | 理由 / 落点 |
|---|---|---|
| 1 | **书架接口走 `/api/reader/shelf`，不用大纲写的 `/shelf`** | 同 P5 的 D-7：`/api/reader/**` 是「会落用户数据的写接口」的约定前缀，且**落在 `anyRequest().authenticated()` 里，不用改 `SecurityConfig`** |
| 2 | ~~`POST …/shelf/{novelId}` 做成切换~~ → **改成 `POST` 加入 / `DELETE` 移出** | ★ **S2 推翻了方案**，理由见 D-1 |
| 3 | **`collect_count` / `novel.score` 一律【重算】不【增减】** | 增减会因并发 / 重试失败累积误差，且误差**看起来永远是对的**。重算是 `COUNT(*)` / `AVG(score)`，有 `idx_novel_id` / `idx_target` 撑着 |
| 4 | **两个冗余字段：算在 `interaction`、写在 `content`** | `novel_comment` / `user_shelf` 是 interaction 的表，`novel` 是 content 的。`content → interaction` 只允许走 `CommentTextLookup` 那条缝，**不能为了统计在 content 里手写 join**；而 `interaction → content` 已经存在。于是跨表 SQL 一行都不出现 |
| 5 | **回复单独走 `POST /api/comments/{parentId}/replies`，发表 DTO 里不加 `parentId`** | 父评论已经带 `targetType/targetId`，服务端**继承**就不会出现「路径说书评、字段说章评」的不一致 |
| 6 | **回复只允许两级**：回复的回复直接拒（新码 `4006`） | 三级以上要做「回复 @某人」前缀和递归渲染，产品价值远小于成本。拒绝比静默展平更容易解释 |
| 7 | **`CommentVO.novelId` 拆成 `targetType` + `targetId`** | 原字段的警告就写在 `CommentVO` 上：「不要保留一个叫 `novelId` 却可能装 `chapterId` 的字段」—— 前端拿它去查详情会查到**别人的书**。★ 现在拆是免费的：已核实 reader-web 从未调用过评论接口 |
| 8 | **目录分页新开 `GET /api/novels/{id}/chapters`，`NovelDetailVO` 移除 `chapters`** | ★ **对 P3 决定的反转**，见 D-10 |
| 9 | **`NovelDetailVO` 补 `firstChapterId`** | 「开始阅读」原来靠 `chapters[0]`，分页后第一页不一定拿到 |
| 10 | **上传逻辑抽成公共 service，`AuthorUploadController` 改调它** | 不抽就得把魔数校验 / 白名单**复制一份**到读者侧 —— 那是把 P4 的 D-10 安全逻辑变成两份、迟早只改一份。抽的时候**行为逐字不变** |
| 11 | **`stores/user.js` 是 md5 锁定的，一个字节都不许改** | 所以头像 / 昵称**不能靠 store 缓存**，个人中心页自己持 ref；改完靠 `syncFromStorage()` 让导航栏跟着变 |
| 12 | **阅读历史不做删除** | 大纲没要求；表无 `deleted`，做了只能物理删，且「误删历史」不可恢复 |
| 13 | **`read_history` 的「已读/未读」「最大进度」不碰** | `ReadHistoryMapper` 已写明「读过的最大进度是另一个产品概念，不该复用这一列」 |
| 14 | ★ **个人资料后端放 `modules/system/`，不放 `interaction/`** | **方案写错了**，理由见 D-14 |
| 15 | ★ **章评不带评分（`score` 一律传 `null`）** | **S6 新拍的决定**，理由见 D-5 |
| 16 | ★ **管理端「待审核」这一档额外加 `deleted = 0`** | **S8 修的真 bug**，理由见 D-8 |

## 设计要点与坑

### D-1 ★★ 书架**不是 toggle** —— 推翻方案的决定 2

方案写的是「`POST /api/reader/shelf/{novelId}` 做成【切换】」。S2 实现时改成了**加入 `POST` / 移出 `DELETE` 两条路径**。理由写在 `ReaderShelfController` 的类注释里：

> toggle 既不幂等也不可重试 —— 用户点「加入」，响应超时（服务端其实成功了），客户端重试，第二次把书**移出**了，而两次响应都是 200。

这是一个**只在网络抖动时出现、且两次都是成功响应**的故障，前端没有任何办法识别。拆成两条路径之后两个接口都幂等，重试无害。

前端因此是「调用方知道自己在做什么」的形态：详情页按 `onShelf` 选调哪个，书架页的「移除」永远调 `removeFromShelf`。

### D-2 ★★ 章评的数据模型：`target_id` 到底装什么

`novel_comment` **没有 `novel_id` 列**，只有 `target_type` + `target_id`：

```
书评：     target_type=1, target_id=novel_id
章评：     target_type=2, target_id=chapter_id
二级回复： target_type/target_id 【继承父评论】，只有 parent_id 指向父
```

★ **二级回复必须继承，不能自己填**。若回复时按「它所在的页面」去填 target，章评的回复看起来是对的，**但书评的回复没有 `chapterId` 可填**，那条路径立刻自相矛盾。继承是唯一能同时覆盖两种父评论的规则。

★★ **按 novel 筛章评是个陷阱**：管理端「按作品筛评论」原来写的是 `target_id = #{novelId} AND target_type = 1`。加了章评之后，`target_id` 对章评来说是 **chapterId** —— **同一个数字在两种 target_type 下是两本不同的书 / 章**。所以「按作品筛」必须拆成：

```sql
(target_type = 1 AND target_id = #{novelId})
OR (target_type = 2 AND target_id IN (SELECT id FROM chapter WHERE novel_id = #{novelId}))
```

**这是本模块最容易写错、且错了不报错的一处** —— 筛出来的结果「有东西」，只是少了一半。

### D-3 ★★ 回复树怎么查才不 N+1

一页 10 条一级评论，每条要挂子回复。**绝不能循环里查**（10 次往返）。做法照抄本类里昵称的既有范式：

```
① 查一级评论分页（parent_id IS NULL）
② 拿这一页的 id 集合，一条 SQL 查全部子回复（parent_id IN (…)）
③ 按 parentId 分组贴回各自的父
④ 昵称一次 IN 批量查 —— ★ 一级和二级的 userId 【合并成一个集合】再查一次，别查两轮
```

**产品细节（必须定死，否则前端没法写）**：

- 子回复**不分页**，但每条一级评论**最多内联 3 条**，另给 `replyCount`（总数）。
- 「还有 N 条回复」**展开要重新请求**（走 `GET …/comments/{id}/replies`），不能在已经分页的接口上假装全都有。
- 内联的是**最早 3 条（正序）** —— 展开是「追加」，顺序反了会变成「点一下多出来几条更早的」。

★ 方案里**漏了展开接口**，S4 才发现：只有写入接口和「最多 3 条内联」，第 4 条回复就永远看不到。

### D-4 ★★ 二级回复的删除与审核：父子状态不联动

- 删一条**一级评论** → 它的子回复**级联逻辑删**（同一事务），否则子回复变成孤儿：页面上永远不显示、却占着库、`replyCount` 还对不上。
- 但**状态不联动**：一级被驳回（`status=2`）时子回复**保持原状**。管理员的驳回是针对那条内容的，不是针对整条线索；读者端查询会因为父不可见而整条线索不显示，效果上已经够了。
- ★ **读者端查子回复的 WHERE 里必须带自己的 `status = 1` 和 `deleted = 0`**，不能只靠父可见 —— 否则父通过、子被驳回时，子会漏出来。

### D-5 ★★ 取消点赞：Redis Set 与 MySQL `like_count` 是两套状态

点赞态在 **Redis Set**，总数在 **MySQL `like_count` 列**。取消点赞让这两套状态**第一次出现分叉的可能**。

**写死的策略：**

- **Redis Set 是权威**（谁是点赞人），`like_count` 是**派生展示值**，由 Set 基数重算写回。
- 「取消一个本来就没赞的」→ **幂等成功**（用户意图是「让它变成未赞」，已经是了）。
- **Redis 丢了 Set 怎么办**：`like_count` 会大于 Set 基数，此时**以 Set 为准重算，数字会变小**。这可以接受 —— `like_count` 是展示字段，「少几个赞」远比「赞数为负」或 500 好。**不要**试图从 MySQL 恢复 Set（没有 `comment_like` 表，恢复不出来）。
- ★ **`like_count` 永不允许为负**：重算值先 `Math.max(0, n)` 再写库。
- ★ **取消点赞不用判「是不是自己的」**：Set 成员是 userId，取消时只能删掉自己的那个，天然安全。

**已赞态怎么批量返回**（`CommentVO.liked`）：一页 10 条 → 一次 `SISMEMBER` ×10 是 10 次往返。用 **`executePipelined`**（10 条一次 RTT）。★ 两个实测确认的细节：
- Lettuce 的 `setCommands().sIsMember()` 回的就是 `Boolean`，`executePipelined` 确实拿得到；
- **callback 必须 `return null`** —— 返回非 null 会被当成一次写而抛错。

★ **匿名请求书评列表时 `liked` 留 `null`**（`non_null` 让 key 消失），前端写 `row.liked ?? false`。**不要返回 `false`** —— 那是在说「这个人没赞过」，而我们根本不知道他是谁（同 `deleted` 用 `Boolean` 的理由）。

★ **同一套理由产生了 `mine`**（S9 开工时发现的真空缺）：删自己的评论要带确认框，但读者端**没有任何办法知道哪条是自己写的** —— `userId` 是刻意不给的，`nickname` 又会重名（两个人都叫「书友」是常态）。不给的话前端只能「先显示、点了再说」，代价是**每条别人的评论上挂一个必然失败的按钮**。
★ `mine` 是**相对于看这一页的人**，绝不是评论人自己 —— 传反了不报错，只是删除按钮长在别人的评论上、在自己的评论上消失。已写进 javadoc。

### D-6 ★★ 章评不带评分（决定 15）

`CommentCreateDTO#score` 自己写着「仅书评有」，而 `createChapterComment` 之前传的是 `dto.getScore()` —— **声明和实现不一致**。交上来的分会被存库、显示在章评行上，却永远进不了 `novel.score`（算子里有 `target_type = 1`）→ **一个不报错的静默落差**。S6 改成传 `null`（同 reply）。

前端跟着做的：管理端章评那行**不显示「未评分」** —— 章评没有评分这个概念，显示「未评分」等于在说读者没打。

### D-7 ★★ `collect_count` / `novel.score` 的维护时机

| 字段 | 什么时候重算 |
|---|---|
| `collect_count` | 加入书架、移出书架（两个接口各一次） |
| `novel.score` | ① 书评**审核通过** ② 被驳回 / 隐藏 ③ 被删（逻辑删） ④ **`score` 为 null 的不计入** |

★ **算子里必须带 `deleted = 0` 和 `score IS NOT NULL`**。手写 `@Select`/`@Update` 时 `@TableLogic` **完全不生效** —— 漏了 `deleted = 0` 会把已删书评的分数算进去，而**分数看起来永远合理**（除非有人删过评论）。

★ **`ROUND(AVG(score), 1)`** —— 列是 `DECIMAL(3,1)`。实测 `ROUND(AVG(5,4,4,2),1) = 3.8`（**HALF_UP，不是截断**），`AVG(4,4,2)=3.3333 → 3.3`。
★ **没有评分时** `AVG` 返回 `null`，不能写进 `NOT NULL DEFAULT 0.0` 的列 → `IFNULL(…, 0)`。

★ **详情页要区分「0 分」和「没人评分」**：`score = 0.0` 有两种含义。前端按 `scoreValue > 0` 才显示星星，否则「暂无评分」；**后端不额外加字段**（`novel.score` 的语义就是「0 = 还没人评」）。

### D-8 ★★ 待审队列里堆着「已被作者撤回」的评论（S8 修的真 bug）

**症状**（先是在开发库上看到的）：`?status=0` 出来 8 条，其中 6 条是**灰色的「已删除」行**，审核按钮全是禁用的 —— 一屏里 75% 是点不动的行。

**成因不是测试数据脏，是一条正常路径**：评论人发完评论、在管理员审之前自己把它删了 → 行还在，`status` 原封不动是 0，`deleted` 变 1。这些行于是**永远待在待审队列里、且永远处理不了**（审核走 `selectById`，对它们返回 `4001` 所以按钮禁用）。

**修法**：`selectAdminPage` 里「待审核」这一档**额外加 `deleted = 0`**。判据是**语义**的：

> 待审核是**队列**（等着我处置），不是**检索视图**；作者已经撤回的评论不等着任何人。

P5 那条「要能看到已删除的评论」（有人投诉一条评论、管理员却找不到，因为评论人自己先删了）服务的是**检索** —— 那一档是「全部状态」，**行为一字未改**（`?novelId=` 不带 status 时照样返回已删除行，本步已断言）。

★ **不做**「加一个『含已删除』开关、默认关」：那会连**不带筛选**的默认视图一起改掉，动到 P5 已验收的契约。窄修只影响 P6 新引入的那一档。
★ 反过来说，**这里不能靠「顺手补 `deleted = 0`」**：mapper 顶上那段 javadoc 明确写着「这是全项目唯一一处刻意不写 `deleted = 0` 的手写查询」。改完在那段下面补了一句「唯一的例外是待审核分支」，免得下一个人以为自相矛盾。

### D-14 ★★ 个人资料后端放 `modules/system/`，不是方案写的 `interaction/`

`grep -rn "reader/profile" backend/` → **零命中**，方案把它记在了 `modules/interaction/` 下。实际落在 **`modules/system/`**，理由：

1. 三个接口只碰 `sys_user` **一张表**，那是认证服务的表（`AuthServiceImpl` 就在这查它）。放进 interaction 会开一个「**交互服务直接读写认证服务的表**」的口子，而这条接缝除了这一个页面没有任何别的消费者 —— M 期拆服务时要多定义一条。
2. **先例**：`ReaderAuthorApplyController` / `ReaderNoticeController` 同样在 `system`、同样挂 `/api/reader/`。**`/api/reader/` 说的是「使用者是读者」，不是「代码属于哪个模块」。**
3. 白拿一个好处：`/api/reader/**` 落在 `anyRequest().authenticated()` 里，**不用改 `SecurityConfig`**。

★ **另开 `ProfileVO` 而不给 `UserVO` 加 `email`**：`UserVO` 会被三端的 `stores/user.js` **整个塞进 `localStorage[novel_user]`**，是登录/注册/`me` 三条路径共用的形状、三个应用共享的事实标准。加一个三端没有一处读的 `email`，只会让「登录响应里为什么有 email」变成没人能回答的问题。同 D-11 那条。

★ **`ProfileVO` 刻意不提供 `from(LoginUser)` 重载** —— 数据源只能是数据库。Redis 那份登录态是登录那一刻的快照，用它回显会出现「改完变回去、刷新又对」。`LoginUser#avatar` 那段注释（S1 写的）已经把这个决定记下了，**P6 不做 `TokenStore.updateProfile`**。

★★★ **前端最关键的一条：改完必须【合并】写回 `localStorage`**

`ProfileVO` 里**没有 `roles` / `role` / `permissions`**，而 `localStorage[novel_user]` 里存的是完整 `UserVO`，`role` 是**三个应用共用**的路由守卫判据。直接 `auth.setUser(res)` 会把角色从这份共享数据里抹掉 —— 症状是「**在阅读端改了个昵称，跳去创作中心被弹回登录页**」，刷新一下又好了。

所以只能 `setUser({ ...(getUser() || {}), nickname, avatar })`。

同步路径（**锁定文件一行没动**）：`auth.setUser(...)` 写 localStorage → `userStore.syncFromStorage()` 让 store 重读 → 导航栏右上角立刻变。这正是 `syncFromStorage` 存在的意义（`setLoginInfo` 要 token，这里没有）。

★ **头像放导航栏不是装饰** —— 它是「换头像立刻生效」最直接的证据：个人中心里传完图，不刷新不跳转，那一小块立刻跟着变。老账号的 `localStorage` 里没有 `avatar` 这个 key（是 `undefined` 不是 `null`），所以写 `userInfo?.avatar || ''`，**不写 `=== null`**。

★ **页面路径是 `/profile` 不是方案里写的 `/user/profile`**：和 `/shelf`、`/history` 同一层级。多包一层 `/user/` 是在暗示将来会有 `/user/:id`「看别人的主页」，而本项目**刻意不做**。

**② 谁写**

## 实施记录（对方案的修正）

### ① ★★ 方案里「已核实 admin-web 不读 `chapters`」是错的（S7）

见 D-10。**教训写成通用的一条**：方案里凡是写「已核实 X 没有消费者」的，落地前都要自己再 grep 一次 —— 这次漏掉的三处躺在 `components/` 而不是 `views/` 下面。

### ② ★★ S4 把 content 和 interaction 绕成了一个 Bean 环（真·启动失败）

**症状**：`mvn package` 成功，jar 起不来：

```
The dependencies of some of the beans in the application context form a cycle:
AuditLogServiceImpl → CommentTextLookupImpl → NovelServiceImpl → AuditLogService → …
```

**怎么来的**：S4 要给章评的审核流水补「《书名》第N章」，于是让 interaction 侧的 `CommentTextLookupImpl` 注入了 content 的 `NovelService` / `ChapterService` 去拼位置串；而 `NovelServiceImpl` 审作品时要记流水，注入了 `AuditLogService`。**环的两条边各自都是对的**，删哪条都不行。

**根因不是「循环依赖」，是位置拼接站错了边**：它是审核日志页的版式，而 `AuditLogServiceImpl` 本来就同时持有 `NovelMapper` / `ChapterMapper`，另外三种 `targetType` 的标题也都在那儿拼。

**改法**：缝的返回值从「拼好的标题串」降级成**素材**（`CommentBrief(text, novelId, chapterId)`），位置串由 `AuditLogServiceImpl` 自己拼。
- interaction 不再依赖 content 的任何 Service，环消失；
- 缝变「哑」了，也更像一条真的服务边界（见 D-15 ⑧）；
- ★ **没有**用 `spring.main.allow-circular-references: true`，也没用 `@Lazy` —— 那是把这个环和以后所有的环一起**静默放行**。

**顺带的行为变化**：位置不再要求「作品已上架 / 章节已发布」，只要求对象没被逻辑删。理由写进了 `AuditLogServiceImpl#commentTitle`：审核日志是管理端页面，「这本书已经下架了」正是查流水时该看到的信息。

### ③ ★★ MP 的 `maxLimit` 在【空页】上不生效（P2 起就存在）

`MybatisPlusConfig` 里的 `PaginationInnerInterceptor.setMaxLimit(100)` 是在 `beforeQuery` 里夹的，而 `willDoQuery` 在「count 查出来是 0」时直接返回 false，MP 于是**跳过整条查询** —— `beforeQuery` 根本没跑，`page.getSize()` 保持原值。

现象：`?size=100000`
- 列表**非空** → 响应里 `size: 100`（夹住了）
- 列表**为空** → 响应里 `size: 100000`（没夹）

**影响**：**没有数据泄露**（`records` 本来就是空的；非空时一定夹得住）。只有「把 `size` 原样回显到分页组件」的前端会显示一个荒唐的每页条数。**全项目所有分页接口都是这个行为**，P6 不修 —— 修它要动一个 P2 起就被回归过的公共组件，收益只是「空页时回显好看一点」。

★ **验证脚本不要断言「空列表时 `size` 被夹到 100」，会假红。** 要断言就断言 **`records.length <= 100`**，那才是真正重要的那条。
★ 另一半（S7 补的）：**非空页的 `size` 是可信的** —— `?size=100000 → 100`，`?size=-1 → 10`（兜底成默认页大小），且 `records` 也只有 10 条。

### ④ ★ 验收脚本别只看 HTTP 状态（我自己的错，S2 第一轮）

`POST /api/reader/history` 因为作品还是草稿而失败时返回的是 **HTTP 200 + code 2001**（铁律 3），而脚本只断言了 `http == "200"` → **假绿**。一条「作品已上架」的前置校验因此被漏掉，后面 10 条断言跟着全红。

★ 每一条写接口的断言都要带 `body["code"] == 200`。

### ⑤ ★★ `reply` 的检查顺序：待审核的父评论返回 `4001`，不是 `4006`

顺序是 **频控 → 父评论可见性 → 是不是二级**。所以拿一条**还没过审的回复**去回复它，撞上的是 `4001`（父不可见），走不到 `4006`。

这是刻意的（同 `4001` 那四种情况合并的理由：区分开就是一份「管理员审到哪了」的探针），但★ **写验收脚本时必须先把父评论审过**再测「只允许两级」，否则测的不是那条规则。

### ⑥ ★★ 重算 vs 增减：这次是**实测**出来的，不是推断

S5 的对照实验：A、B 都赞（`like_count = 2`）→ 从 Redis 侧 `DEL novel:like:user:{id}`（Set 没了、列还是 2）→ A 再赞 → **返回 1**。
**如果当初写的是 `+1`，这里会是 3。** 这条断言把一个「两种写法在正常情况下表现完全一样」的选择变成了可验证的。

★ 同类手法（S6）：**当一个 WHERE 的某一项「漏了也不报错、只是数字悄悄变」时，唯一能验它的办法是造一条只被那一项挡住的行。**
`novel.score` 的算子里有 `target_type = 1`，为了验它，直接 `INSERT` 一条 `target_type=2, target_id=N1, score=1` 的评论 —— 如果算子漏了 `target_type`，它就正好撞上 `target_id = #{novelId}`。结果 `3.8`（而不是 `(5+4+4+2+1)/5 = 3.2`），证明那道闸真的在。清理按字面 id 物理删。

★ **恒真的断言比没有断言更坏**：S5 第一版把 D-7 的对照组写成了 `check(..., True, "对照")`，它会把失败数掩盖掉。已改成真的查库（同一条路径少写 `/like` → `deleted = 1`；走 `/like` → 那条评论 `deleted = 0`、仍在列表里）。

★ **`post_comment` 返回 `None` 时要立刻断言**，否则后面一整段断言会因为「对着 `None` 做检查」而以**错误的原因**通过或失败。

### ⑦ ★★ 种子作品对读者端**完全不可见**

种子作品 1、2 都是 `deleted = 1` + `status = 0` 的草稿，所以 `GET /api/novels/1` 返回 `2001 作品不存在` —— **读者端根本没有可见的种子作品**。任何「拿种子作品走读者接口」的断言都是假的（S6 第一版就写了一条，它以 `api=None` 失败）。

→ **新增了开发样例数据**：`.tmp-p6/mkdev.py` 造一本书 + **25 章**（全部已发布），故意超过 20 条，好让详情页的分页条真的出现；`.tmp-p6/mkdev2.py` 再给它塞 4 条评论 + 1 条回复，覆盖「书评已通过带评分 / 书评待审 / 章评已通过 / 章评待审」。**id 全在 `.tmp-p6/cleanup.txt` 里，S17 已删。**
★ 重跑 `mkdev.py` 会再造一本（不会覆盖旧的）—— 只在没有样例时跑。

### ⑧ ★★ 「删作品 / 删章节」是**逻辑删**，清理断言不能写「这一行不存在」

`@TableLogic` 之后行还在。S7 第一版把清理断言写成了「这一行不存在」，48/49 —— **失败的是断言自己，不是被测的东西**。正确写法是 **`WHERE id IN (…) AND deleted = 0` 一条都不剩**。

★ 新手法（S6）：**开头给种子的相关列拍快照**（`SELECT id, score, collect_count, status, deleted`），结尾逐字节比对。**比「数行行数」强得多 —— 行数不变但值被改了是查不出来的。**

### ⑩ ★ 管理端「默认筛待审核」这条 P5 建议**是对的，但不够**

`docs/P5-管理后台.md:550` 的遗留项原文：

P5 给的办法是**只改前端默认筛选**。S8 照做了 —— 然后发现**不够**：那些「已删除」的行 `status` **就是 0**，所以默认筛「待审核」之后它们**一条不少地还在队列里**，只是换了个入口进来。**必须后端一起改**（D-8）。

★ 顺带订正：P5 文档 `:73` 那句「**含已删除的**（否则没法审已经删掉的）」里，「否则没法审已经删掉的」**本来就说不通** —— 审核走 `selectById`，对已删除的行返回 `4001`，**根本审不了**，页面上那个按钮一直是禁用的。真正成立的理由是**查证**（有人投诉一条评论，管理员得找得到它），不是「审」。P6 已在那两处加了指针。

### ⑪ ★ 历史页的续读目标有个**真实的不对称**（S11 记录）

| | 书架项 | 历史项 |
|---|---|---|
| 有 `lastChapterId`（最新章节） | ✅ | ❌ |

所以章节被撤回时：书架的三个字段（`readChapterId`/`No`/`Title`）一起消失，可以退到 `lastChapterId`；而**历史项没有这个退路** —— 它只有「我读到的那一章」。退到最新章就是**剧透**，所以历史页的第三种情况是给「查看目录」跳详情页，由用户自己挑。**那是唯一不撒谎的选项。**

### ⑫ ★ S11/S12 的几处「有意的不一致」

- **详情页不显示收藏数**：`NovelVO` 上没有 `collectCount`（它只在 `NovelBriefVO` / `ShelfStatusVO` 上）。要显示就得从 `/reader/shelf/{id}` 拿，而那个接口**需要登录** → 同一页，登录的人看到「87 收藏」，游客看不到。**同一页按登录态显示不同的事实，比不显示更糟。**
- **不复用 `NovelCard.vue`**：书架卡片长得像作品卡片，但 `ShelfItemVO` 没有 `id`（主键叫 `novelId`）、没有 `isFinish` / `wordCount` / `viewCount`，而 `NovelCard` **无条件渲染**后三个。复用的话每张书架卡都显示「连载 · 0 章 · 0 字 · 0 阅读」—— ★ **不是缺字段，是显示了一个错的数字**，而且看起来很正常。
- **确认框：书架页弹，详情页不弹**：两者误点成本不同。书架页「移除」点错那一行就消失、且未必记得删了哪本 → 弹；详情页「已在书架」按钮本身写着状态，点错**再点一次就回来** → 不弹。**给一个一眼能看懂、一下能撤销的按钮加确认框，只会让「取消收藏」变得很烦。**
- **退出登录要把 `onShelf` 清掉**：阅读端的退出**不跳转**（首页是公开页），用户完全可能在详情页上点「退出」—— 这时按钮还写着「已在书架」，而它已经不属于任何人了，再点走未登录分支提示「登录后可以加入书架」，**看着像 bug**。加了一个 watch 把状态清成 false。
- **导航里「书架 / 历史」未登录也显示**，不做 `v-if` —— 藏起来的话游客不知道有这回事。**个人中心头像则相反**：未登录不显示，因为给他一个点进去必跳登录的链接没有意义。（书架/历史对游客是「值得先登录再回来的地方」，个人中心不是。）

### ⑬ ★ 未登录引导是本仓的空白处，P6 定了一套

全仓没有任何页面级引导样板。`components/LoginPrompt.vue` **三处共用**（书评区 / 章评区 / 书架空态），定了四条规矩：**不藏入口、说收益不说要求、不自动跳转、登录后回原地**。

★ 路由 `meta.requiresAuth` 在 S11 落地时是**惰性的**（守卫还没写），未登录敲 URL 靠「接口 401 → `request.js` 统一处理 → 回登录页」兜着，能用但**丢了 `redirect`**。S14 补上守卫后 `meta` 才真正生效。

## 环境与工具踩坑（P6 期间新踩到的）

### 1. ★★ 移动端布局视口会横向拓宽 —— 「量位置」必须在溢出修好之后

见 S15 的坑 2。这条的普适意义：**任何「元素位置对不对」的自动化断言，都要先确认页面没有横向溢出**，否则量到的是「内容坐标系」里的位置，和用户看到的不一样。

### 2. ★★ `overflow-x: hidden` 在 `body` 上会静默废掉 `window.scrollTo()`

见 S15 的坑 1。这条的症状极其隐蔽：**页面能滚**（用户用滚轮照样滚），但**代码里的 `scrollTo` / `scrollY` 全部失效** —— 于是「阅读器恢复到上次位置」这类功能**看起来只是偶尔不准**。

### 3. ★★ `Page.captureScreenshot` 的 `clip` 是文档坐标

`clip: {y: 0}` 永远截页面顶部，不是当前视口顶部。要截视口得自己加 `window.scrollY`。

### 4. ★ 无头 Chrome 是**机器上本来就有的**，不用装 Playwright

`--headless=new --remote-debugging-port=9222` + Node 24 的全局 `WebSocket` + `Target.createTarget` / `attachToTarget{flatten:true}` / `Runtime.evaluate` / `Emulation.setDeviceMetricsOverride` / `Input.dispatchKeyEvent` / `Input.dispatchMouseEvent`。**仓里没有 playwright / puppeteer / jsdom**，将来要验 UI 就直接照这套来。

### 5. ★ 机器上没有 `redis-cli`

S5 的脚本里手写了 **60 行 RESP over socket**（`AUTH` → `SELECT 0` → 命令）。**以后要动 Redis 就用这个 `redis_cmd()`，别再去找客户端。**

### 6. ★ `grep -v` 的退出码会掩盖 `mysql` 的成功

`mysql … 2>&1 | grep -v "Using a password"` 里，`grep` 把唯一一行滤掉之后返回 **1**，于是 `&&` 链断掉 —— 看起来像 `mysql` 失败了。改用 `2>/dev/null` 并直接看 `$?`。

### 7. ★ `ls -1` 不显示点文件

一度据此得出「`docs/docker/.env.example` 不存在」的错误结论。它在。**不加 `-a` 会跳过点文件。**

★ README 里那段注册 curl **行内不能写中文** —— Windows 命令行的活动代码页是 ANSI(GBK)，中文会被按 GBK 编码而 JSON 要 UTF-8，服务端解不出来就报 **400**，看起来像「接口写错了」。所以必须**先写进文件再 `--data-binary @file`**。

### 9. ★ `docs/部署.md` 的 `alias` + `try_files` 是个坑，改成 `root`

写 Nginx 配置时第一版用了 `alias /var/www/novel/reader/;` + `try_files`。**`alias` 会把 location 前缀整个替换掉，`try_files` 拼路径时的基准跟着变** —— 轻则 SPA 回落失效、重则 rewrite 循环 500。改成 server 级 `root /var/www/novel;` 之后，`location /reader/` + 请求 `/reader/assets/a.js` 拼出来正好是 `/var/www/novel/reader/assets/a.js`，**和产物目录结构天然对上**，不需要 alias。

### 10. ★ 生产只有**一个**必需的环境变量

`grep -rn '\${[A-Z]' backend/src/main/resources/*.yml` 只返回两处：`application-dev.yml`（带 dev 默认值）和 `application.yml:74` 的 **`secret: ${JWT_SECRET}`（故意没有默认值）**。
★ **故意不给默认值**：生产忘了配就**直接启动失败**；给了默认值则会**静默用那个写在 git 里的值启动** —— 等于全世界都知道签名密钥，任何人都能自己签发一个「我是 admin」的 token。这种事故不报错，只会安安静静地被攻破。

★ 另外**确认了 E1 之前没有 AES 密钥相关的环境变量**：`modules/ai/` 下只有 `AiAsyncConfig` / `AiController` / `AiRequestDTO` / `AiScene` / `AiStreamSource` / `MockAiStreamSource` / `AiQuotaVO`，**没有 `AiConfig` 实体** —— `ai_config` 表建好了但读写它的接口属于第三期。

### 11. ★★ 清 Redis 登录态：`novel:auth:token:` 后面有**两段**，别用 `rsplit` 取 userId

S17 收尾顺手清「已删用户的孤儿登录态」。键的构造是 **`novel:auth:token:{userId}:{jti}`**（`RedisKeyConstant.AUTH_TOKEN` 的 javadoc 里写得很清楚，**我没先看就动手了**）。
我用 `key.rsplit(":", 1)[-1]` 当 userId 去比对 `sys_user` —— 取到的其实是 **jti**，于是**每一条都被判成孤儿**，
一轮 `DEL` 把 **179 条登录态全删了**。正确取法是 `key.split(":")[3]`。

**后果**：不丢数据，但**所有已登录的浏览器会话当场失效**（下一次请求 401 → 前端跳登录页）。
★ 这类「清理脚本自己写错判据」的破坏**比删数据更隐蔽** —— 它删的全是「本来就该过期」的东西，
报错为零、日志干净，只是所有人突然要重新登录一次。**判据先对着常量类核一遍，再动手。**

（同一次收尾里还发现：`s17_clean.sql` 用范围谓词捞出的东西**比手工台账多 5+1 行** —— 见「数据清理」那一节。同一个道理。）
