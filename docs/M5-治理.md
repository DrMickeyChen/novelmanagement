# M5 · 治理 —— 熔断降级 + 链路追踪 + 跨服务聚合并行

> **一句话**：把 M1 欠下的那笔「可用性耦合」还掉，办法**不是**允许返回错数据，
> 而是把「降级」收紧成一条可判定的规则 —— **「消费方能不能诚实地把这个缺失渲染出来」**。
> 顺带发现：真正串行的聚合不在读者端而在**管理端审核日志**，
> 以及 M4 记的 `FeignIdentityConfig` 份数**多算了一份已经删掉的**。

---

## 一、验收标准（大纲原文）

`项目大纲.md:1304`：

```
| **M5 治理**（2~3 天） | Feign 超时 + Sentinel 熔断降级 + 链路追踪；跨服务聚合改并行调用 |
                        | 停掉一个服务，页面显示降级数据而不是白屏 |
```

### ★★ 开工前先订正大纲的三处

和 M3「实质只有 MQ」、M4「实质是换检索内核」是同一类订正。

#### 订正 1：M5 的实质**不是「加超时」**，超时 M2 就做完了

`spring.cloud.openfeign.client.config.default`（connect 2000 / read 5000）**已经在三个服务里存在**
（content / interaction / search）。**auth 里已经没有 Feign 了** ——
M3 把依赖、配置、`@EnableFeignClients` 整段删掉，`application-dev.yml` 留的是一段
「这里以前有什么、为什么删、怎么复核」的注释。

→ **「五个服务都要配 Feign」这句话是错的，要配的是三个。**
→ **M5 的实质是「熔断 + 降级 + 追踪 + 并行」，超时只是复核一遍取值。**

★ 复核时顺手订正了一条事实错误：`content/application-dev.yml` 原写「Feign 默认【没有读超时】」——
按 OpenFeign 源码 `feign.Request.Options()`，默认是 **connect 10s / read 60s**（不是无限）。
**说法不准，结论方向没错**（60 秒足够把 Tomcat 线程占满）。**M5 订正数字、保留论点。**

#### 订正 2：验收标准里的「白屏」**从来不是真实症状**

实测（三端 + `usePagedList`）：停掉 `:8084` 后搜索页显示的是
**「没有找到与「x」有关的作品，换个书名或作者名试试」**——
一句**语气笃定、还给了下一步建议的谎话**。
失败和「真的没有数据」在 `usePagedList.js` 的 `catch` 里走进**同一个分支**（`list=[]` + `loaded=true`）。

→ **验收口径改成：用户能分清「没有数据」和「暂时拿不到」。**

#### 订正 3：「跨服务聚合改并行」的对象**不是详情页，是管理端审核日志**

前端详情页本来就是并发发多个请求的（`Promise.all`）。
真正的**串行**聚合在 `AuditLogServiceImpl`：审核日志页有**三次串行**的跨服务批量调用
（取评论素材 / 取申请摘要 / 取操作人昵称），其中 `authorApplyTitlesOf` 内部**自己就是两跳串行**。

## 二、★★★ 判断 1：降级判据 —— 而 S5 的实测又把它收紧了一格

### 2.1 M1 的「失败时不降级」**没有被推翻**，它兑现了 M1 排的还款日

M1 在 `ContentUserLookup` 写下了不降级的理由，并**点名 M5**：

> 降级的症状是「首页上所有书的作者名变成空白」，它**看起来像数据坏了**……
> **宁可 500，也不要一个看起来正常但内容是错的页面。**

★★★ **这条理由在 M5 之后仍然成立。** 所以 M5 不是「现在允许返回错数据了」，
而是把「降级」收紧成一条**可判定**的规则。

### 2.2 第一版判据（方案里的），以及它**不够**

> 降级只对「缺失在界面上**可见**」的字段成立；对「参与筛选的输入」一律不降级。

| 方法 | 失败时给什么 | 用户看到 | 判 |
|---|---|---|---|
| `ContentUserLookup.nicknamesOf` | 空 Map → `authorName` 为 null | 每张卡片作者名 `—`（★ 全局 `non_null`：**key 从 JSON 里消失**） | ✅ |
| `ContentUserLookup.nicknameOf` | `null` | 详情页作者名 `—` | ✅ |
| `ContentUserLookup.authorApplyTitlesOf` | 空 Map | 审核日志显示「作者申请 #5」 | ⛔ **见 2.3，这条后来被推翻** |
| `CommentTextLookup.commentBriefs` | 空 Map | 审核日志显示「评论 #5」 | ⛔ **见 2.3，这条后来被推翻** |
| ★★ **`ContentUserLookup.userIdsByNickname`** | 空 List | **「没有找到相关作品」** —— 和「真的没有这个作者」一模一样 | ❌ **不降级，仍抛** |

★★★ **最后一行是这条判断的价值所在。** `userIdsByNickname` 返回的是
**喂给 `in(authorId)` 的筛选输入**（LIKE 降级路径）。它一旦降级成空集合，结果集就是 **0 条**，
而界面上写的是「没有找到相关作品」—— **那正是 M1 说的「看起来正常但内容是错的页面」**。

**★ 现成的机制，不新造**：`ShelfStatusVO.onShelf` 的注释早就写明了原理 ——
「一律是 `Boolean` 而不是 `boolean`……布尔字段一不小心漏填，表现正好是**「看起来很正常」**。」

→ **M5 的降级 = 让字段从 JSON 里消失**（靠既有的 `non_null` + 包装类型），
**不是**填 `0` / `false` / `""` 这些「看起来正常」的假值。
★ 推论：**降级前必须先检查字段是不是基础类型** —— `int` 表达不了「未知」，降级它只会把 `0` 送出去。

★ 于是 **M5 必须动前端**（大纲把它写成了纯后端任务）。
后端只能让「缺失」在 JSON 里**可表达**；让它**可见**是渲染的事。

### 2.3 ★★★ 判据收紧：从「缺失看不看得见」到「消费方能不能诚实地渲染它」

**上面那张表里有两行是错的**，而推翻它们靠的是**停掉 interaction 实测一次**。

方案把 `CommentTextLookup.commentBriefs` 判成「有编号、没正文，一眼可辨」→ ✅ 可降级。
S5 照此改成 `logThenDegrade(空 Map)`，实测结果是：

```
停掉 interaction  →  这个接口【HTTP 200】
                  →  审核日志那一行渲染成「评论 #94（已删除）」
```

★ 「（已删除）」是复刻 `admin-web/views/log/index.vue` 的 `targetLabel()`：
`targetTitle` 为空就拼「（已删除）」。

★★★ **而那条评论根本没有被删。降级把「拿不到」说成了一条关于数据的具体假话**，
还是在**审核日志这种用来追责的页面**上。

> ### ★★ 修正后的判据
>
> 判据**不是**「缺失看不看得见」，而是**更靠前的一步**：
> **【消费方能不能诚实地把这个缺失渲染出来】。**
>
> 评论正文那一格只有**两个渲染分支** ——「有标题」或「已删除」，
> **没有第三个状态能容纳「暂时拿不到」**，所以这里**没有安全的降级值**。

★ 同一陷阱有**第二个入口**：`AuthUserClientFallbackFactory` 的 `briefsOf`（作者申请摘要），
它喂的是**同一列 `targetTitle`**、落进**同一个 `targetLabel()`**，只是 `targetType` 是 4。
**两条一起判、一起改** —— 只改一条会留下一个不对称的洞。

★★ 这不是新判断：`CommentTextLookupImpl` 的类注释（M1 写的）和
`CommentTextLookup#briefsOf` 的注释（P6 写的）都写了这个症状，结论都是「宁可 500」。
**方案表把这条标成「可降级」是错的。**

### 2.4 实测：降级长什么样

**停 auth**（`:8081`），`/api/novels` 前后两份 JSON 逐 key 对拍：

| | auth UP | auth DOWN |
|---|---|---|
| `total` | 12 | **12**（★ **书一本不少** —— 页面不是空的） |
| `records[i]` 的 key 集合 | 含 `authorName` | ★ **少了 `authorName` 一个 key**，其余全等 |

→ **降级 = 一个 key 从 JSON 里消失**，不是空串、不是「佚名」。

## 三、判断 2：前端 —— 「失败」和「空」必须是两个状态

`usePagedList.js`（三端各一份，**不在 12 个锁定文件里**）原来的 `catch`：

```js
} catch (e) {
  error.value = e
  list.value = []        // ← 失败被写成了「空」
  total.value = 0
  loaded.value = true
}
```

★★ **`error` 这个 ref 的注释是「页面可以据此显示重试按钮」，而它在三端 20 个调用点里【零消费者】。**
**「加了一个 ref 但没人用」和「没有护栏」是等价的**（铁律 8 的另一种形状）。

### 3.1 处置：不改签名，让它**能被消费**

新增两个 `computed`，**由构造互斥**（不是靠调用方记得判两次）：

```js
const failed  = computed(() => loaded.value && !!error.value)
const isEmpty = computed(() => loaded.value && !error.value && list.value.length === 0)
```

★★ `!error` 那半个条件是 `isEmpty` 存在的理由：`catch` 里 `list` 被清空，
于是「失败」和「空」的 `list.length` **都是 0**。少写它，页面就会把失败说成「还没有作品」——
**而忘写不会有任何报错，只会有某个页面悄悄开始说谎。**
把它写在 `usePagedList` 里而不是让调用点各写一遍，就是为了这个。

### 3.2 四类页面

| # | 页面 | 停谁 | 现状（谎言） | M5 后 |
|---|---|---|---|---|
| 1 | 评论列表 | interaction | 「暂无评论」 | 「评论暂时加载失败」+ **重试按钮** |
| 2 | 收藏按钮 | interaction | ★ **显示成「未收藏」** —— 用户会以为收藏丢了，然后去点它，再失败一次 | 按钮**禁用** + 文案 `—` |
| 3 | 首页/分类/榜单/历史的列表 | content 等 | 「暂无作品」 | 各块一条「…暂时加载失败」+ 各自的重试 |
| 4 | 搜索页 | search | 「没有找到相关作品」 | 「搜索暂时不可用」+ 重试 |

★ 第 2 行最危险：`onShelf=null` 和 `onShelf=false` 在前端**必须走不同分支**。
`reader-web/views/novel/index.vue` 的 `onShelf` 因此是**三态**，
不变量是「**`null` 只有一个来源 —— 一次失败的查询**」（初始值 `false` 但那时页面在 `v-loading` 下，
查询中由 `shelfLoading` 挡住），所以「还没查」和「查不到」在界面上**不可能混淆**。

### 3.3 ★ 一条明确**不改**的：`sse.js` 的 401 策略

`author-web/src/utils/sse.js` 是**全项目唯一**把失败做对的地方
（结构化 `reason`、**保留部分产出**、非阻断提示、401 **不跳登录**）。
它的 401 策略**刻意**与 `request.js` 不同 —— 「此刻作者正在创作中心写东西，**一跳走就等于丢稿**」。

★★ **同一端里存在两套 401 策略是【故意的】，M5 不许「统一」它们。**
也**不许**让 `sse.js` 去复用 `usePagedList` 的逻辑，反之亦然 —— 两者的取舍不同且都有注释论证。

### 3.4 ★ S10 顺手补的一处：作者名 `—`（本期最后改的一处代码）

**缺口**：判断 1 说「降级 = 让缺失在界面上可见」，
而列表卡片的作者名回落写的是 **`|| '佚名'`** —— auth 挂掉时渲染成「佚名」，
一个**看起来完全正常**的值。**那正是 M1 立规矩要挡的东西。**

**处置**：新增 `reader-web/src/utils/format.js` 的 `formatAuthorName()`，
四处渲染点（`NovelCard` / 详情页 / 书架 / 阅读历史）改用它。

★ 放进 `format.js` 而不是四处各写一遍，抄的是**同一个文件里 `formatWordCount` 的既有理由**：
「各写一份的话，规则改一次要改两处 —— **而漏掉的那一处不报错**，只是在某个页面上显示成另一种写法」。

★★ **为什么「佚名」在本系统里是假话而不是合法兜底**：`novel.author_id` 是外键，
**每本书都必然有作者** —— 「佚名」不是一个可能的状态，
它是把「服务器没问到」说成了「这本书没有作者」。

★ **刻意保留的不对称**：同一张卡片上的 `categoryName` 仍然回落成「未分类」——
分类是 content **自己库里的表**（JOIN），不跨服务，取不到只可能是「真被删了」。
**判据是「这个字段会不会因为别人挂了而消失」，不是「它重不重要」。**

## 四、判断 3：并行化与追踪、熔断**互相咬住**

三件事必须在同一期做，因为它们**抢同一个东西**：

```
要并行  →  必须换线程
          ├─ MDC（traceId 的家）是 ThreadLocal   → 换线程就丢
          └─ Sentinel 的 Context 是 ThreadLocal  → 换线程就丢？
```

### 4.1 ★★ 「Sentinel Context 也会丢」是**猜测，已被源码推翻**

| 疑问 | 源码结论 |
|---|---|
| 换线程后熔断统计还进得去吗 | ★ **进得去。** SCA 的 `SentinelInvocationHandler` 在**调用发生的那个线程里**显式 `ContextUtil.enter(resourceName)`，不依赖父线程的 ThreadLocal |
| 万一那句 `enter` 也没有呢 | ★ 兜底：`CtSph.entryWithPriority` 在 `ContextUtil.getContext() == null` 时**自动建一个默认 Context** |
| 熔断按 Context 还是按资源索引 | ★ **按资源名**：`DegradeRuleManager.getCircuitBreakers(r.getName())`，与 Context 无关 |

★★ **所以并行化不需要为 Sentinel 做任何事。`TaskDecorator` 只为 MDC 而装。**
真正会丢的是 `origin` 和链路模式的调用树 —— 而这两样本项目都没用
（没有 `limitApp`、没有 `AuthorityRule`、没有链路流控），**所以不引入**（引入反而是没用的复杂度）。

### 4.2 处置

| 丢失的东西 | 怎么补 |
|---|---|
| MDC（traceId） | ★ **唯一的真问题**：`ContextPropagatingTaskDecorator`（common）：提交时快照 MDC → 任务里 `setContextMap` → `finally` 里 `clear` |
| ~~Sentinel Context~~ | ★ **不需要处理** —— 但**仍实测过**（见下） |

★ **独立线程池**（大纲点名）：
**绝不能用 `ForkJoinPool.commonPool`** —— 它是 JVM 全局的，
一个慢下游会把 commonPool 占满，然后**整个 JVM 里所有并行流一起卡住**，
而症状是「某个不相干的接口变慢了」，排查方向会完全跑偏。

### 4.3 ★★ 阳性对照：摘掉 `TaskDecorator` 的差分

**只验「装回去之后有」是不够的 —— 那可能本来就是有。**
先摘掉跑一次确认异步段**真的没有** traceId，再装回去。

★ 而 S9 的 Q5′ 是这条判断的**跨服务**版本（零成本，因为日志行本来就有）：

| 组 | 谁发起的 | traceId | 身份头 |
|---|---|---|---|
| **实验组** | search 的**池线程**（异步重建的 Feign） | `d5f69b2d…`（= 提交请求那个） | `X-User-Id=1 X-Username=admin` |
| **对照组** | 匿名直连 `:8082/internal/novels/index-page`（只带内部密钥） | **自己生成的** | **没有，只有 `X-Internal-Token=***` |

→ 证明 `ContextPropagatingTaskDecorator` **同时**搬了 MDC 与 `UserContext`：
① traceId 到了 content（否则 content 会用自己生成的）；
② **异步重建那次调用不是匿名的**。

### 4.4 ★★ `CallerRunsPolicy` 用在哪、不用在哪 —— 两个池**故意不一样**

| 池 | 策略 | 理由 |
|---|---|---|
| `AuditAggExecutorConfig`（审核日志聚合，core4/max8/queue64） | **`CallerRunsPolicy`** | 队列满 → 任务在**请求线程**上直接跑完 → 页面**慢一点但正确**。明显好过「当场 500」 |
| `ReindexExecutorConfig`（重建，core1/max1/queue2） | ★★ **`AbortPolicy`** | ★ **`CallerRunsPolicy` 会让「异步化」恰好在最需要它的那一刻【静默退化回同步】** —— 任务跑在 Tomcat 请求线程上，`POST` 照常返 200，而管理员以为它异步了 |

★ `CallerRunsPolicy` 还有一段分支是 **`if (e.isShutdown()) return;`** ——
任务被**静默丢弃**，而调用方还在 `join()` 上等 → **永久挂起**。
`AuditLogServiceImpl` 的 `joinOrRethrow` 因此要处理这个情形（见 §十 S7）。

## 五、判断 4：可降级点比大纲说的**少得多**，而「content 不在范围」**正好是对的**

★★★ 结构性事实：**`NovelVO` / `NovelDetailVO` 里没有 `collectCount`，也没有 `commentCount`。**
读者端的**收藏态**和**评论**都是**前端直接打 interaction** 的，**不经过 content**。

→ 「停 interaction → 收藏态/评论数降级」**后端一行都不用改**，它整个是前端工作。

### 5.1 真实的全量接缝 × 降级矩阵

| 接缝 | 方向 | 谁调它 | 失败后的降级 | 判 |
|---|---|---|---|---|
| `AuthUserClient.nicknamesOf` | content → auth | 列表/详情的作者名 | `authorName` key 消失 → `—` | ✅ |
| ★ 同上，`userIdsByNickname` | content → auth | **按作者名搜索的筛选输入** | — | ❌ **不降级** |
| `AuthNicknameClient` | interaction → auth | 评论列表的作者昵称 | 昵称 `null` → `—` | ✅ |
| `AuthUserClient.briefsOf` | content → auth | 审核日志的申请摘要 | — | ⛔ **不降级**（§2.3） |
| `CommentBriefClient` | content → interaction | 审核日志的评论正文 | — | ⛔ **不降级**（§2.3） |
| `ContentClient`（interaction→content，7 个读端点） | interaction → content | 书架/历史/评论列表的**主数据装配** | ★ **没有降级可言** | ❌ |
| `ContentClient`（search→content，4 个） | search → content | 搜索结果装配 + 降级路径 | ★ **同上** | ❌ |

★★ **后两行就是「content 不在范围」的事实依据**，不是妥协：
**content 是主数据源，停掉它没有任何「降级数据」可以显示** ——
唯一的选项是显示一个空列表，而那正是 M1 反对的「看起来正常但是错的」。
**M5 对这一条的处置是：熔断 + 快速失败 + 前端显示「暂时拿不到」，而不是「编一个降级值出来」。**

★ 顺带销掉一条疑似风险：`search → content` 在 M4 的降级**只覆盖「ES 挂了」**
（降级路径本身也要调 content），所以**停 content 时搜索 500 是预期行为**，不是 M5 要修的 bug。

### 5.2 ★ 一条**如实记下、不重写**的归因偏差

```java
try {
    return searchByEs(...);          // ★ 这里面【包含】一次 Feign 调 content
} catch (Exception e) {              // ← 全捕获
    log.warn("ES 检索失败，降级到数据库 LIKE | ...");   // ★ 归因是错的
    return degradeToLike(...);       // ← 这一次 Feign 【没有 catch】→ 直接冒泡 500
}
```

→ **停 content** 时的真实行为是两跳：第一次调用被吞掉、被归因成「ES 检索失败」，
第二次才抛出来。**日志里的归因是错的**，会把「content 挂了」说成「ES 挂了」。

★★ S8 的实测**真的撞上了它**：熔断打开时日志写着
「ES 检索失败，降级到数据库 LIKE | … `UndeclaredThrowableException: null`」，
而真实原因是 content 的 Feign 调用被熔断。
**M5 不重写这段**（`try` 的语义被刻意限定为「ES 这条路不通」，那是 M4 的既有设计），
**只记录**。★ S8 的日志判据（分开 `index_not_found` 与 `ConnectException`）是它的补充。

## 六、判断 5：链路追踪 —— 自建 traceId

**不上 SkyWalking。** 零新中间件、零 `-javaagent`；代价是没有拓扑图。

| 环节 | 落在哪 | 要点 |
|---|---|---|
| **生成** | 网关 `JwtAuthGlobalFilter#filter` | `TraceContext.newTraceId()`；★ 与鉴权同一个 filter，`order=-100` |
| ★★ **剥离** | **同一个 filter 里，`IdentityHeaders.strip()` 之后、写头之前** | 不剥 → 客户端可以自带 `X-Trace-Id`，**把别人的日志关联到自己身上** |
| **放 / 清** | 四个 servlet 服务的 `TraceIdFilter`，`finally { TraceContext.clear() }` | ★ 照 `HeaderAuthenticationFilter` 的 `finally` 范式 |
| **日志** | 五处 `logging.pattern` 加 `[%X{traceId}]` | 键名必须与 `TraceContext.MDC_KEY` **逐字相同** |
| **透传** | `common/internal/FeignIdentityConfig` 的 `RequestInterceptor` | 与身份头同一处、同一次出站 |
| ★★ **跨 MQ：不做** | —— | 见下 |

★ **剥离的成本为零**，严重性如实评：**低危**（不是身份伪造），
但**不剥会在「我们管理的头」这一组里留下一处不对称**。

★ 网关侧还有一处细节：`forward(...)` 把 traceId 当**参数**往下传（而不是从 MDC 读），
因为**下游路由（`NettyRoutingFilter`）那一段的日志没有 traceId** ——
关联依据不能「大部分时候对」。

### 6.1 ★★ 一个 Spring 默认值造成的顺序坑（**实测通过**）

`TraceIdFilter` 若写成普通的 `@Component OncePerRequestFilter`，
**Spring Boot 会自动注册它，且默认顺序是 `LOWEST_PRECEDENCE`** ——
而 Spring Security 的过滤器链注册顺序是 **`-100`**。

→ **它会排在 Security 之后** → **被 401 / 403 短路掉** → **鉴权失败的请求日志里没有 traceId**。
★ 而那恰恰是最需要 traceId 的一类请求。

**处置**：**显式注册**（`TraceIdFilterConfig` 的 `FilterRegistrationBean` +
`setOrder(Ordered.HIGHEST_PRECEDENCE)`），
而不是靠 `@Component` 自动注册 —— 四个 `SecurityConfig` 里给 `HeaderAuthenticationFilter`
配的那个 `setEnabled(false)` 的 `FilterRegistrationBean` 是同一个套路的另一半。

**★★ 阳性对照（这条判据本身必须是可失败的）**：打一个**在 servlet 服务里被 Security 拦掉**的请求
（READER 的 token 打 ADMIN 端点 → 网关放行 → content 返 403），实测：

```
网关      22:10:28  [1d59c3427b1548f8a39eb3e47e512a3f]  ...
content   22:10:28  [1d59c3427b1548f8a39eb3e47e512a3f]  RestAccessDeniedHandler - 鉴权失败（filter chain 层）
```

**同一个 traceId** ✓。**只验 200 的请求，这个坑永远发现不了。**

★★★ **同一个日志文件里还白捡了一个阴性对照**：调度线程的行是

```
2026-09-23 22:10:19.239 DEBUG [] [novel-sched-1] ... 阅读量落库：无增量
```

**`[]` 是空的** —— 证明 `[%X{traceId}]` 真的是从 MDC 取的，不是一个写死的常量。
（铁律 8：**换差分式判据，别用阈值式** —— 对照组就在同一份日志里，对齐是自动的。）

### 6.2 ★★ 一条如实写下的局限：**前端永远看不到 traceId**

`request.js` 是 **12 个锁定文件之一**（铁律 2），它的响应拦截器 **`return res.data`** ——
**响应头在前端被彻底丢掉**。

→ **traceId 只活在后端日志里，不可能显示在错误提示上。**
→ 后果：用户报错时**提供不了 traceId**。
→ **不违反铁律 2 的缓解**：五个服务的日志里 traceId 与 `时间戳 + 请求路径 + 用户 id` 同屏，
**客服可以按「时间 + 页面」反查**。
★★ **这句必须写下来**，否则下一个人会以为「加了 traceId 就能让用户报号」。

### 6.3 ★★ 跨 MQ 不做（说明理由，不是漏了）

五条消息**不带 traceId**。三条理由：
① traceId 的语义是「一次请求」，而消费是「一次投递」—— **生命周期不同**；
② 消费者有 `maxReconsumeTimes = 3` 的重试，同一个 traceId 会出现**多次**，反而污染关联；
③ 排查消费问题的入口是 `novelId`（载荷里有），**它比 traceId 更直接**。

★ 如实记为债：**「跨 MQ 的关联要靠 `novelId` 人工串」**，M5 不解决。

## 七、判断 6：Sentinel —— 规则必须**代码加载**，且必须**证明它会开**

### 7.1 ★ 哪三个服务装 —— 一条可 grep 的不变量

**只有 `content` / `interaction` / `search` 三个服务需要熔断，因为只有它们有出站调用。**
`auth` 的出站边是 **0 条**（M3 挣来的），**既不需要 Feign 配置，也不需要熔断。**

★ 不变量：`grep -l openfeign backend/*/src/main/resources/application-dev.yml`
和 `grep -l sentinel ...` 必须是**同一组三个文件**。（差分式判据，不数个数。）

★★ **网关不装**（BOM 里有 `sentinel-spring-cloud-gateway-adapter`，是**不选**的路）：
在网关加一层会把「谁降级的」变成两个地方都要查。**记进文档，不实施。**
★ BOM 里还有 `spring-cloud-circuitbreaker-sentinel` —— 也**不选**：
本项目的 Feign 客户端是**接口 + 注解**的形状，`fallbackFactory` 直接就能接上，**多一层抽象换不到东西**。

### 7.2 规则写在代码里（`SentinelRules.loadSlowCallRules`），不接数据源

| 不选 | 理由 |
|---|---|
| `sentinel-datasource-nacos` | 实施它等于在 M5 顺手推翻 M0「不接 Nacos Config」的决定。**升级路径写明，不实施。** |
| SCA **文件数据源** | ★★ **数据源配错是【静默】的** —— `SentinelDataSourceHandler` 把异常整个 catch 掉只打一行 ERROR，连「规则文件不存在」都被吞。**代码加载没有这个失败面**：规则是常量，编译期就在，加载失败就是启动失败 |

★★ 选 `loadRules` **不是因为它简单，是因为它少一个只能靠读日志发现的失败模式。**
（同一个判据 M4 也用过 —— 「去重算一次」永远比「算好的结果」好维护。）

★ 加载时机是 **`@PostConstruct`** 而不是 `ApplicationRunner`：前者在 **bean 装配阶段**执行，
早于 Servlet 容器开始接客（那是 `finishRefresh()` 的事）。用 Runner 的话，
启动到最后一步之间进来的请求会跑在「无规则」状态下 —— **那个窗口很短，但它是真实存在的，
而且没有任何日志能证明它发生过。**

### 7.3 ★★ 熔断需要的是「**慢**」，不是「死」

| 场景 | M4 怎么造 | M5 需要什么 |
|---|---|---|
| 下游**死**（连接拒绝） | TCP 代理杀掉 | ★ 只能验「快速失败」，**验不了熔断** —— 熔断按「慢调用比例 / 异常比例」决策 |
| 下游**慢** | —— | ★★ **延时代理**：收到请求后**先 sleep N 秒再转发** |

### 7.4 ★★ 夹具的取值 —— 这三个数字**必须**一起看，否则夹具永远开不了

| 参数 | 取值 | ★ 为什么是这个数 |
|---|---|---|
| 代理延时 | **800ms** | ★★ **必须 < `read-timeout`（5000）** —— 超了就变成抛异常，喂的是异常比例、不是慢调用比例。**「慢但成功」才是慢调用比例规则的食物。** |
| `count`（慢调用 RT 阈值） | **500** | 落在「800ms 之上、5000ms 之下」，这样**只有被延时的那些算慢** |
| `slowRatioThreshold` | **0.5** | ★★ **不设 = 1.0 = 100% → 永远打不开**。官方文档这一格是**空的**，只有源码写了 1.0 |
| `minRequestAmount` | 保持默认 5 | ★ 判据是「**严格大于**」→ 窗口内**至少打 6 次**，夹具按 10 次设计留余量 |
| `timeWindow` | **10**（秒） | `timeWindow` 与 `count` **都没有默认值**，不设就是 0 —— 熔断立刻结束，等于没开 |

★ 一句话：`slowRatioThreshold`、`timeWindow`、`count` 三个必须显式写，
其中 `timeWindow`/`count` 不写是 0（一眼能看出不对），**而 `slowRatioThreshold` 不写是 1.0（看不出来）**。

★★ **M5 的三份规则（`SentinelRules.SLOW_RT_MS=500` / `SLOW_RATIO_THRESHOLD=0.5` /
`TIME_WINDOW_SECONDS=10` / `MIN_REQUEST_AMOUNT=5`）是常量，三处共用同一套取值。**

### 7.5 ★★★ 铁律 8：两个「不会失败的护栏」，各配一个阳性对照

| # | 护栏 | 阳性对照 |
|---|---|---|
| ① | **熔断规则** | ★ 「**不加规则 = 一条永远不会触发的护栏**」。必须证明：**加规则**时慢下游能让它**开**；**不加规则**时同样的慢下游**不会**开 |
| ② | **规则真的加载了** | 启动日志逐条打印资源名 + **状态变更观察者**。**「规则数组是空的」和「规则生效了」在没有下游故障时长得一模一样** |

★ 判定性证据：熔断**打开之后**，下游即使恢复，**请求仍会被快速失败**直到半开探测
→ 「恢复后自动切回」必须在**同一个进程**里观测到（不能靠重启）。

### 7.6 ★★ 资源名必须按 SCA 的公式拼

```
resourceName = 大写 HTTP 动词 + ":" + hardCodedTarget.url() + 方法上的 path
例：POST:http://novel-auth/internal/users/nicknames
```

★ 这个字符串**猜不出来**，所以 `SentinelRules` 的类注释里写了公式，
三份 config 里每条规则上面都标了它对应哪个客户端。
★ `ContentClient`（search → content）**没有 `path` 属性**，所以资源名里也就没有那一段 ——
**这正是「按公式拼」而不是「按直觉拼」的例子。**

### 7.7 ★★ `fallback` 必须能说出原因 —— `fallback=` 是**彻底不可见**

| | `fallback=` | `fallbackFactory=` |
|---|---|---|
| 拿得到 `Throwable` 吗 | ✗ 被包成 `FallbackFactory.Default`，**把 cause 丢掉、只打一行 TRACE** | ✓ |
| 本项目能看到那行 TRACE 吗 | ★ **不能** —— 没有 logback 配置、级别走默认 INFO | —— |

★★ **所以 `fallback=` 的降级是【一个字都不留】的**，不是「说得不清楚」而已。
★ 症状对照：用错的那个，「降级原因」这一栏**永远是同一个字符串**（或者干脆没有）。

★★ **可见性要两条通道合起来**：

| 通道 | 回答什么 |
|---|---|
| `FallbackSupport`（在 `fallbackFactory` 里） | 「**这一次**为什么降级」—— 熔断 / 超时 / 注册中心没实例 / 500，带 traceId |
| `EventObserverRegistry.addStateChangeObserver(...)`（`SentinelRules` 里注册） | 「熔断器**什么时候**开的、什么时候恢复的」—— `prevState / newState / rule / snapshotValue` |

★ 第二条正是 7.5 说的「同一个 PID 观测打开 → 半开 → 恢复」所需要的那个东西。
★ 而 `fallbackFactory` 里**拿不到**的：堆栈（`DegradeException.fillInStackTrace()` 返回 `this`）、
以及**熔断器处于 OPEN 还是 HALF_OPEN**。

### 7.8 ★★ 两种失败，两种日志级别 —— 这是判据不是风格

`FallbackSupport` 有**两个**入口，选哪个是**接缝级**的决定（§2.2 / §2.3 的表）：

| 方法 | 级别 | 语义 |
|---|---|---|
| `logThenDegrade(call, cause, 降级值)` | **WARN** | 「改用降级值」—— 继续走 |
| `logThenRethrow(call, cause)` | **ERROR** | 「这条刻意不降级」—— 抛出 |

★ 症状对照：停 auth 时 content 日志里**同时**出现两种 ——
`取作者昵称` 是 WARN（降级），`按昵称反查用户` 是 ERROR（不降级）。
**同一个下游、同一个失败、两种级别 —— 一眼就能看出哪条接缝降了、哪条没降。**

### 7.9 ★ Sentinel 自己的日志**不在 `backend/logs/`**

Sentinel 默认写到 `${user.home}/logs/csp/`。★ 这和 CLAUDE.md 那条
「日志路径跟着工作目录走、改了就静默换目录」**是同一类账**：
**熔断的日志和业务日志不在一个地方，排查时会以为「降级没记日志」。**

**处置**：显式钉到 `logs/csp`（相对路径，与 `logging.file.name` 同源）。

★★ 而这里有一条**只能靠实测发现**的细节：**直接往 yml 里写 `csp.sentinel.log.dir` 是无效的** ——
SCA 是从 `spring.cloud.sentinel.log.dir` 映射到那个系统属性的。
★ 证据是 S4 配这一项**之前**的实测：`logs/csp/` 下出现了
`sentinel-block.log`（**既没有 PID，也没有日期**）与
`sentinel-record.log.2026-09-23.0 / .0.1 / .0.2` ——
**同一个进程写三份带序号的 rolling 文件**，因为三个服务共用一个日志目录而无法区分。
配 `switch-pid: true` 之后按 PID 分开了。

### 7.10 ★ R13：Sentinel 拖进来一个 **8719 端口**

`sentinel-transport-simple-http` 被 starter 非 optional 地拖进来 →
**三个服务各多监听一个 8719**（被占则向上探测）。

★★ **端口清单变了**，排查时会多一个「这是谁的端口」。
★ **生产必须和 `8081~8084` 一起被防火墙挡掉** —— 它就是给 dashboard 用的，
等于又一个对内网暴露的面。

## 八、判断 7：顺带还债 —— 而其中一处**不改就是错的**

### 8.1 ★ 订正：`FeignIdentityConfig` 是**两份变三份**，不是「三份变四份」

M4 文档（§十二 与目录树）写的是「从三份副本变成四份（新增 search 那份）」。
**实测：`find backend -name FeignIdentityConfig.java` → M5 前是 3 个**（content / interaction / search）。
**auth 那份在 M3 就随整条边一起删掉了。**
→ **M4 那句把已经删掉的 auth 那份算了进去。** 本文件订正。
★（M5 之后这 3 份合并成了 `novel-common` 里的**单源 1 份**。）

### 8.2 ★★ `Retryer.NEVER_RETRY`：那个 bean **是个 no-op**，而它的理由写错了

interaction 的 `FeignIdentityConfig` 里有一个 `@Bean Retryer feignRetryer() { return NEVER_RETRY; }`，
类注释说它「让 5 个读接口失去自动重试」，并引用「Feign 默认的 `Retryer.Default`（最多 5 次尝试）」。

★★★ **核实结果：那段话里有一句事实错误，而且这个 bean 本身什么也没做。**

`spring-cloud-openfeign` 的 `FeignClientsConfiguration` **自己就注册了**：

```java
@Bean
@ConditionalOnMissingBean
public Retryer feignRetryer() { return Retryer.NEVER_RETRY; }
```

→ 三件事：

1. **Spring Cloud OpenFeign 的默认【本来就是】不重试**（自 `spring-cloud-starter-openfeign 2.2.6` 起）。
   `Retryer.Default`（最多 5 次尝试）是**裸 Feign** 的默认。
2. **所以那个 `@Bean` 是重复声明框架默认值** —— 行为上**等于什么都没改**。
   **它不是「一道护栏」，是一行让人以为有护栏的注释。**
3. ★★ **连带订正**：`docs/M2-摘出content.md` 那句「Feign 默认带 `Retryer.Default`」
   **对 Spring Cloud 而言是错的**。M5 **只订正、不改写 M2 的文档**（它记的是当时的事实）。

★★ **这反而让结论更强，不是更弱**：读调用不开重试**不需要论证**，它就是框架默认；
M5 要做的只是**把这个 bean 删掉**（合并成单源时它自然消失），
**并且不再用一个不存在的危险去为它辩护**。

★★★ **而「万一将来真开了重试」的答案，熔断让它变得明确：仍然是不开。**
理由不是「重试不好」，是**重试与熔断相互放大**：
- 熔断**打开之前**：重试把「1 次慢调用」放大成 N 次，**加速熔断打开**（好），
  但同一时刻**下游已经吃力**，重试是在往一个过载的服务上再加负载（坏）；
- 熔断**打开之后**：重试全被快速失败挡住，**一次真正的请求都不会发生** —— 收益为零。

→ **落点：合并成单源，读客户端一律 `NEVER_RETRY`；把「抖动恢复」交给熔断的半开探测。**
★ 合并后的 `FeignIdentityConfig`（现在住在 `novel-common`）**不声明 `Retryer`** ——
并在注释里写明「将来要给某个读客户端单独开重试，用 `@FeignClient(configuration = ...)` 配，
**而不是在这里加一个全局的 `Retryer` bean**」。
★★ 这**兑现了 interaction 那段注释里的原话**（「而不是把这个 bean 删掉 ——
因为下一个写接口出现时，你不会有第二次机会想起这里曾经有过一道护栏」）：
**护栏的形状被保留下来了**，而它守的那个危险被证明不存在。

### 8.3 alias 原子切换 —— 它不再是「更稳一点」，而是**修掉一个已实测的破坏性失败模式**

M4 实测出来的失败模式：

```
  索引不存在   → 抛异常 → 降级到 MySQL LIKE → 结果【是全集】，只是排序退化  ← 好
  索引存在但空 → 无异常 → 返回 0 条         → 结果【是空的】，且无人报错    ← 坏
```

**M4 的处置是止血**（失败就把索引删掉，让系统停在「可降级」的那一侧），
**M5 的处置是根治**：写 `novel_index_v{ts}` → bulk 灌 → **原子切 alias** → 删旧索引。

| 变化 | 细节 |
|---|---|
| `novel_index` 从**索引**变成**别名** | 检索代码**一行不改**（搜别名和搜索引是同一个词法） |
| ★ **空索引窗口消失** | 新索引装满之前，别名还指着旧索引 —— **「索引存在但为空」这个状态物理上无法出现** |
| ★ `ensureIndex()` 判据 | 从 `HEAD /novel_index` 改成判**别名**（`HEAD /_alias/novel_index`） |
| ★ `isEmpty()` 同理 | 「别名不存在」= 从没建过 → 触发全量重建 |
| ★ 每个新物理索引都要带上**全套 settings + mappings** | `number_of_replicas: 0`、IK 双分析器、显式 mapping —— 一个都不能少 |
| ★ 清理：切完删旧索引 | 「删除」这一步**失败不影响正确性**（旧索引只是占空间），所以它**不该让整个重建失败** |

★★★ **一个只有实测才会发现的坑：bulk 写入默认 `refresh=false`。**
文档要等下一次 refresh（默认 1 秒）才可检索 —— **「灌满」≠「检索得到」**。
别名切到一个「满了但还看不见」的索引上，症状与 S8 要消灭的那个状态**一模一样**：
HTTP 200、`total=0`、**没有任何报错**。

**修法**：`refresh` 写在 **`switchAlias` 内部**，不是调用方。
理由：本方法的不变式是「别名永远不许指向一个检索不到的索引」——
**这个不变式只有和「切换」写在同一个方法里才拦得住**；
放调用方的话，下一个调用方忘了写，这个 bug 就**静默地**回来了（铁律 8 的形状）。

**双端夹具 + 结果**（同一轮里既打应用 `/api/search?keyword=剑`，又直接打 ES `_count`）：

| | 样本 | `total=0` | 应用与 ES 不一致 | 零值窗口 |
|---|---|---|---|---|
| **修复前** | 3881 | **123** | 2 | ★ `21:32:22.574 → 22.927`，**连续 353ms** |
| **修复后** | 2241 | **0** | 0 | — |

★★ **阳性对照的第一版是错的**（0/26 检出）：空索引用**没有 mapping** 建的 →
排序字段不存在 → 查询 400 → 被 `SearchService` 的 `catch` 吞掉 → 降级到 LIKE →
返回了**正确答案**。
**教训：对照组必须和被测对象同构，否则量的是另一条代码路径。**
★ 第二版用 settings+mapping **完全相同**的空索引 → 30/30 `total=0` → **检测器会失败** ✓。

★★ **别名带来的一个新失败模式，必须写下来**：
**别名指向一个不存在的索引** → ES 报 `index_not_found_exception`
→ **会被 M4 的 catch 吞掉 → 静默降级到 LIKE**。
★ 严重性**可接受**（降级路径是对的，用户拿到的是全集），
但**必须有一条能指认它是别名悬空的日志** —— 否则排查方向会去查 ES 容器。
**实测**：`ElasticsearchException: [es/search] failed: [index_not_found_exception] no such index [novel_index]`，
**可与 `ConnectException` 区分**（前者指向别名/索引，后者指向 ES 容器）✓

### 8.4 reindex 改异步

| 设计点 | 选择 |
|---|---|
| 提交 | `POST /api/admin/search/reindex` → 立刻返回 `{taskId}` |
| 进度 | `GET /api/admin/search/reindex/{taskId}` → 轮询 |
| 进度存哪 | **Redis**（Hash，TTL 24h）—— ★ `IndexRebuildService` 自己用**分布式锁**暗示了「多实例」这个前提，用内存 Map 会和那个前提自相矛盾 |
| ★ 任务失败 | 轮询结果里带 `status` + `error` + `failedAt` —— 铁律 8：**「永远不完成的任务」和「还在跑的任务」在没有状态字段时长得一模一样** |
| ★ 兼容 | **不保留同步入口** —— 两个入口会有一条**没人维护**，改重建逻辑时很容易只测常用的那个 |

★★ **这次改动的账要写清**：

| | 内容 |
|---|---|
| ★ **买到** | 网关/浏览器**不再被一个长任务占住**。同步时代的失败模式是「库大到超过读超时 → 管理员看到超时，而重建其实还在跑」—— 他收到的是一个**无法判断**的结果。现在「还没好」是一个合法答案（`status=RUNNING`） |
| ★★ **卖掉** | ① 管理员**要轮询**；② ★★ **「提交成功」不再等于「重建成功」** —— 200 只说明任务进了队列。**这一条必须写死，否则下一个人会把 200 读成「索引已经好了」** |

★ 而 M4 那个 `RebuildReport{skipped, indexed, elapsedMs}` **没有丢** —— 它整个搬进了轮询结果。
**`skipped` 那个字段尤其留着**：「没做」和「做了 0 条」在响应里长得不一样。

★★ **失败处理的载体换了**：M4 时代的选择是「不吞异常、让它变成 500」，
理由是「管理员正站在屏幕前等着结果」。**异步化之后那个理由消失了** ——
提交请求早就返回了，异常是在池线程上抛的，**没有任何人接得住它**。
所以异常改成落成 `status=FAILED` + `error`。
★ **仍然保留 500 的那一处**：提交时队列满 —— 那一次失败发生在**请求线程上**，还来得及告诉调用方。

★ **`ResultHttpStatus` 不作用于普通 `@RestController` 的返回值**（实测）：
`return Result.error(ResultCode.NOT_FOUND, …)` 拿到的是 **HTTP 200**。
要真 404 必须 `ResponseEntity.status(ResultHttpStatus.of(code)).body(…)`（先例：`PingController#fail`）。
→ 「任务不存在」因此走**真 404**，理由和 ping 那两处一样：**「返回值 200 就等于没有监控」**。

### S8 alias 原子切换
见 §8.3。★★ 顺带**第一次真的观测到熔断器打开**（见 §5.2 的归因偏差）。

★★★ **S8 还发现了一个计划里没有的缺陷：成功重建留下的幽灵锁会卡死启动自愈**

```
21:36:23  一次【成功】的重建跑完，别名切好 —— 锁没人删，留着（TTL 30 分钟）
21:39:21  重启 search：探到「别名不存在」→ 触发全量自愈
21:39:21  ★ 拿不到锁 → skipped=true，灌入 0 条
→         ES 里【一个索引都没有】，全站搜索走 LIKE 降级，直到 22:06 锁自己过期
```

复验：`EXISTS novel:lock:search-index-rebuild` → `1`，`TTL` → **1436 秒**。

**为什么原来的「不释放」判断是错的**：原文说「不主动释放（理由同 `NovelStatReconcileJob`）」，
而那条理由说的是释放的**做法**要小心（不能裸 `DEL`），**不是「释放这件事没必要」**。
不释放的代价**没算过「启动自愈」这条路径**，而它正好被卡死。

**修法**：`UNLOCK_SCRIPT`（Lua，`GET == ARGV[1]` 原子 compare-and-delete）。

★ **顺带修掉两处「说了假话」**：
① 自愈日志原来无论做没做都打「启动自愈完成 | 灌入=0 条 … skipped=true」——
字面每个字段都对，但第一眼读到的是**完成**，实际是**什么都没做、索引仍然是空的**；
② `isEmpty()` 的 catch 默认值一度从 `false` 翻成 `true`（理由是「别名悬空会走到这里」），
**被实测推翻**：**ES 在索引被删掉时会连带删掉指向它的别名**，
所以「悬空」以「别名不存在」的形态出现，根本到不了 catch。
而翻成 `true` 的真实语义是「**一次 ES 网络抖动 = 一次全库重建**」。**已改回 `false`。**

### S9 reindex 异步化
见 §8.4。交付 6 个新类（`ReindexTaskStatus` / `ReindexTaskVO` / `ReindexSubmitVO` /
`ReindexTaskStore` / `ReindexTaskService` / `ReindexExecutorConfig` + 控制器两个端点），
**前端零调用方**（消费者是运维/curl）。

★ 验证：成功路径 `SUCCEEDED/skipped=false/indexed=12`；
★ 停 content 造一次**必然失败** → `FAILED` + `error`，**403ms 快速失败，不是永远 RUNNING**；
★ 不存在的 taskId → **真 404**；★ 真有人持锁 → `skipped=true` 且**别人的锁毫发无伤**（TTL 296/300）。

### ★★★ S9 的第二个缺口：**失败路径不放锁**（S8 只修了成功那条）

```
21:54:31.068  已释放锁（成功路径，S8 修的）
21:54:42.669  重建失败 → 【不放锁】
21:55:38.197  再提交 → skipped=true  ← 就是上面那次失败留下的锁，TTL 还有 1745s
```

★★ 而 `skipped=true` 在文档与直觉里的成因写的是「**另一个重建正在跑**」—— **那是一句假话**。
管理员修好 content 想重试，拿到的是一个「成功但什么都没做」的结果，
**且无从知道要等 30 分钟**。

**判定依据用的是 S8 自己立的那条规则**：

> 锁的寿命要对齐它保护的东西的寿命。

失败时：半成品新索引被 `deleteIndexQuietly` 删掉、别名没切、旧索引原样在用
（★ 实测：失败后 ES 里仍然只有一个物理索引）—— **锁保护的东西一件都不剩了**。

★ S8 当时只放了成功那条，理由写的是「放锁会把『上一轮跑崩了』和『上一轮跑完了』
在下一个**人**眼里抹平」。**那句话本身没错，错的是它把那个「人」放在了锁这个通道上** ——
M5 之后那个人的通道是**任务记录**（FAILED+error / SUCCEEDED+skipped），**锁上没人读这份区别**。

**处置**：`rebuildAll()` 拆成两层 —— 外层「拿锁 → `try { doRebuild() } finally { releaseLock() }`」，
内层 `doRebuild(startedAt)` 只管干活。
★ **S8 想守的那条边界没被抹掉**：**`kill -9` 时 `finally` 不执行**，
那条路仍然只能等 TTL —— 也就是「跑崩了」依旧与「跑完了」长得不一样（taskId 停在 `RUNNING`）。

★★ **决定性差分（两臂都实测到了）**：

| | 同样的动作序列 | 结果 |
|---|---|---|
| **修复前** | 停 content → 提交（失败）→ 起 content → 提交 | `skipped=true / indexed=0` ← **什么都没做** |
| **修复后** | 同上 | `skipped=false / indexed=12` |

★ 而 `releaseLock()` **必须不抛**，这里有**第二条、也更硬的理由**：
它现在由 `finally` 调用，抛出去会把**最初那个业务异常整个替换掉** ——
日志和 `error` 字段会显示「删锁失败」而不是「content 连不上」。

## 十一、验证

### 11.1 三个降级场景（★ 每个都带「空」的对照臂）

**判定性判据：「失败」和「空」必须**能**被分开。** 所以每个场景都**同时**打两次：
一次打「真的没有数据」的对象，一次打「服务挂了」的同一路径 —— **两者渲染出来的东西必须不同**。
★ **只验后者的话，「降级生效了」和「本来就长这样」分不开。**

| 场景 | 「空 / 正常」臂 | 「失败」臂 | 分得开吗 |
|---|---|---|---|
| 停 **auth** → 列表作者名 | `authorName` 在场 | ★ **key 整个消失**，`total` 仍是 12 | ✅ |
| 停 **auth** → **按作者名搜索**（★ `:8082/internal/search`，不是 `/api/search`） | `keyword=墨白` → **200 total=0**；`keyword=测试作者` → **200 total=12** | ★★ **HTTP 500** | ✅ |
| 停 **interaction** → 评论 | **200 total=0** | **500 → 503**（★ 见下） | ✅ |
| 停 **interaction** → 收藏态 | **200 `onShelf=false`** | **500 → 503** | ✅ |
| 停 **interaction** → 管理端审核日志 | **200** | ★ **500**（**刻意**，见 §2.3） | ✅ |
| 停 **search** → 搜索页 | `keyword=修仙` → **200 total=0** → 「没有找到相关作品」 | ★★ **500 → 503** → 「搜索暂时不可用」 | ✅ |

★★★ **「500 → 503」不是笔误，是【两个窗口】** —— S11 复跑时第一次探到 500、S10 记的是 503，
两个都对，因为下游刚停时有**两个阶段**：

| 窗口 | Nacos 里的状态 | 网关给什么 | 判据（网关日志） |
|---|---|---|---|
| **前 ~10~20 秒** | 实例**还挂着**（心跳没过期），但**进程已经死了** | **500** | 路由解析得到一个死地址 → 连接被拒 |
| **之后** | 心跳超时，**注销** | **503** | `RoundRobinLoadBalancer - No servers available for service: novel-interaction` |

★ **实测**：interaction 那次 500 持续了 4 次探测（~10s），search 那次持续了 10 次（~20s）才转 503。
★ 两个窗口对**前端没有区别**（都不是 2xx → `failed` 为真 → 显示重试），
但**对复核的人有区别**：照着文档复现、立刻探到 500，会以为文档写错了。
**所以两个值都要写下来。**

★★★ **按作者名搜索那三行是同一条 URL、只有 auth 的存活状态在变**：

**URL = `GET http://localhost:8082/internal/search?keyword=<作者名>`**（直连 content，带 `X-Internal-Token`）。

| keyword | auth | HTTP | total |
|---|---|---|---|
| 墨白 | UP | 200 | 0 |
| 测试作者 | UP | 200 | **12** ← ★ 证明这条路径**真的在工作**，不是「反正都返回空」 |
| 墨白 | **DOWN** | ★ **500** | — |

★ **中间那一行是判据的判据**：没有它，「500 是刻意的不降级」和「这个接口本来就坏」分不开。

★★★ **一个 S11 复跑时踩到的坑，值得单独记：这条接缝【不能】用 `/api/search` 去验。**
第一版记录里我写的是走网关的 `/api/search?keyword=墨白` ——
**停掉 auth 之后它返回 200 + `total=0`，看起来像「降级生效了」，其实什么都没验到**：

| 端点 | 谁实现 | auth 挂了会怎样 |
|---|---|---|
| `:8080/api/search`（走网关） | **search 服务**，检索的是 **ES 文档** —— `authorName` **是文档里的一个字段** | ★ **200**，根本不调 auth |
| `:8082/internal/search`（直连） | **content 服务**，**MySQL `LIKE`** —— 靠 `userIdsByNickname` 把作者名换成 `author_id` | ★★ **500** |

★★ **两条路在「按作者名搜」这件事上恰好都能用（ES 里存了 authorName），
但只有一条依赖 auth。** 用错端点的话，测出来的是「ES 里确实有这个字段」，
而**被测的那条接缝一次都没被调用** —— 这正是铁律 8 的第一种形状（判据看着对、其实验不到），
只不过这次的「对照组」不是别的脚本，而是**另一个实现同一功能的端点**。

### 11.2 ★ 恢复：全部**无需重启**

三个服务停掉再拉起，**content 全程没有被重启过**（S11 复跑：PID `2792` 走完三个场景）：
- interaction 恢复后 —— 审核日志那一格立刻回到 200（**~8 秒**）
- search 恢复后 —— 搜索回到 200（**~6 秒**）

★★ **但「恢复」和「停」一样有那个窗口** —— 拉起来之后不能立刻断言，
因为**网关要等 Nacos 注册表刷新**。这也是 §11.2 下面那条纪律的现场。

★★ **踩到的坑：「端口在监听」不等于「网关能路由」。**
interaction 拉起来后 `/dev/tcp/127.0.0.1/8083` **立刻连得上**，
而经网关打同一个接口**仍然是 503** —— 因为 `lb://` 走的是 **Nacos 注册表**，
**注册发生在端口监听之后**。一秒后自己就好了。
★ 这是 CLAUDE.md 那条「『进程在』不等于『服务在』，看端口在不在监听」的**下一格**：
**「端口在监听」也不等于「已经注册进 Nacos」**。快速复验脚本必须**重试到 200**。

## 十二、踩坑

1. **★★ `ResultHttpStatus` 不作用于普通 `@RestController` 的返回值** ——
   `return Result.error(...)` 拿到的是 HTTP 200。要真 404 必须 `ResponseEntity.status(...)`。
2. **★ `@Qualifier` 写在 Lombok 字段上不生效**（本仓库没有 `lombok.config`）→
   按类型注入会撞上 Boot 的 `applicationTaskExecutor`（同样是 `ThreadPoolTaskExecutor`）→
   **启动失败**。→ 显式构造函数 + 参数上的 `@Qualifier`（`AiController` 的先例）。
3. **★ `elapsedMs` ≠ `finishedAt - startedAt`** —— 前者是 `RebuildReport` 自己量的重建耗时，
   后者还含排队与首跳开销（实测 4254ms vs 5458ms）。★ **两个都留着**：
   一个说「重建本身多慢」，一个说「从提交到拿到结果多久」。
4. **★★ 对照组必须和被测对象【同构】**（S8 第一版阳性对照 0/26 检出，见 §8.3）。
5. **★ `grep -c` 数 pom 会连注释一起数**（见 §11.4）。
6. **★ Windows console 的码页**：`curl | python -c "json.load(sys.stdin)"` 读中文会乱码
   （stdin 走 ANSI 码页）→ 必须先 `-o file` 再 `io.open(..., encoding='utf-8')`；
   **输出**同理，要打印中文得 `encode('unicode_escape')`。
7. **★ 对照臂要在对的时刻抓**：S10 第一次把「基线」跑在 interaction 已经停掉之后，
   于是对照组也拿到 503，**两个文件一模一样**。
