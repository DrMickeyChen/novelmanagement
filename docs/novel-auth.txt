novel-auth 面试问答
说明：基于当前项目代码整理。区分已经实现的机制与已知限制，不把开发演练说成生产实践。

一、模块职责与登录链路（必会）

问1：novel-auth 负责什么？
答：负责登录、注册、退出登录、用户资料、角色菜单、公告及作者申请等业务。网关负责统一入口和 JWT 验证，认证服务负责签发 JWT，并执行自身的接口权限与业务校验。

问2：一次登录的完整链路是什么？
答：前端提交用户名和密码，请求经过网关进入 AuthController。Controller 将 JSON 转为 LoginDTO 并校验参数，调用 AuthServiceImpl.login()。业务层查询 MySQL 用户记录，验证密码和账号状态，查询角色权限，生成 JWT，并把 LoginUser 保存到 Redis。最后返回 LoginVO，Controller 包装为 Result，前端收到 JSON 后保存 token。

问3：密码怎么验证？为什么不用 equals？
答：注册时用 BCrypt 生成密码哈希，数据库不存原始密码。登录时通过 passwordEncoder.matches(输入密码, 数据库哈希) 校验。BCrypt 使用随机盐，同一密码多次生成的哈希通常不同，不能重新 encode 后直接比较字符串。

问4：密码哈希与 JWT 签名有什么区别？
答：密码哈希用于检查输入密码是否正确；JWT 签名用于验证凭证内容是否被篡改。密码哈希不是可逆加密，JWT 签名也不是把内容加密，JWT 载荷通常可以读取。

问5：为什么用户名不存在和密码错误返回相同结果？
答：两者统一返回 1002“用户名或密码错误”，减少攻击者通过不同提示筛选真实账号的机会。后端日志仍记录具体原因。这只能减少通过错误响应枚举账号的机会，不能宣称消除了所有枚举途径。

问6：为什么账号禁用检查放在密码验证之后？
答：如果先返回“账号已禁用”，不知道正确密码的人也能确认该账号存在。先验证密码，再检查状态，可以避免通过这条提示绕过统一错误反馈。

二、JWT、Redis 与退出登录（必会）

问7：JWT 在哪里生成，包含什么？
答：AuthServiceImpl.login() 调用公共模块 JwtUtil.generateToken()，写入用户 ID、用户名、jti、签发和过期时间等信息，使用配置的密钥按 HS256 签名。角色权限不放进 JWT。

问8：前端怎样使用 JWT？
答：登录响应通过 LoginVO 返回完整 token。前端保存到 localStorage 的 novel_token，后续请求由请求拦截器添加 Authorization: Bearer <token>。JWT 密钥不返回给前端。

问9：网关如何验证前端 token？是与 Redis token 比较吗？
答：不是逐字比较两份 token。网关先用 JWT 密钥验证签名并检查有效期，再读取 userId 和 jti，查询 Redis 中对应的登录记录。验签通过且登录记录存在，才确认登录身份。

问10：Redis 存什么？LoginUser 和 LoginVO 有什么区别？
答：Redis key 为 novel:auth:token:{userId}:{jti}，value 是 LoginUser，包含用户信息、jti、角色和权限，并设置过期时间。LoginVO 则返回给前端，包含 JWT、token 类型、有效期和 UserVO。Redis 不保存这份完整 LoginVO 或完整 JWT。

问11：已经有 JWT，为什么还需要 Redis？
答：有效 JWT 本身无法表达“用户刚刚登出或被强制下线”。Redis 登录态使系统能主动撤销登录凭证。代价是每次有效凭证请求需要查询 Redis，认证链路增加了存储依赖，不再完全无状态。

问12：退出登录怎么立即生效？
答：根据当前用户 ID 和 jti 删除对应 Redis 登录记录。旧 JWT 即使签名正确且尚未过期，后续也查不到登录态，按匿名处理。前端还会清理本地 token，但只清理前端不能撤销后端凭证。

问13：为什么电脑和手机能同时在线？
答：每次登录生成不同 jti，Redis key 中包含这个编号。因此同一用户可以有多份独立登录记录，退出当前登录只删除对应的一份。

问14：角色修改、封号或密码重置后，旧 token 怎么办？
答：相关业务调用 TokenStore.removeAll(userId) 清除该用户的登录态，旧 token 不再被认可。用户重新登录时重新查询角色权限。不能只说“角色不放 JWT 就自动实时更新”，因为 Redis 中也是登录时的身份快照。

问15：批量清除登录态为什么用 SCAN，不用 KEYS？
答：KEYS 会一次扫描匹配键并可能造成长时间阻塞；SCAN 用游标分批处理。本项目用集合去重后删除。SCAN 不是并发快照，清理过程中新增的登录记录可能遗漏，当前实现不能保证与并发登录之间严格原子地全部撤销。

问16：Redis 暂时不可用怎么办？
答：网关查询登录态失败时返回 HTTP 500，而不是把故障解释为未登录并返回 401，避免前端清除有效登录信息。JWT 无效或登录记录不存在则按匿名转发，由下游判断该接口是否允许匿名。

问17：JWT 密钥为什么认证服务与网关必须一致？
答：认证服务使用密钥签名，网关用同一密钥验签。不同会导致签名验证失败。开发配置提供默认密钥，生产应使用外部配置；仅启用 prod 不会自动提供安全密钥。

三、注册、数据库事务与并发（必会）

问18：注册做了哪些操作？
答：检查用户名，组装 SysUser，对密码做 BCrypt 哈希，设置昵称和启用状态，插入 sys_user，再查 READER 角色并写入 sys_user_role，最后返回 UserVO。这个方法不生成 JWT，也不保存登录态，注册不等于自动登录。

问19：先查用户名不存在，为什么还会插入冲突？
答：两个并发请求可能都查到“不存在”，然后同时插入。前置查询用于友好提示，数据库 uk_username 唯一索引才保证唯一性。插入冲突捕获 DuplicateKeyException，转换为“用户名已被注册”。

问20：为什么注册需要 @Transactional？
答：创建用户与关联读者角色涉及两张表，必须一起提交或一起回滚。角色不存在或关联失败时，不能留下一个没有角色的账号。rollbackFor = Exception.class 将回滚范围设为 Exception 及其子类；异常需要经事务代理传播才能触发相应处理。

问21：Spring 事务什么时候可能不生效？
答：常见原因包括同类内部直接调用事务方法绕过代理、对象不是 Spring 管理、异常被吞掉等。本项目 Controller 调用 Spring 管理的 Service 实现是正常入口。事务主要保护同一数据库资源，不自动覆盖 Redis、磁盘文件或 RocketMQ。

问22：为什么注册角色写死为 READER？
答：角色由后端决定，RegisterDTO 不接受角色字段，避免用户提交 ADMIN 获得管理员权限。作者身份通过申请和审核获得。

问23：逻辑删除后为什么原用户名可能不能重新注册？
答：selectByUsername() 的手写 SQL 过滤 deleted = 0，查不到已删除用户；但数据库唯一索引仍可能包含该行的用户名。插入仍会冲突，当前实现将其转换为用户名已注册。

问24：MyBatis-Plus 的逻辑删除能自动过滤所有 SQL 吗？
答：不能。框架支持的生成操作会处理逻辑删除；本项目手写 selectByUsername SQL 必须显式加 deleted = 0。不能因为配置了 @TableLogic 就认为所有手写 SQL 都安全。

问25：DTO、Entity、Mapper、Service、VO 分别负责什么？
答：DTO 接收输入，Entity 对应数据库记录，Mapper 执行数据库访问，Service 执行业务规则，VO 组织输出。比如 LoginDTO 接账号密码，SysUser 保存查询记录，SysUserMapper 查表，AuthServiceImpl 验证登录，LoginVO 返回 token。

四、身份与权限边界（必会）

问26：认证与授权有什么区别？
答：认证确认“你是谁”，授权判断“你能做什么”。网关确认登录身份，下游 Security 配置检查接口角色，Service 继续检查归属、状态等业务条件。

问27：前端隐藏管理员按钮能保证安全吗？
答：不能。用户可以绕过页面直接请求接口。认证服务用 /api/admin/** 的 ADMIN 角色规则保护后台入口，并在业务层处理具体限制。

问28：项目实现了完整的细粒度权限码 API 鉴权吗？
答：没有。当前 AuthSecurityConfig 明确使用角色保护后台路径，菜单权限码主要用于前端显隐，不参与这里的 API 鉴权。可以描述角色与菜单管理，不能夸大为每个按钮对应严格的后端权限码校验。

问29：为什么业务接口不让前端传当前用户 ID？
答：用户可以篡改输入 ID。个人资料和作者申请等自己的业务，从 UserContext 取得后端确认的用户 ID，避免操作别人的数据。

问30：下游为什么能信任网关的身份头？
答：网关清除客户端传来的身份与内部令牌头，再写可信身份和共享内部令牌。下游 HeaderAuthenticationFilter 验证内部令牌后建立身份。生产还需要服务端口内网隔离；共享令牌泄露会削弱这个信任边界，不等同于 mTLS。

问31：/internal/** 配置 permitAll，是否代表完全公开？
答：不是。这里放行的是后续 Security 登录判定，内部令牌校验仍由 HeaderAuthenticationFilter 执行。应结合过滤器顺序理解，不能只看 permitAll 就判断接口无保护。

问32：/api/auth/me 与 /api/reader/profile 有什么区别？
答：/me 从 UserContext 中的登录身份生成用户返回值，不直接查 MySQL；个人资料接口会查询当前用户记录。Redis 登录快照与数据库最新资料可能存在差异，不能把 /me 描述成每次读取数据库最新信息。

问33：UserContext 为什么需要清理？
答：请求身份上下文使用线程相关存储，服务线程会复用。如果请求结束不清理，后续请求可能读取前一请求身份。切换到线程池也不能假定身份自动传播，应显式传递并清理上下文。

五、作者申请状态与并发（进阶）

问34：审核通过是否只修改申请状态？
答：不是。还要关联 AUTHOR 角色，并清除申请人的旧登录态，重新登录才能获得新角色。只改状态会导致页面显示通过，但用户仍进不了创作中心。

问35：两个管理员同时审核同一申请怎么办？
答：更新时同时限定申请 ID 和读到的前置状态，类似 UPDATE ... WHERE id = ? AND status = PENDING。先成功的修改状态，后一个影响行数为 0，则返回状态冲突。这是状态条件更新，不是仅靠 @Transactional，也不是使用 @Version 字段的乐观锁插件。

问36：重复审核是否幂等？
答：已经处于相同终态的重复操作按既有结果处理，不重复产生正常审核副作用；不允许将已通过直接改成驳回或反向改判。若两个并发请求都先读到待审核，后一个条件更新失败仍可能返回冲突，不能宣称所有重复请求都返回成功。

问37：授予作者角色时用户已经有 AUTHOR 怎么办？
答：用户角色唯一约束阻止重复关联，代码捕获重复键异常并跳过授予，因为用户成为作者的目标已达成。后续仍清理旧登录态。

问38：提交申请前查询没有待审核记录，能严格防止并发重复提交吗？
答：仅靠先查询再插入不能保证，并发请求可能都通过检查。当前 submit() 有前置检查，不能因此宣称实现了严格并发去重。若需要加强，可以设计数据库约束、用户级锁或原子状态记录，并验证相应边界。

六、RocketMQ 事务消息（进阶重点）

问39：novel-auth 的 MQ 用在哪里？
答：作者申请审核产生 AUDIT_RECORD 消息，由 AuthorApplyAuditProducer 发往 RocketMQ，内容服务 AuditRecordConsumer 消费后写 audit_log。它替代认证服务直接调用内容服务写流水，普通登录注册不依赖这条消息链路。

问40：为什么审核流水使用事务消息？
答：需要将本地审核数据库事务结果与消息是否可消费关联，避免审核回滚却留下“审核成功”的流水。它提供本地事务与消息可见性的协调，不是两个服务数据库的全局原子事务。

问41：这个项目怎样实现事务消息？
答：审核方法的数据库事务中先发送半消息，Broker 保存但暂不可消费；注册 Spring 事务回调，afterCommit 后发 COMMIT，回滚后发 ROLLBACK。数据库事务由审核 Service 执行，不是本类 executeLocalTransaction() 执行。

问42：为什么不能刚发完半消息就 COMMIT？
答：此时外层数据库事务可能还没提交。提前让消息可消费，可能先写出流水，然后审核事务回滚。项目把最终确认放到 afterCommit，确保本地事务已经提交。

问43：为什么没有直接用 sendMessageInTransaction()？
答：项目需要在外层 Spring 事务真正提交后再确认消息，而当前所用客户端版本的模板返回结果不保留延迟 endTransaction 所需的原始 offsetMsgId。实现自己发送半消息并保留原生 SendResult，供提交回调使用。这是当前版本与实现的具体取舍，不应概括为 RocketMQ 模板普遍不能使用。

问44：半消息发送失败怎么办？
答：让异常传播，审核数据库事务回滚，管理员收到失败结果。这样不允许审核已经成功却连待确认消息都没有留下。

问45：数据库提交成功，但 COMMIT 通知发送失败怎么办？
答：记录警告，等待 Broker 事务回查。回查读取 author_apply，检查结果状态和审核人是否与消息吻合。吻合返回 COMMIT，不吻合返回 ROLLBACK，数据库暂时不可用返回 UNKNOWN。回查受次数、服务可用性等条件限制，不是无限期绝对保证。

问46：为什么 afterCommit 中通知失败不继续抛异常？
答：数据库已经提交，抛异常不能撤销审核，却可能让管理员收到失败并再次操作。半消息已保存在 Broker，可走事务回查补充裁决，因此这里记录日志而不向调用方继续抛。

问47：事务消息是否保证流水立即出现、只出现一次？
答：不保证立即出现，也不提供业务层恰好一次。内容服务异步消费，故障或积压会延迟；重复投递要由消费端幂等处理。

问48：审核流水消费端怎样去重？
答：内容服务按 messageKey 使用 Redis setIfAbsent(key, "1", 24小时)，原子认领后写库；重复认领失败则跳过。写库抛异常时删除认领键再抛出，给重投留下机会。这里在 novel-content，不在 novel-auth。

问49：当前去重能保证严格不丢、不重吗？
答：不能。Redis 认领与数据库写入不是同一事务：认领后进程崩溃可能导致重投被跳过；数据库提交后未确认也存在重复处理边界；键过期或被淘汰后无法继续去重。可考虑数据库唯一业务键或消费记录与业务写入同事务等改进，当前代码不应宣称恰好一次。

问50：失败消息怎样处理？
答：当前审核流水消费者显式限制重试次数为 3，超限进入死信流程。还需要死信监控、告警和人工处置或重放机制；不能只说“有重试所以不会丢”。

七、资料、上传与运行边界（补充）

问51：头像现在存哪里？用了 MinIO 吗？
答：当前落在后端机器的 ${user.home}/novel-uploads/ 磁盘目录，数据库保存头像访问地址。认证服务写头像，互动服务提供 /uploads/** 文件访问，依赖共享目录。尚未接入 MinIO，跨机器或隔离容器部署需要共享存储或对象存储改造。

问52：头像上传有哪些检查？
答：校验空文件、扩展名、文件头魔数与类型匹配，并设置头像 2MB 限制。不能只凭文件名后缀认为文件可信。上传成功后由后端生成地址并更新用户记录。

问53：上传方法有事务，文件也会自动回滚吗？
答：不会。数据库事务保护数据库修改，不自动撤销磁盘文件。写文件后数据库失败可能留下孤儿文件；旧头像当前也不自动删除，需要补偿或清理策略。

问54：MySQL、Redis、MQ 放在哪里，Nacos做什么？
答：项目方案中间件运行在 Ubuntu 虚拟机 Docker 容器里，Java 服务在 Windows 主机运行。Nacos登记服务名与地址，网关发现地址后直接调用服务，业务请求不经 Nacos 转发。RocketMQ NameServer 提供 Broker 路由，Broker 接收和保存消息。

问55：哪些地方不能夸大？
答：不能说已实现 MinIO、所有接口细粒度权限码鉴权、MySQL与Redis统一事务、消息恰好一次、无限可靠回查、生产高并发指标。描述当前代码机制、开发验证范围和已知边界，改进方案应明确说是未来方案。
