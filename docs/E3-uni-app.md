## 一、判断 1：工具链被钉死，且比桌面端**老一个版本**

`@dcloudio/vite-plugin-uni` 的 `peerDependencies.vite` 是 **`"5.2.8"`（精确值，没有范围符）**，
它的依赖里 `@vue/compiler-*` 全部精确锁 **`3.4.21`**。于是移动端实际被钉在：

| | mobile-web | 对照：三端（`reader-web/package.json`） |
|---|---|---|
| vite | **5.2.8** | `^8.3.0` |
| vue | **3.4.21** | `^3.5.42` |
| sass | 1.77.8 | 同左 |
| `@dcloudio/*` | `3.0.0-5020620260917001`（**五个包，全部不含 `^`**） | —— |

★ **代价是真的：移动端不能用 Vue 3.5 的特性**（`useTemplateRef` 等），`<script setup>` 按 3.4 写。
★ 隔离靠「每端独立 `node_modules`」（根 `package.json` **没有 `workspaces`**，用的是 `npm --prefix`）
→ **不会互相污染**，这一点反而救了这次：R4 的「以为是 Vite 版本冲突 → 去改三端」是本期的头号误诊风险。

★★ **`@dcloudio/*` 的版本号禁止带 `^`**：npm 上这个包的 `latest` tag 指向的是 **Vue2 时代的旧线**，
带 `^` 会浮动到那儿去，症状是「装完起不来，而报错内容与版本毫无关系」。

**结构判据（不数个数，钉在结构上）**：

```bash
node -e "console.log(require('mobile-web/node_modules/@dcloudio/vite-plugin-uni/package.json').peerDependencies.vite)"
# → 5.2.8
node -e "const d=require('mobile-web/package.json').dependencies;
         console.log(Object.keys(d).filter(k=>k.startsWith('@dcloudio/')).map(k=>k+'='+d[k]).join('\n'))"
# → 五项的版本号都不以 ^ 开头
```

**Node 版本**（R6）：本机 **v24.16.0**；uni 模板 `engines` 写 `>=16`、Vite 5.2.8 要求 `>=20`
→ 24 满足。S1 实测能起（不是推断）。

## 二、判断 2：H5 的 `uni.*StorageSync` **就是 `localStorage`**，且**不加任何前缀**

读 `@dcloudio/uni-h5` 产物得到的结论（不是查文档转述）：`setStorageSync` 直接落到
`localStorage.setItem(key, value)`，**key 原样、无前缀**；并且
**非字符串值会被包成 `{"type":…,"data":…}` 之后再 `JSON.stringify`**。

而 `:3000` 这个 origin 下已经有三端的 `novel_token` / `novel_user`
（`reader-web/src/utils/auth.js:55,58`），且**同源共享登录态是本项目刻意的设计**
（`CLAUDE.md`：开发入口一律走 `:3000`，localStorage 按 origin 隔离）。

→ **两条规则，都写进了 `mobile-web/src/utils/auth.js` 的注释：**

1. ★★ **只写字符串**：
   `uni.setStorageSync(TOKEN_KEY, token)`（string → 原样存）、
   `uni.setStorageSync(USER_KEY, JSON.stringify(user))`（string → 原样存）。
   **写成对象就坏** —— 桌面端读出来是 `{"type":"object","data":{…}}`，登录态从此失效，
   **而两端都不报任何错**。
2. **key 沿用桌面端同款**（`novel_token` / `novel_user`）→ 在 `/reader/` 登录后打开 `/mobile/` 就是已登录。

### 阳性对照（做了一次，不是写在注释里的一句话）

故意用**对象**写 `USER_KEY` → `/reader/` 读出来是坏的（登录态失效，且无报错）。
★ 这条对照的价值在于：它证明「只写字符串」这条护栏**真的在起作用**，
而不是一句没人验过的注释（铁律 8）。

### 差分判据（对照组就在同一个浏览器里，成本为零）

- `/reader/` 登录 → `/mobile/` 已登录；反向亦然。实测登录后 `novel_user` 的形状是**裸对象（正确）**、
  键名与桌面端同款。
- **退出登录跨端生效**：从移动端点真按钮 + 弹窗上的「确定退出」→ `/reader/` 立刻变成未登录。
  ★ 这一条配了**成对的阴性对照**：同一份探针、同一页，**不点**时 token 仍在、页面仍是已登录；
  **点**了之后 token 没了、页面变成「还没有登录」。没有这组对照，「点完 token 没了」这句话
  **永远为真且与点击无关**（浏览器会话本来就不是每次都带 token）。

## 三、判断 3：同一个 localStorage 里，**进度要共用、设置要隔离**

桌面端阅读器在 localStorage 里放**两类**东西（`reader-web/src/utils/readerStorage.js`）：
`novel_reader_progress_{novelId}`（读到哪）、`novel_reader_settings`（字号 / 行距 / 主题）。

判据**不是**「都共用」或「都隔离」，而是 **「共用的收益是否大于互相踩的代价」**：

| 数据 | 处置 | 理由 |
|---|---|---|
| `novel_reader_progress_{novelId}` | **共用** ✓ | 「读到哪」跨端一致**是优点**（手机上读到一半，电脑上接着读） |
| `novel_reader_settings` | **隔离** ✗ → `novel_reader_settings_mobile` | 屏幕形态不同。共用的症状是「我在手机上把字号调大，**把电脑上的也改了**」，而且**没有任何提示** |

★ 验收用**差分判据**（两组对照都在同一个浏览器里）：
在 `/mobile/` 改字号 → `/reader/` 字号**没变**；在 `/mobile/` 读到第 3 章 → `/reader/` 的进度**跟着变了**。

★ **进度那半同时还有一个「两套真相」的问题**：桌面端只把进度写进 localStorage，
所以「换台电脑就没有进度」。移动端**同时写服务端**（`read_history`），
而**历史页读的是服务端那一份** —— 于是「只写本地」这个缺口在历史页上是**看得见的**。
实测：移动端读到第 3 章 → 服务端 `read_history` 出现一行（进度 46），
历史页渲染出 3 行且百分比与库里**逐行对得上**（独立算出来的期望值，不是从页面回读的）。

## 四、判断 4：「跨端」在没有小程序工具链时，只能按**结构性判据**验

不能声称「小程序端能跑」。**能验的是「源码遵守了跨端约束」**，而那是一个**静态判据** ——
静态判据必然踩铁律 8（**一条不会失败的护栏比没有护栏更糟**）。
所以自检脚本 `docs/tools/check-mobile-crossplatform.cjs` 的每一组检查都**自带对照**，
对照跑不过脚本整体就算失败 —— 因为「没报错」在这种情况下的含义是零。

| 判据 | 形式 | 实测 |
|---|---|---|
| A · 模板里不出现 `div` / `span` / `img` / `p` / `ul` / `li` | 只扫 `<template>` 块、剥掉 HTML 注释、按标签名匹配 | **命中 0** |
| B · 不出现 `axios` / `vue-router` / `element-plus` | `.vue` 只扫 `<script>`、`.js`/`.json` 扫全文件、**剥掉 JS 注释后**匹配 | **命中 0**（真依赖只有 `@dcloudio/*` + `pinia` + `vue`） |
| C · `#ifdef H5` 逐处记账 | 列出每一处，**它是跨端的真实代价、不是脏东西** | **全项目只有 1 处**（见下） |
| D · `window.` / `document.` 逐处列账 | **只列不判**（"附近有没有守卫"用正则判不准，会误报） | 10 处，逐条可读 |

### 阳性对照与反面对照（两样都要，缺一不可）

- **阳性**：脚本喂进人造违规（六个标签各一个 + `import axios from 'axios'`）→ 断言**全部被报**。
- **阳性（真树）**：往 `mobile-web/src/` 临时放一个含 `<div>` 与 `axios` 的 `.vue` →
  判据 A/B 各命中 1 并**点名那个文件**、退出码 1；删掉后回到 0 与退出码 0。
  ★ 这一步比人造输入更强：它证明的是**真实的扫描路径**（目录遍历、文件过滤、扩展名判断）没写错。
- **反面**：喂进**不该被报**的东西 —— `<video>` / `<scroll-view>` / 注释里的 `<div>` /
  `myAxiosWrapper` / 模板文本里的 `axios` → 断言**一个都不报**。
  ★ **会误报的判据和不会报的判据一样没用**，只是错的方向相反。

### ★★ 判据 B 的第一版**在真实源码上报出 6 处命中，全部是注释**

原句包括「桌面端是 `FormData` + `File`，走 axios」这种**在解释为什么这里不用它**的句子。
这与 M5 记的 `grep -rn "novel-content"` 是**同一个形状**（铁律 8 第三种形状：
**判据被自己的说明文字推翻**）——

> **本项目的注释密度是既定风格，于是任何「钉在词上」的判据都会迟早被注释绊倒，
> 而且每写一次说明就离通过更远一步。**

解药与 M5 相同：**换成差分式判据（和对照组比），或者把判据钉在结构上**（这里是「剥掉注释后的代码」）。

### ★ 写这段判据时，注释把代码写坏了（同一天的第二例）

`stripJsComments` 的文档注释里有一句要**逐字写出「什么会提前结束块注释」**，
而那个字面量本身必然含「星号 + 斜杠」两个字符 ——
**注释于是在它自己解释"什么会提前结束注释"的那一句上提前结束了**，
后面几行注释变成代码，`node` 报的错在 20 行之外的另一个字符上。

与 E1 的 `{{ '{{x}}' }}` 是**同一个病**：文字与代码混在同一个解析上下文里时，**文字会参与解析**。
本项目的三例（E1 的模板、M5 的 grep、E3 的这一条）应当作为同一类事故记着。

### `#ifdef H5` 的逐处记账（全项目 **1 处**）

| 位置 | 为什么必须条件编译 |
|---|---|
| `mobile-web/src/pages/applyAuthor/applyAuthor.vue:224-229` | 「进入创作中心」在 H5 上是**同源跳转**（`window.location.href = '/author/'`，dev 走 `:3000` 的 dev-proxy、生产走 Nginx）；小程序 / App 里**没有 `/author/` 这个页面**，只能提示「请在电脑浏览器中打开」。★ 这是本页唯一一处，也是一笔**真实的跨端代价**：同一个按钮在两个端上做的是不同的事 |

★★ 与之相对，`stores/user.js` 的跨标签页登录态同步**故意不用** `#ifdef H5`，而用
`typeof window !== 'undefined'` 的运行时判断：条件编译会把那段代码从非 H5 产物里**整段删掉**，
于是它「跑一下发现没有 window」的机会都没有；而运行时判断让「**零条件编译**」成为一个
**可验收的结论**，而不是一句声明。（判据 D 那个「只列不判」的清单就是它的账本。）

### `#ifdef APP-PLUS` 的逐处记账（全项目 **1 处**，E3 收尾时补）

★ 上面那张表记的是 `#ifdef H5`。这里补的是**当时漏掉的一处** ——
它不是"顺手加的"，是一次**真实故障**的修复，症状值得完整记下来。

| 位置 | 为什么必须条件编译 |
|---|---|
| `mobile-web/src/utils/request.js:147` | App（安卓 / iOS 原生运行时）**没有 origin 这个概念**，相对地址 `/api` 没有解析基准 → 请求直接失败。所以它必须和小程序一样拿绝对地址；★ 而**绝对地址必须是局域网 IP** —— 模拟器 / 真机上的 `localhost` 指的是**设备自己**，不是开发机 |

★★★ **故障原文（E3 收尾实测）**：这条分叉原来只有两支 ——
`#ifdef MP-WEIXIN` → `http://localhost:8080/api`，`#ifndef MP-WEIXIN` → `/api`。
**于是 H5 和 App 落在同一支里，都拿到相对地址 `/api`。** 这在 H5 上是对的（靠 `:3000` 转发），
在 App 上必然错。同一个"连不上后端"在三个端上是**三个不同的原因**：

| 端 | 表现 | 为什么 |
|---|---|---|
| 微信小程序 | **通** | 它走 `MP-WEIXIN` 支拿到绝对地址；★ 更关键的是**小程序不是浏览器、不受 CORS 约束** —— 这一条解释了"为什么只有它通" |
| H5 | 不通 | 它假设有同源转发，而当时是从 HBuilderX 直接起的 5176（`:3000` 没起、5176 上没有 `/api` 转发） |
| App | 不通 | 相对地址没有解析基准，**修好 H5 那一半也对它无效** |

★ 所以这一处踩的是**两个独立的坑叠在同一个症状上**，只修一个端仍是"连不上"——
而这个词对三者完全一样，没有报错文本可区分。

**修法与它的实测判据**（`#ifdef APP-PLUS` 一支 + 内层嵌套 `#ifndef`）：
判据用 uni 自己的条件编译预处理器跑真实源码
（`@dcloudio/uni-cli-shared/dist/preprocess` 的 `initPreContext(platform)` + `preJs(code)`），
**不需要真机**：

| platform | 拿到的 `DEFAULT_API_BASE` |
|---|---|
| `h5` | `/api` |
| `mp-weixin` | `http://localhost:8080/api` |
| `app` | `http://192.168.1.189:8080/api` |

★ **两个对照都跑了**，因为"结果看起来对"不算验过（铁律 8）：
- **差分对照**：把**改动前**那段分叉喂进同一个探针 → `app` 拿到 **`/api`**，
  **故障在探针里复现**。这才证明探针能分辨平台，而不是三个平台都返回同一份文本；
- **阳性对照**：把内层 `#ifndef APP-PLUS` 删掉 → 块数从 1 跳到 **3**，
  且预处理器当场报「条件编译失败：`#endif` 缺少配对」。→ 嵌套那两行是**承重的**，
  写错会被发现。

★★ **为什么用嵌套 `#ifndef` 而不是 `#ifndef MP-WEIXIN || APP-PLUS`**：
后者的求值方向（「非 A，或 B」还是「非 (A 或 B)」）本项目**没有实测过**，
而猜错的后果是**静默的** —— H5 会拿到绝对地址，于是从「同源」变成「跨域」→ 403，
而 403 长得像后端问题。多两行换掉一个"猜"。

★ **App 侧那个地址是 dev 专用值**（`192.168.1.189` = 本机实测局域网 IP，换网络就变）。
它写在源码里是因为 **HBuilderX 不经过 npm 脚本**、Vite 的 mode 只取 `NODE_ENV`（不带平台名），
所以 `.env.[平台]` 在 HBuilderX 里永远不会被加载 —— 与上面小程序那条**同因**。
真要发 App 仍走 `VITE_API_BASE=https://域名/api` 覆盖。
★ 顺带：这一改让 `assetUrl()` 也一起对了（它从绝对 `API_BASE_URL` 里剥出 origin，
见判断 5 末段），头像那类根相对 `/uploads/**` 不用改第二处。

## 五、判断 5：★★★ uni-app 的 H5 运行时会**按 `router.base` 重写根相对地址**

**这是本期最贵的一个坑**，值得单独成章，因为它的症状会把人引到完全错误的方向。

### 机理

后端 `sys_user.avatar` 存的是 `/uploads/avatar/2026/09/25/xxx.png` —— 一个**根相对**路径。
直觉上它应该能用：根相对路径由浏览器按 origin 解析。桌面端就是这么用的。
**这个直觉在 uni-app 的 H5 上是错的。** 源码在 `@dcloudio/uni-h5` 的 `getRealPath()`：

```js
if (filePath.indexOf('/') === 0) {              // 根相对
  if (filePath.indexOf('//') === 0) { filePath = 'https:' + filePath }
  else { return addBase(filePath.slice(1)) }    // ← 就是这一行
}
```

而 `addBase` 就是 `router.base + 路径`。本工程 `base = '/mobile/'`，
于是 `/uploads/x.png` 被改写成 **`/mobile/uploads/x.png` → 404**。

### 为什么症状极具误导性（这是重点）

`@error` 把 `avatarBroken` 置真 → `v-if` 换回首字占位 →
**`uni-image` 元素被从 DOM 里整个摘掉**。于是探针看到的是「页面里 `uni-image` 数为 0」，
读起来像**「图根本没渲染」**，真相是**「渲染了、加载失败了、被替换掉了」**。
**这两件事的修法完全不同。**

### 分清它们靠的是浏览器自己的账本，不是页面代码的自我报告

```js
performance.getEntriesByType('resource').filter(e => e.name.includes('/uploads/'))
// → ["http://localhost:3000/mobile/uploads/avatar/.../7d038959....png"]   ← 多了 /mobile/
```

★★ **而同一份输出里还有一条「修好没修好都是 200」的伪判据**：
`fetch(url)`（url 就是那个根相对路径）**在修之前也是 200** ——
因为 `fetch` 按 origin 解析，**绕过了 uni 的重写**。它单独用等于没验。
这条伪判据被**刻意保留**在探针 `s6-avatar-fixed.js` 里当反面对照：
**页面代码会把自己的失败渲染成"另一种正常状态"，看不出破绽；只有浏览器自己的记录不会。**

### 修法与它的判据

新增 `mobile-web/src/utils/asset.js`，唯一一个地址拼装点：

- `API_BASE_URL` 是**绝对**地址（小程序 / App 的构建方式）→ 去掉 `/api` 就是 origin；
- H5 + 相对配置（开发与生产的默认形态）→ **只有浏览器知道 origin**，取 `window.location.origin`；
- 非 H5 + 相对配置 → **没有正确答案，原样返回**（如实的失败，不假装成功 —— 铁律 10）。

★ 旧写法（`API_BASE_URL.replace(/\/api\/?$/, '')` 再拼）**在配了绝对地址时是对的**，
在默认配置下**悄悄退化成了空串**，而两种配置的产物在页面上**看不出区别**（都要等到图片 404）。
这正是它当初没被发现的原因。

**修完的实测（两处判据，来自两个不同的信息源）**：

```
.avatar的HTML           → <uni-image class="avatar"> … background-image: url("http://localhost:3000/uploads/avatar/…png")
是首字占位吗             → false
uni-image元素数          → 1        （渲染）
取过uploads的请求        → ["http://localhost:3000/uploads/avatar/…png"]   ← 没有 /mobile/ 了
还有没有/mobile/uploads  → false
取到了几个字节           → [136]    （加载：正是那个 136 字节的夹具）
```

★ `assetUrl` 另有 **9 例手写对照**（空 / `null` / 根相对 / 无斜杠相对 / `http` / `https` /
协议相对 `//` / `blob:` / `data:`），**期望值是手写死的、不是从函数里算出来的** ——
否则测试只会复述实现。9/9 通过。
★ 其中 `blob:` 那一条尤其要紧：`uni.chooseImage` 在 H5 上给的 `tempFiles[i].path`
就是一个 `blob:` 地址，**给它补 origin 会直接毁掉**刚选中的文件预览。

### 顺带：这个坑在 mobile-web 里只有**一个**消费者

全项目 `mobile-web/src/` 里 `<image>` 只出现 **1 次**（`profile.vue` 的头像），
书架 / 历史 / 首页的卡片是**纯文字卡、不渲染封面**（也没有任何 CSS `url()`）。
所以 blast radius 是 1 —— **但这条规则本身是普遍的**，任何要交给 `<image>` 的后端路径都适用。
哪天真把文件挪到对象存储（那是另一个域名），改 `asset.js` 一个函数即可。

## 七、踩坑（工具链与验收手法）

### 坑 1 ★★★ Chrome 只在**用户激活**时才打开文件选择框

`uni.chooseImage` 在 H5 上是「创建 `<input type="file">` → 挂到 body → `.click()`」。
用页面里的 `el.click()` 触发时，**元素确实被创建、也确实被点了（`isConnected=true`），
但 `change` 事件永远不来** —— 因为那是**不可信事件**，Chrome 拒绝为它打开选择框。
（uni 自己的源码里就有一句 `uni.chooseFile.notUserActivation` 的告警。）

**处置**：给 CDP 驱动加一条**真点击**通道（`Input.dispatchMouseEvent` 的
`mouseMoved` + `mousePressed` + `mouseReleased`），并开
`Page.setInterceptFileChooserDialog` + `DOM.setFileInputFiles` 挂文件。
★ 教训：**「点了没反应而且不报错」这类症状，先怀疑事件可信度，别先怀疑代码。**

### 坑 2 ★★ uni-app 的 H5 深链在 **history 模式**下不能写成 `#/pages/x`

`manifest.json` 的 `h5.router.mode` 是 **`history`**，所以正确形式是
`http://localhost:3000/mobile/pages/profile/profile`。
写成 `http://localhost:3000/mobile/#/pages/profile/profile` 时，
**hash 被忽略、路由落到首页、页面正常渲染** ——
于是「我的」页的探针在看到首页 DOM 后报「`.avatar` 是 null、`uni-image` 为 0」，
**看起来完全像"刚修的 bug 没修好"**。
★ 判据要钉在**挂载的页面**上（`uni-page[data-page]`），不是钉在 URL 上 ——
单页应用里 URL 变了不等于页面渲染了。

### 坑 3 ★★ `uni.chooseImage` 的 `sizeType: ['compressed']` 在 H5 上是**空操作**

H5 实现里那一行被注释掉了，所以「压缩」不发生，2MB 上限是**真的会被手机原图撞到**的。
（这是后端 `ImageKind.AVATAR` 的限制，不是前端随手定的。）

### 坑 4 ★★ 上传前那个「扩展名白名单」检查曾**必然误报**

旧代码用 `(file.path || '').split('.').pop()` 取扩展名，
而 H5 上 `file.path` 是 **`blob:` 地址**（`URL.createObjectURL` 的产物，没有扩展名），
于是**每一张图都会被拒**，理由还是一句看着很合理的「只支持 JPG / PNG / WEBP」。
正确做法是取 `file.name`（真实文件名），并且**取不到扩展名时放行**（真正的拒绝在后端，铁律 6）。
★ 教训：**同一段代码在两个端上跑，字段的含义可能完全不同** —— `path` 在 App 端是文件路径，
在 H5 上是一个 URL。换端时这类字段是重灾区。

### 坑 5 ★ `uni.uploadFile` 是**唯一**一条不走 `request()` 的通道

它自己拼 multipart（**不该**设 Content-Type）、Authorization 要自己加、
响应体是**字符串**（要自己 `JSON.parse`）、**同样把 4xx/5xx 放进 success**（R5 在它身上照样成立）。
★ 所以 `API_BASE_URL` 被**导出**：导出的是**已经算好的值**，不是让调用方再读一次
`import.meta.env` —— 两处各读一次的话默认值 `'/api'` 就要写两遍，迟早有一处被改掉。

### 坑 6 ★ 两次真点击之间必须等一会儿（驱动已支持 `|` 串起多次点击）

「退出登录」先弹 `uni.showModal`，要再点弹窗上的「确定退出」才真的退出。
弹窗是**上一步点击之后**才进 DOM 的，同一帧里找它的选择器一定是 `null`。

### 坑 7 ★ 页面里的 `@error` + `v-if` 会让「元素数 0」有两义（见判断 5）

**「没渲染」和「渲染了但被替换掉」在元素计数上完全一样。**
分开它们要用 `performance.getEntriesByType('resource')`（浏览器账本），
或者用 `@error` 之外的状态位（如 `avatarBroken`）——但后者是页面自述，可信度低一档。

### 坑 8 ★ `uni-text` 的 `clientHeight` 在父元素不是 flex/block 容器时是 0

与 M4/M5 那批「量不到 ≠ 不存在」的坑同族：**量到的 0 要先问一句「这个 0 说明得了什么」。**

## 九、明确不改

| 不动的 | 理由 |
|---|---|
| **12 个锁定文件** | 铁律 2。移动端**不复制**它们 —— 它有自己的四件套（`axios` → `uni.request`、`localStorage` → `uni.*StorageSync`、`html/body/#app` 选择器在 uni 里不存在），逐字节复用**做不到**。替代它的是判断 2/3 的**协议兼容判据**（同名 key + 只写字符串 + 同形状 JSON），那才是铁律 2 想保住的东西 |
| **后端全部** | 网关是唯一入口，三端怎么走移动端就怎么走。`/api`、`/uploads`、网关路由、Nginx 的 `/api` 段**一行都不动** |
| **三端的 `request.js` / 401 策略** | 两套 401 策略是**设计不是债**（读者端跳走会丢稿）—— 移动端照抄这套语义，不「顺手统一」 |
| **`reader-web` 本身** | 它已经能手机用（诚实 2）。E3 是**新增一个客户端**，不是替换它 |
| **`ai_*` 六张表与 AI 端点** | 只做读者端 → 移动端不碰 AI |

**不做的事**：① 小程序 / App 端验收 ② 作者端与 AI ③ 阅读器的选中抑制（`text` 组件不长按选中）
④ 把 `reader-web` 改成共用组件库（三端 element-plus / 移动端 uni 内置组件，是这次拆分的既定代价）
⑤ 推送 / 离线缓存 / 本地书架（PWA 那套，超出范围）。
