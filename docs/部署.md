# 生产部署

> **开发期怎么跑**看根目录 [README.md](../README.md)；**中间件怎么搭**看 [环境配置.md](环境配置.md)。
> 这一份只讲「怎么把它放到一台服务器上，让别人能访问」。

## 一、拓扑：生产 Nginx 就是开发期的 dev-proxy

三端登录态共享靠的是 **localStorage 按 origin 隔离**这个浏览器规则 —— 三个应用必须**同域**。
所以生产用 Nginx 按路径把三个前端分发到同一个域名下，**和开发期 `dev-proxy` 做的事逐条对应**：

| 路径 | 开发期（`dev-proxy/vite.config.js`） | 生产（Nginx） |
|---|---|---|
| `/reader/` | → `localhost:5173`（Vite HMR） | → `reader-web/dist` 静态文件 |
| `/author/` | → `localhost:5174` | → `author-web/dist` |
| `/admin/` | → `localhost:5175` | → `admin-web/dist` |
| `/api/` | → `localhost:8080` | → 网关 `127.0.0.1:8080` |
| `/uploads/` | → `localhost:8080` | → 网关 `127.0.0.1:8080` |

> ★ **M0 起 `:8080` 是网关，不是后端**（后端退到内部端口，不再对外；M1 拆出 `:8081`，M2 又拆出 `:8082` / `:8083`）。
> 四个进程里**只有网关对外**，`:8081` / `:8082` / `:8083` 必须只对内网或只绑 `127.0.0.1`。
> ★ 这张表**一行都不用改** —— 这正是把网关放在 8080 而不是另开端口的原因：Nginx、
> `dev-proxy`、三个前端的 `request.js` 里写的都是 8080，而 8080 上确实还有东西在接。
> 网关再去 Nacos 问 `novel-auth` / `novel-content` / `novel-interaction` 现在在哪
> （`lb://novel-auth` / `lb://novel-content` / `lb://novel-interaction`），
> 所以第二期每摘一个服务，Nginx 和前端**都不用动**。

★ **这张表就是「开发期拓扑 == 生产拓扑」那句话的全部含义。**
它的价值是：任何「只在部署后才暴露」的问题（路径前缀、SPA 回落、跨域、登录态读不到）
在开发期就已经暴露过了 —— 因为你每天开发时走的就是同一套路径。

★ **改 Nginx 配置时对照着 `dev-proxy/vite.config.js` 改**，两边不要出现「生产多了一条、
开发没有」的规则。那种差异不会报错，只会让某个功能**只在上线后**坏掉。

## 二、构建前端

### ★ 先改网关地址（这一步漏了，前端会连到 localhost）

三端的 `VITE_GATEWAY_URL` 目前只在 `.env.development` 里，值是 `http://localhost:3000`。
**Vite 是在构建时把 `import.meta.env.VITE_*` 内联进产物的** —— 不改的话，构建出来的
JS 里写死的就是 `http://localhost:3000`，部署上去所有人的浏览器都会去连**自己的** localhost。

给三个前端各建一个 `.env.production`：

```bash
# reader-web/.env.production、author-web/.env.production、admin-web/.env.production
VITE_GATEWAY_URL=https://你的域名
```

> ★ **`VITE_READER_WEB_URL` 留空**即可，`utils/auth.js` 会自动取
> `${VITE_GATEWAY_URL}/reader/`。三个应用这一项必须指向**同一个**地址（401 统一跳阅读端登录页），
> 留空是保证它们一致的最省事做法。
>
> ★ 要填的话**必须以斜杠结尾**：`https://域名/reader/` 对，`https://域名/reader` 会 404。
>
> ★ `utils/auth.js` 和 `utils/request.js` 是 **md5 锁定的 12 个文件之二**，任何一期都不许改 ——
> 所以换域名只能靠环境变量，不能去改代码。

### 打包

```bash
npm run install:all
npm run build          # 三端依次打包，产物在各自的 dist/
```

产物结构（`base` 决定了资源引用前缀，不用手工改）：

```
reader-web/dist/   →  挂到 /reader/
author-web/dist/   →  挂到 /author/
admin-web/dist/    →  挂到 /admin/
```

> ★ **不要在某个子项目跑着 `vite dev` 的时候打包** —— 会争 `node_modules/.vite`，把 dev server 搞崩。

## 三、Nginx 配置

按上面的对照表逐条写。放在 `/etc/nginx/conf.d/novel.conf`：

```nginx
server {
    listen       80;
    server_name  你的域名;

    # 前端产物放在这里：/var/www/novel/{reader,author,admin}/
    root /var/www/novel;

    # ---------- 后端 API ----------
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # ★ AI 写作助手是 SSE 流式响应，这三条少了会「整段憋完才一次性吐出来」
        proxy_buffering    off;
        proxy_cache        off;
        proxy_read_timeout 300s;
    }

    # ---------- 上传的文件（封面 / 头像）----------
    # 走后端，和开发期一致。后端有 /uploads/** 的静态资源映射。
    location /uploads/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        # 上传的文件内容不会变（文件名带 UUID），可以放心让浏览器缓存
        expires 30d;
    }

    # ---------- 三个前端 ----------
    #
    # ★★ `try_files ... /reader/index.html` 这段【不能省】：
    #   三个应用都是 SPA，「路由」是前端自己管的 —— 刷新 /reader/novel/123
    #   时，服务器磁盘上【没有】这个文件（只有 index.html）。
    #   不写回落就是 404；写了才是「不管什么子路径，都给 index.html，让前端路由去解析」。
    #   ★ 而 base 前缀（/reader/）是必须的：Vite 打包时资源引用写的是 /reader/assets/xxx.js，
    #     产物目录挂错位置会全部 404 —— 页面一片空白，控制台一堆 404。
    #
    # ★★ 这里【用 root 而不用 alias】。上面 server 段的 `root /var/www/novel;`
    #    已经够了：location 是 /reader/，请求 /reader/assets/a.js 拼出来正好是
    #    /var/www/novel/reader/assets/a.js —— 和产物目录结构天然对上。
    #    写成 `alias /var/www/novel/reader/;` 看着更「直接」，但 alias 与
    #    try_files 的组合在 nginx 里是出了名的边界情况多（alias 会把 location
    #    前缀整个替换掉，try_files 拼路径时的基准跟着变），轻则回落失效、
    #    重则 rewrite 循环 500。**没有必要去趟这个雷**。

    location /reader/ {
        try_files $uri $uri/ /reader/index.html;
    }

    location /author/ {
        try_files $uri $uri/ /author/index.html;
    }

    location /admin/ {
        try_files $uri $uri/ /admin/index.html;
    }

    # 访问根路径 → 给个入口（可选）
    location = / {
        return 302 /reader/;
    }
}
```

### 可选优化：让 Nginx 直接发上传的文件

上面 `/uploads/` 是转发给后端的（**和开发期一致，推荐先用这个**）。
文件量大了可以改成 Nginx 直接读磁盘 —— 少一次进程间转发：

```nginx
location /uploads/ {
    alias /srv/novel-uploads/;     # ★ 必须等于后端的 novel.upload.path
    expires 30d;
}
```

★ 改了这里，**后端的 `novel.upload.path` 和 Nginx 的 `alias` 必须是同一个目录** ——
对不上就是「上传成功但图片全是裂图」，而且后端日志里一切正常。

### HTTPS

三个应用同域，证书按常规配即可（certbot 最省事）。
★ 上线后记得把 `.env.production` 里的 `VITE_GATEWAY_URL` 换成 `https://` 并**重新构建** ——
构建时内联，改域名必须重打。

## 四、后端

### 打包

```bash
mvn -Dmaven.repo.local=<你的本地仓库> -f backend/pom.xml package
# 产物【五个】（M0 起是 Maven 多模块，一次打包出五个可执行 fat jar + 一个库 jar）：
#   backend/novel-gateway/target/novel-gateway.jar          ← 网关，监听 :8080（唯一对外入口）
#   backend/novel-auth/target/novel-auth.jar                ← auth，监听 :8081（M1 新增）
#   backend/novel-content/target/novel-content.jar          ← 内容服务，监听 :8082（M2 新增）
#   backend/novel-interaction/target/novel-interaction.jar  ← 互动服务，监听 :8083（M2 由 novel-backend 改名）
#   backend/novel-search/target/novel-search.jar            ← 搜索服务，监听 :8084（★ M4 新增）
#   backend/novel-common/target/novel-common-1.0.0.jar      ← 库，【不是】可执行 jar，不部署
```

★ **必须在后端停掉的时候打包** —— jar 正在运行时 `repackage` 会失败，并留下一个**瘦 jar**
（没有依赖，`java -jar` 起来就报 `NoClassDefFoundError`）。这个失败是静默的，很容易带着瘦 jar 上线。

★ **五个 jar 都要部署、都要起**，每个少了的症状都不一样：
少网关 → `:8080` 上没有任何进程，Nginx 转发过去就是 **502**（看起来像后端挂了）；
少 auth → **登录全挂**，而且匿名首页也 500（首页要调 auth 取作者昵称）；
少 content → 作品/章节分类/审核/AI 全 **503**，评论区还是好的；
少 interaction → 评论/书架/历史全 **503**，而**书架和历史的列表还会 500**
（它们要反过来问 content 要书名 —— 这是 M2 造出的那条 `content ⇄ interaction` 环的直接后果）；
少 search → ★ **搜索接口全 500**（不是 503 —— 见下），**而且降级路径也不在了**
（降级是 search 内部的行为，不是网关的），而其它接口一切正常。

★★ **为什么少 search 是 500 而不是 503**（M4 实测）：进程没了，但 **Nacos 摘除是滞后的**，
实例还挂在注册表里 → 网关照样拿到实例去连 → `Connection refused` → 兜成 **500**。
**503 的语义是「一个实例都没有」，停一个进程到不了那个状态。**
★ 所以验收判据要写成「**非 2xx**」，别写死 503 —— 写死的话，下一个人跑出 500 会去查「路由是不是没配好」。

★★ **生产必须只暴露 `:8080`**。`:8081` / `:8082` / `:8083` / `:8084` 要走防火墙 / 安全组 / 只绑 `127.0.0.1`，
**绝不能对外**。M1 的共享密钥（`X-Internal-Token`）只是第二道锁 ——
它挡的是「误配暴露」，不是「有备而来的攻击者」。第一道锁永远是网络隔离。
★ **`INTERNAL_TOKEN` 在 M4 之后必须六处一致**：网关 + 四个业务服务 + 手工 curl 的头。
少配一处，那个服务就把所有请求当**匿名**（症状是全站 401），或者把兄弟服务的调用当伪造（症状是 `/internal/**` 403）。

★★★ **ES 也必须只对内网开放，而且生产不能沿用 dev 的 `xpack.security.enabled: false`** ——
`docs/docker/docker-compose.yml` 里那一行自己就写着「生产环境绝对不能这么配」。
M4 沿用了 dev 配置（**这是刻意的**，见 `docs/M4-摘出search.md`），
但**上线前必须开安全并配口令**，否则任何人 `curl :9200/_search` 就能把全站作品拖走。

### 配置

`application.yml` 里 `spring.profiles.active` 默认是 `dev`，生产用命令行覆盖：

```bash
java -jar novel-gateway.jar     --spring.profiles.active=prod   # 网关，:8080
java -jar novel-auth.jar        --spring.profiles.active=prod   # auth，:8081
java -jar novel-content.jar     --spring.profiles.active=prod   # 内容服务，:8082
java -jar novel-interaction.jar --spring.profiles.active=prod   # 互动服务，:8083
java -jar novel-search.jar      --spring.profiles.active=prod   # 搜索服务，:8084（★ M4 新增）
```

★★ **ES 地址走 `ES_URIS` 环境变量**（`spring.elasticsearch.uris: ${ES_URIS:http://192.168.127.137:9200}`）。
★ **不配不会报错，只会静默连 `localhost:9200`**（只有一行 INFO，没有 WARN）——
症状是「服务起得来、接口有响应，但检索永远走降级路径」。
**生产上必须显式 export `ES_URIS`。**
★★ **生产也要用自建镜像**（`docs/docker/Dockerfile-es`），不能用 `docker.elastic.co` 的官方镜像 ——
官方镜像**不含 IK 中文分词器**，没有它中文会被切成单字，而且**不报错**。

★★ **M1 起网关也必须写 `--spring.profiles.active=prod`** ——
M0 时网关只有一个 `application.yml`，所以那会儿这条参数可以省；
**M1 给网关加了 `application-dev.yml`**（装 Redis 口令、JWT 密钥、共享令牌的 dev 默认值），
而 `application.yml` 里 `spring.profiles.active` 默认是 **`dev`**。
漏掉这条参数的后果：网关在生产拿 dev 默认值去连 **`192.168.127.137` 的 Redis** ——
连不上时它不是启动失败，而是**每个请求都 500**（见 `JwtAuthGlobalFilter` 的 Redis fail-closed），
看起来像「全站挂了」而不是「配置错了」。

★ 三个业务服务都必须**注册进 Nacos**（`spring.cloud.nacos.discovery.server-addr` 指向生产 Nacos），
否则网关的 `lb://novel-auth` / `lb://novel-content` / `lb://novel-interaction` 找不到实例，
`:8080/api/**` 全部返回 **503** —— 而 503 在浏览器里看起来就像「服务挂了」。四个 jar 的 `application.yml` 里都有这段配置。

★ **生产环境要改掉 Nacos 的默认账号** `nacos`/`nacos`（容器自带演示值），
四个服务的 `discovery.username` / `.password` 都要改。

★ **M2 起要新建【四个】`application-prod.yml`**（四份都**已被 `.gitignore` 忽略**，
不会误提交 —— 真实密码就该待在这里，不要写进 `application.yml`）：

| 文件 | 装什么 |
|---|---|
| `novel-content/src/main/resources/application-prod.yml` | 数据源 + Redis + Nacos + **`rocketmq.name-server`** + `novel.upload.path` + 关文档 |
| `novel-auth/src/main/resources/application-prod.yml` | 同上，**`novel.upload.path` 必须是同一个值**（见下）。★ 它的 `rocketmq.producer.group` 是 **`novel-tx-audit`**（事务组，和另外两个不同，别抄错） |
| `novel-interaction/src/main/resources/application-prod.yml` | 数据源 + Redis + Nacos + **`rocketmq.name-server`** + **同一个 `novel.upload.path`**（`/uploads/**` 由它对外提供） |
| `novel-gateway/src/main/resources/application-prod.yml` | Redis + Nacos（网关没有数据源、不碰文件，**M3 起也不连 MQ**） |

★ **M3 起中间件多一个 RocketMQ**，但它**不是第五个进程** —— 它是中间件，
和 MySQL / Redis / Nacos 一样部署在虚拟机上。三个业务服务各自连它，
**网关完全不连**（决定 4，理由见 `docs/M3-引入MQ.md` 判断 G）。

★★ **`novel.upload.path` 在 auth / content / interaction 三处必须写成同一个绝对路径**：
头像由 **auth** 写盘、封面由 **content** 写盘，而 `/uploads/**` 由 **interaction** 提供
（网关把那条路由指给了它）。
两边不一致的症状是**「上传成功但图片全是裂图」**，而且三个服务的日志里一切正常 ——
没有任何一处会报错。这是共享库决策带来的连带约定，见 `docs/M1-摘出auth.md` R10。

> ⚠️ **这一条在生产容器化时会失效**：三个服务各自有自己的文件系统，
> 写在一个容器里的封面，另一个容器读不到 → 404。M1/M2 **接受**这个限制（记为 M5 债：
> 接 MinIO/OSS，或把 `/uploads/**` 按 `cover`/`avatar` 子路径拆开各自服务）。
> 单机裸 jar 部署（本文档这套）没有这个问题 —— 三个进程共享同一个绝对路径目录。

`novel-content` 那份至少要有：

```yaml
spring:
  datasource:
    url: jdbc:mysql://<生产库地址>:3306/novel?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&useSSL=false
    username: <生产库账号>
    password: <生产库密码>
  data:
    redis:
      host: <生产 Redis>
      password: <生产 Redis 密码>

  # ★ M0 起业务服务要注册进 Nacos（M1 起是 auth + 内容服务两个），网关才找得到它们
  cloud:
    nacos:
      discovery:
        server-addr: <生产 Nacos>:8848
        username: <改掉默认的 nacos>
        password: <改掉默认的 nacos>
        # ★ 多网卡机器（装了 Docker / VMware / Hyper-V）必须显式指定注册上去的 IP，
        #   否则注册的是虚拟网卡地址，网关连不上 —— 症状是 503，看起来像路由配错了。
        #   单网卡的生产机器可以省掉这一行。
        # ip: <本机内网 IP>

novel:
  upload:
    # ★★ 必须是【容器/服务器上的绝对路径】，绝不能落在 jar 里或 resources/static/ 下
    #    —— 见 docs/P4 的 D-10：上传目录在应用目录里，重新部署一次就全丢了。
    path: /srv/novel-uploads/
    url-prefix: /uploads/

# ★ 生产环境关掉接口文档（Knife4j 会把全部接口和数据结构暴露出去）
springdoc:
  api-docs:
    enabled: false
  swagger-ui:
    enabled: false

logging:
  level:
    root: info
    com.novel: info
```

### 环境变量

| 变量 | 必需 | 说明 |
|---|---|---|
| **`JWT_SECRET`** | ★★ **必需** | JWT 签名密钥。**长度必须 ≥ 32 字节**（HMAC-SHA256 的要求，短了 jjwt 直接抛 `WeakKeyException`）。生成：`openssl rand -base64 48` |
| **`INTERNAL_TOKEN`** | ★★ **必需**（M1 新增） | 服务间共享密钥，走 `X-Internal-Token` 头。**M4 起四个业务服务 + 网关都要配成同一个值**。生成：`openssl rand -base64 48` |
| **`ROCKETMQ_NAME_SERVER`** | ★★ **必需**（M3 新增） | RocketMQ 的 namesrv 地址，形如 `<broker 主机>:9876`。★ **M4 起是四个**：auth / content / interaction / **search**（网关不用 —— 它没有 MQ 依赖，见 `docs/M3-引入MQ.md` 判断 G）。★ 和上面两个同样是 `${ROCKETMQ_NAME_SERVER}`、**没有默认值**，不配就启动失败 |
| **`ES_URIS`** | ★★ **必需**（M4 新增） | Elasticsearch 地址，形如 `http://<es 主机>:9200`。**只有 search 用**。★ 与上面三个不同：它**有默认值**（`${ES_URIS:http://192.168.127.137:9200}`），所以**不配不会启动失败，只会静默连到一个错的地方** —— 生产必须显式配 |

> ★★ **M1 起三个 jar 都要配 `INTERNAL_TOKEN`**，而且**值必须相同** ——
> 网关写这个头（连同身份头），两个服务的 `HeaderAuthenticationFilter` 拿它验；
> 服务之间调 `/internal/**` 也用它（Feign 的出站拦截器加）。
> ★ 值不一致的症状**很难查**：网关写的头不被下游认，下游把**每一个请求**都当匿名 ——
> 表现为「全站 401」，看起来像 token 坏了或 Redis 没连上。
> ★ 这个变量和 `JWT_SECRET` 同样是 **`${INTERNAL_TOKEN}`、没有默认值**，
> 不配就**启动失败**（配了默认值就等于把密钥提交进 git）。

> ★★ **`application.yml` 里写的是 `${JWT_SECRET}`，故意没给默认值** —— 生产环境忘了配就会
> **直接启动失败**，一眼能看出是密钥没配。
> 反过来，如果给了默认值，忘记配的时候它会**静默用那个默认值启动**，
> 而那个默认值就写在提交进 git 的文件里 —— 等于全世界都知道你的签名密钥，
> 任何人都能自己签发一个「我是 admin」的 token。这种事故不报错，只会安安静静地被攻破。
>
> （开发环境能用是因为 `application-dev.yml` 里给了默认值，那个文件只用于本地虚拟机。）

启动（★ **四个进程，都要起**；`JWT_SECRET` / `INTERNAL_TOKEN` / `ROCKETMQ_NAME_SERVER` 都要 export）：

```bash
export JWT_SECRET='<你自己生成的>'
export INTERNAL_TOKEN='<你自己生成的，另一个值>'
export ROCKETMQ_NAME_SERVER='<broker 主机>:9876'
export ES_URIS='http://<es 主机>:9200'          # ★ M4 新增，只有 novel-search 用

# 五个都要起；网关可以最后起（Nacos 里还没实例时它会 503，实例上来就好）
nohup java -jar /srv/novel/novel-auth.jar --spring.profiles.active=prod \
  > /var/log/novel/auth.log 2>&1 &         # auth，:8081
nohup java -jar /srv/novel/novel-content.jar --spring.profiles.active=prod \
  > /var/log/novel/content.log 2>&1 &      # 内容服务，:8082
nohup java -jar /srv/novel/novel-interaction.jar --spring.profiles.active=prod \
  > /var/log/novel/interaction.log 2>&1 &  # 互动服务，:8083
nohup java -jar /srv/novel/novel-search.jar --spring.profiles.active=prod \
  > /var/log/novel/search.log 2>&1 &       # 搜索服务，:8084
nohup java -jar /srv/novel/novel-gateway.jar --spring.profiles.active=prod \
  > /var/log/novel/gateway.log 2>&1 &      # 网关，:8080（Nginx 只转发到这里）
```

> ★★★ **必须先起 RocketMQ，再起 auth / content / interaction / search**（网关无所谓，它不连 MQ）。
> ★ **M4 已实测**（补掉了 M3 的 R3 遗留项）：namesrv 不可达时 `novel-search` **起不来**，
> 报 `RemotingConnectException: connect to null failed`（抛在 `DefaultMQPushConsumerImpl.start`）——
> **消费组注册失败 = 服务起不来**，不是「起来了但不消费」。
> ★ **caveat 要一起引用**：测的是 **namesrv 不可达**，不是「namesrv 在、broker 挂了」。
> ★★ **ES 不一样：ES 挂掉时服务照常能起**（M4 实测，指向死地址也 9 秒起来、日志里 0 条 ES 访问）——
> 这个不对称是刻意的：ES 在**请求路径**上（有降级），MQ 在**注册路径**上（注册不了就没得谈）。
> ★ **诊断陷阱**：启动失败的 JVM **不一定会退出**（Netty / RocketMQ 的非守护线程会吊住进程）——
> **「进程在」不等于「服务在」，看端口在不在监听。**
>
> ★★ **生产必须改成同步刷盘 + 主从同步复制。** 仓库里的 `docs/docker/broker.conf` 是
> **开发配置**（`flushDiskType = ASYNC_FLUSH` + `brokerRole = ASYNC_MASTER`，拿可靠性换吞吐），
> 它还开着 `autoCreateTopicEnable` / `autoCreateSubscriptionGroup`。
> 生产要：① 换 `SYNC_FLUSH` + `SYNC_MASTER`；② **关掉两个 auto-create** ——
> 关掉之后 Topic 必须预先建好，**而 `defaultTopicQueueNums = 4` 这个队列数必须显式传给建 Topic 的命令**
> （顺序消息的设计依赖「队列数是已知的」，见 `MqConstant` 的注释）。
> ★ 这一段是面试里会被追问「你配的是同步刷盘吗」的答案，别跳过。

> ★ 生产日志走 stdout 交给采集器即可 —— `application-dev.yml` 里那份「同时写 `backend/logs/`」
> 是开发期为了方便回头看才加的，它**只在 dev profile 下生效**，生产不会往容器里堆日志文件。
> ★ 网关的 `logging.file.name` 目前写在 `application.yml` 里，
> 所以网关在生产**会**往工作目录下写 `logs/novel-gateway.log`。
> ★ M1 起网关已经有 `application-dev.yml` 了，所以「没拆 profile、没地方放」这个理由
> 已经不成立；它留在原地的原因是**挪它等于改生产行为**，那件事归 M5 做生产部署时一并处理。
> 代码里那段注释也写了同样的说明，看到别以为是漏搬。
