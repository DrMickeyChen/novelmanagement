## Context

项目是第一期的**单体** Spring Boot 3.2.12（JDK 21）+ 三个 Vue3 应用。P0 已验收通过（四套骨架、proxy 打通、MySQL/Redis 连通、21 张表已建、三端 token 共享 key 定死）。

P1 开始前 `backend/` 全项目只有 **23 个 Java 文件**，`com.novel` 下**一个 auth 相关的类都没有**，也**没有 service 层**（`PingController` 直接注入 mapper）。所有登录都是假的：

- `reader-web/src/views/login/index.vue` 用 `setTimeout` 伪造了 `mock-token-for-p0-verification` 和硬编码的 `role:'ADMIN'`
- `author-web` / `admin-web` 的路由守卫里 `ENFORCE_ROLE = false` —— **任何人带个假 token 就能进管理端**

P1 要做的是把洞堵上：**真实注册/登录、签发 JWT、每请求校验、按角色挡人**，同时把身份装进 `UserContext` 供 Service 直接取 —— 这是大纲 §696 定下的约定，也是第二期把认证搬到网关（M1）前必须先立住的地基。

**验收标准（大纲 §1258 原文）**：Postman 能登录拿到 token，带 token 能访问 `/api/auth/me`，不带 token 返回 401。

**范围（大纲 §1258 原文）**：注册/登录/JWT/拦截器/角色表/种子管理员账号。

### ★ 决定 4 的修订（P1 收尾时实施）

**新规则**：协议层的错误恢复真实 HTTP 状态码，业务错误仍返 HTTP 200。

```
code 在 400 ~ 599（401/403/404/405/500…）→ HTTP 状态码 = code
其余业务码（1002 用户名或密码错误、2001 作品不存在…）→ HTTP 200，码只在 body 里
```

**为什么改**：原来的「一律 200」让 APM / 网关 / 告警**完全看不出鉴权失败和 5xx** ——
所有响应在监控上长一个样，只能靠人翻应用日志。改完之后这些就是普通状态码，
Nginx、SkyWalking、告警规则不用任何配置就能用。

**为什么业务码还是 200**：「用户名或密码错误」是**一个合法请求的正常结果**，不是系统故障。
给它 4xx 会让告警把「用户输错一次密码」记成异常；而且前端 `request.js` 靠
`code === 401` 判断「踢回登录页」，业务码走的是「弹提示、留在原地」，这两种必须分得开。

**这条规则不是新发明的**：`ResultCode` 自己的分段本来就是
`400~500 通用 HTTP 语义错误` / `1001~ 用户模块` —— 前一段和 HTTP 语义一一对应，
后一段是纯业务语义。这次只是把枚举里已有的分类落实到 HTTP 层。

**落点（一个判断逻辑，四处调用）**：

| 文件 | 作用 |
|---|---|
| `common/result/ResultHttpStatus.java` | **唯一**的判断逻辑。`of(code)` → `HttpStatusCode` |
| `common/exception/GlobalExceptionHandler.java` | 全部 handler 改成 `ResponseEntity<Result<Void>>`，经私有 `respond()` 出口 |
| `common/security/SecurityResponseWriter.java` | `setStatus` 从写死 200 改成 `ResultHttpStatus.of(...)` |
| `modules/system/controller/PingController.java` | `/db`、`/redis` 失败分支改成 `ResponseEntity`（**这是最容易漏的一处**，见下） |

> ★ **为什么不能用 `@ResponseStatus` 注解**：它是**写死的常量**，没法跟着 `code` 走。
> 而 `BusinessException` 带的 code 是运行时才知道的（`UserContext.requireUserId()` 抛的
> 就是 `UNAUTHORIZED(401)`）。既然必须有一处用动态方式，就全都用 `ResponseEntity` ——
> 一半注解一半动态，以后改规则必然漏掉一半。

> ★★ **一致性靠「只有一处判断逻辑」保证，不靠人肉对齐**：
> 鉴权失败有两条路 —— URL 级走 `EntryPoint`/`DeniedHandler` → `SecurityResponseWriter`；
> 方法级（`@PreAuthorize`）走 `@RestControllerAdvice`。两边**都调 `ResultHttpStatus`**，
> 所以同一个「权限不足」不可能出现两种状态码。
> （P1 里还没有任何 `@PreAuthorize`，方法级那条路**已接好但还没有调用方**，
> P2 给管理端接口加注解时才会真正走到 —— 那时要专门验一次两个 403 是否一致。）

> ⚠️ **`PingController` 是最容易漏的一处**：它不抛异常，而是在 `catch` 里直接
> `return Result.error(SYSTEM_ERROR, ...)`，所以**不经过 `GlobalExceptionHandler`**，
> 改完 advice 它仍然是 HTTP 200 —— MySQL 挂了、Redis 挂了，在监控上还是「一切正常」。
> 而这两个接口恰恰是给监控和运维看的。已改成 `ResponseEntity`，
> 顺带给 `Result` 加了 `error(code, message, data)` 重载（失败但保留 `data` 里的排查线索）。

### 三个必须遵守的既有约定（来自大纲，不能违反）

- **§177**：`网关做认证，服务做鉴权。网关校验 JWT 并把用户信息（userId / roles）写进请求头，下游服务不再各自解析 token`
  → **「解析 token → 得到身份」和「拿身份判权限」必须分成两层**，第二期只搬走第一层。
- **§696**：`当前用户 UserContext（ThreadLocal）由 JWT 拦截器写入，Service 直接取`
- **§573-586 错误码表**：**401 专指「未登录 / token 失效」**。用户名密码错误属于 `1001~` 用户模块，**绝不能用 401**，否则前端 `request.js` 会把用户从登录页踢走。

## 设计要点

### 认证与鉴权分两层（为 M1 搬迁准备）

```
【认证层】JwtAuthenticationFilter → JwtUtil(验签) → TokenStore(查Redis) → 写 SecurityContext + UserContext
    ↓  第二期：这一层整体搬到 novel-gateway，改成从请求头读 X-User-Id
【鉴权层】@PreAuthorize("hasRole('ADMIN')")  +  UserContext（服务内越权校验，如 novel.author_id == 当前用户）
    ↓  第二期：这一层原地不动
```

**鉴权用 `@EnableMethodSecurity` + `@PreAuthorize`，不自己造注解。** 理由：

- `@PreAuthorize` 是 Spring Security 的标准答案 —— 既然大纲 §90 选它就是为了面试价值，再造一个 `@RequireRole` 反而把标准答案换成了自研轮子
- 自己写要维护角色匹配逻辑、多一条 403 路径，代码量多约 80 行
- `@PreAuthorize` 能标在 **Service 方法**上，比只能拦 Controller 的 `HandlerInterceptor` 更贴合 §177 的「服务做鉴权」
- M1 搬迁**不受影响**：网关接管认证后，服务侧加个小 filter 从请求头填 SecurityContext，`@PreAuthorize` 照常工作

**`ROLE_` 前缀的处理**：`CommonConstant.ROLE_ADMIN` 是裸的 `"ADMIN"`（对应 DB 的 `sys_role.role_code`，**不能改，改了就破坏数据契约**）。所以在**构建 authorities 时**拼前缀：`"ROLE_" + roleCode` → `hasRole('ADMIN')` 正好匹配。前缀只活在 Java 层。

### Redis 存「完整身份」而非「标记」

`novel:auth:token:{userId}:{jti}` → 存 `LoginUser` 对象（必须放在 `com.novel.` 下，否则 `RedisConfig` 的 `BasicPolymorphicTypeValidator` 白名单会拒绝反序列化 —— 这是**故意**的防 gadget 攻击设计，不要放宽），TTL = JWT 剩余有效期。

**为什么**：角色/权限改动、封禁账号能**立刻生效**（不用等 token 过期、也不用重新登录）；JWT 里就不必塞 roles/permissions，token 保持短小，也不存在「token 里的角色是旧的」问题。

**代价**：Redis 挂了 = 校验失败 = **fail closed**（返回 500），所有人下线。本项目接受，写进注释。**不能 fail open** —— 那等于把已登出的 token 全部复活。

### JWT 只装身份标识

claims：`sub` = userId、`jti` = UUID、`username`。**不装 roles/permissions**（那些从 Redis 的 `LoginUser` 里取，避免两个事实来源）。

### 前端 `role` 与后端多对多的阻抗失配

DB 是 `sys_user_role` 多对多，而 `stores/user.js` 的 getter 读的是**单个** `userInfo.role`（`isAuthor`/`isAdmin` 都基于它），两个路由守卫也直接判 `user?.role === 'ADMIN'`。

**方案**：`UserVO` 同时给**两个**字段 —— `roles: string[]`（真实数据，P2 多角色 UI 用）+ `role: string`（派生：按 `ADMIN > AUTHOR > READER` 取最高，后端算好）。VO 上注明 `roles` 是唯一事实来源、`role` 只是便捷字段。

→ 好处：**「角色从单个变多个」这件事本身，一个前端文件都不用改**。
三个 store 里 `isAuthor`/`isAdmin` 读的还是 `userInfo.role`，两个守卫判的还是 `user.role === 'ADMIN'` ——
后端多给一个派生好的 `role` 字段，这些读法原样成立，不用全前端排查一遍 `.role` 的用法。

> ★ 说清楚免得误会：这三个 store 和两个守卫在 P1 里**确实改了**，
> 但改的原因是别的事（store 加 `login`/`logout` action、守卫打开硬拦截），
> **不是因为多对多这件事**。这两件事要分开看 ——
> 否则以后有人看到「文件被改过」就以为上面的结论错了。

### 防用户名枚举

登录时「用户不存在」和「密码错误」**都返回 `USER_PASSWORD_ERROR(1002)`**，不返回 `USER_NOT_FOUND(1001)` —— 否则攻击者能靠错误码枚举出哪些用户名存在。`1001` 留给其他场景（如管理端按 id 查用户）。这是个好的面试点。

### 后端（对应大纲 §1258 的原话验收）

```bash

  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin123"}'

# 2. 带 token 访问 /me

# 3. 不带 token

# 4. 密码错误 → 1002，且 HTTP 必须仍是 200
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"admin","password":"wrong"}'

# ★ 这一条是决定 4 修订的【关键对照】：协议层错误返真实状态码，

curl -s -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"nobody","password":"wrong"}'
# 期望：{"code":1002,...} —— 和上一题返回【完全一样】的 message

#   根本走不到路由匹配那一步，验不到 404

## 风险与坑（按危险程度排序）

> ★ 标了「★ 实施时踩到」的 5 条是**实施之后才发现的**，方案里没有预见；
> 其余是方案阶段就列出来的。但排序仍按危险程度 ——
> 「已经踩到」不代表「更危险」，第 1 条就是最典型的例子。
> 第 9 条（`catch` 里直接造失败响应）是**收尾改 HTTP 状态码时才暴露的**：
> 它说明「改了一处规则」不等于「所有地方都改了」，得顺着调用路径挨个查。

| # | 坑 | 症状 |
|---|---|---|
| 1 | **子路径部署时地址必须以 `/` 结尾**（★ 实施时踩到） | `http://localhost:3000/reader` → **404**，加斜杠才对。三个应用都部署在子路径下（Vite `base`），服务器把 `/reader` 当文件找。拼接时也受影响：`${READER_WEB_URL}login` 对、`${READER_WEB_URL}/login` 会出双斜杠 |
| 2 | **角色不符时跳登录页会造成死循环**（★ 实施时踩到） | 用户**已登录**、只是角色不对，`redirectToReaderLogin()` 带上 `?redirect=` 后：登录页 → 登录成功 → 跳回 → 又被拦 → 再回登录页，永远出不去。这个函数只适合「该登录而没登录」 |
| 3 | **退出登录不跳转会把人留在原地**（★ 实施时踩到） | 守卫只在**路由跳转**时跑，退出不触发跳转 → 守卫不重跑 → 用户留在创作中心/管理端，顶栏显示「未登录」但页面还在，点任何东西才 401 被踢走 |
| 4 | **`ElMessage` 提示会被紧接着的跳转吃掉**（★ 实施时踩到） | 先 `ElMessage.warning(...)` 再 `window.location.href = ...`，提示随页面卸载一起消失，用户只看到「闪了一下就跳走了」。需要延时再跳 |
| 5 | **引入 security 后全站锁死** | 一启动 `/api/ping`、`/doc.html` 全部 401。必须和 `SecurityConfig` 同一步落地 |
| 6 | **`/error` 必须放行** | 出异常时 Spring 转发到 `/error`，若它受保护会出现「401 套 401」的诡异现象 |
| 7 | **`@PreAuthorize` 拒绝变成 `code:500`** | `GlobalExceptionHandler` 没有 `AccessDeniedException` 处理器，兜底 `Exception.class` 把 403 吃成 500 |
| 8 | **两条鉴权失败路径只堵了一条** | filter chain 的 URL 级失败走 `AccessDeniedHandler`，`@PreAuthorize` 的方法级失败走 advice。**少一条就有洞** |
| 9 | **`catch` 里直接 `return Result.error(...)` 会绕过全局处理器**（★ 实施时踩到） | `PingController` 的 `/db`、`/redis` 不抛异常，在 `catch` 里直接构造失败响应 —— 于是改完 `GlobalExceptionHandler` 之后它们**仍然是 HTTP 200**。MySQL 挂了、Redis 挂了，监控上还是「一切正常」，而这两个接口恰恰是给监控看的。**凡是「不抛异常、直接造失败响应」的地方都要单独检查一遍** |
| 10 | **登录失败误用 401** | 用户一输错密码就被 `request.js` 踢去登录页。必须用 `1002` |
| 11 | **登录失败误用 1001** | 「用户不存在」返回 1001 会让人枚举出哪些用户名存在。两种情况都返 `1002` |
| 12 | **手写 SQL 不走 `@TableLogic`** | `SysUserMapper` 新加的两个查询若忘写 `deleted = 0`，已删除用户/菜单会混进来 |
| 13 | **Redis 默认类型白名单** | `LoginUser` 若不在 `com.novel.` 包下，反序列化直接抛异常。这是**故意**的安全设计，不要放宽 |
| 14 | **`password` 泄漏** | `SysUser` 上没有 `@JsonIgnore`，全靠 VO 转换。`UserVO` 里绝不能有 password |
| 15 | **`hasRole()` 的 `ROLE_` 前缀** | `CommonConstant.ROLE_ADMIN` 是裸的 `"ADMIN"`。前缀要在构建 authorities 时拼，**不要去改 `CommonConstant` 或 DB 里的 `role_code`** |
| 16 | **`sys_user_role` 没有 `deleted` 列** | 实体上不要加 `@TableLogic`，否则 MyBatis-Plus 会拼一个不存在的字段 |
| 17 | **HS256 密钥长度** | jjwt 0.12 要求 ≥256 bit（32 字节）。dev 默认值必须够长，否则启动抛 `WeakKeyException` |

| 19 | **生产环境静默用 dev 密钥** | 所以 `application.yml` 写 `${JWT_SECRET}` **不给默认值**，dev 默认值只放 `application-dev.yml` |

## 实施记录（对方案的修正）

> 上面各节里凡是标了「★ 实施记录第 N 条」的地方，完整理由都在这里。
> ①②③④ 是 P1 主体实施时的：① 是**方案本身写错了**（没有照做），②③④ 是**方案漏写**（做的时候才发现的）。

### ① 守卫里【不能】改用 `redirectToReaderLogin()` —— 方案这条写错了

方案原文（「前端 —— 打开角色拦截」一节）：*「顺手修一个既存缺陷：两个守卫在拦截分支里跳的是 `window.location.href = READER_WEB_URL`，没带 `redirect=` 参数 …… 改用已经 import 好的 `redirectToReaderLogin()`。」*

**没有采纳，原因是一个转不出去的死循环：**

1. 用户是登录状态（`token` 存在），只是角色不对（比如 READER 想进创作中心）
2. `redirectToReaderLogin()` 跳到 `/reader/login?redirect=<创作中心地址>`
3. 用户在登录页登录成功 → 跳回创作中心
4. 角色还是不对 → 又被拦 → 又回登录页 → **回到第 2 步**

关键区别在于：`redirectToReaderLogin()` 是给「**该登录而没登录**」准备的 —— 那种情况下登录一次就能解决。
而角色不符是「**登录了但没权限**」，登录一百次也解决不了。
正确做法是把他送回**他能正常使用的地方**（阅读端首页），而不是送回一个他填不完的表单。

现在的写法保持 `window.location.href = READER_WEB_URL`，另外加了 **800ms 延时**（对应第 ④ 条）。

### ② `utils/auth.js` 的地址常量缺结尾斜杠 —— 方案说「一行都不用改」，实际必须改

方案原文：*「`utils/request.js` 和 `utils/auth.js` 一行都不用改」*。**这句是错的。**

`http://localhost:3000/reader`（无斜杠）实测 **404**，`http://localhost:3000/reader/` 才正常 ——
三个应用都部署在子路径下（Vite `base: '/reader/'`），服务器会把 `/reader` 当**文件**去找。

这**不是潜在风险，是当时就在线上**的问题：

- 创作中心顶栏的「阅读端」按钮 → 404
- 管理端顶栏的「阅读端」「创作中心」按钮 → 404
- 阅读端首页卡片上的「跳到创作中心 / 跳到管理端」→ 404

**为什么一直没被发现**：唯一还在用这个裸地址的**守卫分支**正好被 `ENFORCE_ROLE = false` 挡着，
从来没执行过。而上面那几个按钮是 P0 就有的 —— 说明 P0 验收时没点过它们，
或者点了没在意。**P1 一打开角色拦截，被拦的人就会直接摔到 404 页上。**

修法是给三个常量补结尾斜杠，并改掉两处拼接：

```js
export const READER_WEB_URL = ... || `${GATEWAY_URL}/reader/`   // ← 结尾斜杠

redirectToReaderLogin()  →  `${READER_WEB_URL}login?redirect=${back}`   // 不能写 /login
author-web/views/home   →  gotoApp(READER_WEB_URL + 'login')           // 同上
admin-web/views/home    →  gotoApp(READER_WEB_URL + 'login')
```

三个 `.env.development` 里「留空则自动取 `${VITE_GATEWAY_URL}/reader`」的注释也一并补了斜杠和警告 ——
原来那句话照着填就会踩同一个坑。

### ③ 退出登录后必须跳走（创作中心 / 管理端）

方案只写了「退出按钮改成 `await userStore.logout()`」，没说退完去哪。

**问题**：路由守卫只在**发生路由跳转**时执行，而退出登录不触发跳转。
所以用户在创作中心点「退出」之后，token 清了、顶栏变成「未登录」，
但**页面还停在创作中心**，内容照旧显示 —— 点任何东西才会 401 被踢走。这看起来很诡异。

- **创作中心 / 管理端**：退出后 `window.location.href = READER_WEB_URL` 跳回阅读端首页。
  用 `location.href` 而不是 `router.replace('/')`，因为这本来就是跨应用跳转，本应用的路由器管不到阅读端（§7.5 第 2 条）。
- **阅读端**：退出后**不跳**。首页是公开页，未登录也能看，停在原地正好让用户看到导航栏
  从「昵称 + 退出」变成「登录」，这是最直观的反馈。

### ④ `ENFORCE_ROLE` 开关是【删掉】的，不是翻成 `true`

方案写的是 `ENFORCE_ROLE = false` → `true`。实际把整个开关删了。

理由：这个开关存在的唯一目的就是「P0 先放行，等 P1 有真实角色了再收紧」。
现在收紧了，留一个恒为 `true` 的常量只会让以后读代码的人多花几秒想「它还能被改成 false 吗」。
删掉之后守卫就是一条直线：没 token → 去登录；token 在但用户信息损坏 → 去登录；角色不对 → 硬拦。

顺带补了「token 在但 `getUser()` 返回 null」这个分支 ——
`getUser()` 内部有一条「JSON 坏了就删掉 key 并返回 null」的兜底路径，所以这种残缺状态是真实可达的，
不放行也不当成「角色不对」，直接当未登录处理。

> 另外两处**没有延时就会失效**的提示（守卫的角色提示、以及被跳转打断的任何 `ElMessage`）：
> `ElMessage` 挂在 body 上，`window.location.href` 一跳、页面一卸载，提示跟着消失。
> 用户只会看到「闪了一下就跳走了」，不知道发生了什么。所以那两处都是**先提示、延时 800ms 再跳**。

### ⑤ 修监控盲区：方案说的 `@ResponseStatus` 是【错的】，实际用了 `ResponseEntity`

「待办」里原本记的是「`GlobalExceptionHandler` 那几个处理器没有 `@ResponseStatus`……要不要补」。
**这个方向不能照做**，两个原因：

1. **`@ResponseStatus` 是常量，跟不了动态 code。** `handleBusinessException` 拿到的
   `e.getCode()` 是运行时才知道的 —— `UserContext.requireUserId()` 抛的就是 `UNAUTHORIZED(401)`，
   而别的调用方抛的是 `1002`。一个注解表达不了「有时 401、有时 200」。
2. **只给 advice 加注解会造成新的不一致。** 鉴权失败有两条路（URL 级走
   `SecurityResponseWriter`，方法级走 advice）。只改 advice 的话，同一句「权限不足」，
   其中一条返 403、另一条返 200 —— 比改之前**更难排查**，因为现在得先判断走的是哪条路。

所以改成 `ResponseEntity` + 一处集中的判断逻辑（`ResultHttpStatus`），
四个落点全部覆盖。完整规则见上文「决定 4 的修订」。

**这次改动真正的收获不是状态码，而是暴露了第 9 条风险**：
`PingController` 因为没有抛异常、在 `catch` 里直接造响应，**天然绕过了全局处理器** ——
「改一处规则」和「所有地方都改了」是两件事，得顺着**每一处产生响应的路径**挨个查，
而不是只改那个名字里带 `ExceptionHandler` 的文件。

## 遗留（不影响验收，但面试可能被问）

- **`@PreAuthorize` 在 P1 没有任何生产用途。** 框架（`@EnableMethodSecurity` + `SecurityConfig` + `GlobalExceptionHandler` 里的 `AccessDeniedException` 处理器）全部就位，但 P1 的四个端点没有一个需要它。验证两条鉴权失败路径时是在 `/api/auth/me` 上**临时**加了一句 `@PreAuthorize("hasRole('ADMIN')")`，验完就撤了。
  → 被问到「`@PreAuthorize` 在哪用了」，答：**框架已就位，第一个真实用例在 P2**（管理端接口）。
- **两条路径的验证证据**（撤掉临时注解之前的日志）：匿名访问 → `RestAuthenticationEntryPoint` 打 `WARN 认证失败`；READER 访问 → `GlobalExceptionHandler` 打 `WARN 鉴权失败（方法级）`，返回 `code:403` 而**不是 500**（风险表第 7、8 条已排除）。两次都**没有**出现兜底的 `ERROR 系统异常` —— 这是判断「异常有没有掉进兜底处理器」的关键信号。
