## 一、从一个具体问题讲起

用本项目的场景。作者点「发布章节」，系统要干这五件事：

1. 保存章节正文到数据库
2. 更新小说的字数、章节数、最后更新时间
3. 重建搜索索引（ES）
4. 给收藏了这本书的用户发更新提醒
5. 更新排行榜

### 不用 MQ 的做法

全在用户的请求线程里做完。问题有三个：

- 用户在浏览器前等 5 秒才看到「发布成功」，其实他只要知道**第 1 步**成功了就行
- 第 4 步发通知如果失败了，前面 1、2、3 要不要回滚？回滚的话第 3 步的 ES 索引怎么撤？
- 收藏这本书的有 10 万人，光发通知就要 30 秒

### 用 MQ 的做法

```
用户请求 ──> 保存章节（50ms）──> 往 MQ 丢一条消息 ──> 立刻返回「发布成功」
                                      ↓
                          （另一个线程 / 进程慢慢做）
                          2. 更新冗余字段
                          3. 重建索引
                          4. 发通知
                          5. 更新榜单
```

用户 50ms 拿到响应。后面四件事失败了会**自动重试**，不会牵扯到用户的请求。

> **这就是消息队列的存在意义：把「必须同步做完的事」和「可以稍后做的事」分开。**

## 二、本质是什么

一句话：**一个可靠的、可以堆积的待办事项清单。**

| 角色 | 比喻 |
|---|---|
| 生产者 Producer | 把活儿写成便签，贴到墙上 |
| 消息队列 MQ | 那面墙 —— 而且便签不会掉、不会丢 |
| 消费者 Consumer | 有人从墙上撕便签下来干活 |

关键在于：**贴便签的人不需要知道谁来撕，撕便签的人也不需要知道谁贴的，两拨人甚至不需要同时在场。**

这就是「解耦」两个字的真实含义。在本项目里，`content` 服务发一条「章节已发布」，它**完全不知道**有人在监听、有几个服务在监听、它们什么时候上线。以后想加一个「数据分析服务」来消费这条消息，`content` 服务一行代码都不用改。

## 三、三大作用（面试核心考点）

### 1. 异步 —— 别让用户等不重要的活

**本项目场景**：章节发布后重建搜索索引。

索引重建慢，而且跟「发布成功」这个结果无关。丢给 MQ，用户先走。

### 2. 解耦 —— 生产者不关心消费者是谁

**本项目场景**：`content` 服务发「章节已发布」，`content`（更新冗余字段）和 `search`（重建索引）两个服务各拿各的。

以后加第三个消费者，生产者不改代码。这是「发布-订阅」的威力。

### 3. 削峰填谷 —— 洪峰来了先缓冲

**本项目场景**：阅读量上报，峰值 3000 QPS。

数据库撑不住 3000 QPS 的写，但 MQ 可以 —— 它就是个高速的缓冲池。消费者按自己的节奏来，比如每 500ms 批量拉 32 条，聚合后每 5 秒执行一次 `UPDATE`。

```
数据库写入压力：3000 QPS  ──MQ 缓冲──>  0.2 QPS
```

**「削峰填谷」拆开看**：洪峰削掉（缓冲在 MQ 里），低谷填上（闲时继续消费堆积的消息）。最终让下游看到的流量变得平缓。

## 四、核心概念速查

| 概念 | 含义 | 比喻 |
|---|---|---|
| **Producer** | 生产者，发消息的一方 | 写便签的人 |
| **Consumer** | 消费者，收消息的一方 | 撕便签干活的人 |
| **Broker** | 消息服务器，MQ 本身 | 那面墙 / 邮局 |
| **Topic** | 主题，消息的分类 | 邮局里的一个信箱 |
| **Tag** | 标签，Topic 下的二级分类 | 信箱里的分格 |
| **Queue** | 队列，Topic 物理上分成多个队列 | 分格里的格子 |
| **Message** | 消息，一条具体的数据 | 一张便签 |
| **Consumer Group** | ★ 消费组 | 一组快递员 |
| **Offset** | 位点，消费到哪了 | 书签 |
| **ACK** | 确认，消费成功回执 | 签收 |
| **死信队列** | 重试多次仍失败的消息，扔这儿人工处理 | 疑难件区 |

### ★ 消费组 —— 最容易搞混的概念

两条规则：

- **同一个组内**：一条消息只被组里的**一个**消费者处理（负载均衡）
- **不同组之间**：各自都收到**全量**消息

用快递打比方：

- 同一个消费组 = 一个快递站有 3 个快递员，一个包裹**只需要一个人**送。加人是为了加快速度。
- 不同消费组 = 顺丰和京东各送各的，互不干扰。

**回到本项目**：

```
Tag: CHAPTER_PUBLISHED          章节发布
  ├── 消费组 group-content-stat   → 更新小说冗余字段
  └── 消费组 group-search-index   → 重建 ES 索引
```

这条消息**两个组都要拿到**（两件事都得做），但在 `group-search-index` 组内部，如果部署了 3 个 search 实例，这条消息只会给其中一个（避免重复建索引）。

> 这个点面试必问，答不出来很掉分。

## 五、市面上有哪些 MQ

### 主流四家

| | **RocketMQ** | **RabbitMQ** | **Kafka** | **ActiveMQ** |
|---|---|---|---|---|
| 语言 | Java | Erlang | Scala / Java | Java |
| 出身 | 阿里 | Pivotal | LinkedIn | Apache |
| 吞吐 | 十万级 | 万级 | **百万级** | 万级 |
| 延迟 | ms 级 | **μs 级（最低）** | ms 级 | ms 级 |
| 事务消息 | ✅ 原生 | ❌ | ⚠️ 有限 | ⚠️ 有限 |
| 顺序消息 | ✅ 原生 | ⚠️ 单队列 | ✅ 分区内 | ⚠️ |
| 延时消息 | ✅ 任意精度 | ⚠️ 插件 | ❌ | ⚠️ |
| 积压能力 | 强 | **弱（压内存）** | 极强 | 弱 |
| 现状 | 国内主流 | 仍大量使用 | 大数据领域统治 | **基本淘汰** |

### 选型口诀

| 需求 | 选 |
|---|---|
| 业务系统，要事务 / 顺序 / 延时消息 | **RocketMQ** |
| 轻量、低延迟、路由复杂（如按 header 分发） | **RabbitMQ** |
| 日志采集、埋点、流式计算、超大规模 | **Kafka** |

### 其他值得知道的

- **Pulsar** —— 后起之秀，存算分离（Broker 无状态，存储用 BookKeeper），支持多租户。技术先进但生态仍在追赶，国内用得少。
- **云厂商托管版** —— 阿里云 RocketMQ、腾讯云 CKafka、AWS SQS/SNS。生产环境上云时通常直接用托管版，省运维。
- **Redis 做 MQ** —— 见下一节。

## 六、Redis 能做消息队列吗

能，但要看用哪个数据结构。这也是面试常问的。

| 方式 | 原理 | 能否当 MQ 用 |
|---|---|---|
| **List** | `LPUSH` 生产 / `BRPOP` 消费 | ⚠️ 最简陋。没有 ACK、没有重试、没有广播，消息弹出就没了 |
| **Pub/Sub** | 发布订阅 | ❌ 消息**不持久化**，消费者不在线就永久丢失。只能做实时通知 |
| **Stream** | Redis 5.0 引入，有消费组、有 ACK、有 pending 列表 | ✅ 最接近真正的 MQ |

**但即使 Stream 也不该在正经项目里替代 MQ**，因为它缺：

- 失败重试和死信队列
- 消息积压的监控和管理
- 消息轨迹查询（「这条消息到底被消费了没」）
- 持久化保障（Redis 本身可能丢数据）

> **结论**：Redis 适合做**缓存和计数**（本项目里的阅读量、榜单就该用它），**不适合做消息队列**。

## 七、什么时候不该用 MQ

这点很重要。不是所有异步都需要 MQ —— 滥用 MQ 是新手常见病。

| 场景 | 该用什么 |
|---|---|
| 只是想让一个方法异步执行，不跨服务、不怕丢 | **`@Async` / 线程池**就够了 |
| 需要跨服务、需要持久化、需要重试 | **MQ** |
| 需要延迟执行（30 秒后干某事） | 简单场景用**定时任务**，复杂用 MQ 延时消息 |

### 引入 MQ 的代价

面试时主动说出来很加分：

- **系统复杂度上升** —— 多一个中间件要部署、监控、运维
- **凭空多出三个经典问题** —— 消息丢失、重复消费、顺序错乱（第十二节整节都在讲这个）
- **排查变难** —— 请求不再是线性的，得沿着消息链路追

> **判断标准**：当你能说出「我需要持久化 / 跨服务 / 削峰 / 重试」中的至少一条时，才上 MQ。

## 八、回到本项目

对照[三大作用](#三三大作用面试核心考点)，四个 MQ 场景这样落位：

| 场景 | 主要作用 | 用到的特性 |
|---|---|---|
| 章节发布 → 更新冗余字段 / 重建索引 | **解耦** | 事务消息（保证发消息和写库原子） |
| 阅读量 / 进度上报 | **削峰** | 顺序消息（同一用户不能乱序） |
| 评论提交 → 敏感词审核 | **异步** | 普通消息 |
| 审核结果通知 | **异步** | 延时消息（失败 30 秒后重试） |

### 面试时这样组织回答

先说三大作用，再说你这个项目分别在哪里用到了哪一个。**比干巴巴地列「我用了 RocketMQ」高一个层级。**

参考话术：

> 「我在项目里按三种场景引入了 MQ。解耦方面，章节发布后要触发冗余字段更新和 ES 索引重建，这两个动作跨服务且未来可能扩展，所以用事务消息发布事件，让下游各自订阅；削峰方面，阅读量上报峰值 3000 QPS，直接写库撑不住，用 MQ 缓冲后消费者批量聚合，数据库写入降到 0.2 QPS；异步方面，评论的敏感词审核和审核结果通知都不该阻塞用户请求。」

## 九、常见误区

| 误区 | 纠正 |
|---|---|
| 「MQ 是为了提高性能」 | 它**不提高单次请求的速度**，反而多一次网络往返。它提高的是**系统的吞吐能力和可用性** —— 让慢活不阻塞快活 |
| 「用了 MQ 就不会丢消息」 | 默认配置下**会丢**。生产端、Broker、消费端三段都要单独配置可靠性（见第十二节） |
| 「MQ 保证消息不重复」 | 绝大多数 MQ 只保证 **at-least-once**（至少一次），重复是常态，**必须消费端做幂等** |
| 「MQ 保证顺序」 | 默认**不保证**。要顺序必须显式使用顺序消息，且要接受并行度受限的代价 |
| 「消费组越多越好」 | 每个消费组都会拿到全量消息。组越多，同一条消息被处理的次数越多，下游压力越大 |
