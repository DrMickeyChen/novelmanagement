## 一、从一个具体问题讲起

用本项目的场景。作者点「发布章节」，系统要干这五件事：

1. 保存章节正文到数据库
2. 更新小说的字数、章节数、最后更新时间
3. 重建搜索索引（ES）
4. 给收藏了这本书的用户发更新提醒
5. 更新排行榜

### 不用 MQ 的做法

全在用户的请求线程里做完。问题有三个：

- 用户在浏览器前等 5 秒才看到「发布成功」，其实他只要知道**第 1 步**成功了就行
- 第 4 步发通知如果失败了，前面 1、2、3 要不要回滚？回滚的话第 3 步的 ES 索引怎么撤？
- 收藏这本书的有 10 万人，光发通知就要 30 秒

### 用 MQ 的做法

```
用户请求 ──> 保存章节（50ms）──> 往 MQ 丢一条消息 ──> 立刻返回「发布成功」
                                      ↓
                          （另一个线程 / 进程慢慢做）
                          2. 更新冗余字段
                          3. 重建索引
                          4. 发通知
                          5. 更新榜单
```

用户 50ms 拿到响应。后面四件事失败了会**自动重试**，不会牵扯到用户的请求。

> **这就是消息队列的存在意义：把「必须同步做完的事」和「可以稍后做的事」分开。**

## 二、本质是什么

一句话：**一个可靠的、可以堆积的待办事项清单。**

| 角色 | 比喻 |
|---|---|
| 生产者 Producer | 把活儿写成便签，贴到墙上 |
| 消息队列 MQ | 那面墙 —— 而且便签不会掉、不会丢 |
| 消费者 Consumer | 有人从墙上撕便签下来干活 |

关键在于：**贴便签的人不需要知道谁来撕，撕便签的人也不需要知道谁贴的，两拨人甚至不需要同时在场。**

这就是「解耦」两个字的真实含义。在本项目里，`content` 服务发一条「章节已发布」，它**完全不知道**有人在监听、有几个服务在监听、它们什么时候上线。以后想加一个「数据分析服务」来消费这条消息，`content` 服务一行代码都不用改。

## 三、三大作用（面试核心考点）

### 1. 异步 —— 别让用户等不重要的活

**本项目场景**：章节发布后重建搜索索引。

索引重建慢，而且跟「发布成功」这个结果无关。丢给 MQ，用户先走。

### 2. 解耦 —— 生产者不关心消费者是谁

**本项目场景**：`content` 服务发「章节已发布」，`content`（更新冗余字段）和 `search`（重建索引）两个服务各拿各的。

以后加第三个消费者，生产者不改代码。这是「发布-订阅」的威力。

### 3. 削峰填谷 —— 洪峰来了先缓冲

**本项目场景**：阅读量上报，峰值 3000 QPS。

数据库撑不住 3000 QPS 的写，但 MQ 可以 —— 它就是个高速的缓冲池。消费者按自己的节奏来，比如每 500ms 批量拉 32 条，聚合后每 5 秒执行一次 `UPDATE`。

```
数据库写入压力：3000 QPS  ──MQ 缓冲──>  0.2 QPS
```

**「削峰填谷」拆开看**：洪峰削掉（缓冲在 MQ 里），低谷填上（闲时继续消费堆积的消息）。最终让下游看到的流量变得平缓。

## 四、核心概念速查

| 概念 | 含义 | 比喻 |
|---|---|---|
| **Producer** | 生产者，发消息的一方 | 写便签的人 |
| **Consumer** | 消费者，收消息的一方 | 撕便签干活的人 |
| **Broker** | 消息服务器，MQ 本身 | 那面墙 / 邮局 |
| **Topic** | 主题，消息的分类 | 邮局里的一个信箱 |
| **Tag** | 标签，Topic 下的二级分类 | 信箱里的分格 |
| **Queue** | 队列，Topic 物理上分成多个队列 | 分格里的格子 |
| **Message** | 消息，一条具体的数据 | 一张便签 |
| **Consumer Group** | ★ 消费组 | 一组快递员 |
| **Offset** | 位点，消费到哪了 | 书签 |
| **ACK** | 确认，消费成功回执 | 签收 |
| **死信队列** | 重试多次仍失败的消息，扔这儿人工处理 | 疑难件区 |

### ★ 消费组 —— 最容易搞混的概念

两条规则：

- **同一个组内**：一条消息只被组里的**一个**消费者处理（负载均衡）
- **不同组之间**：各自都收到**全量**消息

用快递打比方：

- 同一个消费组 = 一个快递站有 3 个快递员，一个包裹**只需要一个人**送。加人是为了加快速度。
- 不同消费组 = 顺丰和京东各送各的，互不干扰。

**回到本项目**：

```
Tag: CHAPTER_PUBLISHED          章节发布
  ├── 消费组 group-content-stat   → 更新小说冗余字段
  └── 消费组 group-search-index   → 重建 ES 索引
```

这条消息**两个组都要拿到**（两件事都得做），但在 `group-search-index` 组内部，如果部署了 3 个 search 实例，这条消息只会给其中一个（避免重复建索引）。

> 这个点面试必问，答不出来很掉分。

## 五、市面上有哪些 MQ

### 主流四家

| | **RocketMQ** | **RabbitMQ** | **Kafka** | **ActiveMQ** |
|---|---|---|---|---|
| 语言 | Java | Erlang | Scala / Java | Java |
| 出身 | 阿里 | Pivotal | LinkedIn | Apache |
| 吞吐 | 十万级 | 万级 | **百万级** | 万级 |
| 延迟 | ms 级 | **μs 级（最低）** | ms 级 | ms 级 |
| 事务消息 | ✅ 原生 | ❌ | ⚠️ 有限 | ⚠️ 有限 |
| 顺序消息 | ✅ 原生 | ⚠️ 单队列 | ✅ 分区内 | ⚠️ |
| 延时消息 | ✅ 任意精度 | ⚠️ 插件 | ❌ | ⚠️ |
| 积压能力 | 强 | **弱（压内存）** | 极强 | 弱 |
| 现状 | 国内主流 | 仍大量使用 | 大数据领域统治 | **基本淘汰** |

### 选型口诀

| 需求 | 选 |
|---|---|
| 业务系统，要事务 / 顺序 / 延时消息 | **RocketMQ** |
| 轻量、低延迟、路由复杂（如按 header 分发） | **RabbitMQ** |
| 日志采集、埋点、流式计算、超大规模 | **Kafka** |

### 其他值得知道的

- **Pulsar** —— 后起之秀，存算分离（Broker 无状态，存储用 BookKeeper），支持多租户。技术先进但生态仍在追赶，国内用得少。
- **云厂商托管版** —— 阿里云 RocketMQ、腾讯云 CKafka、AWS SQS/SNS。生产环境上云时通常直接用托管版，省运维。
- **Redis 做 MQ** —— 见下一节。

## 六、Redis 能做消息队列吗

能，但要看用哪个数据结构。这也是面试常问的。

| 方式 | 原理 | 能否当 MQ 用 |
|---|---|---|
| **List** | `LPUSH` 生产 / `BRPOP` 消费 | ⚠️ 最简陋。没有 ACK、没有重试、没有广播，消息弹出就没了 |
| **Pub/Sub** | 发布订阅 | ❌ 消息**不持久化**，消费者不在线就永久丢失。只能做实时通知 |
| **Stream** | Redis 5.0 引入，有消费组、有 ACK、有 pending 列表 | ✅ 最接近真正的 MQ |

**但即使 Stream 也不该在正经项目里替代 MQ**，因为它缺：

- 失败重试和死信队列
- 消息积压的监控和管理
- 消息轨迹查询（「这条消息到底被消费了没」）
- 持久化保障（Redis 本身可能丢数据）

> **结论**：Redis 适合做**缓存和计数**（本项目里的阅读量、榜单就该用它），**不适合做消息队列**。

## 七、什么时候不该用 MQ

这点很重要。不是所有异步都需要 MQ —— 滥用 MQ 是新手常见病。

| 场景 | 该用什么 |
|---|---|
| 只是想让一个方法异步执行，不跨服务、不怕丢 | **`@Async` / 线程池**就够了 |
| 需要跨服务、需要持久化、需要重试 | **MQ** |
| 需要延迟执行（30 秒后干某事） | 简单场景用**定时任务**，复杂用 MQ 延时消息 |

### 引入 MQ 的代价

面试时主动说出来很加分：

- **系统复杂度上升** —— 多一个中间件要部署、监控、运维
- **凭空多出三个经典问题** —— 消息丢失、重复消费、顺序错乱（第十二节整节都在讲这个）
- **排查变难** —— 请求不再是线性的，得沿着消息链路追

> **判断标准**：当你能说出「我需要持久化 / 跨服务 / 削峰 / 重试」中的至少一条时，才上 MQ。

## 八、回到本项目

对照[三大作用](#三三大作用面试核心考点)，四个 MQ 场景这样落位：

| 场景 | 主要作用 | 用到的特性 |
|---|---|---|
| 章节发布 → 更新冗余字段 / 重建索引 | **解耦** | 事务消息（保证发消息和写库原子） |
| 阅读量 / 进度上报 | **削峰** | 顺序消息（同一用户不能乱序） |
| 评论提交 → 敏感词审核 | **异步** | 普通消息 |
| 审核结果通知 | **异步** | 延时消息（失败 30 秒后重试） |

### 面试时这样组织回答

先说三大作用，再说你这个项目分别在哪里用到了哪一个。**比干巴巴地列「我用了 RocketMQ」高一个层级。**

参考话术：

> 「我在项目里按三种场景引入了 MQ。解耦方面，章节发布后要触发冗余字段更新和 ES 索引重建，这两个动作跨服务且未来可能扩展，所以用事务消息发布事件，让下游各自订阅；削峰方面，阅读量上报峰值 3000 QPS，直接写库撑不住，用 MQ 缓冲后消费者批量聚合，数据库写入降到 0.2 QPS；异步方面，评论的敏感词审核和审核结果通知都不该阻塞用户请求。」

### ★★ M3 落地情况（**2026-09-22 实施后补记 —— 上面那张表是设计稿，这里是实际长出来的样子**）

★ **这份笔记本身不重写** —— 上面是「MQ 的一般知识 + 当时的落位设想」，
下面是「真的做出来之后和设想差在哪」。**两者的差异本身就是内容。**

**实际切出来的不是 4 个 Tag，而是这 4 条边（方向很重要）：**

| Tag | 方向 | 消费模式 | 防乱序靠什么 |
|---|---|---|---|
| `VIEW_REPORT` | content **自发自消** | CONCURRENTLY | 不用防（推的是**增量**） |
| `PROGRESS_REPORT` | interaction **自发自消** | ★ **ORDERLY**（`hashKey = userId`） | 传输层顺序 |
| `NOVEL_STAT` | interaction → content | CONCURRENTLY | **载荷时间戳 + 单调写** |
| `AUDIT_RECORD` | auth → content | CONCURRENTLY | SETNX 幂等 |

**与上面那张落位表的偏差，三条：**

1. ★★ **「阅读量 / 进度上报」被拆成了两个 Tag，而且是各自的【服务自发自消】。**
   原设想是「一个 Tag、消费组 `group-interaction-stat`、批量聚合后落库」——
   但那个消费组要**同时写 content 的 `novel.view_count` 和 interaction 的 `read_history`**，
   而项目自己的铁律是「服务之间不共享数据库表」。**两条不能同时成立。**
   → 拆成两个 Tag、两个消费组，各自只写自己的表。
   ★ 所以「阅读量的消费方是 content，不是 interaction」——
   这和大纲 §11.2 把生产者写成 `gateway/content → interaction` 的两种可能里选的那一种有关，答案见下一节。

2. ★ **`NOVEL_STAT` 没有用顺序消息，用的是「应用层单调写」。**
   原因见 [M3 文档](M3-引入MQ.md) §四 判断 B′ —— 而且那一节记的是**一次被实测推翻的设计论证**，
   值得单独读：初稿依据的那条「顺序消息永不进 DLQ、永久卡死」的性质，**在本项目里从来没有生效过**。

3. ★ **`AUDIT_RECORD` 这个 Tag 有【两个】生产者，发送方式故意不一样**：
   auth 发**事务消息**（它在 `@Transactional` 里），interaction 发**普通消息**（提交后发）。
   ★ 差别不在「谁更重要」，而在**发送方在不在一个事务里**。

**实测数字（可以直接甩的）：**

- **阅读量**：2000 条消息 → **21 次 `UPDATE`**（**1 : 95**）。
  拆开看：1000 条 / 同一个 novelId → **1 次 UPDATE**；1000 条 / 20 个 novelId → **20 次**。
  ★ 落库值**恰好 +1000**，零丢失。
- **投递失败 ≠ 读者看到错误**：压测里 **3982 次投递失败回调**，而 **2000/2000 个请求全部 HTTP 200**。
  ★ 这两个数字说的不是同一件事，混着讲就会把「埋点降级成功」说成「丢了几千条」。
- **事务消息**：「半消息裁决 → 消费者落库」**178 ms**；
  修 `TransactionSendResult` 掉 `offsetMsgId` 那个 bug 之前，靠 Broker 回查要 **~14 秒**。
- **ORDERLY 的代价（实测，不是推测）**：毒消息 → 本地重试**固定 1 秒** × 3 次 →
  进 `%DLQ%` 放行。**该 MessageQueue 被阻塞约 4 秒。**
  对照并发消费：重试阶梯是 **10s / 30s / 60s**，走 `%RETRY%` Topic 往返 Broker。
- **环境**：中间件那台虚拟机是「饿」的 —— Nacos 就绪 3.1 s，MySQL `SELECT 1` 往返 194~295 ms，
  `asyncSend` 会因为客户端自己拿不到 async 信号量而抛 `RemotingTooMuchRequestException`。
  ★ 排查时**别看 `e.getMessage()`**：RocketMQ 对非 connect / timeout 的异常统一包装成 `"unknown reason"`，
  真因在 `cause` 里。

**★ 一个新增的、比上面「三大作用」更该在面试里说的判断：**

> **推「增量」的可以乱序；推「绝对值」的，要么顺序、要么带时间戳做单调写。**

这条比对「同一用户进度不能乱序」的说法更根本 —— 它同时解释了为什么收藏数也要防乱序。

### ★★★ M4 落地情况（**2026-09-23 实施后补记 —— 第五条消息，也是五条里最省的一条**）

M4 上了 ES，搜索要跟着作品变更重建索引 —— **这听起来是「再加一条消息」，
实际做出来是一条形状完全不同的消息**，值得单独记：

| Tag | 方向 | 消费模式 | 载荷 | 防乱序/防重靠什么 |
|---|---|---|---|---|
| **`NOVEL_INDEX`** | content → search | CONCURRENTLY | ★★ **只有一个 `novelId`**（+ 一个 `reason` 供观测） | ★★★ **什么都不用防** |

★★★ **它是五条消息里唯一「幂等免费、顺序无关」的 —— 因为载荷里没有数据。**
推的是「**这本书的索引可能过期了，去重算一次**」这个**指令**，
消费者拿到 id 之后**自己去读当时的真值**、写进 ES。

于是：两条乱序消息各自触发一次重建 → **两次都读同一份当前状态、写同一个文档** → 结果一样。
重复消费也一样。**不需要 SETNX、不需要时间戳、不需要 ORDERLY。**

★ 对照着看另外四条就明白了：`VIEW_REPORT` 推增量（累加天然可交换）、
`PROGRESS_REPORT` 推绝对值（靠 ORDERLY）、`NOVEL_STAT` 推绝对值（靠时间戳单调写）、
`AUDIT_RECORD` 推事实（靠 SETNX）。
**前四条都在防「同一份数据被写两次/写乱」，第五条把数据本身拿掉了，所以没得乱。**

★★ **可推广的一句话：「去重算一次」这个指令，永远比「算好的结果」好维护。**
★ 面试里比「我会用事务消息」更难答、也更值分的是：**什么时候【不】用。**

**M4 顺手证伪的两条大纲设计（都记在 [M4 文档](M4-摘出search.md) 里）：**

1. ★★ **大纲设计的 `group-content-stat` 消费组根本不该存在。**
   它想把「章节发布 → 更新小说冗余字段（字数/章节数/更新时间）」也改成消息 ——
   但那两张表**同库、同服务，而且本来就在同一个事务里**（`syncNovelStat` 自己带 `@Transactional`）。
   改成「发消息 → 自己消费 → 再写」= 把一个**原子操作降级成最终一致**，
   还额外引入「消息丢了就永久不一致」，**纯粹变差**。
   → M4 只有一个消费方：search。
   ★ 判据：**先问那个数据到底在哪张表、谁的事务里**，再决定要不要拆。

2. ★★ **这条消息【不需要】事务消息。**
   M3 文档里曾预测「M4 会用 `CHAPTER_PUBLISHED` 事务消息 + 索引重建」——
   M4 只兑现了后半句。两条理由：
   ① 仓内已有的判据（`AfterCommit` 类注释）写的是「**有对账兜底的用 `AfterCommit`，无对账的才用事务消息**」，
     而 M4 引入了**定时全量重建**（= 对账）→ 按这条判据就该用 `AfterCommit`；
   ② ★ **事务消息买到的东西已经被另一条设计吸收掉了** ——
      ES 侧 `filter(status=2)` + content 侧装配时的可见性条件（两道闸门）让
      「索引里出现一个不存在的状态」的后果**完全消失**（最坏是索引里多一条草稿文档，用户看不见）。
      **剩下的只有「提交后崩溃」那个窗口。**

★ **还有一个纯工程的理由**：走事务消息必须新开专用事务组（M3 已经为完全相同的理由开过 `novel-tx-audit`），
而 content 与 interaction **共用** `novel-producer` 实例池 ——
半消息可能被投给**没有 `@RocketMQTransactionListener` 的进程**，回查返回不了真值、半消息悬着**且不报错**。

**一条 M4 新踩的坑（值得单独记）：**

| 现象 | 根因 |
|---|---|
| ★★ 给消息载荷里的**枚举**填了一个非法值 → 消息**一条都没被消费，直接进 DLQ**，而我们的 `try/catch` **一行日志都没打** | `rocketmq-spring` 的**消息转换**发生在 `@RocketMQMessageListener` 方法被调用**之前** —— **我们的 `try/catch` 根本没机会执行** |

★★ **推广：「我的消费者代码永远不会抛异常」这个保证，只覆盖【方法体之内】。**
★★★ **实操警告：给消息载荷里的枚举改名或删值，在途消息会【全部】静默进 DLQ** ——
枚举的兼容性不是编译期问题，是运行时问题。

## 九、常见误区

| 误区 | 纠正 |
|---|---|
| 「MQ 是为了提高性能」 | 它**不提高单次请求的速度**，反而多一次网络往返。它提高的是**系统的吞吐能力和可用性** —— 让慢活不阻塞快活 |
| 「用了 MQ 就不会丢消息」 | 默认配置下**会丢**。生产端、Broker、消费端三段都要单独配置可靠性（见第十二节） |
| 「MQ 保证消息不重复」 | 绝大多数 MQ 只保证 **at-least-once**（至少一次），重复是常态，**必须消费端做幂等** |
| 「MQ 保证顺序」 | 默认**不保证**。要顺序必须显式使用顺序消息，且要接受并行度受限的代价 |
| 「消费组越多越好」 | 每个消费组都会拿到全量消息。组越多，同一条消息被处理的次数越多，下游压力越大 |
