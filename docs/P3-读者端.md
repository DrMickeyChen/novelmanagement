## 设计要点与坑

### D-1 ★★ 白名单按方法收紧（P2 留下的一个静默口子）

`SecurityConfig.WHITELIST` 原有 `"/api/categories"` 和 `"/api/novels/**"`。**`requestMatchers(path)` 不限定 HTTP 方法** —— 意味着以后任何人往 `/api/novels/**` 下加一个 `POST /api/novels/{id}/delete`，都会**静默匿名放行**：不报错、不崩溃、测试全过，只是所有人都能调。

改法是把这两条从 `WHITELIST` 拿掉，改成方法限定的三条 + 一条精确 POST 窄口子：

```java
.requestMatchers(HttpMethod.GET,  "/api/categories").permitAll()
.requestMatchers(HttpMethod.GET,  "/api/novels/**").permitAll()
.requestMatchers(HttpMethod.GET,  "/api/search").permitAll()
.requestMatchers(HttpMethod.POST, "/api/novels/*/view").permitAll()   // ★ 单星
```

**默认值因此是安全的**：新加一个 GET 自动公开（读者端本就该公开），新加一个写接口自动要求登录。不需要再维护路径清单。

> ★ **千万不要把 `"/api/novels/**"` 加回 `WHITELIST`** —— 那会让上面几行彻底失效，而且没有任何症状，直到有人往这个前缀下加了写接口。

`POST /api/novels/*/view` 敢开放，是因为三件事同时成立：**不写库**（只 INCR 一个 Redis 计数器）、**不产生数据**（无 INSERT、无唯一键、不记录调用者）、**不放宽读的口径**（对不存在的书与未上架的书一视同仁）。

**顺带改掉了 `ReaderNovelController` 的类注释。** 它原文写着「读者端没有写接口，以后也不该有」—— 原意是对的（不能把会写用户数据的接口塞进免登录前缀），但措辞把阅读量埋点也一起禁掉了。新措辞：

> ★ **读者端不写用户数据。** 这个前缀下没有改动任何业务表的接口。会落用户数据的写接口（评论、书架、阅读进度）仍然必须放在需要登录的 `/api/reader/**` 下。

> 考虑过的替代方案：把埋点挪到 `/api/views/{id}` 单独开一个匿名前缀，这样能原文不动地保住那条约定。没采用是因为它把同一份资源拆到两个前缀下（`/api/novels/{id}` 读、`/api/views/{id}` 写），而约定要守的是「不写用户数据」这个**目的**，不是路径形状。

### D-2 阅读量计数：`StringRedisTemplate` + 脏集合 + 定时落库

**★★ 必须用 `StringRedisTemplate`，不能用 `RedisTemplate<String,Object>`。** 后者的 value serializer 是 `GenericJackson2JsonRedisSerializer` + `activateDefaultTyping`，`opsForValue().increment()` 写进去的不是整数 `1`，而是一坨带 `@class` 的 JSON —— INCR 一个 JSON 值 Redis 直接报 `ERR value is not an integer`。`StringRedisTemplate` 是 Boot 自动配置好的（`RedisConfig` 只覆盖了 `RedisTemplate<String,Object>`），直接注入即可。

**key**：复用 `NOVEL_VIEWS = "novel:novel:views:"`（+ novelId），脏集合新增 `NOVEL_VIEW_DIRTY = "novel:novel:view_dirty"`（Set）。

**写**：`POST /api/novels/{id}/view` → 先校验书存在且已上架 → `INCR` + `SADD`。

> ★ 校验存在性**不是为了正确性，是为了不给匿名接口一个无限造 Redis key 的口子**。不校验的话，攻击者 POST 一百万个随机 id，就在 Redis 里留下一百万个永不过期的 key。未上架的书也不计数 —— 它的正文读者根本读不到。

**落库**：`@Scheduled(fixedDelayString = "PT30S")`。★ 用 ISO-8601 的 Duration 写法，别写裸数字（裸数字单位是毫秒，`30` 会变成每 30 毫秒跑一次）。

**★★ 顺序不能反：先 `SREM` 认领，再 `GETDEL` 取数。**

```java
if (stringRedisTemplate.opsForSet().remove(NOVEL_VIEW_DIRTY, id) == 0L) continue; // 别的实例领走了
String raw = stringRedisTemplate.opsForValue().getAndDelete(NOVEL_VIEWS + id);
// → UPDATE novel SET view_count = view_count + ? WHERE id = ?
```

先 `GETDEL` 再 `SREM` 有个窗口：我们读到 100 → 用户又点一次 INCR 成 1 并 SADD → 我们 SREM 把它删掉 → **那一次阅读量永久丢失**，而且脏集合也被清干净了，再没有任何一轮会来救它。

★ **由此推出的一条：不要在循环末尾再补一次 SREM。**「反正处理完了，再 SREM 一次保险」是有害的 —— 处理期间如果有读者点击，他会把 id 重新 SADD（那是尚未落库的新增量），收尾那一刀会把这个新标记删掉。

★ **`INCR` 和 `SADD` 的顺序同样不能反**：先 SADD 再 INCR，中间恰好夹了一次落库（SREM 成功 → GETDEL 拿到 null → 空转），脏集合里的标记就被摘掉了，这个值要等下次有人点击才会落库。

★ **`SREM` 返回 1 才处理 —— 它本身就是一个分布式锁**，所以这里**不需要** `RedisKeyConstant.LOCK_PREFIX`。但这个结论只对「消费型」的 key 成立（取走就没了）；哪天改成「读出来再更新」，这个原子性立刻消失。

★ **「DB 更新失败要收尾」这个问题在认领式设计下根本不存在**：`SREM` 发生在最前面，等到执行 DB 更新时 id 早已不在脏集合里了，失败也不会留下任何需要清理的痕迹。方案初稿写的是「在 `finally` 里补一次 SREM」，那是**先 GETDEL 后 SREM** 那个设计的补丁 —— 换成认领式之后，那个 `finally` 不但多余，而且有害（见上一条）。

**★★ 失败方向是刻意选的：宁可少算，不可多算。** DB 更新失败时**不做补偿、不回滚 Redis**，只记 WARN 把丢失的量写进日志。少算的补偿是时间（下次有人读这本书会重新 SADD，`GETDEL` 把积压的一起捞出来，是**自愈**的）；多算没有任何办法修正，而「UPDATE 已提交但响应回不来」是会真实发生的。

**不做防刷去重**，理由：去重键要么是 IP（本地 / 内网 / dev-proxy 转发后全是 `127.0.0.1`，会让榜单在本地看起来完全不动，排查成本远高于它挡住的那点虚高），要么是用户（匿名读者没有）。真正有效的防刷要「用户维度 + 限流」，那是二期上 Sentinel 时的活。这里的虚高只影响榜单排序，不是资损。

### D-3 搜索：`.and()` 括号是安全边界

**★★ 绝不能把 `.like()` / `.or()` 平铺在顶层。** 平铺生成的是 `WHERE status = 2 AND title LIKE ? OR author_id IN (...)`，而 SQL 里 `AND` 优先级高于 `OR`，等价于 `WHERE (status = 2 AND title LIKE ?) OR (author_id IN (...))` —— **只要作者命中了，那本书是不是已上架根本不参与判断，未上架的草稿会被搜出来**。这是真实的内容泄露，而且不报错。

```java
LambdaQueryWrapper<Novel> qw = new LambdaQueryWrapper<Novel>()
        .eq(Novel::getStatus, NovelStatus.PUBLISHED)
        .and(w -> w.like(Novel::getTitle, kw)
                .or(!authorIds.isEmpty(), x -> x.in(Novel::getAuthorId, authorIds)));
// 生成：WHERE status = 2 AND (title LIKE ? OR author_id IN (...))
```

另外三条：
- **空关键词在进 wrapper 之前就 `return PageResult.empty()`** —— 否则会生成 `AND (title LIKE '%%')`（什么都没过滤），作者列表也空时更会生成 `IN ()`，直接 SQL 语法错误。
- **作者 id 列表有上限（`LIMIT 100`）**。`sys_user.nickname` **没有索引**，昵称模糊查是全表扫描，而且前导通配符让任何索引都用不上。
- **`userIdsByNickname` 用 `LambdaQueryWrapper` 写，不手写 `@Select`** —— 理由和 `NovelMapper` 是空接口一样：wrapper 让 `@TableLogic` 自动补 `deleted = 0`，手写就得自己记得写，忘了的话已注销用户的书会混进搜索结果。

> ★ 这里的 `.last("LIMIT 100")` 和「绝不拼 SQL」那条规矩**不冲突**：拼进去的是一个编译期常量，不含任何来自请求的字符。区别是「值从哪来」，不是「用不用 `.last`」。

**为什么搜索单独开 `/api/search` 而不复用 `/api/novels?keyword=`**：语义不同。列表页的 `keyword` 是「在当前分类里筛书名」，搜索页是「跨全站搜书名或作者名」。混成一个会让分类页的筛选框在用户输入作者名时返回一堆不相关的书。

### D-4 榜单：不拼 SQL，用 `buildPage(1, limit)` + `selectPage`

**不要用 `.last("LIMIT " + limit)`** —— 那是字符串拼 SQL，`limit` 一旦来自请求参数就是注入口。用已有的 `buildPage(1, limit)` + `selectPage`，`limit` 再在 Service 里夹到 `[1, 50]`。

三个排序都**末尾加 `.orderByDesc(Novel::getId)` 兜底** —— `view_count` 有大量并列（种子数据里尤其多），没有兜底列时分页顺序不稳定，同一个请求两次可能给出不同顺序。

**★ 路径用 `/api/novels/rank?type=`，不是大纲 §6.3 原来写的 `/api/novels/hot`。** 理由三条：① 三个榜是同一个接口，`/hot?type=new` 自相矛盾；② §7.1 的页面本来就叫 `/rank`；③ 它彻底避开了 `/api/novels/{id}` 的路径变量竞争 —— 虽然 Spring 的 `PathPattern` 比较器里字面量优先于变量（`/rank` 会稳定命中），但一旦有人拼错成 `/api/novels/hott`，请求会掉进 `{id}` 分支，报的是「Failed to convert 'hott' to Long」这种完全指不到问题所在的错。**已同步改进 `项目大纲.md` §6.3。**

> ★ 方案文档自相矛盾过一次：负向用例表写「`limit=9999` → 最多 100 条」，而 D-4 的正文写「夹到 `[1, 50]`」。**实现取 50**（`RANK_MAX_LIMIT`），测试也按 50 断言。留这条记录是因为面试问到「你的上限是多少」时，两份文档不一致比一个数字更难解释。

### D-5 `modules/interaction/` —— 阅读进度

```
modules/interaction/
├── entity/ReadHistory.java          ★ 无 createTime、无 @TableLogic
├── mapper/ReadHistoryMapper.java    一条 @Insert ... ON DUPLICATE KEY UPDATE + 按 (userId, novelId) 查
├── service/HistoryService.java + impl/HistoryServiceImpl.java
├── dto/HistoryReportDTO.java
├── vo/ReadHistoryVO.java
└── controller/ReaderHistoryController.java   → /api/reader/history
```

**依赖方向**：`interaction → content`（用 `NovelAccessGuard.requireChapterInNovel` 校验章节归属）。和 `content → system` 同向，是允许的；二期 M3 拆出去时这个调用变成 Feign。

**★★ `ReadHistory` 实体绝对不能有 `createTime` 字段。** `read_history` 表**没有 `create_time` 列**，而 `MybatisMetaObjectHandler` 的 `strictInsertFill` 会把带 `@TableField(fill = INSERT)` 的字段塞进 INSERT 语句 —— 结果是每一次进度上报都 `Unknown column 'create_time'`。同理这个表**没有 `deleted` 列，所以实体不能有 `@TableLogic`**。

> 这与 P2 的 `AuditLog` 是**同一类坑的两个方向**：那张表没有 `update_time`，所以那个实体不能有 `updateTime`。P2 文档记的是后一半，这里是前一半。

**upsert 用 `INSERT ... ON DUPLICATE KEY UPDATE`**（手写 `@Insert`，一条 SQL 原子完成）。不选「先查后插 + 捕获 `DuplicateKeyException`」：那要写两个分支 + 一个 catch，而 `uk_user_novel` 的存在就是为了让数据库来裁决。★ `read_history` 没有 `deleted` 列，所以 P2 的 C-8「手写 SQL 必须自己写 `deleted = 0`」这条**不适用**——注释里要说明为什么这里可以破例，否则后来人会以为是漏了。

**校验顺序**（别信前端）：novel 存在且已上架（否则 2001）→ `requireChapterInNovel`（否则 3001）→ 章节已发布（否则 3001）→ `progress` 夹到 `[0, 100]`。**这四步和 `ChapterServiceImpl.readerDetail` 的校验完全一致是刻意的** —— 上报的进度必须指向一个「读者本来就能读到的位置」，否则可以拿它当探针探测未上架的书有哪些章。

### D-6 前端

**结构**：阅读器**脱离 `BasicLayout`**，放顶层路由 —— 它要全屏，而且进度计算必须基于**自己的滚动容器**（`scrollTop / scrollHeight`），不是 `window`，否则顶部导航栏的高度会让百分比永远算不准。滚动容器的高度用 `100%` 而不是 `100vh`（移动端地址栏收放会让 `100vh` 跳）。

**`scrollBehavior` 恢复 `savedPosition`** —— 原来是 `return { top: 0 }` 把 `savedPosition` 丢了，从详情页进详情页再返回会永远滚回顶部。

**状态存放**：设置进 Pinia（`stores/reader.js`：字号 4 档 / 行距 3 档 / 背景 4 色），**进度不进 Pinia**（按 novelId 分片、只被阅读器一页读，放进全局 store 等于每次翻页都触发全站响应式更新）。

**设置用 CSS 变量落地，不用 class 组合** —— 4×3×4 = 48 种组合，用 class 要写 48 条规则且每加一档翻倍。改成往阅读器根节点绑 4 个行内变量（`--reader-font-size` / `--reader-line-height` / `--reader-bg` / `--reader-fg`）。

**★★ 进度上报 / 阅读量埋点必须带 `{ silent: true }`。** 不带的话，token 过期时 `request.js` 的 401 分支会 `clearAuth()` + 600ms 后 `window.location.href` 整页跳登录页 —— **读者正在往下滚，页面突然整页跳走，进度全丢**。这个 bug 本地几乎测不出来（开发环境 token 很少过期），一定会漏到线上。`silent` 是自定义标记，**请求拦截器和响应拦截器两处都要判**，少判一处就是「成功时安静、失败时弹窗」的半静默。

> ★★ **但 `silent` 不等于不会 reject。** 拦截器照样把 Promise 拒出去，只是拒得悄无声息。所以**调用方必须自己兜住**：`reportNovelView(id).catch(() => {})`。漏了就是 unhandledrejection —— 控制台一片红，接了 Sentry 之类的上报工具会被当成真错误报上去，而它其实只是「阅读量少记了一次」。
> 这一点在实施时**真的漏了一处**：阅读器页面上报进度那处写了 `.catch(() => {})`，详情页的埋点没写。负向用例 14 的前端侧（用 `Network.setBlockedURLs` 掐掉埋点 + 监听 `unhandledrejection`）把它抓了出来。

**进度恢复的判定顺序**：
1. localStorage 里有记录**且 `chapterId` 与 URL 上的章节一致** → 恢复像素偏移
2. 不一致（用户是链接直达）→ 用**服务端返回的百分比**兜底，**且只在服务端的 chapterId 也对得上时才用**
3. 都没有 → 置顶

> ★ 第 2 条括号里那句话是**对方案的一处收紧**：方案原文只说了「用服务端百分比兜底」。实施时改成「服务端的 chapterId 也必须匹配」—— 理由和 `readerStorage.js` 自己不存百分比是同一条：**一个属于别的章的百分比是没有意义的**，套上去只会停在一个莫名其妙的位置。已验证：打开另一章不会被套上服务端的百分比。

服务端百分比的恢复必须在 `nextTick` + `document.fonts.ready` **之后**应用 —— 字体加载完 `scrollHeight` 才稳定，早于它会恢复到一个偏小的位置，用户看到的就是「进度没记住」。`max = scrollHeight - clientHeight <= 0` 时直接返回（正文短于一屏，没有可恢复的位置）。

**上报**：滚动 1 秒防抖；`beforeunload` 里再报一次（接受其不可靠）。**★ 不用 `navigator.sendBeacon`** —— 它不带 `Authorization` 头，要带 token 只能塞进 URL，等于把 token 写进 access log（§7.5 明确拒绝过）。**游客只写 localStorage、不发请求**。

**★★ 事件监听器签名冲突（P3 期间真实踩到的 bug，详见「实施记录 ⑤」）**：`window.addEventListener('beforeunload', flushProgress)` 会把 **Event 对象**当作第一个实参传进去。`flushProgress` 有 `forChapterId` 形参，于是 `Number(event)` = `NaN` → `JSON.stringify({chapterId: NaN})` → `{"chapterId":null}`，**每次页面卸载都把好记录覆盖成读不出来的**。必须包一层无参的 `handleBeforeUnload()`。

**中文语言包**：`main.js` 没有 `app.use(ElementPlus)`（按需引入），全仓 grep `zh-cn` 原来零命中 —— `el-pagination` 显示 "Total 128"、`el-empty` 显示 "No Data"，且不报错。在 `App.vue` 用 `<el-config-provider :locale="zhCn">` 包住 `<router-view />`。★ 它管不到命令式 API（`ElMessageBox.confirm` 的按钮文案要显式传参）。★ 只在 reader-web 加 —— author-web / admin-web 没有用 `el-pagination`，不需要。

**`composables/usePagedList.js`** —— 全仓第一个分页范式，首页 / 分类 / 榜单 / 搜索共用。两个必须记住的点：`loaded` 要区分「还没查过」和「查过但为空」（少了它首屏 loading 和 `el-empty` 会同时出现）；`changeSize` **必须重置 `page = 1`**（不重置的话从 10 条/页切到 50 条/页时 page 还是 13，列表空白而 total 很大，看起来像后端分页算错了）。
★ 它忽略服务端返回的 `current` / `size`，因为 `PageResult.empty()` 硬编码返回 `current=1, size=10`。

**阅读器功能范围**：大纲 §7.2 的 1~5（基础翻页 / 目录抽屉 / 阅读设置 / 进度记忆 / 键盘快捷键），第 6 项移动端滑动推到 P6。正文用 `{{ content }}` + `white-space: pre-wrap`，**严禁 `v-html`**。键盘翻页判 `e.repeat`（长按会连翻十几章）、`e.ctrlKey/altKey/metaKey`（不抢浏览器快捷键），并 `e.preventDefault()`；焦点在 INPUT/TEXTAREA/contentEditable 时直接返回。

**「继续阅读」的目标不能用 `novel.lastChapterId`** —— 它是 `syncNovelStat` 维护的「最新章节」，语义是「最新」不是「已读」，拿它当续读目标会**把用户扔到最新一章，也就是剧透**。正确来源是本机进度记录，三级回退：记录里的章节仍在目录里 → 目录第一章 → `null`（按钮置灰）。

**详情页目录**：`NovelDetailVO` 是**一次性全量返回**的，「章节目录（分页）」P3 不做（一本书 3~8 章，分页无意义），**记进遗留**。

### D-7 种子数据的冗余字段不变量

`syncNovelStat` **只在章节状态流转时被调用** —— 直接 `INSERT` 的种子书，四个冗余字段永远不会被重算，必须手工写对。13 条不变量（`author_id` 用子查询取、分类覆盖 1~8、`is_finish=1` 恰好 2 本、`chapter_count`/`word_count`/`last_chapter_id`/`last_update_time` 与章节对齐、`chapter_no` 从 1 连续、**每章都要有 `chapter_content` 行**、正文 ≥ 1500 字、`view_count` 给非 0 初值、书名不含单引号、`INSERT IGNORE` + 显式 id）全部写在 `docs/sql/seed.sql` 的种子块注释里。

> **第 10 条（正文要够长）不是洁癖**：正文短于视口高度时 `scrollHeight == clientHeight`，`max <= 0`，进度永远 100%，**看起来像进度功能坏了**。当前库里就有一条这样的真实数据，见「遗留 ②」。

## 实施记录（对方案的修正）

方案里的 S0~S10 全部执行。以下是**实施中发现方案本身有问题**、或者方案没预料到的地方。

### ① `PageResult.empty()` 硬编码 `current=1, size=10`

方案说空结果返回 `PageResult.empty()`。实施时发现它返回的 `current` / `size` 是写死的 1 和 10，**和请求里的分页参数无关**。行为上没问题（前端 `usePagedList` 本来就只认自己的 page/size），但如果哪天有调用方信任服务端回显的 `current`，就会出现「请求第 3 页，服务端说你在第 1 页」。已在 `usePagedList` 的注释里点名。

### ② 方案漏了：**审核作品不会顺带审核章节**

方案的主链路验证写的是「作者提交 → 管理员通过 → 匿名能读」。实施时发现**作品和章节是两条独立的审核链**：`PUT /api/admin/novels/{id}/audit` 只改作品状态，章节要单独走 `PUT /api/admin/chapters/{id}/audit`。

结果是「作品已上架、章节还是待审」——读者能看到详情页和目录，**点进章节却是 3001**。这个组合状态在方案里完全没有提到，回归脚本第一次跑就撞上了。已在回归脚本里补上第二步，并保留两条断言（确认 3001 与 200 两种状态都真实存在过）。

### ③ 负向用例 10 一开始写成假阳性

「上报一本未上架书的进度 → 2001」第一次跑返回 200。**不是 app 的问题，是测试写错了**：用例跑在 A 段之后，而那本书在 A 段已经被审核上架了，200 才是正确答案。改成**新造一本保持草稿状态的书**来测。这条记下来是因为「测试自己写错」和「代码真的错了」在输出上长得一模一样。

### ④ `redis-probe.py` 的输出是 `命令 -> 结果`，不是裸结果

两次踩到同一个坑：脚本里 `redis("GET", key) == "abc"` 永远为假。原因有两层 —— ① 它打印的是 `GET novel:novel:views:1004 -> 'abc'` 整行；② **字符串结果带单引号**（`'abc'`），整数不带（`1`、`0`）。

第二层其实是 redis-cli 的**正确行为**，那个引号区分「字符串 `"1"`」和「整数 `1`」—— 正是 Redis 里 INCR 能不能跑的决定性差别，所以不要「顺手去掉引号」，要在断言里按带引号的样子写。

### ⑤ ★★ 事件监听器把 Event 对象当成第一个实参（**唯一的真 bug**）

**症状**：阅读器刷新之后进度永远回到开头，「记住进度」这条验收标准直接不成立。

**定位过程**（三步，每步都排除了一个假设）：
1. 从**另一个 URL** 进入同一章，恢复是好的 → 排除「恢复逻辑本身写错」。
2. 重现失败，读 localStorage，发现存的是 `{"chapterId": null, ...}` → 问题在**写**的一侧，不在读。
3. 用 `Page.addScriptToEvaluateOnNewDocument` 钩住 `Storage.prototype.setItem` 记录调用栈 → **新文档里 0 次写入** → 说明这次写入来自**旧文档的卸载过程**。

**根因**：

```js
window.addEventListener('beforeunload', flushProgress)   // ← flushProgress(forChapterId)
```

`beforeunload` 触发时，浏览器会把 **Event 对象**作为第一个实参传进来。`flushProgress` 此时已经加了 `forChapterId` 形参（为了让切章时能保存**旧**章的位置），于是：

```
forChapterId = Event  →  Number(Event) = NaN
                      →  JSON.stringify({chapterId: NaN}) = {"chapterId":null}
```

而 `loadProgress` 的字段校验会拒绝 `chapterId: null`（这是对的），于是记录读不出来，**每次刷新都从头开始**。

**修复**：包一层无参的 `handleBeforeUnload()`，注册和注销都用它。

**同时加的第二道防线**：`saveProgress` 在写之前校验 `chapterId`，不合法就**整个放弃这次写入**。理由是读的一侧已经在校验了，写的一侧不校验的话，一个坏值会**覆盖掉本来好好的旧记录** —— 下次连正确的位置也读不回来。宁可保留上一次的正确位置，也不要写进去一个读不出来的值。

**★ 同类陷阱**：任何「带形参的函数直接当事件监听器」都会中招。`@scroll` 绑的是 `onScroll`（无参），安全；**不能**把它改成 `flushProgress`。

**留下的取证签名**：`Number(undefined)` → `NaN`；`JSON.stringify({a: NaN})` → `{"a":null}`。看到 `"chapterId": null` 就该想到这条路。

### ⑥ 阅读器里自检出来的三处（在测试之前就改掉了）

- 切章时 `watch(chapterId)` 会把**新的** chapterId 和**旧的**滚动位置一起存下去（所以 `flushProgress` 才需要 `forChapterId` 参数）。
- 「第 N 章」原来用的是目录数组下标，不是 `chapterNo`。
- 另加一个 `watch(novelId)` 会跟 `watch(chapterId)` 重复触发 `loadChapter`。最终**只留一个 chapterId 的 watcher**（chapterId 全局唯一，换书时两者必定同时变），并在里面用 `novelId` 判断要不要重新拉详情。

### ⑦ `ReadHistory` 的 upsert 里 `chapter_id` 不能漏

`ON DUPLICATE KEY UPDATE` 的字段列表必须包含**所有**会变的列。第一次写的时候漏了 `chapter_id`，表现是「换了章节上报，进度百分比变了但章节没变」—— 这种「部分更新」的 bug 在只有一条断言时很容易漏过，所以回归里专门有一条「第二次上报覆盖了第一次」。

```sql
--    chapter_count 为 NULL 时 NULL = 0 结果是 NULL，HAVING 判假 → 漏报

LEFT JOIN chapter c ON c.novel_id = n.id AND c.status = 2 AND c.deleted = 0
WHERE n.deleted = 0 GROUP BY n.id, n.chapter_count
HAVING (n.chapter_count <=> COUNT(c.id)) = 0;
-- 实测 0 行 ✅

-- A2 word_count 漂移
SELECT n.id, n.word_count, COALESCE(SUM(c.word_count),0) FROM novel n
LEFT JOIN chapter c ON c.novel_id = n.id AND c.status = 2 AND c.deleted = 0
WHERE n.deleted = 0 GROUP BY n.id, n.word_count
HAVING (n.word_count <=> COALESCE(SUM(c.word_count),0)) = 0;
-- 实测 0 行 ✅

-- A3 last_chapter_id 漂移（含指向已删章节）
SELECT n.id, n.last_chapter_id, t.mx_no FROM novel n
LEFT JOIN (SELECT novel_id, MAX(chapter_no) mx_no FROM chapter
           WHERE status = 2 AND deleted = 0 GROUP BY novel_id) t ON t.novel_id = n.id
LEFT JOIN chapter lc ON lc.id = n.last_chapter_id
WHERE n.deleted = 0 AND (lc.chapter_no <=> t.mx_no) = 0;
-- 实测 0 行 ✅

-- A4 分类覆盖。★★ 必须加 c.deleted = 0，否则会把 P2 软删掉的测试分类算进来
SELECT c.id, c.name FROM novel_category c
LEFT JOIN novel n ON n.category_id = c.id AND n.status = 2 AND n.deleted = 0
WHERE c.deleted = 0 GROUP BY c.id, c.name HAVING COUNT(n.id) = 0;
-- 实测 0 行 ✅（P3 期间是 1 行 —— 分类 12「验收临时分类」，已按遗留 ① 处理）

-- A5 完结书数量：期望 2
SELECT COUNT(*) FROM novel WHERE status = 2 AND is_finish = 1 AND deleted = 0;
-- 实测 2 ✅

-- A6 ★ 已发布章节缺正文（最容易漏的一条）
SELECT c.id, c.chapter_no FROM chapter c
LEFT JOIN chapter_content cc ON cc.chapter_id = c.id
WHERE c.status = 2 AND c.deleted = 0 AND cc.chapter_id IS NULL;
-- 实测 0 行（种子 47 章 + 正文 47 行）✅

-- A7 正文过短。★★ 必须 join chapter 限定 status = 2，
--    否则会把草稿/软删章节的短正文一起算进来，误报
SELECT cc.chapter_id, CHAR_LENGTH(cc.content) FROM chapter_content cc
JOIN chapter c ON c.id = cc.chapter_id
WHERE c.status = 2 AND c.deleted = 0 AND CHAR_LENGTH(cc.content) < 800;
-- 实测 0 行 ✅（P3 期间是 1 行 —— novel 3《P2验收书-地域》的 33 字正文，已按遗留 ② 处理）
-- 12 本种子书的 47 章，正文长度区间 1791~2042 字 ✅
```

> A4 和 A7 两条**在本库上不是 0 行**，而且两条都不是种子数据的问题：A4 漏了 `c.deleted = 0`（查询写错），A7 漏了 `status = 2`（查询写错）。修正后的剩余命中都指向 P2 的验收遗留数据。**把这段写进文档是因为「自检 SQL 报错」的第一反应应该是先怀疑 SQL 自己** —— 这两条第一次跑的时候，看起来都像是种子数据写坏了。

### 1. ★ CDP 驱动 headless Chrome 做 E2E，不需要 puppeteer

```
chrome.exe --headless=new --remote-debugging-port=9333 --remote-allow-origins=*
           --user-data-dir=%TEMP%\p3-chrome-profile
```

然后 `fetch('http://127.0.0.1:9333/json/list')` 拿 `webSocketDebuggerUrl`，用 Node 22+ 内置的全局 `WebSocket` 连上去发 CDP 命令。三个特别好用的能力：

- **`Page.addScriptToEvaluateOnNewDocument`** —— 在页面自己的脚本之前执行。用它钩 `Storage.prototype.setItem` 记录调用栈，是定位实施记录 ⑤ 的关键；用它装 `unhandledrejection` 监听才能抓到页面加载期间的未处理拒绝。
- **`Network.setBlockedURLs`** —— 精确掐掉某一个接口，模拟「这个请求整个失败」。
- **`Runtime.evaluate` 里造合成 `KeyboardEvent`**（含 `repeat: true`）比 `Input.dispatchKeyEvent` 更好用 —— 长按、修饰键这些分支能直接构造。

**两个测试自身的坑**：
- **`history.length` 必须按增量比。** `Page.navigate` 自己会往历史里加条目，拿绝对值比等于什么都没测。要在切 Tab **之前**取一次基线。
- **`requests.length = 0` 要在页面加载完之后再清。** 否则会把上面那次 `Page.navigate` 自己产生的 NAV 记录当成「401 导致的整页跳转」。

### 2. `mvn` 不在 PATH 上

`D:/MickeyChen/usefultool/apachemaven/download/apache-maven-3.9.9/bin/mvn`。

### 3. Git Bash 里 `curl -d` 传内联中文必炸

和 P2 记的是同一条：用 `--data-binary @file`，行内中文会因为 ANSI 码页假报 400。P3 期间的验证脚本一律用 Python `urllib` 发请求，彻底绕开这一层。

### 4. Windows 上 `mvn package` 会因为没有权限重命名 jar 而失败

后端 `java -jar target/novel-backend.jar` 还跑着的时候 `mvn package` 必失败，**而且会留下一个 thin jar**（没有依赖，`java -jar` 起不来）。打包前先停后端。
