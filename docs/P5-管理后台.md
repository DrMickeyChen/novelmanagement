# P5 · 管理后台 —— 实施方案与实施记录

> 对应项目大纲 §1286。**验收原话**：
>
> > **P5 管理后台**（4~5 天）｜大盘、审核页、用户管理、评论管理｜**验收：管理员能在界面上审完一本书的全部章节**

## Context

P0（脚手架）、P1（认证权限）、P2（内容主干）、P3（读者端）、P4（创作中心）已验收。P5 的起点是一个**反直觉的错位**：

**后端缺口比 P4 小得多。** 审核（作品 / 章节）、分类、审核日志三个模块的后端在 P2 就写完了 —— `AdminNovelController` / `AdminChapterController` / `AdminCategoryController` / `AdminAuditLogController` 四个 Controller 一直在，`curl` 一直能跑通。但 `admin-web` 里**一个能调它们的页面都没有**：整个 P2 之后，「管理员审核」这件事在界面上是不存在的，只能在 Postman 里跑。

所以 P5 补齐的是两件不同性质的事：

1. **后端**：大盘、评论、用户、作者申请、角色菜单、公告六块（`novel_comment` / `author_apply` / `sys_notice` / `sys_role` / `sys_menu` 五张表在 `schema.sql` 里早就建好了，Java 侧一行都没有）；
2. **前端**：`admin-web` 从 14 个文件长成一整套后台（12 个页面 + 11 个 api 文件 + 4 个共用组件）。

**P5 是这个项目第一个「能被演示」的里程碑** —— 面试时打开 `:3000/admin/`，能在界面上把一本书从待审审到发布。P4 之前的所有验收都建立在 curl 上，P5 之后才有一套完整的人工走查路径。

### 起点状态

- HEAD = `431159d 日志落盘到 backend/logs/`。
- 后端 `:8080`，前端四端口 `3000`(代理) / `5173`(reader) / `5174`(author) / `5175`(admin)。
- `admin-web` 有 14 个源文件，**没有** `composables/`、**没有** `utils/format.js`，`api/` 里只有 `auth.js` + `ping.js`。
- `admin-web` 缺三样东西，**每一样都只在特定组件上暴露、且都不报错**（它们是 S1 先修掉的地基，详见 D-10）。
- **可直接复用、没有重造的资产**：`CommentStatus` 枚举（含 `canTransitTo`）、`COMMENT_NOT_FOUND(4001)`~`COMMENT_TOO_FAST(4004)`、`AuditTargetType.AUTHOR_APPLY(4)`、`TokenStore.removeAll(userId)`（「踢下线」原语，P1 就有）、`PageResult` + `buildPage` 兜底范式、`reader-web` 的 `usePagedList.js` / `format.js`。
- ★ **大盘不需要改 seed**：`sys_menu` 的 15 行里没有「数据大盘」，但 `AdminLayout.vue` 的 `/ 工作台` 本来就是 `ready: true` 且无 `perm` —— 大盘直接占 `/`。

## 已拍板的决定（不要重新讨论）

| # | 决定 | 理由 / 落点 |
|---|---|---|
| 1 | **大盘放 `modules/content/`，不放 `modules/system/`** | 见 D-1。放 system 会**反转依赖箭头**，让 M1→M2 的拆分顺序作废 |
| 2 | **不建 `modules/admin/` 包** | 大纲 §175 原文：「admin-web 就是调用各服务已有的管理接口…拆出一个 admin-service 只会多一层无意义的转发」 |
| 3 | **评论的写入接口（读者侧）提到 P5 一起做** | 没有写入路径就造不出待审评论，「评论管理」页无从验收 |
| 4 | **公告管理 / 角色权限树 / 作者申请审核三个「可选」全部做** | ★ 诚实提示：做完之后 P5 从大纲的「4~5 天」拉长到 **8~10 天**，所以顺序上把可砍项排在最后（S13 之后），做到哪算哪 |
| 5 | **封禁 = `status = 0` + `tokenStore.removeAll(userId)`，两件事一起做** | 见 D-3。只改 status 挡不住已登录的人 |
| 6 | **改角色同样 `removeAll` 强制重新登录** | 角色/权限是**登录时**从库里查出来存进 Redis 的。不踢下线的话管理员改完角色，对方界面**看起来没变化** |
| 7 | **大盘 30 天趋势必须零填充** | 见 D-2。ECharts 折线图会把缺失的日期**连成直线**，图上完全看不出来 |
| 8 | **`sys_role_menu` 的赋权用物理 `DELETE` + `INSERT`** | 该表**没有 `deleted` 列**（`schema.sql:118`），不能逻辑删 |
| 9 | **admin-web 不重写 `request.js` 等四个文件** | 与另两端逐字节相同的 md5 约束 |
| 10 | **ECharts 装进 `admin-web`（第一个新运行时依赖）** | 大纲 §66 点名 admin-web 用 ECharts。另两端不装。最终版本 `echarts ^6.1.0` |
| 11 | **读者侧 UI 只做「公告横幅」这一处（~40 行）** | 公告管理如果没有任何读者侧展示，这个功能是自闭的。书评 UI / 作者申请表单留给 P6（那是 P6 的验收线） |
| 12 | **防「管理员把自己锁死」** | 见 D-6。这是角色权限树**唯一**的高危点 |
| 13 | **审核日志的 `targetTitle` 补不出来的就留 `null`** | 见 D-13。为了给已删除对象补标题而绕过 `@TableLogic` 是错误的修法 |

### P5 明确**不做**的

reader-web 的书评区 UI、书架、作者申请表单 UI（都是 P6 的验收线，P5 只把**后端接口**做到 curl 可验）；AI 配置页 `/ai/config`（大纲 §8 属第三期 E1）；违禁审核 `/ai/audit`（E1）；`sys_menu` 的**增删改**（只做「按角色给菜单勾选」，菜单本身是 seed 数据）；操作日志导出；用户的新增（管理员不建号，注册是读者自己的事）；大盘的实时刷新 / 自动轮询；用户列表批量封禁。

## 设计要点与坑

### D-1 ★★ 大盘必须放 `modules/content/`

直觉会把它放 system（「管理后台嘛」），**那是错的**，两个理由：

1. **会反转依赖箭头。** 项目规定 `content → system` 是**唯一**允许的方向，且只有 `ContentUserLookup` 这一个接缝。大盘要同时读作品、章节（content）、用户（system）、评论（interaction）—— 它**天然是 content 层的**（多数指标是内容指标）。放进 system 就等于让 `system → content`，M2 摘 content 时会出现双向依赖，**拆不开**。
2. **`ContentUserLookup` 是给「content 读 system」用的**，反方向没有、也不该有对应的 Lookup。

★ **实现上不新建业务 Service 之外的 mapper**：`DashboardMapper`（全 `@Select`）放 `modules/content/mapper/`，跨表 SQL 都写在这里，Service 只做编排和零填充。

★ 跨表 SQL 里 `sys_user` / `novel_comment` 是**别的模块的表**，直接 join 的地方都写了注释说明：P5 还是单体所以能 join，第二期拆开之后大盘要么跟着 content 走、要么改成调接口。**别默默 join** —— 那样拆服务时没人知道这里埋了跨库查询。

### D-2 ★★ 30 天趋势必须零填充，否则图表在说谎

```java
// ★★ GROUP BY DATE(create_time) 只会返回【有数据的那几天】。
//    直接丢给 ECharts 折线图，它会把这些点按 x 轴顺序连起来 ——
//    于是「9/1 有 5 本、9/20 有 3 本」会被画成一条【穿过 9/2~9/19 的平滑斜线】，
//    图上完全看不出中间 18 天是 0。这不是显示问题，是【图在说谎】。
List<String> days = IntStream.range(0, days)
        .mapToObj(i -> LocalDate.now().minusDays(days - 1 - i).format(DATE_FMT))
        .toList();
```

配套三条：

- **`days` 参数夹上限（1~90）**。不夹的话 `?days=100000` 会生成十万个日期对象 —— 一个请求打满 CPU。和 `size` 的 `buildPage` 兜底是同一类问题。**已实测**：`?days=100000` 返回 90 个桶。
- **日期用 `LocalDate.now()`**，而 SQL 里 `DATE(create_time)` 走的是**数据库时区** —— 两边不一致时（容器 UTC、MySQL `Asia/Shanghai`）会出现「今天的柱子画在昨天」。
- **逻辑删除的统计必须手写 `deleted = 0`**。`@Select` 是手写 SQL，**`@TableLogic` 完全不生效**（它只对 MP 自动生成的 SQL 生效）。漏了的话「作品总数」会包含已删除的书，而这个数字**看起来永远是对的**。**已实测**：删掉一本书后 `novelTotal` 减 1。

★ 另一条实测教训：`@Select` 返回 `Map` 时的 key 大小写敏感于驱动配置，`get("cnt")` 可能拿不到 → **NPE**。所以状态分布返回的是 `StatusDistVO` 而不是 `Map<String, Object>`。

### D-3 ★★ 封禁：`status` 挡不住已登录的人

**事实（P1 就定下的）：**
- `AuthServiceImpl` **有** `STATUS_ENABLED` 校验 → 改 `status = 0` 后**新登录会被拒**（`USER_DISABLED 1003`），且校验刻意放在**密码校验之后**（否则「账号已被禁用」本身就是一条用户枚举情报）。
- `JwtAuthenticationFilter` 的身份**只从 Redis 读**（`tokenStore.get(userId, jti)`），**每请求都不查库**。→ 已经登录的人**继续畅通无阻**，直到 token 自然过期（7 天）。

**结论：封禁必须是两件事，缺一不可。**

```java
user.setStatus(0);  userMapper.updateById(user);
tokenStore.removeAll(userId);   // ★ 没有这一行，界面上显示「已封禁」但对方还在正常用
```

★ **解封不需要** `removeAll`（对方本来就没会话）。★ **重置密码 / 改角色同理要 `removeAll`**。★ `removeAll` 用 `SCAN` 扫，**不要自己写 `KEYS`**（大 key 空间下会阻塞 Redis 单线程）。★ 前端文案必须说清楚「该用户的在线会话已被强制下线，需重新登录」—— 不说的话管理员不知道发生了什么。

### D-4 ★★ `sys_role_menu` 没有 `deleted` 列 —— 赋权只能物理删

```sql
-- schema.sql:118  sys_role_menu
UNIQUE KEY `uk_role_menu` (`role_id`,`menu_id`)
-- ★ 没有 deleted 列
```

「给角色重新勾选菜单」的正确做法是 **`DELETE FROM sys_role_menu WHERE role_id = ?` + 批量 `INSERT`**。★ **反过来 `sys_menu` / `sys_role` 有 `deleted` 列**，手写 SQL 时**必须自己写 `deleted = 0`**。两张表规则相反、又长得几乎一样，**这是本模块最容易搞混的一处**。

★ 另一个连带后果记在 D-6：`sys_role` 的 `uk_role_code` **不含 `deleted`** —— 逻辑删除一个角色之后，它的 `role_code` 永远不能再用。

### D-5 ★★ 作者申请通过 = 改申请状态 + 写 `sys_user_role`，两件事一个事务

- **通过时必须真的给 AUTHOR 角色**。只改 `author_apply.status` 而不写 `sys_user_role`，用户会看到「申请已通过」但仍然**进不去创作中心**（`SecurityConfig` 的 `hasAnyRole("AUTHOR","ADMIN")` 拦下）—— **这是本模块最典型的半成品 bug**，而且不报错。
- **`insertUserRole` 撞唯一键要吞掉**（`INSERT IGNORE` / 捕获忽略），否则重复授权 → `DuplicateKeyException` → 500。
- **同目标状态幂等**：同一份申请批两次，第二次**返回成功**而不是报错。
- **驳回不写角色**，且要写 `audit_remark`。

### D-6 ★★ 角色权限树的唯一高危点：管理员把自己锁死

**两种自锁，都必须拦：**

1. **删掉自己脚下的梯子** —— 管理员编辑**自己所属角色**，取消勾选 `system:role:list` / `system:menu:list` → 保存成功 → 左侧菜单里「角色管理」「菜单管理」**立刻消失**，**再也没有界面能改回来**（只能进数据库改）。→ `1020 ROLE_SELF_MENU_LOCK`，**拒绝且不产生部分写入**。
2. **删掉内置角色** —— 删 `ADMIN` 会让**所有管理员同时失效**。→ `BUILTIN_ROLE_CODES = Set.of("ADMIN","AUTHOR","READER")`，删除 / 停用 / 改标识全部返 `1018 ROLE_BUILTIN`。

★ 这两条**不是过度设计** —— 它们各自只需要几行判断，而中招之后的恢复成本是「进 MySQL 手工 `INSERT`」。**这是本项目里唯一一处「UI 操作能造成不可逆损害」的地方。**

★ 相关的三个号是一组：`1012 USER_CANNOT_BAN_SELF`、`1013 USER_CANNOT_REMOVE_OWN_ADMIN`、`1020 ROLE_SELF_MENU_LOCK` —— 拦的都是「管理员把自己关在门外」。

### D-7 ★ `/api/author-applies` 这个命名不要用

`/api/author/**` 在 `SecurityConfig` 里是 `hasAnyRole("AUTHOR","ADMIN")`。Ant 匹配下 `/api/author/**` **不会**匹配 `/api/author-applies`（`/**` 要求 `/` 后跟任意段），所以**技术上它确实是安全的**。

**但这是个陷阱**：读代码的人一眼会把 `/api/author-applies` 看成「作者接口」，而它实际是**读者**在用的（提交申请的人恰恰**还不是作者** —— 是 READER）。将来有人「整理」`SecurityConfig` 时把它收进去，就会**静默**变成「非作者不能申请成为作者」，**逻辑死锁**。

→ 用 `/api/reader/author-apply`。语义正确，且和 `/api/reader/**` 的既有命名同族。

### D-8 `SecurityConfig` 只加两条，且有三个现成的坑

```java
.requestMatchers(HttpMethod.GET, "/api/notices").permitAll()
.requestMatchers(HttpMethod.GET, "/api/novels/*/comments").permitAll()
```

1. **块注释里的 `*/` 会提前结束注释**。写 `/api/novels/*/comments` 的注释时如果写进块注释，注释在那里就结束了。
2. **白名单条目默认方法无关** —— 不写 `HttpMethod.GET` 就等于把将来任何 `POST /api/notices`（发公告）一起匿名放行了。**已实测**：匿名 `POST /api/notices` → **401**；匿名 `POST /api/novels/1001/comments` → **401**。
3. **必须放在 `.anyRequest().authenticated()` 之前** —— 顺序错了规则不生效且**没有任何报错**。

★ **`/api/admin/**` 一条都不用加** —— `hasRole("ADMIN")` 那条规则已经在了，新端点**自动继承**。**已实测**：匿名 `GET /api/admin/users` → **401**；`reader01` 的 token → **403**（401 和 403 的区别是 P1 定的：匿名 401、身份不足 403）。

### D-9 评论的 10 秒频控：复用已有的键

```
SET novel:comment:limit:{userId} <timestamp> NX EX 10
→ 返回 false 说明 10 秒内已经发过 → 4004 COMMENT_TOO_FAST
```

★ **必须 `NX` + `EX` 一起用**。「先 GET 判断、再 SET」是**两步非原子操作**，连点两下能同时通过。★ **按 `userId` 限流，不按 IP** —— 一套 NAT 后面的整个公司共用一个出口 IP。★ 用 `StringRedisTemplate`，不是 `RedisTemplate<String,Object>`（后者的 JSON 序列化器会让 key 带上引号）。

### D-10 前端三处「不报错的静默故障」（S1 先修，否则后面每一步都在猜）

| 缺什么 | 症状 |
|---|---|
| `App.vue` 的 `<el-config-provider :locale="zhCn">` | `el-pagination` 显示 **"Total 137"**、`el-empty` 显示 **"No Data"** —— 而页面其它中文全是好的，很难联想到语言包 |
| `main.js` 的 `import 'element-plus/es/components/message-box/style/css'` | `ElMessageBox` **弹出来没有样式**（无遮罩、按钮错位） |
| `router/index.js` 的 `scrollBehavior` | 翻页后滚动位置停在上一次的中间，**看起来像点错了** |

★ **`ElMessageBox` 是命令式 API，读不到 `el-config-provider` 的 locale** —— 确认/取消按钮的文字**必须手写**「确定」/「取消」。这是语言包也修不了的一处。

★ **`el-tree` 用 `check-strictly = true`**（各选各的，不做父子联动）—— 父子联动会让「只想给 `system:user:list`」变成「顺带给了整个 `/system` 目录」，而左侧菜单是按**叶子**的 perm 过滤的，勾了反而让人以为多授了权。

### D-11 ECharts

★ **装依赖 / `npm run build` 之前必须先停掉同子项目的 `vite dev`** —— 两者争用 `node_modules/.vite` 缓存，Windows 上会让 dev server 直接崩掉。★ 装完 **Vite 会自己重启一次 server**（预构建新依赖），那几秒 `:5175` 是关的、`curl` 拿到连接拒绝 —— **这是正常的**。★ **按需引入**（`echarts/core` + 只引用到的图表类型），`import * from 'echarts'` 会把 ~1MB 整包打进来。

### D-12 ★★ 审核页是验收线，先做且要一次做对

**P5 的验收原话是「管理员能在界面上审完一本书的全部章节」** —— 所以**作品审核 + 章节审核两个页面（S3）必须最先做完**，它单独就构成 P5 的验收。

★ **章节审核页要支持「按作品聚合」**：一本书几十章，管理员需要「进入某本书 → 看到它的全部待审章节 → 逐章通过/驳回」这条路径。**只有一个扁平的全局待审列表是不够的** —— 那正是「审完一本书的全部章节」这句话要防的。

★ **批量通过/驳回照抄 `author-web/src/views/chapters/index.vue` 的 `runBatch`**：顺序 `for...of await`（**绝不 `Promise.all`** —— 审核通过的章节会 re-UPDATE 同一本 `novel` 的统计列），`busyIds` 用 **set 替换**（原地 `add` 不触发响应式），被跳过的条目**必须 `ElMessage.info` 报出来**（绝不静默过滤）。

### D-13 ★ `targetTitle` 补不出来就留 `null`

`AuditLogServiceImpl#toVOList` 按 `targetType` 分成四组各自查一次（一页 20 条最多 4 次查询，不是 20 次）—— **混着查不会报错，只会给作品 5 补上章节 5 的标题**。

★ 作者申请的 `target_id` 是**申请表的 id**，不是申请人的 `user_id` —— 补标题要两跳（`apply_id → user_id → nickname`）。混用不会报错，只会显示成别人的申请。

★ **查不到的 id（对象已被逻辑删除）就返回 `null`，前端显示「作品 #5（已删除）」**。为了补出已删除对象的标题而绕过 `@TableLogic` 是错误的修法。

### ① ★★ 负向用例 18「驳回不填理由」—— 方案预设了一个**不存在**的后端 400

方案里写的是：

> | 18 | 驳回时不填理由 | 拒绝（验 D-12） |

**实测是 200，成功驳回了。这不是 bug。** 打开两个 DTO 的 javadoc，写得很清楚：

> 「驳回必须填理由」是**审核规范**，不是数据完整性要求 —— 库里 `audit_remark` 这一列本来就可空。**后端刻意不拦，拦它的是前端。**

真正拦它的是 `AuditDialog.vue` 的 `remarkRequired`（默认 `true`，作者申请审核页没关掉；评论审核页显式设成 `false` —— 因为隐藏一条评论不写理由是有正当场景的）。

**这个修正值得单独记一笔**，因为它暴露的是**验收脚本的期望从哪来**：方案的负向用例表是按「应该拦」的直觉写的，而实现时按「这是前端规则」落的地。两边都没错，**但如果不实测就写文档，这条会被当成「后端有校验」记录下来**。→ 记住这条口径：**后端只管数据完整性，前端管业务规范。**

### ② ★★★ 回归脚本把种子角色当试验台 —— **READER 角色的菜单被污染成 ADMIN 全集**

这是 P5 期间最值得记的一个事故。

**现象**：S16 的回归脚本跑到一半崩了（没执行到清理段），重跑时断言 `B106 READER 的菜单 = []` 失败。

**根因**：脚本里「角色赋权」那一组实验**直接拿种子角色当试验台** —— 给 READER 赋 ADMIN 的全部 15 条菜单、再取消、反复三次（为了验 D-4「物理删 + 唯一键不产生重复行」）。崩在中间那一次，READER 就永久停在了「拥有 ADMIN 全集」的状态上。

**为什么危险**：`sys_role_menu` 没有 `deleted` 列，**破坏是不可逆的**（没有历史可回滚）；而且症状很隐蔽 —— 用 `reader01` 登录，左侧会莫名多出整个管理端菜单。

**修法两层**：

1. **所有赋权实验改跑在一次性角色 `S16R<时间戳>` 上**，绝不碰 `role_code IN ('ADMIN','AUTHOR','READER')` 这三个种子角色；
2. 用一次性脚本把 READER 还原成 `[]`，并**在回归脚本里加三条「种子数据未被破坏」的断言**：READER=0 条、AUTHOR=2 条、ADMIN=15 条。

→ **规矩**：**验收脚本绝不能拿种子数据当试验台。** 造一次性对象（一次性账号 / 一次性角色 / 一次性作品），跑完就删；并且**为种子数据的完好性写断言** —— 否则「脚本改坏了种子数据」这件事只有在下次它自己失败时才会暴露。

（同类教训：一次性账号一律带时间戳后缀，如 `s16r9981486`。这既避免了撞唯一键，也让收尾时能用一条 `IN (...)` 精确清掉。）

### ③ ★ 四套「重复审核」的口径**各不相同** —— 不实测就会写错三处

| 对象 | 重复提交同一动作 | 为什么是这样 |
|---|---|---|
| **作品** | 需要前置判断「是否已经待审」 | 有 `OFFLINE → PUBLISHED` 这条边，重复审会撞车 |
| **章节** | 直接 `3003 CHAPTER_STATUS_ILLEGAL` | 状态机限死，`canTransitTo` 直接拒 |
| **作者申请** | **同目标状态幂等成功**，跨终态 `1016` | 管理员连点两下是常态，报错反而烦人 |
| **评论** | `4005 COMMENT_STATUS_ILLEGAL` | 和章节同一类 |

**这四种都是对的**，因为它们面对的用户意图不同。但写文档时**极易**把它们统一成一句「重复审核会报错」—— 那就是错的。

### ④ ★ A64：重复删除分类返 `7001` 而不是幂等成功

`DELETE` 一个已经删掉的分类，返回的是 `6001 CATEGORY_NOT_FOUND`。**而 `CategoryServiceImpl` 的注释写得比代码满** —— 注释描述了一条「已经删过就当作成功」的幂等分支，但 `requireXxx` 在方法开头就把异常抛了，那个分支**不可达**。

→ 不是 bug（返 6001 完全合理），但**注释与真实行为不符**，属于「读代码的人会被引到沟里」的那类问题。**留作已知项**：要么删掉那段注释，要么真的把幂等分支做出来。**不要照注释写文档。**

### ⑤ ★ seed.sql 只 `INSERT` 的**第二半**：改了文件 ≠ 库里变了

`seed.sql` 全部是 `INSERT IGNORE`，**没有一条 `UPDATE`**。所以：

- 第一半（早就记了）：**新增行不要写死 id**，用业务唯一键关联；
- ★ **第二半（P5 才撞上）**：**改已有行的值，重跑 seed 无效**。S14 修 `sys_menu.path`（`'/novel/list'` → `'/novel'`）时，改完文件、库里那 11 行**一条都没变**，而脚本一声不响地跑完了 —— 得**另外手工跑一条 `UPDATE`**。

→ 规矩：**改已有行的值 = 改文件 + 手工 UPDATE 那个库**，两件事都要做。（刻意不补一堆 `UPDATE` 来「自动对齐」：那会把文件的语义从「补种子数据」变成「声明式同步」，而后者要覆盖每一张表每一列 —— 做不到就是更隐蔽的半同步。）

### ⑥ ★ 单列 `.select()` 投影 + 可空列 → `List` 里有 `null` → 方法引用 NPE → **500**

MyBatis-Plus 的 `.select(Novel::getTitle)` 这类**单列投影**，遇到该列为 `NULL` 的行会往结果 `List` 里塞一个 `null` 元素（不是跳过）。随后一个 `list.stream().map(String::toUpperCase)` 之类的**方法引用**就会 NPE —— 而 500 的错误信息完全指不到 SQL 那一层。

→ 规矩：**单列投影要么加 `WHERE 列 IS NOT NULL`，要么返回实体/VO 而不是裸列。**

### ⑦ 我自己猜错的**三处表结构**

写检查脚本时凭印象写了列名，全错：

| 我写的 | 实际 | 后果 |
|---|---|---|
| `novel.user_id` | **`novel.author_id`** | SQL 报错（还算好的） |
| `novel_comment.novel_id` | **`target_type` + `target_id`** | 报错 |
| `reading_history` 表 | **叫 `read_history`** | 报错 |

→ 教训：**动手前先 `SHOW COLUMNS` / 查 `information_schema`**，别凭记忆写列名。这次是「报错」所以无害，但如果表名恰好存在、列名恰好错到另一列上（比如 `user_id` → `author_id` 都是 bigint 且都存在），就会**静默算错**。

### ⑧ ★ 同秒 DATETIME 打平 —— 排序必须带 `id DESC` 兜底

MySQL 的 `DATETIME` 默认不带小数秒，同一秒内产生的多条记录**完全平手**，只按 `create_time DESC` 排的话顺序不确定 → 列表在两次刷新之间**跳来跳去**（A37）。

→ 规矩：**所有「按时间倒序」的列表都带 `id DESC` 兜底**。

### ⑨ 「已发布但无发布时间」这条不变式靠 `@NotNull` + Service 兜底

公告的 `publishTime` 有四种行为（新建即发布 / 草稿 / 发布 / 下线）。不变式是「`status = 1` ⟹ `publishTime` 非空」。**已实测**（`dbcheck.sql` 第 5 项）：库里 0 行违反。

★ 顺带一条 **`RoleSaveDTO.status` 是 `@NotNull`** —— 新建角色必须传 `status`，否则 400「请选择角色状态」。（这个在写回归脚本时踩到了。）

### ⑩ ★ 公告段错误码**只有一条**，这不是没做完

`ResultCode` 的公告段只有 `7001 NOTICE_NOT_FOUND`，和分类段的 3 条、角色段的 5 条形成对比。**理由是公告这个功能的错误面本来就这么小**：

```
没有「重名」   —— 公告标题【没有唯一约束】，也不该有。
                 「系统维护通知」一年要发好几次，标题重复是正常的。
没有「状态非法」—— 公告【没有状态机】。发布/下线/再发布/再下线是自由的，
                 重复执行同一个动作都是幂等的。
没有「被引用」 —— 公告不挂在任何别的东西上，删了就是删了。
```

空参数（标题超长、内容为空、`type` 传了 3）全部由 `NoticeSaveDTO` 的校验注解拦成 **HTTP 400** —— 那是**请求格式错误**，不是业务失败，不该占一个 7xxx 的号。

### ⑪ ★ 决定**不往 `seed.sql` 里塞公告**

理由：公告是**运营数据**，不是**种子数据**。种子数据的作用是「让库能跑起来」（账号、角色、菜单、分类、演示作品）；公告的作用是「让人看到横幅」。把一条公告写进 seed，下次 `seed.sql` 重跑会在一个**已经跑了一阵的库**里插进一条「系统维护公告」—— 而它多半已经下线了。

→ 读者的横幅**空着是正常状态**（`NoticeBanner.vue` 在没有公告时**整个组件不渲染** —— 横幅是运营位，不是内容区）。演示时在公告管理页发一条即可。

## 环境与工具踩坑（P5 期间新踩到的）

### 1. ★★ Vite 的「模块编译校验」必须看 `content-type`

验证一个 `.vue` / `.js` 改得对不对，可以请求 Vite 的模块 URL。但有两个陷阱：

- **模块 URL 必须带 `base` 前缀**：`admin-web` 是 `/admin/`、`reader-web` 是 `/reader/` —— 少了前缀是 404 `text/plain`；
- ★★ **请求一个不存在的模块也返回 200**（SPA 回落到 `index.html`）。所以判据**不是状态码**，而是 `content-type: text/javascript`。看到 `text/html` 就说明拿到了回落页，等于什么都没验。

### 2. ★★ Windows 上 Python 的 stdin **也是文本模式**

`curl ... | python -c "json.load(sys.stdin)"` 会因控制台 ANSI 码页（GBK）解码产生**代理对**，然后 `UnicodeEncodeError: surrogates not allowed`。

→ 稳妥做法：**curl 输出到文件**，再用 `io.open(path, encoding='utf-8')` 读。同理 **`print` 只能输出 ASCII**（中文在控制台会是乱码，但不会崩）。

### 3. ★ 端口漂移：四个 `vite.config.js` 全部补上 `strictPort: true`

这是 P4 记下的遗留项，P5 顺手做掉了。**最需要它的是 dev-proxy 的 `:3000`** —— 它是唯一一个要手敲的地址（书签、面试演示、验收脚本里写的都是它），换到 3001 之后打开 `:3000` 看到的是**上一个还活着的代理**转发的旧内容：页面能开、接口能通，**只有代码的改动不生效**。

★ 另外两条相关：`TaskStop` **不会杀掉 `concurrently` 的子进程**（只杀外壳，四个 vite 会变成孤儿占着端口）→ 必须用 `Get-NetTCPConnection -State Listen` 找 PID 再 `Stop-Process -Force`；**绝不在某个子项目跑着 `vite dev` 时在同一子项目跑 `npm run build`**。

### 4. mysql 客户端在 Workbench 目录里

`PATH` 上没有 `mysql`。用 `/c/Program Files/MySQL/MySQL Workbench 8.0/mysql.exe`，配 `MYSQL_PWD=root123456` + `-h192.168.127.137 -uroot novel --default-character-set=utf8mb4 < file.sql`，并 `grep -v "Using a password"`。（含明文密码的临时脚本用完即删。）
