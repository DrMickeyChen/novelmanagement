## 总览：一共要装六个中间件

先知道自己在装什么。这六个东西是后面写代码时要用到的：

| 中间件 | 干什么用的 | 端口 | 什么时候用得上 |
|---|---|---|---|
| **MySQL 8** | 业务主库，存小说、章节、用户 | 3306 | 第一期就要 |
| **Redis 7** | 缓存、阅读量计数、排行榜、幂等去重 | 6379 | 第一期就要 |
| **Nacos** | 注册中心 + 配置中心（微服务才需要） | 8848 / 9848 / 9849 | 第二期 |
| **RocketMQ** | 消息队列，削峰、解耦、异步审核 | 9876 / 10911 | 第二期 |
| **Elasticsearch** | 全文搜索（按书名、作者搜） | 9200 | 做搜索功能时 |
| **Sentinel** | 限流熔断（可选，第三期） | 8858 | 第三期 |

六个都用 Docker 装 —— **不用一个个去编译安装，一条命令全部拉起**，这是 Docker 最大的价值。


## 开工前：确认磁盘空间（★ 先做这个）

**在虚拟机终端里跑第一条命令之前，先看磁盘。**

```bash
df -h /
lsblk
```

### 为什么要专门检查这个

Ubuntu Server 安装时如果选了 LVM 分区（默认就是），**安装器不会把整块盘都给根分区**。常见情况是 60G 的盘，根分区只分到 14G：

```
/dev/mapper/ubuntu--vg-ubuntu--lv   14G   14G     0 100% /     ← 危险
```

六个中间件的镜像加起来约 **5G**，加上系统本身和 ES / MySQL 的数据，14G 撑不了多久。**磁盘一满，表现是容器毫无征兆地反复重启**，而且报错信息五花八门（Redis 报 `No space left on device`、MySQL 报数据目录损坏、RocketMQ 报一个莫名其妙的 `NullPointerException`），很容易误判成配置写错了，白白排查半天。

**所以这一步要在装任何东西之前做完。**

### 判断标准

| `df -h /` 的 Size | 结论 |
|---|---|
| ≥ 50G | ✅ 正常，直接去第 0 步 |
| 20~40G | ⚠️ 够用但紧张，建议扩 |
| **≤ 20G** | ❌ **必须先扩**，否则装到一半必炸 |

### 怎么扩（以 60G 盘只分了 14G 为例）

先看清楚现在是什么状况：

```bash
lsblk     # 看分区
sudo vgs  # 看卷组还剩多少没分配（看 VFree 那列）
sudo lvs  # 看逻辑卷
```

典型输出长这样 —— **有两层空间被浪费了**：

```
sda (60G)  ├─ sda3 = 28G   ← ① 分区只用了 28G，磁盘还有 30G 没划进来
           │    └─ ubuntu-vg = 28G   VFree 14G   ← ② 卷组里还有 14G 没给根卷
           │         └─ ubuntu-lv = 14G
           │              └─ / (14G, 满了)
```

**逐层扩上去：**

```bash
# --- ① 先把分区撑满整块磁盘 ---
which growpart || sudo apt install -y cloud-guest-utils
sudo growpart /dev/sda 3      # 3 是分区号，以 lsblk 里 ubuntu-lv 所在的 sdaX 为准

# 重启，让内核重新读分区表（★ 不重启下一步的 pvresize 认不到新空间）
sudo reboot
```

重连之后再继续：

```bash
# --- ② 让 LVM 认到新分区大小 ---
sudo pvresize /dev/sda3
sudo vgs                      # 这时 VFree 应该变成 40G 左右

# --- ③ 把卷组剩余空间全给根逻辑卷 ---
sudo lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv

# --- ④ 在线扩容文件系统（不用卸载、不用重启）---
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv

# --- ⑤ 验收 ---
df -h /
```

`df -h /` 应该显示 `57G` 左右、`Use%` 降到 20% 出头。

> **这四步分别在干什么？**
>
> | 命令 | 作用 |
> |---|---|
> | `growpart` | 改分区表的**末尾位置**，把分区撑到磁盘末尾。不动任何数据 |
> | `pvresize` | 让 LVM 重新扫描分区，把新增空间纳入卷组 |
> | `lvextend` | 把卷组的空闲空间分配给逻辑卷 |
> | `resize2fs` | 扩大文件系统本身。**ext4 支持在线扩容**，根分区挂载着也能做 |
>
> 少任何一步都会卡住：不 `growpart` 就只有 28G，不 `pvresize` 卷组看不到新空间，不 `resize2fs` 逻辑卷变大了但文件系统还是旧的。

**✅ 确认**：`df -h /` 的 `Avail` 大于 40G。

## 第 0 步：拿一个镜像加速地址

**在 Windows 的浏览器上做，不是在虚拟机里。**

国内直连 Docker Hub 基本拉不动镜像，必须先配一个加速器。

1. 打开 https://cr.console.aliyun.com/cn-hangzhou/instances/mirrors
2. 左侧菜单「镜像工具」→「镜像加速器」
3. 复制那个形如 `https://xxxxxx.mirror.aliyuncs.com` 的地址，**先记在记事本里**，第 3 步要用

> ### ⚠️ 这个地址只能给 Docker 用，不要去动 apt
>
> 拿到手的是个 `https://xxxxxx.mirror.aliyuncs.com` 的地址，很多人会顺手拿它去改 apt 源 —— **这是错的，会得到一个 `403 Forbidden`。**
>
> | 地址 | 用途 | 填在哪 |
> |---|---|---|
> | `xxxxxx.mirror.aliyuncs.com` | **Docker 镜像**仓库 | 第 3 步的 `/etc/docker/daemon.json` |
> | `mirrors.aliyun.com/ubuntu` | **apt 软件包**仓库 | apt 源（本文档用不到） |
>
> 两者完全不相干：前者只提供 Docker registry API，你去请求 apt 仓库的路径，它当然只能回 403。

> **为什么是阿里云？** 2024 年以后，国内公开的镜像站（中科大、网易、Docker 中国等）基本全关停了。阿里云容器镜像服务个人版是免费的，只是需要你登录拿一个专属地址。**别去网上抄别人博客里的地址**，抄了也是白配。

**✅ 确认**：记事本里有了一个 `https://` 开头、`.mirror.aliyuncs.com` 结尾的地址。

## 第 1 步：检查 apt 源（**大多数情况直接跳过**）

**在虚拟机终端里操作。** 后面的命令都在虚拟机里跑，只有特别说明的才回 Windows。

**先跑这一条**，看看你现在的源是什么：

```bash
sudo apt update
```

### 如果输出全是 `Hit` —— 跳过这一步

```
Hit:1 http://tw.archive.ubuntu.com/ubuntu jammy InRelease
Hit:2 http://tw.archive.ubuntu.com/ubuntu jammy-updates InRelease
Hit:3 http://tw.archive.ubuntu.com/ubuntu jammy-backports InRelease
```

`Hit` 表示源是通的、速度也可以。**那就什么都不用改，直接去第 2 步。**

> 现在很多 Ubuntu 安装镜像（尤其亚太区）默认用的就是就近的镜像站，本来就不慢。**别为了"换源"而换源** —— 改错一个字符反而会把 `apt` 弄坏。

### 只有出现 `Err` / 超时，才需要换源

```bash
# 先备份，改坏了能还原
sudo cp /etc/apt/sources.list /etc/apt/sources.list.bak

# 看看当前用的是哪个地址（★ 关键：确认要替换的字符串是什么）
grep -E "^deb " /etc/apt/sources.list

# 把原地址换成阿里云（把 archive.ubuntu.com 换成上面 grep 看到的那段）
sudo sed -i 's|http://archive.ubuntu.com|https://mirrors.aliyun.com|g; s|http://security.ubuntu.com|https://mirrors.aliyun.com|g' /etc/apt/sources.list

sudo apt update
```

> **`sed -i` 是什么？** 直接修改文件内容。`s|A|B|g` 意思是"把所有 A 替换成 B"。
>
> **★ 为什么必须先 `grep` 一下？** 因为 `sed` 是**严格字符串匹配**。如果原来的地址是 `tw.archive.ubuntu.com`，而你替换的是 `archive.ubuntu.com` —— 那 `sed` 一个字符都匹配不上，**它会静默地什么都不做**，你以为换了其实没换。先看清楚原字符串再替换。

### ⚠️ 别把 Docker 加速器地址填到这里

如果 `apt update` 报这种错：

```
Err:4 https://xxxxxx.mirror.aliyuncs.com/ubuntu jammy-security InRelease
  403  Forbidden
```

说明你把**第 0 步那个 Docker 镜像加速地址**当成 apt 源了 —— 两者是不同的东西，见第 0 步的说明。修复方法：

```bash
# 找出坏在哪
sudo grep -rn "aliyuncs" /etc/apt/sources.list /etc/apt/sources.list.d/

# 在 sources.list 里 → 恢复备份
sudo cp /etc/apt/sources.list.bak /etc/apt/sources.list

# 在 sources.list.d/ 下的某个文件里 → 删掉那个文件（文件名用上面 grep 打印出来的）
sudo rm /etc/apt/sources.list.d/换成实际文件名
```

**✅ 确认**：`sudo apt update` 输出**全是 `Hit`，没有任何 `Err`**。

## 第 2 步：装 Docker

### 2.1 装依赖和密钥

Ubuntu 自带源里的 `docker.io` 版本太老，所以用 Docker 官方源装。但官方源在国内慢，**这里用的是阿里云镜像的官方源**（内容一样，速度快）。

```bash
# 装三个工具：证书、下载器、密钥管理
sudo apt install -y ca-certificates curl gnupg

# 建密钥目录
sudo install -m 0755 -d /etc/apt/keyrings

# 导入 Docker 官方的 GPG 签名密钥（用来验证软件包没被篡改）
curl -fsSL https://mirrors.aliyun.com/docker-ce/linux/ubuntu/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

# 把 Docker 的软件源加进 apt 列表
# $(. /etc/os-release && echo $VERSION_CODENAME) 会自动取出系统代号 —— 22.04 是 jammy
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://mirrors.aliyun.com/docker-ce/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
```

> **GPG 密钥是干什么的？** 软件源相当于一个"应用商店"，密钥用来验证你下载的包确实来自 Docker 官方、中途没被人改过。不加这一步 apt 会拒绝安装。

### 2.2 装 Docker

```bash
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

装了四个东西：

| 包 | 作用 |
|---|---|
| `docker-ce` | Docker 引擎本体 |
| `docker-ce-cli` | `docker` 命令行工具 |
| `containerd.io` | 底层容器运行时 |
| `docker-compose-plugin` | `docker compose` 命令（★ 注意是插件形式，不再是独立的 `docker-compose`） |

### 2.3 免 sudo + 开机自启

```bash
# 把你的用户加进 docker 组（否则每条 docker 命令都要 sudo）
sudo usermod -aG docker $USER

# 让 Docker 开机自启，现在立刻启动
sudo systemctl enable --now docker

# 让用户组变更在当前终端生效
newgrp docker
```

> **为什么需要这一步？** Docker 的守护进程以 root 运行，普通用户默认没权限跟它说话。加进 `docker` 组相当于给了你这个权限。
>
> ⚠️ **加进 docker 组等于给了 root 权限**（容器可以挂载宿主机文件系统）。开发机上没问题，生产环境要注意。

### 2.4 验证

```bash
docker version
docker compose version
```

**✅ 确认**：两条命令都输出了版本号，没报 "command not found"。

> 如果报 `permission denied`，说明用户组还没生效 —— 关掉终端重新登录一次虚拟机。

## 第 3 步：配镜像加速器

把第 0 步拿到的地址填进去。

```bash
sudo mkdir -p /etc/docker

sudo tee /etc/docker/daemon.json > /dev/null <<'EOF'
{
  "registry-mirrors": ["https://这里换成你的专属地址.mirror.aliyuncs.com"],
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "3" }
}
EOF

sudo systemctl daemon-reload
sudo systemctl restart docker
```

**★ 把 `这里换成你的专属地址` 那段替换成第 0 步复制的真实地址再执行。**

> **`daemon.json` 里另外两项是什么？**
> `log-driver` + `log-opts` 是在限制日志文件大小。不配的话，容器日志会无限增长，几个月后能把磁盘撑爆 —— 这是 Docker 的一条经典运维经验。

**✅ 确认**：

```bash
docker info | grep -A2 "Registry Mirrors"
```

能看到你填的地址就对了。

## 第 4 步：调系统参数

**这一步有两个参数是硬性要求**，不改的话容器起来就退出或在日志里刷警告。

```bash
# 临时生效，马上能用
sudo sysctl -w vm.max_map_count=262144
sudo sysctl -w vm.overcommit_memory=1

# 写进配置文件，重启也不丢
echo "vm.max_map_count=262144"  | sudo tee -a /etc/sysctl.conf
echo "vm.overcommit_memory=1"   | sudo tee -a /etc/sysctl.conf
echo "fs.file-max=655360"       | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

> **这三个参数是什么？**
>
> - `vm.max_map_count` —— 一个进程最多能创建多少块内存映射。ES 用 Lucene 建索引，每个索引段都要映射文件，默认的 65530 不够用，ES 会直接启动失败报 `max virtual memory areas vm.max_map_count [65530] is too low`。**这是 ES 最经典的部署坑。**
> - `vm.overcommit_memory = 1` —— 允许内核超量分配内存。**Redis 后台做持久化（AOF rewrite / RDB）时会 fork 一个子进程**，fork 依赖写时复制，而 Linux 默认的内存分配策略在内存紧张时会拒绝这次分配，导致 fork 失败、持久化中断、数据丢失。不配的话 Redis 会在启动日志里明确警告：
>   ```
>   WARNING Memory overcommit must be enabled! ... add 'vm.overcommit_memory = 1' to /etc/sysctl.conf
>   ```
> - `fs.file-max` —— 系统级最大文件句柄数。ES 和 RocketMQ 都会大量读写文件，调大防止 "too many open files"。

**✅ 确认**：

```bash
cat /proc/sys/vm/max_map_count     # 262144
cat /proc/sys/vm/overcommit_memory # 1
```

两个都对上就 OK。

## 第 5 步：加 4G swap

**8G 内存跑这套中间件（约吃 5G），swap 是安全气囊。**

```bash
# 先看看现在有没有
free -h

# 创建一个 4G 的交换文件
sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile          # 只有 root 能读写，安全要求
sudo mkswap /swapfile             # 格式化成 swap 格式
sudo swapon /swapfile             # 启用

# 写进 fstab，重启后自动挂载
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

> **swap 是什么？** 内存不够时，把暂时不用的内存页挪到磁盘上，腾出物理内存。慢，但总比被 OOM Killer 杀掉进程强。
>
> **为什么必须做？** 不配的话，内存冲上去的瞬间，Linux 的 OOM Killer 会**随机杀一个容器** —— 通常是 ES 或 MySQL，而且杀谁不确定。症状是"用着用着某个服务没了但看不出原因"，很难排查。有了 swap，最多是变慢，不会突然死。

**✅ 确认**：

```bash
free -h
```

`Swap:` 那一行应该是 `4.0Gi`。

## 第 7 步：改两处配置

### 7.1 生成 `.env`

```bash
cd ~/novel-docker
cp .env.example .env
```

`.env` 里存的是密码和 IP，它被 `.gitignore` 排除，不会提交到 git。

### 7.2 改 IP 和 Nacos 密钥

```bash
nano .env
```

改这两行：

```bash
# 改成虚拟机的 IP
RMQ_BROKER_IP=192.168.127.137

# 换成下面这条命令生成的新值
NACOS_AUTH_TOKEN=生成的token
```

生成新 token：

```bash
openssl rand -base64 32
```

> **Nacos 这个 token 是干什么的？** Nacos 开鉴权后，服务端用它来签名校验请求。**必须是 Base64 编码后至少 32 字节**，所以不能随便写一个字符串。`openssl rand -base64 32` 生成的正合适。
>
> 改完按 `Ctrl+O` 保存，`Ctrl+X` 退出。

### 7.3 改 `broker.conf`（★ 最重要的一处）

```bash
nano broker.conf
```

把 `brokerIP1` 改成同一个 IP：

```
brokerIP1 = 192.168.127.137
```

> ### ★ 这是 RocketMQ 容器化最经典的坑，一定要理解
>
> Broker 启动时会**把自己的地址注册到 NameServer**。客户端先从 NameServer 查到 Broker 的地址，再直接去连它。
>
> 如果不配 `brokerIP1`，Broker 会把自己的**容器内网 IP**（`172.17.0.x`）注册上去。你 Windows 上的客户端拿到这个 IP —— 那是 Docker 内部的虚拟网段，你的电脑根本访问不到，直接报错：
>
> ```
> connect to 172.17.0.3:10911 failed
> ```
>
> 而且这个错误日志很难让人联想到"是容器 IP 的问题"，所以特别浪费时间。**配成宿主机的真实 IP 就对了。**

**✅ 确认**：

```bash
grep -E "RMQ_BROKER_IP" .env
grep -E "brokerIP1" broker.conf
```

两处显示的应该是**同一个 IP**。

## 第 8 步：启动全部中间件

```bash
cd ~/novel-docker
sudo docker compose up -d
```

> **`-d` 是 detach**，让容器在后台跑，不占着你的终端。
>
> 命令会自动做三件事：从镜像仓库拉取镜像 → 创建容器 → 按依赖顺序启动。**第一次要下载 3~4G 的镜像，慢的话十几分钟。**
>
> 重新登录过虚拟机的话，`sudo` 可以去掉。

### 看看启动状态

```bash
sudo docker compose ps
```

期望是六个全 `Up`。**但 ES 和 MySQL 会先显示 `health: starting`** —— 它们要跑完 self-check 才变 `healthy`，给它 1~2 分钟，这不是故障。

### ⚠️ 如果某个容器显示 `Restarting`

`Restarting (N)` 表示它起来就崩、崩了又起，在循环。**这时候看 `ps` 没用，要看日志。**

```bash
# 把最后的「服务名」换成要看的那个：mysql / redis / es / rmqbroker / nacos
sudo docker compose logs --tail=50 服务名
```

我踩过的、以及这次实际撞到的，按概率排下来是这四个：

#### ① 磁盘满了

日志里出现 `No space left on device`。

**回「开工前：确认磁盘空间」把根分区扩掉。** 这是最容易被误判的一个 —— 它不会报"磁盘满"，而是让各个中间件报出**各自不同的、看起来毫不相关的错**：

| 组件 | 磁盘满时的假象 |
|---|---|
| Redis | `Can't open or create append-only dir appendonlydir: No space left on device` |
| MySQL | `--initialize specified but the data directory has files in it`（初始化写一半就断了） |
| RocketMQ | 一段 `NullPointerException`（真实错误被关闭流程盖住，**完全看不出是磁盘问题**） |
| ES | `failed to obtain node locks` |

四个不同组件、四种不同报错，**其实是同一个原因**。所以修之前先 `df -h /` 看一眼，能省掉大量弯路。

#### ② 绑定挂载目录的属主不对（★ 容器化经典坑）

日志里出现 `AccessDeniedException`、`Permission denied`，或者**某个容器该写的目录根本没被创建**（比如 RocketMQ 的 `data/rmq/broker/logs/rocketmqlogs/` 一直是空的）。

**原因**：`docker-compose.yml` 里的 `./data/xxx` 这类绑定挂载，如果宿主机目录不存在，**Docker 会用 `root:root` 自动创建它**。但有些镜像声明了非 root 用户，进程就写不进去：

| 镜像 | 容器内进程身份 | 能写 root 的目录吗 |
|---|---|---|
| `redis:7-alpine` | root | ✅ |
| `mysql:8.0` | 先 root，再 chown 给 mysql | ✅ |
| `nacos/nacos-server` | root | ✅ |
| `apache/rocketmq`（**NameServer**） | root | ✅ |
| **`elasticsearch:8.13.4`** | **uid 1000** | ❌ |
| **`apache/rocketmq`（Broker）** | **uid 3000** | ❌ |

**所以只有 ES 和 Broker 会挂，其他四个好好的** —— 这个规律本身就是最好的线索。

修复：把目录交给容器里那个用户。**别写死数字，让镜像自己报**：

```bash
cd ~/novel-docker

ES_UID=$(sudo docker run --rm --entrypoint id docker.elastic.co/elasticsearch/elasticsearch:8.13.4 -u)
RMQ_UID=$(sudo docker run --rm --entrypoint id apache/rocketmq:5.3.1 -u)
echo "ES uid=$ES_UID  RMQ uid=$RMQ_UID"

sudo chown -R "$ES_UID:$ES_UID" data/es
sudo chown -R "$RMQ_UID:$RMQ_UID" data/rmq

sudo docker compose up -d elasticsearch rmqbroker
```

> `--entrypoint id` 绕过了镜像自带的启动脚本，直接问"你在容器里是什么身份"。用 `--rm` 起完即删，不留垃圾。

#### ③ MySQL 数据目录残缺

日志里出现：

```
[ERROR] [MY-010457] [Server] --initialize specified but the data directory has files in it. Aborting.
```

**成因**：MySQL 首次启动要跑 `mysqld --initialize` 初始化数据目录。如果这一步被中断（最常见就是磁盘满），会留下**建了一半的目录** —— 关键的 `mysql` 系统库没建成，但 `ibdata1` 之类的文件在。

于是死循环：entrypoint 检查 `$DATADIR/mysql` 不存在 → 判定是新库 → 再跑 `--initialize` → 但目录里有残留文件 → 拒绝执行 → 退出 → 重启……

**全新库没有数据，直接清掉重来**：

```bash
cd ~/novel-docker
sudo docker compose stop mysql
sudo rm -rf ./data/mysql          # ★ 整个删目录，不要用 ./data/mysql/*（* 不匹配隐藏文件）
sudo docker compose up -d mysql
```

> ⚠️ **这条只在库是全新的时候用。** 已经有业务数据了就不能删，得去做数据恢复。

#### ④ 镜像拉不动（只有 ES 会这样）

`docker.elastic.co` 不在 Docker Hub 上，**阿里云的加速器管不着它**。单独重试：

```bash
sudo docker compose up -d elasticsearch
```

还是不行就先跳过 —— ES 是做搜索功能时才用得到的，不影响其他五个。

**✅ 确认**：`sudo docker compose ps` 里 `mysql`、`redis`、`es` 三个是 `(healthy)`，六个全是 `Up`。

### 建库建表

建表脚本有两个文件，在 **`docs/sql/`** 目录下：

| 文件 | 内容 |
|---|---|
| `schema.sql` | 21 张表的建表语句（纯 DDL） |
| `seed.sql` | 初始数据：角色、管理员账号、分类、AI 提示词模板 |

**先传上去：**

```powershell
# 在 Windows PowerShell 里执行
scp D:\MickeyChen\Life\project\novelManagement\docs\sql\schema.sql mickey@192.168.127.137:~/novel-docker/init/
scp D:\MickeyChen\Life\project\novelManagement\docs\sql\seed.sql   mickey@192.168.127.137:~/novel-docker/init/
```

> `init/` 目录已经挂在 `docker-compose.yml` 里映射到容器的 `/docker-entrypoint-initdb.d`。MySQL 容器**首次启动**时会按**文件名顺序**自动执行这个目录下的所有 `.sql`（`schema.sql` 排在 `seed.sql` 前面，正好先建表再灌数据）。

#### ⚠️ 但你的 MySQL 很可能已经初始化过了

**自动执行只在 `~/novel-docker/data/mysql/` 是空的时候才触发。** 只要 MySQL 容器成功启动过一次（哪怕没建任何业务表），这个目录里就有了系统库文件，**之后往 `init/` 里放多少脚本都不会再自动跑**。

所以更常用的其实是手动导入。**在虚拟机终端里执行**：

```bash
cd ~/novel-docker

# ① 先灌表结构
sudo docker exec -i novel-mysql mysql -uroot -proot123456 < init/schema.sql

# ② 再灌初始数据
sudo docker exec -i novel-mysql mysql -uroot -proot123456 < init/seed.sql
```

> **注意这里不要写库名**。脚本第一行就带了 `CREATE DATABASE IF NOT EXISTS novel;` 和 `USE novel;`，你如果再加个 `novel` 参数反而会冲突。**让它自己建库。**
>
> 两个脚本都是**幂等**的（`CREATE TABLE IF NOT EXISTS` + `INSERT IGNORE`），跑第二遍不会报错也不会产生重复数据，可以放心重跑。

#### 验收

```bash
# 21 张表
sudo docker exec -it novel-mysql mysql -uroot -proot123456 -e "USE novel; SHOW TABLES;"

# 管理员账号（密码 admin123）
sudo docker exec -it novel-mysql mysql -uroot -proot123456 -e "USE novel; SELECT id, username, nickname FROM sys_user;"

# 种子数据条数：分类 8 / 菜单 15 / AI 模板 5
sudo docker exec -it novel-mysql mysql -uroot -proot123456 -e "USE novel; SELECT (SELECT COUNT(*) FROM novel_category) AS 分类, (SELECT COUNT(*) FROM sys_menu) AS 菜单, (SELECT COUNT(*) FROM ai_prompt_template) AS AI模板;"
```

> **默认管理员账号：`admin` / `admin123`**，密码是 BCrypt 哈希存的。上线前记得改。

## 重启虚拟机之后，要手动做什么

**结论：虚拟机里一般什么都不用做，Windows 这边全要手动起。**

### ① 中间件：会自动回来，前提是你没 `stop` 过

`docker-compose.yml` 里**每个服务都写了 `restart: unless-stopped`**，
所以 Docker 守护进程一启动，容器就自己跟着起来，不用敲任何命令。

`unless-stopped` 的准确含义是「**除非是我人为停的**」，所以：

| 你上次是怎么离开的 | 重启后 |
|---|---|
| 直接关虚拟机 / `shutdown` | 容器自动起 ✅ |
| 敲过 `docker compose stop` 或 `down` | 被标记为人为停止，**不会自启** ❌ |

> ★ **所以做完实验别敲 `stop` / `down`，直接关虚拟机就行。**
> 尤其是 `down -v` —— 那个 `-v` 连数据卷一起删，库就没了。

开机后进虚拟机确认（刚开机时容器可能还在 `starting`，等十几秒再看）：

```bash
systemctl is-enabled docker    # 期望 enabled。不是的话 sudo systemctl enable docker
docker ps                      # 期望 novel-mysql / novel-redis 状态是 Up (healthy)
```

真没起来就手动补一刀（**按需启动，8G 机器全开吃 5G**）：

```bash
cd ~/novel-docker
docker compose up -d mysql redis
```

### ② 虚拟机 IP：进虚拟机第一件事就是确认它

`application-dev.yml` 里 MySQL 和 Redis 的地址、`broker.conf` 里的 `brokerIP1`，
**三处都写死了 `192.168.127.137`**。VMware NAT 一般按网卡 MAC 记住租约，
这个 IP **通常不变**，但不是保证。

```bash
hostname -I
```

| 变了的话要改哪 | 位置 |
|---|---|
| MySQL 连接串的 host | `backend/src/main/resources/application-dev.yml` 的 `spring.datasource.url` |
| Redis 的 host | 同文件的 `spring.data.redis.host` |
| RocketMQ 的 `brokerIP1` | `docs/docker/broker.conf`（★ 改完要重启 broker 容器才生效） |

嫌每次都要确认就固定 IP，见下面附录。**第二期要接 Nacos 之后这事更烦，建议早点定。**

### ③ 系统参数：持久化了就不用管，但值得验一眼

第 4 步的三个参数**已经写进 `/etc/sysctl.conf`，是持久的**，正常重启不会丢：

```bash
cat /proc/sys/vm/max_map_count     # 期望 262144
cat /proc/sys/vm/overcommit_memory # 期望 1
```

> ⚠️ **例外**：`docker-compose.yml` 头部注释里那句
> `sudo sysctl -w vm.max_map_count=262144` 是**临时的**（`-w` 只改运行时内存里的值，不落盘）。
> 如果你当时只照注释跑了那一条、没做第 4 步的持久化，现在 `cat` 出来就是 `65530`，
> 第三期起 ES 时会报 `max virtual memory areas vm.max_map_count [65530] is too low`。

### ④ Windows 这边：每次开机都要手动起

| 起什么 | 怎么起 | 会自动起吗 |
|---|---|---|
| 中间件（虚拟机里） | 见上面 ① | ✅ 一般会 |
| 后端 `backend/` | IDEA，或 `mvn spring-boot:run`，或根目录 `npm run dev:backend` | ❌ |
| 三个前端 + 代理 | **项目根目录** `npm run dev` | ❌ |

**★ 顺序：先中间件 → 再后端 → 最后前端。**

后端启动时就要建 MySQL 连接池（HikariCP 默认 fail-fast，`application-dev.yml` 里也没关），
虚拟机没通的话后端**直接起不来**。前端无所谓，起得来，只是请求发不出去。

一键清单：

```bash
# ---- 虚拟机里 ----
hostname -I                              # 1. 确认还是 192.168.127.137
docker ps                                # 2. 确认 novel-mysql / novel-redis 是 Up

# ---- Windows，项目根目录 ----
npm run dev:backend                      # 3. 或 IDEA 里点绿三角
npm run dev                              # 4. 四个前端一起起

# ---- 浏览器 ----
# http://localhost:3000/
```

## 常见问题

| 现象 | 原因 / 解决 |
|---|---|
| `docker: command not found` | 重新登录虚拟机，或 `newgrp docker` |
| `permission denied ... docker.sock` | 用户组没生效，同上 |
| `docker pull` 超时 / `context deadline exceeded` | 加速器没配或配错。检查 `cat /etc/docker/daemon.json`，改完 `sudo systemctl restart docker` |
| ES 容器起来就退出 | `vm.max_map_count` 没生效，回第 4 步 |
| ES 报 `Exit code 137` | 被 OOM 杀了。关掉别的服务，或把 compose 里 `ES_JAVA_OPTS` 改成 `-Xms512m -Xmx512m` |
| **容器反复 `Restarting`，日志里 `No space left on device`** | **磁盘满了。回「开工前：确认磁盘空间」** |
| **容器反复 `Restarting`，日志里 `AccessDeniedException`，或该写的目录根本不存在** | **绑定挂载目录属主是 `root`，而镜像是非 root 用户。见第 8 步 ②** |
| **只有 ES 和 RocketMQ Broker 反复重启，其他四个好好的** | 就是上面那条 —— 只有这两个镜像以非 root 用户运行 |
| **MySQL 反复 `Restarting`，日志 `--initialize specified but the data directory has files in it`** | **首次初始化被中断留下的残缺目录。见第 8 步 ③** |
| **Redis 日志警告 `Memory overcommit must be enabled`** | **回第 4 步加 `vm.overcommit_memory=1`** |
| Nacos 控制台能开，但客户端连不上 | **9848 端口没映射**，`sudo docker compose ps` 检查 |
| RocketMQ 报 `connect to 172.17.0.x:10911 failed` | `broker.conf` 的 `brokerIP1` 不对，回第 7.3 步 |
| MySQL 报 `Public Key Retrieval is not allowed` | 连接串加 `allowPublicKeyRetrieval=true` |
| Windows 连不上虚拟机 | 虚拟机里 `sudo ufw status` 看防火墙；再确认 VMware 网络模式 |
| **重启虚拟机后容器没自动起来** | **你上次敲过 `stop`/`down`，被标记成人为停止了。见「重启虚拟机之后，要手动做什么」** |
| 虚拟机重启后 IP 变了 | 见下面附录 |
| 端口被占用 | `sudo ss -tunlp \| grep 3306` 查是谁 |
| scp 报 `Connection refused` | 虚拟机的 ssh 服务没起：`sudo systemctl start ssh` |
| **往 `init/` 放了 sql 但库里没有表** | `data/mysql/` 已经有文件了，init 脚本只在**首次**启动时跑。手动导入，见第 10 步 |
| **在阅读端登录了，跳到创作中心还是未登录** | **你直接开了 5174。要从 `http://localhost:3000/` 进** —— localStorage 按 origin 隔离，**端口也算数**。见文末附录 |

## 附录：固定虚拟机 IP

虚拟机 IP 一变，`broker.conf` 和后端配置就全失效了。VMware NAT 的 DHCP 租约通常比较稳定，**可以先不管**，等真遇到了再固定。

> ⚠️ 配错会把自己关在门外。所以**用 `netplan try` 而不是 `netplan apply`** —— 它会在 120 秒后自动回滚，除非你按回车确认。

```bash
# 先查清三样东西
ip addr        # 网卡名（ens33 / ens160 之类）
ip route       # 网关地址（default via ...）
hostname -I    # 当前 IP

sudo nano /etc/netplan/00-installer-config.yaml
```

改成（**网卡名、网关、IP 按上面查到的填**）：

```yaml
network:
  version: 2
  ethernets:
    ens33:
      dhcp4: false
      addresses: [192.168.127.137/24]
      routes:
        - to: default
          via: 192.168.127.2
      nameservers:
        addresses: [223.5.5.5, 8.8.8.8]
```

```bash
sudo netplan try     # 120 秒内新开一个终端 ping 一下，通了再回原终端按回车确认
```

**如果 IP 真的变了**，改两个地方再重启 broker：

```bash
cd ~/novel-docker
nano .env            # 改 RMQ_BROKER_IP
nano broker.conf     # 改 brokerIP1
sudo docker compose restart rmqbroker
```

后端的 `application.yml` 也要跟着改。

| RocketMQ NameServer | ~0.3G |
| Redis | ~0.2G |
| Ubuntu + Docker | ~0.8G |
| **合计** | **~5G / 8G** |

还剩 3G 余量，够用但不宽裕。`docs/docker/docker-compose.yml` 里的堆内存是**特意压过**的：

```yaml
Nacos   JVM_XMX: 512m
Broker  JAVA_OPT_EXT: "-Xms512m -Xmx512m -Xmn256m"
ES      ES_JAVA_OPTS: "-Xms1g -Xmx1g"
```

> **别照抄网上教程的值。** 很多教程写 ES `-Xms2g`、RocketMQ Broker 用官方默认的 `-Xmx8g`，在 8G 机器上照抄必 OOM。

## 附录：三个前端怎么访问（★ 别直接开 5173）

三个前端是**独立应用**，各跑各的端口。但开发期**必须从开发代理进**：

| 入口 | 转发到 | 说明 |
|---|---|---|
| `http://localhost:3000/reader/` | reader-web (vite :5173) | 阅读端 |
| `http://localhost:3000/author/` | author-web (vite :5174) | 创作中心 |
| `http://localhost:3000/admin/` | admin-web (vite :5175) | 管理端 |
| `http://localhost:3000/api/` | backend (:8080) | 后端 |

`http://localhost:3000/` 本身是个导航页，三个端都能点进去。

### ★ 为什么不能直接开 5173 / 5174 / 5175

**localStorage 是按 origin（协议 + 主机 + 端口）隔离的 —— 端口也参与。**

`localhost:5173` 和 `localhost:5174` 是**两个不同的 origin**，互相读不到对方的 localStorage。
在阅读端登录后跳到创作中心，那边就是**未登录**状态。

坑的地方在于：**这个问题生产环境不会出现**（生产是同域名 + 三个路径 = 同源），
只在开发期炸 —— 也就是那种「本地好好的，上线也没事，只有开发时莫名其妙」的问题。

实测记录（在 5173 写入 `novel_token`，再从 5174 / 5175 读）：

```
ON_5173 = WRITTEN_ON_5173
ON_5174 = NULL(读不到)
ON_5175 = NULL(读不到)
```

> ★ **别拿 Cookie 的直觉套用。** Cookie 不受端口限制（RFC 6265 §8.5），localStorage 受。
> 两者规则不一样，按 Cookie 想当然就会踩这个坑。

**解法：开发期照搬生产的拓扑。** 三个应用各加一个 `base`（`/reader/` `/author/` `/admin/`），
前面挂一个 `dev-proxy/`（:3000）只做代理，和生产的 Nginx 一一对应。
同源之后登录态才真正共享；而且**开发的拓扑 == 生产的拓扑**，这类差异就不会拖到上线才暴露。

所以：**从 `http://localhost:3000/` 进，不要直接开单个端口。**
直接开 5173 之类的仍然能用（各应用有自己的 `/api` 代理能连后端），
但那是**孤立的 origin**，登录态不共享 —— 只适合单独调某一个应用时用。

完整说明见 **`项目大纲.md` §7.5**。

### 启动顺序

**方式一：一条命令全起（推荐）**

在**项目根目录**（`项目大纲.md` 所在的那一层，同时装着 `backend/` 和三个前端的那层）执行：

```bash
npm run dev
```

四个 vite 一起起来，日志按 `[reader] [author] [admin] [proxy]` 前缀分色。`Ctrl+C` 一次全停。

只想起其中一个：

```bash
npm run dev:reader    # 只起 :5173
npm run dev:author    # 只起 :5174
npm run dev:admin     # 只起 :5175
npm run dev:proxy     # 只起 :3000
```

> 根目录这个 `package.json` 不含任何业务代码，也不参与打包，
> 只负责把四个子项目拉起来（靠 `npm --prefix <子目录>`）。
> 各子项目自己的命令照旧在各自目录里跑。

**方式二：分开手动起**

四个进程，三个前端先起，网关最后起：

```bash
# 三个前端（vite dev server）
cd reader-web  && npm run dev     # :5173
cd author-web  && npm run dev     # :5174
cd admin-web   && npm run dev     # :5175

# 开发代理 —— 从这进
cd dev-proxy && npm run dev     # :3000
```

后端 `backend/` 用 IDEA 或 `mvn spring-boot:run` 起在 `:8080`（根目录也可 `npm run dev:backend`）。

> **装依赖**：`dev-proxy/` 是独立的一个 npm 包（只依赖 vite），
> 首次要单独跑一次 `npm install`。它的 `vite.config.js` 就是生产那段 Nginx 配置的对照表。
> 根目录首次也要 `npm install` 一次（只装 `concurrently` 一个依赖），或者直接 `npm run install:all` 一次装齐五个包。

> ⚠️ **`npm run dev` 起来后的头几秒，proxy 的日志里可能有 `ws proxy error: ECONNREFUSED`。**
> 这是启动竞态：`:3000` 通常 1 秒多就 ready 了，而 `:5173` / `:5174` 要 3~5 秒。
> 这中间如果有浏览器开着页面在重连 HMR，代理找不到目标就会报这个。
> 页面自己会重连，**不影响使用**，不用管。
