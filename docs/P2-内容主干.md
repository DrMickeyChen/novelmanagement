## 包结构：放 `modules/content/`，不是 `modules/novel/`

**这是本方案唯一一个「和直觉不同」的结构决定，理由是给二期铺路。**

大纲 §152 写明二期的 `novel-content` 服务 = **小说 / 章节 / 分类 / 审核**（§1375 同样）。而 P1 建立的约定就是**「一个包对应将来要拆出去的一个服务」**（`modules/system/` ↔ 二期 `novel-auth`，见大纲 §227-228）。

所以 P2 的四个域**合成一个 `modules/content/`**，而不是拆成 `modules/novel/` + `modules/category/` + `modules/chapter/`。

**收益**：二期 M2「摘出 content」变成「把这个包整体搬走」，而不是「从三个包里挑文件」—— 后者最容易漏掉一个 mapper 然后编译不过。面试时这是个能讲清楚的判断依据。

## 设计要点

### `SecurityConfig` 的三条闸

```java
// ① WHITELIST 追加（★ 绝不能写成 "/api/**" —— 那会把 /api/admin/** 一起放行）
"/api/categories",
"/api/novels/**",

// ② authorizeHttpRequests 里，插在 anyRequest() 之前
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.requestMatchers("/api/author/**").hasAnyRole("AUTHOR", "ADMIN")
.anyRequest().authenticated()
```

**为什么 `/api/author/**` 放 ADMIN 进来**：ADMIN 在 seed 里拥有全部菜单，是被当作超级角色设计的。挡住他反而制造「管理员点创作中心被 403」的怪现象。**真正的边界由归属校验兜住** —— 管理员能进这个门，但改不了别人的书。这就是「URL 闸管门、归属校验管物」的分工。

**顺序很关键**：这两条必须**在白名单之后、`anyRequest()` 之前**。放在 `anyRequest()` 之后则永远不生效（`anyRequest` 先命中）。

### 状态机集中在 Service 的一个方法里

大纲原话：*「状态机集中在 Service 的一个方法里，用 `switch` 显式校验，禁止各 Controller 直接改 status 字段」*。

`NovelServiceImpl.transitStatus` / `ChapterServiceImpl.transitStatus` 是**各自唯一的 status 入口**，作者侧和管理侧的所有状态变更都走它。设计点：

- **错误提示里带上「从什么状态到什么状态」**，而不是干巴巴一句「当前作品状态不允许该操作」。状态机报错最常见的原因是前端拿了个过期页面，把 from/to 打出来能一眼定位。
- **`audit_log` 写在状态机方法内部**，不是各 Controller 自己记 —— 这样「想绕开审核日志」就只剩「绕开状态机」一条路，而状态机是唯一入口。
- **`switch` 用表达式而不是语句**。Java 的 switch **语句**对枚举**不做穷尽性检查** —— 将来给枚举加一个状态时会被静默放过，新状态就没有审计日志。switch **表达式**（赋值或箭头返回）才有穷尽性检查，少一个分支直接编译不过。

### 越权校验抽成 `NovelAccessGuard`

`requireExisting(novelId)`（不存在 → 2001）/ `requireOwned(novelId)`（不是我的 → 2002）/ `requireChapterInNovel(...)`。

**为什么抽成一个类而不是两边各写一份 private 方法**：这份校验里有一条 `log.warn("[越权尝试] ...")`。越权返回 2002 / 3002 —— 走 **HTTP 200**，在 APM 上**完全看不出来**。**那条 WARN 是唯一的补偿措施**，两处各写一份的话，改一处忘一处是迟早的事，而漏掉的那一处不会有任何症状。

**责任边界**：它只做「存在性 + 归属」，**不管状态**。「已上架的书不能编辑」属于状态机，不在这里 —— 混在一起会让它变成「什么都管一点」的上帝类。

### `ContentUserLookup`：content → system 的唯一一条依赖

`content` 模块里**唯一**依赖 `system` 模块的地方（取作者昵称）。收在一个类里，是因为大纲 §178 定了「服务之间不共享数据库表」，而包结构就是按二期要拆的服务划的。现在一句 `sysUserMapper.selectById(...)` 就能拿到昵称 —— 但那正是二期拆分时最贵的一笔债。**二期 M2 时只需要把这一个文件内部从「查库」改成「Feign 调 auth 服务」，调用方一行都不用动。**

★ **依赖方向只能 content → system，绝不能反过来**，否则二期的 auth 服务就反向依赖 content 了，拆分顺序（M1 先拆 auth、M2 再拆 content）直接作废。

## 十一个坑的逐条方案

### C-1 ★★ 逻辑删除 + 唯一键冲突（最危险的一个，必现）

`chapter` 上有 `UNIQUE KEY uk_novel_chapter_no (novel_id, chapter_no)`，**这个键不包含 `deleted`**。所以：

```
删掉第 5 章 → UPDATE chapter SET deleted = 1 WHERE id = 7
             → 但 (novel_id=3, chapter_no=5) 这一行【还在索引里】
             → 以后再也插不进 chapter_no = 5 的章节，报 Duplicate entry
```

**这不是理论风险** —— 只要作者删过一次草稿章，后面新建到那个序号就必然炸。`novel_category` 的 `uk_name` 一模一样。（顺带一提：`novel` 表没有这类唯一键，所以作品删除用普通的 `deleteById` 就是安全的。）

**方案：删的时候顺手把唯一键那一段改掉。**

```java
// ChapterMapper —— 注意这是手写 SQL，@TableLogic 完全不管，deleted 要自己写
@Update("UPDATE chapter SET deleted = 1, chapter_no = -id WHERE id = #{id} AND deleted = 0")
int logicDeleteAndFreeChapterNo(@Param("id") Long id);
```

`-id` 为什么一定不冲突：`id` 全局唯一，所以 `(novel_id, -id)` 两两不同；而**存活行的 `chapter_no` 永远是正数**，所以负数段和存活行不可能撞上。

`novel_category` 同理，但名字是字符串：`name = CONCAT(LEFT(name, 20), '_del_', id)`。`LEFT(name,20)` 是因为 `name` 是 `VARCHAR(32)`（`_del_` + 最多 20 位 id 才塞得下，不截断会报 `Data too long`）。

**代价（已写进注释）**：已删除行的 `chapter_no` 不再等于它的真实序号，所以**将来若要做「回收站 / 恢复已删除章节」，恢复时必须重新分配 `chapter_no`**，不能直接把 `-id` 改回正数。

> **实测证据**：删掉 `chapterNo=1` 的章 → 再新建一章 → 拿到 `chapterNo=1`，**没有 `Duplicate entry`**；同理删掉分类后再建同名分类 → 成功。

### C-2 `chapter_no` 怎么分配

`SELECT MAX(chapter_no) FROM chapter WHERE novel_id = ? AND deleted = 0` 然后 +1，**手写 `@Select` 且必须自己带 `deleted = 0`**。

并发下两个请求拿到同一个号 → 唯一键报错。**不写重试循环，直接捕获 `DuplicateKeyException` 返回现成的 `CHAPTER_NUMBER_EXISTS(3004)`。**

理由：① 重试在 MySQL 默认的 REPEATABLE READ 下**必须开 `REQUIRES_NEW` 才是对的**（同一事务里重读 `MAX` 看到的还是旧快照，会一直拿到同一个号、重试三次全失败）—— 为一个「作者同时开两个标签页建章」的低频场景引入两个事务传播级别，复杂度不划算；② 3004 是早就定好的错误码，作者看到「该章节序号已存在」再点一次即可。

★ **另一条路被否掉了**：改按「上一个号 +1」。那样删掉最后一章后新章会跳号，作者在页面上看到「第 12 章」后面跟着「第 14 章」，会以为丢了一章。

### C-3 `chapter_content` 的 upsert 与 `word_count`

`chapter_content` 是 `chapter_id` 做主键的一对一表（正文分离是为了目录查询不拖 LONGTEXT）。

- 先 `selectById(chapterId)`，无则 insert、有则 update。
- `@TableId(type = IdType.INPUT)` —— 主键是手工给的 `chapter_id`，**不是自增**，写成 `AUTO` 会让 MP 忽略传入值。
- `word_count` 从正文算：`content.replaceAll("\\s", "").length()`，写回 `chapter.word_count`。

★ 用 `String.length()` 数的是 UTF-16 码元数 —— 中文和英文都算 1、emoji 算 2。网文场景下这个精度**足够了**（业界就是按「字符数」算字数），代价写进注释，不为它引分词库。

### C-4 ★ 冗余字段同步（`novel` 的四个字段）

`novel` 上有 `chapter_count` / `word_count` / `last_update_time` / `last_chapter_id` 四个冗余字段。

**方案：`NovelServiceImpl.syncNovelStat(Long novelId)`，用「重算」而不是「增量」，只在章节的发布状态发生变化时调用。**

**为什么不用增量 `UPDATE novel SET chapter_count = chapter_count + 1`：** 增量要求「每一条增/删/通过/退回路径都记得调、且方向正确」，而「删一章忘了减 1」是**必然会发生**的漂移 —— 更糟的是它没人会发现（页面上显示 12 章、实际 13 章，谁去数）。重算是**一处实现、永远自洽**。

代价：每次发布多两条 `COUNT`/`SUM` 查询。`chapter` 上的 `idx_novel_status(novel_id, status)` 正好覆盖这个条件，代价可以忽略。

> **实测证据**：章节发布后 `chapter_count = 1`、`word_count = 24`（正文 24 个非空白字符）、`last_update_time` 非空；把已发布章节改存正文触发自动退回后，`chapter_count` 回到 0。

### C-5 状态机唯一入口

见上文「设计要点」。补充两条实施中确认的规则：

- **`updateById` / `update` 必须排在 `syncNovelStat` 之前** —— 反过来的话重算读到的是旧状态，统计会差一章。
- **`NovelStatus.DRAFT` 没有合法的入边**（作品一旦提交就不能退回草稿，只能驳回成 REJECTED）。`transitStatus` 里对此显式 `throw new IllegalStateException(...)` —— 这是**代码 bug**（说明有人绕过状态机硬塞了一个 DRAFT），不是用户操作错误，所以不能抛 `BusinessException`。

### C-6 越权校验写成公共方法

| | 谁触发 | 返回 | 监控可见性 |
|---|---|---|---|
| **角色不够** | URL 闸 / `@PreAuthorize` | **HTTP 403** | ★ 可见 |
| **动了别人的资源** | `NovelAccessGuard.requireOwned` | HTTP 200 + `code 2002` | 不可见，**所以补了一条 `log.warn("[越权尝试] ...")`** |

语义上这两件事本来就不同：403 是「你不该进这个门」，2002 是「这门不是你的」。合并成一个 403 会让「作者点错链接」和「有人在扫别人的书」在日志里长得一模一样。**但那句 WARN 不能省** —— 没有它，资源级越权就是彻底的监控盲区。

> **实测证据**：admin 的 token 去改 author01 的书 → `2002`（过了 URL 角色闸、倒在归属校验上），且日志里出现 `[越权尝试]` 的 WARN —— 两条都验到了。

### C-7 ★ 读者端可见性必须落在**查询条件**里

约束 1：「小说未上架（status ≠ 2）时，读者端**任何接口都查不到它**」
约束 2：「小说下架时，其下所有章节对读者不可见」

**方案：把条件写进 `WHERE`，不是「查出来再 if 判断后抛异常」** —— 后者在**列表接口上必然漏**（列表里混进一本未上架的书，代码不会报错，只是悄悄多了一行）。

**详情接口刻意不区分「不存在」和「未上架」，一律 2001。** 否则匿名调用者可以用 2001 / 2004 的差别枚举出「哪些 id 是真实存在的书」（`/api/novels/{id}` 在白名单里，匿名可访问）。代价：作者看不到「作品尚未上架」这个更友好的提示 —— 但那本来就该去**作者端**看，读者端不承担预览职责。

**约束 2 是最容易漏的一条**，章节正文接口必须**同时**满足两个条件：① 先确认小说已上架；② 再查章节，且确认它确实属于 URL 上那本书。只按 `cid` 查的话，把 `cid` 换成别的书的章节 id，就能从一本已上架的书**读到另一本书的章节**。

> **实测证据**：作品下架后，匿名 `GET /api/novels/3/chapters/{cid}` → `2001`；作品详情 → `2001`；读者列表里这本书消失；而作者自己访问 `/api/author/novels/3` 仍能正常读到。

### C-8 `@TableLogic` 不作用于手写 SQL

任何 `@Select` / `@Update` / `@Delete` **都要自己写 `deleted = 0`**（`SysUserMapper` 的注释里 P1 已经踩过一次）。P2 的手写 SQL 出现在 `selectMaxChapterNo`、`sumPublishedWordCount`、`logicDeleteAndFreeChapterNo`、`logicDeleteAndFreeCategoryName` —— **每一个都在注释里点明这一句为什么必须自己写。**

### C-9 `audit_log.action` 与已有枚举不一致

DB 列注释和大纲 §531 都写 `action(1提交 2通过 3驳回)`，但已有的 `AuditStatus` 是 `PENDING(0)/APPROVED(1)/REJECTED(2)`。

**方案：**
- **新建 `common/enums/AuditAction`**：`SUBMIT(1)` / `APPROVE(2)` / `REJECT(3)` / `OFFLINE(4, "下架")` / `REPUBLISH(5, "重新上架")`。1/2/3 严格对齐 DB 列注释。**4/5 是对列注释的扩展** —— 上下架同样是管理员改变作品对外可见性的动作，不记流水的话「书怎么突然不见了」永远查不出来。★ 代价写进 javadoc：**DB 列注释不跟着改**（改注释要重跑 DDL，不值得），并留一句警告：**将来若按 `audit_log.action` 做「审核通过率」统计，只统计 1/2/3**，否则分母会混进上下架。
- **`AuditStatus` 只改 javadoc，不改名、不改值。** 它的 0/1/2 正好匹配 `author_apply.status` 和 `novel_comment.status`，是那两个列的正确枚举，只是名字起得像通用的。**并明确加一句：`audit_log` 不用这个枚举，它用 `AuditAction`** —— 防止后来人「看着名字像就拿来用」：一旦用了就会往 `audit_log.action` 里写 0，而列注释是 1/2/3，审核日志页会显示成空白或错位。
- **`AuditTargetType` 保留不动**，javadoc 里错写的 `sys_audit_log` → `audit_log`（真表名，纯文档错误）。

> **实测证据**：上下架动作在 `/api/admin/logs` 里显示为 `OFFLINE(4)` 和 `REPUBLISH(5)`，remark 也在。

### C-10 分类删除

**(a) `uk_name` + 逻辑删除** → 同 C-1，删除时改名。

**(b) 已被小说引用** → **拒绝删除**，新增 `CATEGORY_HAS_NOVELS(6003)`。判定走 **MP 的方法**（`novelMapper.selectCount(wrapper.eq(Novel::getCategoryId, id))`），`@TableLogic` 会自动补 `deleted = 0`；**不要手写 SQL**（会忘 `deleted = 0`，把逻辑删除的书也算进去，症状是「分类明明没书却删不掉」）。**口径不限小说状态** —— 草稿、已下架的书也是书，分类没了它们就成孤儿。

★ 新建/编辑小说时，`categoryId` 必须是**存在且 `status = 1`** 的分类，否则抛 `CATEGORY_NOT_FOUND(6001)`。否则作者可以往一个刚被停用的分类里塞书，读者端立刻出现「分类筛选里没有它、但列表里有」的怪状。

## 实施记录（对方案的修正）

### ① ★★ `updateById` 跳过 null 字段 —— 方案整段漏掉了这件事

**这是 P2 全程唯一一个「方案没想到、靠真机验证才暴露」的缺陷，也是最值得记下来的一条。**

起因是走完验收链路后随手复查数据，发现一个不该存在的东西：**一个已经被自动退回成草稿的章节，`publish_time` 却还有值。**

根因是 MyBatis-Plus 的默认行为 —— `updateById(entity)` 生成的 SQL 是
`UPDATE chapter SET <非 null 的字段> WHERE id = ?`，**null 字段被静默跳过**：

```java
chapter.setPublishTime(null);
chapterMapper.updateById(chapter);   // ★ publishTime 根本没进 SQL，库里还是旧值
```

于是「重新提交审核要清掉上次的驳回理由」「退回草稿要清掉发布时间」这类**「把一列置空」**的动作，全都变成了空操作 —— 而且**不报错**，只是数据 quietly 不对。

**同一个 bug 在 `NovelServiceImpl.transitStatus` 里也有**：作者重新提交后，`audit_remark` 里的旧驳回理由没清掉，界面上就会出现「状态：待审核」旁边挂着一条上次的驳回理由。

**修复**：凡是「置空一列」的地方，一律改成 `mapper.update(entity, wrapper)`，并在 wrapper 上显式 `.set(列, null)` —— 但**只在值为 null 时才加这个 set**（实体自己会渲染非 null 的字段，无条件加会出现重复的 SET 子句）：

```java
LambdaUpdateWrapper<Chapter> update = new LambdaUpdateWrapper<Chapter>()
        .eq(Chapter::getId, chapter.getId());
if (publishTime == null) { update.set(Chapter::getPublishTime, null); }
if (remarkToPersist == null) { update.set(Chapter::getAuditRemark, null); }
chapterMapper.update(chapter, update);
```

★ **还有一半，比 SQL 更容易忘**：**必须同时把这个值写回内存里的那个对象**。因为后面的代码路径可能还会对这个对象再调一次 `updateById` —— 那时 `chapter` 里还留着**旧的** `publishTime`，它会被当成有效值重新写回库，前面的修复等于白做。（`ChapterServiceImpl.saveContent` 里就有这么一条路径：自动退回之后紧接着 `updateById` 保存正文。）

**修复后重测**：退回草稿后 `publish_time` 确实为空 ✓；小说和章节重新提交后 `audit_remark` 都被清掉 ✓。

> **这条要记住的教训**：`updateById` 不是「把对象整体写回去」，而是「写回非 null 的字段」。凡是语义上要**清空**一列的地方，它都不适用。

### ② 方案里的 `PageResult` 用法是错的，改用 `selectPage` 的真实返回对象

方案里写的是自己 `count` 一次、再 `selectPage` 一次、然后手工拼 `PageResult`。实际写 `ChapterServiceImpl.adminPage` 时第一版就是这么写的，**当场发现两个问题**：一是 `count` 查询跑了两遍；二是手工拼的时候填的是**入参**的 `page` / `size`，而 MP 的分页拦截器会把 `size` 钳到上限（`setMaxLimit(100L)`）、把 `page` 钳到合法值 —— 结果就是「请求 size=1000，响应里说 size=1000，实际只回了 100 条」。

**改成**用 `selectPage` 返回的 `Page` 对象：

```java
Page<Chapter> result = chapterMapper.selectPage(buildPage(page, size), wrapper);
return new PageResult<>(toVOList(result.getRecords()), result.getTotal(),
        result.getCurrent(), result.getSize(), result.getPages());   // ★ 用 result 的，不是入参的
```

★ 另外 **MP 的 `PaginationInnerInterceptor` 在 `size < 0` 时不做任何分页、直接返回全表**，所以 `buildPage` 必须**同时钳住上下界**（下界 `size >= 1`）。

### ③ `ContentUserLookup` 和 `NovelAccessGuard` 是方案里没有的两个类

方案只列了 4 个 Service，实际多出两个 `@Component`。加它们的理由不是「代码好看」，而是各自兜住一件**漏了就没有症状**的事：

- `NovelAccessGuard` —— 保证「越权必留痕」只有一个实现（C-6 那条 WARN）。
- `ContentUserLookup` —— 把 content → system 的跨模块依赖收成一个文件，给二期拆服务留接缝。

**判断标准**：一个类是「多写一层」还是「堵住一个静默失败」，看**它被绕开时会不会报错**。这两个被绕开都不会报错，所以值得单独存在。

### ④ 审核日志的 VO 组装：小说 id 和章节 id 必须分开批量查

`AuditLogVO` 要显示「这条日志是针对哪本书 / 哪一章」。`audit_log` 的 `target_id` 是个多态外键 —— 它可能是 `novel.id`，也可能是 `chapter.id`，**取决于 `target_type`**。

第一版把两者混在一个 `List<Long>` 里批量查，**结果是错的但不报错**：`novel-5` 的标题会被贴到 `chapter-5` 的日志行上，因为两者 id 都是 5。改成**按 `targetType` 分成两个集合分别批量查**，再 `switch (targetType)` 取对应那一个。

> `COMMENT` / `AUTHOR_APPLY` 两类在 P2 还没有数据，显式 `case -> null`（P6 / P5 再补）。

### 1. Git Bash 里 `curl -d` 传内联中文必炸

用 `curl -d '{"remark":"验收下架"}'` 会得到 **HTTP 400 `请求内容格式不正确`** —— 看起来像后端的 JSON 解析有 bug，实际是 Git Bash 把中文按 ANSI 码页转码后送出去了。

**正确做法**：把 body 写进文件再 `--data-binary`：

```bash
cat > offline.json <<'EOF'
{"status":3,"remark":"验收下架"}
EOF
curl -X PUT .../status -H 'Content-Type: application/json' --data-binary @offline.json
```

★ 用**带引号的 heredoc**（`<<'EOF'`）。不加引号的话 `` ` `` 和 `$` 会被 shell 展开；而用 `printf` 手写 JSON 时，`\n` 会变成一个**真换行**塞进 JSON 字符串里，同样报 400（这次是服务器正确地拒绝了坏 JSON，不是 bug）。

### 2. `mvn spring-boot:run` 的后台输出读不到，改用 `java -jar`

Maven 的输出是**块缓冲**的，挂在后台时日志长时间不出来，看起来像启动卡死。改成：

```bash
mvn -o -q package -DskipTests
java -jar target/novel-backend.jar
```

### 3. Windows 上 `mvn package` 会因为 jar 被占用而失败

```
Unable to rename '...novel-backend.jar' to '...jar.original'
```

原因是**正在运行的 JVM 锁着那个 jar**（Windows 的文件锁语义，Linux 上不会这样）。

**正确顺序**：先停掉后台的 java 进程 → 确认 8080 端口已释放 → 再 `package`。

```powershell
Get-NetTCPConnection -LocalPort 8080 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

### 4. ★ `seed.sql` 的 `INSERT IGNORE` 会**静默跳过**写死 id 的新行

P2 要往 `sys_user` 里补 `author01`，第一版写死 `id = 2`。而测试库里 `id = 2` 早被 `reader01` 占了 —— 于是 `INSERT IGNORE` **一声不响地跳过**，脚本输出一切正常，`author01` 根本没建出来，也没有任何报错。

**结论：新增的数据行不要写死 id**，改用业务唯一键（`username` / `role_code`）关联；`sys_user_role` 也改成 `SELECT ... FROM sys_user JOIN sys_role WHERE username = ? AND role_code = ?` 的形式。这条已经写进 `seed.sql` 的注释里。

## 遗留（不影响验收，但面试可能被问）

1. **`@PreAuthorize` 在生产代码里一个都没有，这是有意的** —— 决定 2 是「角色挡 API，perms 只管前端菜单」。所以细粒度的权限点（`content:novel:delete` 之类）目前只在 `sys_menu` 里存在，**不对任何接口生效**。将来若要做「同一个角色里再分操作权限」，改法是给 Controller 方法补 `@PreAuthorize("hasAuthority('...')")`，`@EnableMethodSecurity` 已经开着。
2. **`chapter_no` 分配在并发下会撞唯一键**，行为是返回 `3004` 让作者重试（C-2，有意为之）。真正的修法是 `REQUIRES_NEW` + 重试，或者用 `(novel_id)` 上的序号表加行锁 —— P2 判断复杂度不划算。
3. **`word_count` 是 UTF-16 码元数**，emoji 算 2 个字。
4. **已删除的 `chapter_no` 是负数**，所以「恢复已删除章节」必须重新分配序号（C-1 的代价）。
5. **`ContentUserLookup` 现在是一次查询一条昵称**（`nicknameOf`）；批量版 `nicknamesOf` 已经在用。二期改成 Feign 调用时，注意 `nicknameOf` 的单条查询会变成一次 RPC —— 列表场景务必走批量版。
6. **`audit_log` 里 `OFFLINE(4)` / `REPUBLISH(5)` 是对 DB 列注释的扩展**，做「审核通过率」统计时只能统计 1/2/3。
